このガイドでは、例示のために[Last.fm](http://millionsongdataset.com/lastfm/)トラック・データセットを使用します。ガイド中で言及されるレイテンシーの数値は、このガイドをM1上で実行して得られたものです。汎用的な[Vespaパフォーマンス - 実践ガイド](../performance/practical-search-performance-guide)も参照してください。

データセットをダウンロードするには、以下を実行します (120 MBのzipファイル):

```bash
$ curl -L -o lastfm_test.zip \
    http://millionsongdataset.com/sites/default/files/lastfm/lastfm_test.zip 
$ unzip lastfm_test.zip
```

ダウンロードしたデータは、[Vespa JSONフィード・フォーマット](../reference/schemas/document-json-format)に変換する必要があります。

この[python](https://www.python.org/)スクリプトを使用して、データセットのファイルを走査し、Vespaのput操作を含むJSONL形式のフィード・ファイルを作成できます。[スキーマ](/ja/basics/schemas)は次のセクションで説明します。トラックの人気度の代理指標として、ユニークな`tags`の数を使用します。

`Paste the above into file create-vespa-feed.py`

```python expandable
import os
import sys
import json
import unicodedata

directory = sys.argv[1]
seen_tracks = set() 

def remove_control_characters(s):
    return "".join(ch for ch in s if unicodedata.category(ch)[0]!="C")

def process_file(filename):
    global seen_tracks
    with open(filename) as fp:
        doc = json.load(fp)
        title = doc['title']
        artist = doc['artist']
        hash = title + artist
        if hash in seen_tracks:
            return
        else:
            seen_tracks.add(hash) 

        track_id = doc['track_id']
        tags = doc['tags']
        tags_dict = dict()
        for t in tags:
            k,v = t[0],int(t[1])
            tags_dict[k] = v
        n = len(tags_dict)

        vespa_doc = {
            "put": "id:music:track::%s" % track_id,
                "fields": {
                    "title": remove_control_characters(title),
                    "track_id": track_id,
                    "artist": remove_control_characters(artist),
                    "tags": tags_dict,
                    "popularity": n
            }
        }
        print(json.dumps(vespa_doc))

sorted_files = []
for root, dirs, files in os.walk(directory):
    for filename in files:
        filename = os.path.join(root, filename)
        sorted_files.append(filename)
sorted_files.sort()
for filename in sorted_files:
    process_file(filename)
```

## Vespaアプリケーション・パッケージの作成

[Vespaアプリケーション・パッケージ](../basics/applications)は、Vespaシステムの振る舞い — 使用する機能、利用可能なドキュメント・タイプ、ランキングの実行方法、フィードおよびインデックス時のデータ処理方法 — を定義する設定ファイルとJavaプラグインの集合です。

基本的な検索アプリケーションを作成するために最低限必要なファイルは`track.sd`と`services.xml`です。設定ファイルと埋め込みモデル用のディレクトリを作成します:

```bash
$ mkdir -p app/schemas; mkdir -p app/search/query-profiles/; mkdir -p app/model
```

### スキーマ

[スキーマ](/ja/basics/schemas)は、ドキュメント・タイプと、追加の合成フィールドおよび[ランキング](../basics/ranking)設定の構成です。

このアプリケーションでは、`track`ドキュメント・タイプを定義します。

以下を`app/schemas/track.sd`に書き込みます:

`Paste the above into file app/schemas/track.sd`

```js expandable
schema track {

    document track {

        field track_id type string {
            indexing: summary | attribute
            match: word
        }

        field title type string {
            indexing: summary | index
            index: enable-bm25
        }

        field artist type string {
            indexing: summary | index
        }

        field tags type weightedset {
            indexing: summary | attribute
            attribute: fast-search
        }

        field popularity type int {
            indexing: summary | attribute
            attribute: fast-search
            rank: filter
        }
    }

    field embedding type tensor(x[384]) {
            indexing: input title | embed e5 |attribute | index
            attribute {
                distance-metric: angular
            }
            index {
                hnsw {
                    max-links-per-node: 32
                    neighbors-to-explore-at-insert: 200
                    multi-threaded-indexing: false
                }
            }
    }

    fieldset default {
        fields: title, artist
    }

    document-summary track_id {
        summary track_id { }
    }

    rank-profile tags {
        first-phase {
            expression: rawScore(tags)
        }
    }

    rank-profile bm25 {
        first-phase {
            expression: bm25(title)
        }
    }

    rank-profile closeness {
        num-threads-per-search: 1
        match-features: distance(field, embedding)

        inputs {
            query(q)  tensor(x[384])
            query(q1) tensor(x[384])
        } 

        first-phase {
            expression: closeness(field, embedding)
        }
    }

    rank-profile closeness-t4 inherits closeness {
        num-threads-per-search: 4
    }

    rank-profile closeness-label inherits closeness {
        match-features: closeness(label, q) closeness(label, q1)
    }

    rank-profile hybrid inherits closeness {
        inputs {
            query(wTags) : 1.0
            query(wPopularity) :  1.0
            query(wTitle) : 1.0
            query(wVector) : 1.0
        }
        first-phase {
            expression {
                query(wTags) * rawScore(tags) + 
                query(wPopularity) * log(attribute(popularity)) + 
                query(wTitle) * log(bm25(title)) + 
                query(wVector) * closeness(field, embedding)
            }
        }
        match-features {
            rawScore(tags)
            attribute(popularity)
            bm25(title)
            closeness(field, embedding)
            distance(field, embedding)
        }
    }
}
```

このドキュメント・スキーマは[実践的な検索パフォーマンス・ガイド](../performance/practical-search-performance-guide)で説明されています。追加されているのは`embedding`フィールドで、ドキュメントの外側の合成フィールドとして定義されています。このフィールドはVespaの[embedding](../rag/embedding)機能によって値が設定されます。[E5](https://huggingface.co/intfloat/e5-small-v2)テキスト埋め込みモデルを使用しています (この[ブログ記事](https://blog.vespa.ai/enhancing-vespas-embedding-management-capabilities/)で説明されています)。

`closeness`ランク・プロファイルが、[inputs](../reference/schemas/schemas#inputs)を使用して2つのクエリー入力テンソルを定義していることに注意してください。

```js
field embedding type tensor(x[384]) {
    indexing: input title | embed e5 | attribute | index
    attribute {
        distance-metric: angular
    }
    index {
        hnsw {
            max-links-per-node: 32
            neighbors-to-explore-at-insert: 200
        }
    }
 }
```

`HNSW`および`HNSW`チューニング・パラメーターの入門については、[HNSWインデックスを使用した近似最近傍探索](/ja/querying/approximate-nn-hnsw)を参照してください。

### サービス仕様

[services.xml](../reference/applications/services/services)は、Vespaアプリケーションを構成するサービス — どのサービスを実行し、サービスごとに何ノードを使用するか — を定義します。以下を`app/services.xml`に書き込みます:

```js expandable
<?xml version="1.0" encoding="UTF-8"?>
<services version="1.0">

    <container id="default" version="1.0">
        <search/>
        <document-api/>
        <component id="e5" type="hugging-face-embedder">
            <transformer-model path="model/e5-small-v2-int8.onnx"/>
            <tokenizer-model path="model/tokenizer.json"/>
        </component>
    </container>

    <content id="tracks" version="1.0">
        <engine>
            <proton>
                <tuning>
                    <searchnode>
                        <requestthreads>
                            <persearch>4</persearch>
                        </requestthreads>
                    </searchnode>
                </tuning>
            </proton>
        </engine>
        <redundancy>1</redundancy>
        <documents>
            <document type="track" mode="index"></document>
        </documents>
        <nodes>
            <node distribution-key="0" hostalias="node1"></node>
        </nodes>
    </content>
</services>
```

`Paste the above into file app/services.xml`

デフォルトの[クエリー・プロファイル](/ja/querying/query-profiles)は、すべてのクエリーに対してデフォルトのクエリーAPI設定を上書きするために使用できます。

以下は、[presentation.timing](../reference/api/query#presentation.timing)を有効にし、`weightedset`フィールドをJSONマップとしてレンダリングします。

```xml
<query-profile id="default">
    <field name="presentation.timing">true</field>
    <field name="renderer.json.jsonWsets">true</field>
</query-profile>
```

`Paste the above into file app/search/query-profiles/default.xml`

最後のステップは、埋め込みモデル・ファイルのダウンロードです

```bash
$ curl -L -o app/model/e5-small-v2-int8.onnx \
    https://github.com/vespa-engine/sample-apps/raw/master/examples/model-exporting/model/e5-small-v2-int8.onnx
$ curl -L -o app/model/tokenizer.json \
    https://github.com/vespa-engine/sample-apps/raw/master/examples/model-exporting/model/tokenizer.json
```

## Vespa weakAndを使用したフリーテキスト検索 

以降のセクションでは、Vespaの[クエリーAPI](../reference/api/query)を使用し、Vespaの[クエリー言語](/ja/querying/query-language)でクエリーを組み立てます。例では、クエリーの実行をサポートする[vespa-cli](../clients/vespa-cli)コマンドを使用します。

CLIは[VespaクエリーAPI](/ja/querying/query-api)を使用します。curl相当のコマンドを見るには`vespa query -v`を使用します:

```bash
$ vespa query -v 'yql=select ..'
```

最初の例は、スキーマで定義された`bm25`ランク・プロファイルを使用した検索とランキングです。`first-phase`の関連性スコアとして[bm25](../ranking/bm25)ランク・フィーチャーを使用します:


```bash
$ vespa query \
    'yql=select artist, title, track_id from track where userQuery()' \
    'query=total eclipse of the heart' \
    'hits=1' \
    'type=all' \
    'ranking=bm25'
```

このクエリーは、YQLの[userQuery()](../reference/querying/yql#userquery)とVespaの[シンプル・クエリー言語](../reference/querying/simple-query-language)を組み合わせています。[クエリー・タイプ](../reference/api/query#model.type)には`all`を使用しており、すべての語句がマッチすることを要求します。

上記のクエリー例は、`default`フィールドセット (スキーマでは`title`フィールドと`artist`フィールドを含む) で *total AND eclipse AND of AND the AND heart* を検索します。

上記のクエリーの[結果](/ja/reference/querying/default-result-format)は次のようになります:

```json expandable
{
    "timing": {
        "querytime": 0.007,
        "summaryfetchtime": 0.002,
        "searchtime": 0.01
    },
    "root": {
        "id": "toplevel",
        "relevance": 1.0,
        "fields": {
            "totalCount": 1
        },
        "coverage": {
            "coverage": 100,
            "documents": 95666,
            "full": true,
            "nodes": 1,
            "results": 1,
            "resultsFull": 1
        },
        "children": [
            {
                "id": "index:tracks/0/f13697952a0d5eaeb2c43ffc",
                "relevance": 22.590392521579684,
                "source": "tracks",
                "fields": {
                    "track_id": "TRKLIXH128F42766B6",
                    "title": "Total Eclipse Of The Heart",
                    "artist": "Bonnie Tyler"
                }
            }
        ]
    }
}
```

このクエリーは、クエリー語句が`AND`で結合されたため、1つのドキュメントにしかマッチしませんでした。デフォルトの`type=all`の代わりに`type=any`を使用するようにマッチングを変更できます。[サポートされているクエリー・タイプ](../reference/api/query#model.type)を参照してください。

```bash
$ vespa query \
    'yql=select artist, title, track_id from track where userQuery()' \
    'query=total eclipse of the heart' \
    'hits=1' \
    'ranking=bm25' \
    'type=any'
```

今度は、クエリーは24,053のドキュメントにマッチし、前のクエリーよりもかなり遅くなります。これら2つのクエリー例の`querytime`を比較すると、より多くのドキュメントにマッチする方が`querytime`が高くなります。最悪の場合、検索クエリーはすべてのドキュメントにマッチします。

クエリーのマッチング・パフォーマンスは、クエリー指定にマッチするドキュメントの数に大きく影響されます。タイプ`any`のクエリーは、タイプ`all`よりも多くの計算リソースを必要とします。  

`type=any`クエリーには、WANDアルゴリズムを実装する`weakAnd`クエリー演算子を使用する最適化があります。詳細については、[using wand with Vespa](../ranking/wand)ガイドを参照してください。 

同じクエリーを、`type=any`の代わりに`type=weakAnd`で実行します。[サポートされているクエリー・タイプ](../reference/api/query#model.type)を参照してください:


```bash
$ vespa query \
    'yql=select artist, title, track_id from track where userQuery()' \
    'query=total eclipse of the heart' \
    'hits=1' \
    'ranking=bm25' \
    'type=weakAnd'
```

24,053のドキュメントを完全にランキングしたタイプ`any`のクエリーと比較して、このクエリーは約3,600のドキュメントのみを`first-phase`ランキング式に公開します。また、この高速化された検索でも、最初の位置に同じドキュメントが返されることに注目してください。 

```bash
$ vespa query \
    'yql=select artist, title, track_id from track where userQuery()' \
    'query="total eclipse of the heart"' \
    'hits=1' \
    'ranking=bm25' \
    'type=weakAnd'
```

この場合、クエリー入力 *"total eclipse of the heart"* はフレーズ・クエリーとして解析され、検索は正確なフレーズにマッチする1つのドキュメントのみを見つけます。  

## Vespa WANDを使用した最大内積探索

前のセクションでは、[言語処理](../linguistics/linguistics)および`match: text`を使用した文字列マッチングと統合される`weakAnd`クエリー演算子を紹介しました。  

以下の例では、[wand()](../reference/querying/yql#wand)クエリー演算子を使用します。`wand`クエリー演算子は、スパースなクエリーとドキュメントのフィーチャー整数重みとの間の最大内積を計算します。`wand`クエリー演算子によって計算された内積ランキング・スコアは、[rawScore(name)](../reference/ranking/rank-features#match-operator-scores)ランク・フィーチャーによってランキング式で使用できます。 

```js
rank-profile tags {
    first-phase {
        expression: rawScore(tags)
    }
}
```

このクエリーは、学習されたスパースな*userProfile*表現を使用してtrackドキュメント・タイプを検索し、`tags` weightedsetフィールドに対して最大内積探索を実行します。 

```bash
$ vespa query \
    'yql=select track_id, title, artist from track where {totalTargetHits:10}wand(tags, @userProfile)' \
    'userProfile={"pop":1, "love songs":1,"romantic":10, "80s":20 }' \
    'hits=2' \
    'ranking=tags'
```

このクエリーは2件のヒットを返すよう要求し、`tags`ランク・プロファイルを使用します。上記のクエリーの[結果](/ja/reference/querying/default-result-format)は次のようになります:

## 厳密な最近傍探索

Vespaの最近傍探索演算子は、デンスな表現を使用した厳密なブルートフォース最近傍探索をサポートしています。最初のクエリー例では、[厳密な最近傍探索](/ja/querying/nearest-neighbor-search)とVespaのembed機能を使用します: 

```bash
$ vespa query \
    'yql=select title, artist from track where {approximate:false,totalTargetHits:10}nearestNeighbor(embedding,q)' \
    'hits=1' \
    'ranking=closeness' \
    'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

クエリーの内訳:

- `query(q)`クエリー・テンソルの10件 (`totalTargetHits:10`) の最近傍を、`embedding`ドキュメント・テンソル・フィールドに対して検索します。  
- `approximate:false`アノテーションは、Vespaに厳密な探索を実行するよう指示します。 
- `hits`パラメーターは、レスポンスで返される結果の数を制御します。要求される`hits`の数は`totalTargetHits`に影響しません。  
- `ranking=closeness`は、どの[ランク・プロファイル](../basics/ranking)でドキュメントをスコアリングするかをVespaに指示します。取得されて`rank-profile`内の`first-phase`ランキング式に公開される`totalTargetHits`件のドキュメントをどのように*ランキング*するかを指定する必要があります。 
- `input.query(q)`は、[embedder](../rag/embedding#embedding-a-query-text)によって生成されたクエリー・ベクトルです。

[ranking](../reference/api/query#ranking.profile)を指定しない場合、Vespaはベクトル類似度を使用しない[nativeRank](../ranking/nativerank)を使用するため、結果はランダムにソートされます。

より多くのCPUリソースを投入することで、厳密な探索の検索レイテンシーを削減できます。ランク・プロファイルを`closeness-t4`に変更すると、Vespaはクエリーごとに4つのスレッドを使用します:

## 近似最近傍探索

このセクションでは、より高速だが近似的な最近傍探索の使用について説明します。`track`スキーマの`embedding`フィールドには`index`プロパティがあり、これはVespaが高速な近似ベクトル探索をサポートするために`HNSW`インデックスを構築することを意味します。`HNSW`とチューニング・パラメーターの入門については、[HNSWインデックスを使用した近似最近傍探索](/ja/querying/approximate-nn-hnsw)を参照してください。

`embedding`フィールドに`index`がある場合、デフォルトのクエリー動作は`approximate:true`です:

```bash
$ vespa query \
    'yql=select title, artist from track where {totalTargetHits:10,hnsw.exploreAdditionalHits:20}nearestNeighbor(embedding,q)' \
    'hits=1' \
    'ranking=closeness' \
    'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

これは次のレスポンスを返します:

```json expandable
{
    "timing": {
        "querytime": 0.004,
        "summaryfetchtime": 0.001,
        "searchtime": 0.004
    },
    "root": {
        "id": "toplevel",
        "relevance": 1.0,
        "fields": {
            "totalCount": 10
        },
        "coverage": {
            "coverage": 100,
            "documents": 95666,
            "full": true,
            "nodes": 1,
            "results": 1,
            "resultsFull": 1
        },
        "children": [
            {
                "id": "index:tracks/0/f13697952a0d5eaeb2c43ffc",
                "relevance": 0.5992897837210658,
                "source": "tracks",
                "fields": {
                    "title": "Total Eclipse Of The Heart",
                    "artist": "Bonnie Tyler"
                }
            }
        ]
    }
}
```

今度は、クエリーはより高速になり、探索中に使用するリソースも少なくなりました。厳密な探索でレイテンシーを20msまで下げるには、4つのマッチング・スレッドを使用する必要がありました。この場合、結果のレイテンシーは単一のマッチング・スレッドで4msまで下がっています。このクエリー例では、近似探索は厳密に同じtop-1ヒットを返し、top-1の位置における精度の損失はありませんでした。全体のクエリー時間は`embed`推論に支配されていることに注意してください。 

`exact`と`approximate`の近傍探索のいくつかの重要な違い:

- `totalCount`が異なります。近似バージョンを使用する場合、Vespaは選択された`rank-profile`内の設定可能な`first-phase`ランク式にちょうど`targethits`件を公開します。厳密な探索は評価中にスコアリング・ヒープを使用し (チャンク化された距離計算)、ある時点でtop-kヒープに載ったドキュメントがfirst phaseランキングに公開されます。

- 探索は近似的であり、厳密な探索の場合のような厳密なtop 10の最も近いベクトルを返さない場合があります。これは、精度、クエリー・パフォーマンス、メモリ使用量の間の複雑なトレードオフです。これらのトレードオフの詳細については、[Billion-scale vector search with Vespa - part two](https://blog.vespa.ai/billion-scale-knn-part-two/)を参照してください。

`approximate:false|true`の設定がサポートされていることで、開発者は厳密な最近傍探索の結果と近似探索の結果を比較して、精度の損失を定量化できます。そうすることで、開発者はrecall@kやoverlap@kを定量化し、検索パフォーマンスと精度の適切なバランスを見つけることができます。`hnsw.exploreAdditionalHits`を増やすと、クエリーが遅くなる代わりに精度 (recall@k) が向上します。

フィルタリングを使用する場合、パフォーマンス上の理由から、フィルターに含まれるフィールドが`index`または`attribute:fast-search`で定義されていることが重要です。[属性フィールドの検索](../performance/practical-search-performance-guide#searching-attribute-fields)を参照してください。

クエリー語句がランキングに影響しない場合に、nearestNeighbor探索とフィルタリングの組み合わせで最適なパフォーマンスを得るには、スキーマで`rank: filter`を使用します ([ランキング式](../reference/ranking/ranking-expressions)を参照):

```js
field popularity type int {
    indexing: summary | attribute
    rank: filter
    attribute: fast-search
}
```

popularityフィールドに対するマッチングはランキングに影響せず、Vespaは最も効率的なポスティング・リスト表現を使用できます。なお、[ランキング式](../ranking/ranking-expressions-features)では引き続き`popularity`属性の値にアクセスできます。 

```js
rank-profile popularity {
    first-phase {
        expression: attribute(popularity)
    }
}
```

次の例では、`title`フィールドには`rank: filter`がないため、代わりに[`ranked`クエリー・アノテーション](../reference/querying/yql#ranked)を使用して、その語句がどのランキング式でも使用されないようにフラグを立てることができます。 

以下は[語句ベースのランキング](../reference/querying/yql#ranked)を無効にし、`title`フィールドに対するマッチングに最も効率的なポスティング・リスト表現を使用できるようにします。

```bash
$ vespa query \
    'yql=select title, artist from track where {totalTargetHits:10}nearestNeighbor(embedding,q) and title contains ({ranked:false}"heart")' \
    'hits=2' \
    'ranking=closeness' \
    'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

前の例では、ランク・プロファイルは[closeness](../reference/ranking/rank-features#closeness(dimension,name))ランク・フィーチャーのみを使用していたため、いずれにせよマッチングはスコアに影響しませんでした。 

Vespaでは、[nearestNeighbor](../reference/querying/yql#nearestneighbor)クエリー演算子を他の任意のVespaクエリー演算子と組み合わせることもできます。  

```bash
$ vespa query \
    'yql=select title, popularity, artist from track where {totalTargetHits:10}nearestNeighbor(embedding,q) and popularity > 20 and artist contains "Bonnie Tyler"' \
    'hits=2' \
    'ranking=closeness' \
    'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

このクエリー例は、探索を`popularity > 20`の`Bonnie Tyler`のトラックに制限します。

### 厳しいフィルターと遠い近傍 

最近傍探索を、ドキュメント総数の2パーセント未満にしかマッチしない厳しいフィルターと組み合わせる場合、Vespaはフィルターで制約されたHNSWグラフの探索の代わりに、厳密な最近傍探索へのフォールバックを行います。どちらの戦略が使用されるかのしきい値を調整する方法については、[フィルター動作の制御](#controlling-filter-behavior)を参照してください。厳密な探索は`totalTargetHits`を超えるヒットを`first-phase`ランキング式に公開する場合があるため、厳密な探索にフォールバックすると、`totalCount`が増加して`totalTargetHits`よりも高くなることが観察されます。これは前の例でも見られます。フィルター付きで厳密な探索を使用する場合、探索はクエリーの評価に複数のスレッドを使用することもでき、レイテンシーへの影響を軽減するのに役立ちます。

多くのヒットを除去する厳しいフィルターでは、ヒット (最近傍) は埋め込み空間において*近い*ものではなく、*遠い*、つまり*遠方の*近傍になる可能性があります。技術的には、すべてのドキュメント・ベクトルはクエリー・ベクトルの近傍ですが、その距離は様々です。

制約の強いフィルターでは、返される近傍の品質が低い (距離が遠い) 場合があります。この影響に対抗する1つの方法は、`nearestNeighbor`クエリー演算子の[distanceThreshold](../reference/querying/yql#distancethreshold)クエリー・アノテーション・パラメーターを使用することです。`distance`の値は、使用される[distance-metric](../reference/schemas/schemas#distance-metric)に依存します。[distance(field,embedding)](../reference/ranking/rank-features#distance(dimension,name))ランク・フィーチャーを`closeness`ランク・プロファイルの`match-features`に追加することで、どの距離が遠すぎると見なされ得るかを分析できます。[match-featuresリファレンス](../reference/schemas/schemas#match-features)を参照してください。

距離0は完璧で、距離1は遠いことに注意してください。`distanceThreshold`は、`distanceThreshold`より**高い**`distance(field, embedding)`を持つヒットを除去します。`distanceThreshold`は、厳密な探索と近似探索のどちらを実行するかに関係なく適用されます。

適切な`distanceThreshold`の設定は、教師あり学習で扱うのが最善です。距離のしきい値は、クエリーの複雑さと、場合によっては返されるtop-kヒットのフィーチャー分布に基づいて調整されるべきだからです。`distance`ランク・フィーチャーを`match-features`として返すようにすることで、カスタムの[再ランキング/フィルタリング・サーチャー](../ranking/reranking-in-searcher)を使用した結果の後処理が可能になります。後処理サーチャーは、返されたtop-kヒットのスコア分布を (`match-features`とともに返されたフィーチャーを使用して) 分析し、結果をエンド・ユーザーに提示する前に低スコアのヒットを除去したり、結果をまったく返さないようにしたりできます。 

## Vespaによるハイブリッドなスパース・デンス検索手法

前のフィルタリングの例では、ランキングはフィルターの影響を受けませんでした。フィルターはリコールにのみ影響し、結果の順序には影響しませんでした。以下の例では、効率的なクエリー演算子を単一のクエリーで組み合わせてハイブリッド検索を実行する方法を示します。ハイブリッド検索は、マルチフェーズ・ランキング・ファネルの最初のフェーズとして使用できます。Vespaの[フェーズド・ランキング](../ranking/phased-ranking)を参照してください。

最初のクエリー例は、`nearestNeighbor`演算子と`weakAnd`演算子を論理和 (`OR`) で組み合わせています。このタイプのクエリーは、セマンティック (ベクトル距離) と従来のスパース (厳密一致) マッチングの両方に基づいた検索を可能にします。 

```bash
$ vespa query \
    'yql=select title, artist from track where {totalTargetHits:100}nearestNeighbor(embedding,q) or userQuery()' \
    'query=total eclipse of the heart' \
    'type=weakAnd' \
    'hits=2' \
    'ranking=hybrid' \
    'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

このクエリーは、スパースな`weakAnd`とデンスな`nearestNeighbor`クエリー演算子を論理和で組み合わせています。両方のクエリー演算子は、それぞれの内部の生スコア関数によってランク付けされた、目標数 (またはそれ以上) のヒットを取得します。

設定可能な`first-phase`ランキング式に公開されるヒットは、2つの異なる検索戦略からの最良のヒットの組み合わせです。ランキングは`hybrid`ランク・プロファイルを使用して実行されます。これは、異なる効率的なリトリーバーを組み合わせる方法の一例として機能します。 

```js expandable
rank-profile hybrid inherits closeness {
        inputs {
            query(wTags) : 1
            query(wPopularity) : 1
            query(wTitle) : 1
            query(wVector) : 1
        }
        first-phase {
            expression {
                query(wTags) * rawScore(tags) + 
                query(wPopularity) * log(attribute(popularity)) + 
                query(wTitle) * log(bm25(title)) + 
                query(wVector) * closeness(field, embedding)
            }
        }
        match-features {
            rawScore(tags)
            attribute(popularity)
            bm25(title)
            closeness(field, embedding)
        }
    }
```

```bash

    'yql=select title, artist from track where rank({totalTargetHits:100}nearestNeighbor(embedding,q), userQuery())' \
    'query=total eclipse of the heart' \
    'type=weakAnd' \
    'hits=2' \
    'ranking=hybrid' \
    'input.query(q)=embed(e5, "Total Eclipse Of The Heart")' 
```

```bash
vespa query \
    'yql=select title, popularity, artist from track where rank(popularity>99,{totalTargetHits:10}nearestNeighbor(embedding,q))' \
    'hits=2' \
    'ranking=closeness' \
    'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

`nearestNeighbor`演算子を`rank`の2番目のオペランドとしてのみ使用するクエリーでは、`HNSW`インデックスを追加する必要がなく、インデックスとメモリのリソース・フットプリントを大幅に節約できます。 

## 同一クエリー内での複数の最近傍探索演算子の使用 

このセクションでは、同じVespaクエリー・リクエスト内で複数の`nearestNeighbor`クエリー演算子インスタンスを使用する方法を見ていきます。次のVespaクエリーは、2つの`nearestNeighbor`クエリー演算子を論理和 (`OR`) で組み合わせ、2つの異なるクエリー・テンソル入力を参照しています:

- `input.query(q)`は*Total Eclipse Of The Heart*のクエリー・ベクトルを保持します。
- `input.query(q1)`は*Summer of '69*のクエリー・ベクトルを保持します。


## フィルター動作の制御

Vespaでは、開発者がフィルターをnearestNeighborクエリー演算子とどのように組み合わせるかを制御できます。*pre-filtering*および*post-filtering*戦略の詳細な説明については、[Query Time Constrained Approximate Nearest Neighbor Search](https://blog.vespa.ai/constrained-approximate-nearest-neighbor-search/)を参照してください。以下のクエリー例では、フィルタリング動作の制御に使用できる2つのクエリー時パラメーターを探ります。パラメーターは以下の通りです

- [ranking.matching.postFilterThreshold](../reference/api/query#ranking.matching) デフォルト 1.0 
- [ranking.matching.approximateThreshold](../reference/api/query#ranking.matching) デフォルト 0.02

これらのパラメーターは、クエリーごとに使用することも、[ドキュメント・スキーマ](../reference/schemas/schemas#post-filter-threshold)のランク・プロファイルで設定することもできます。 

次のクエリーは、*ranking.matching.postFilterThreshold*のデフォルト設定である1で実行されます。これは、post-filteringを実行せず、*pre-filtering*戦略を使用することを意味します:

```bash
$ vespa query \
  'yql=select title, artist, tags from track where {totalTargetHits:10}nearestNeighbor(embedding,q) and tags contains "rock"' \
  'hits=2' \
  'ranking=closeness' \
  'ranking.matching.postFilterThreshold=1.0' \
  'ranking.matching.approximateThreshold=0.05' \
  'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

`totalCount`からわかるように、このクエリーは`totalTargetHits`件をランキングに公開します。次に、同じクエリーを繰り返しますが、*ranking.matching.postFilterThreshold=0.0*を設定して*post-filtering*を強制します:


```bash
$ vespa query \
  'yql=select title, artist, tags from track where {totalTargetHits:10}nearestNeighbor(embedding,q) and tags contains "rock"' \
  'hits=2' \
  'ranking=closeness' \
  'ranking.matching.postFilterThreshold=0.0' \
  'ranking.matching.approximateThreshold=0.05' \
  'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

この場合、Vespaはフィルターがマッチするドキュメント数を推定し、内部で`targethits`をより高い数値に自動調整して、`totalTargetHits`件をfirst phaseランキングに公開しようとします:

`totalCount`からわかるように、このクエリーは16のドキュメントをランキングに公開します。コレクション内には`rock`タグでタグ付けされたドキュメントが`8420`件あり、およそ8%です。 

post-filteringのために`totalTargetHits`を上方に自動調整することは、常に望ましいとは限りません。制約なしでHNSWインデックスから取得するだけの場合よりも遅いためです。`totalTargetHits`の調整係数は、[ranking.matching.targetHitsMaxAdjustmentFactor](../reference/api/query#ranking.matching)パラメーターで変更できます。この場合、1に設定して、`totalTargetHits`の上方調整を無効にします。 


```bash
$ vespa query \
  'yql=select title, artist, tags from track where {totalTargetHits:10}nearestNeighbor(embedding,q) and tags contains "rock"' \
  'hits=2' \
  'ranking=closeness' \
  'ranking.matching.postFilterThreshold=0.0' \
  'ranking.matching.approximateThreshold=0.05' \
  'ranking.matching.targetHitsMaxAdjustmentFactor=1' \
  'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

totalTargetHitsの上方調整なしでpost-filteringを行っているため、最終的なヒット数は少なくなります。 

クエリーを、より頻度の低いタグ、例えば1,695ドキュメント (およそ1.7%) にマッチする`90s`に制限するように変更すると、推定されるフィルターのヒット数が`approximateThreshold`未満になるため、Vespaは厳密な探索にフォールバックします。 

```bash
$ vespa query \
  'yql=select title, artist, tags from track where {totalTargetHits:10}nearestNeighbor(embedding,q) and tags contains "90s"' \
  'hits=2' \
  'ranking=closeness' \
  'ranking.matching.postFilterThreshold=0.0' \
  'ranking.matching.approximateThreshold=0.05' \
  'input.query(q)=embed(e5, "Total Eclipse Of The Heart")'
```

厳密な探索へのフォールバックにより、`totalTargetHits`を超えるドキュメントがランキングに公開されます。最近傍探索とフィルターの組み合わせの詳細については、[Query Time Constrained Approximate Nearest Neighbor Search](https://blog.vespa.ai/constrained-approximate-nearest-neighbor-search/)ブログ記事を参照してください。
