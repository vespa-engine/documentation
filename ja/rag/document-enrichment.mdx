---
title: "LLM によるドキュメント・エンリッチメント"
---

ドキュメント・エンリッチメントは、フィード時に大規模言語モデル(LLM)やカスタムコードを使用して、ドキュメントのフィールド値を自動生成できる機能です。生のテキストをより構造化された表現に変換したり、追加のコンテキスト情報で拡張したりするために利用できます。
エンリッチメントタスクの例には以下が含まれます:

- あいまいマッチングやカスタマイズしたランキングのための固有表現(例:人名、組織名、地名、製品名)の抽出
- フィルタリングやファセットのための分類とタグ付け(例:センチメント分析やトピック分析)
- 検索の再現率(リコール)や検索サジェストを向上させるための関連キーワード、クエリー、質問の生成
- 個人を特定できる情報(PII)を除去する匿名化と、検索結果におけるバイアスの低減
- 多言語検索のためのコンテンツの翻訳
- LLM によるチャンキング

これらのタスクはプロンプトによって定義され、特定のアプリケーションに合わせてカスタマイズできます。
生成されたフィールドは通常のフィールドとしてインデックスおよび保存され、LLM 推論に伴う追加のレイテンシーなしに検索に利用できます。

## ドキュメント・エンリッチメント・コンポーネントのセットアップ

このセクションでは、[LLM document enrichment サンプルアプリ](https://github.com/vespa-engine/sample-apps/tree/master/field-generator)を例に、ドキュメント・エンリッチメントを設定するためのガイドラインを示します。

### 生成フィールドの定義

エンリッチメントは、[generate インデックス式](/ja/reference/writing/indexing-language#generate)を使ってスキーマ内で定義します。
たとえば、次のスキーマは `generate` を使用する 2 つの[シンセティック・フィールド](/ja/operations/reindexing)を定義しています:

```yaml
schema passage {
    document passage {
        field id type string {
            indexing: summary | attribute
        }
    
        field text type string {
            indexing: summary | index
            index: enable-bm25
        }
    }
    
    # Generate relevant questions to increase recall and search suggestions
    field questions type array<string> {
        indexing: input text | generate questions_generator | summary | index
        index: enable-bm25
    }
    
    # Extract named entities for fuzzy matching with ngrams
    field names type array<string> {
        indexing: input text | generate names_extractor | summary | index
        match {
            gram
            gram-size: 3
        }
    }
}
```

インデックス文 `input text | generate questions_generator | summary | index` は次のように解釈されます:
1. `text` という名前のドキュメント・フィールドを入力として受け取る
2. 入力を id が `questions_generator` のフィールドジェネレーターに渡す
3. ジェネレーターの出力をサマリーとして保存する
4. ジェネレーターの出力を字句検索用にインデックスする

このスキーマで生成されたドキュメントの例:
```json
{
    "id": "71",
    "text": "Barley (Hordeum vulgare L.), a member of the grass family, is a  major cereal grain. It was one of the first cultivated grains and is now grown widely. Barley grain is a staple in Tibetan cuisine and was eaten widely by peasants in Medieval Europe. Barley has also been used as animal fodder, as a source of fermentable material for beer and certain distilled beverages, and as a component of various health foods.",
    "questions": [
      "What are the major uses of Barley (Hordeum vulgare L.) in different cultures and regions throughout history?",
      "How has the cultivation and consumption of Barley (Hordeum vulgare L.) evolved over time, from its initial cultivation to its present-day uses?",
      "What role has Barley (Hordeum vulgare L.) played in traditional Tibetan cuisine and Medieval European peasant diets?"
    ],
    "names": [
      "Barley",
      "Hordeum vulgare L.",
      "Tibetan",
      "Medieval Europe"
    ]
}
```

### フィールドジェネレーターの設定

1 つのスキーマには、1 つまたは複数のフィールドジェネレーターを使用する複数の生成フィールドを含めることができます。
使用するすべてのフィールドジェネレーターは `services.xml` で設定する必要があります。例:

```xml expandable
<services version="1.0">
    ...
    <container id="container" version="1.0">
        ...
        <component id="questions_generator" class="ai.vespa.llm.generation.LanguageModelFieldGenerator">
            <config name="ai.vespa.llm.generation.language-model-field-generator">
                <providerId>local_llm</providerId>
                <promptTemplate>Generate 3 questions relevant for this text: {input}</promptTemplate>
            </config>
        </component>
        
        <component id="names_extractor" class="ai.vespa.llm.generation.LanguageModelFieldGenerator">
            <config name="ai.vespa.llm.generation.language-model-field-generator">
                <providerId>openai</providerId>
                <promptTemplateFile>files/names_extractor.txt</promptTemplateFile>
            </config>
        </component>
        ...
    </container>
    ...
</services>
```

すべてのフィールドジェネレーターは、言語モデルクライアントを参照する `<providerId>` を指定する必要があります。
言語モデルクライアントは、ローカル LLM、OpenAI クライアント、またはカスタムコンポーネントのいずれかです。

言語モデルに加えて、フィールドジェネレーターにはプロンプトが必要です。
プロンプトは次の 3 つの部分から構成されます:

1. プロンプトテンプレート。`<promptTemplate>` 内にインラインで指定するか、`<promptTemplateFile>` にパスを指定してアプリケーション・パッケージ内のファイルで指定します。
2. インデックス文からの入力。例:`input text`(`text` はドキュメントのフィールド名)。
3. 生成されるフィールドの出力型。

`<promptTemplate>` と `<promptTemplateFile>` のどちらも指定されていない場合、デフォルトのプロンプトは入力部分になります。
両方が指定された場合は、`<promptTemplateFile>` が優先されます。

プロンプトテンプレートには `{input}` プレースホルダーを含める必要があり、これは入力値に置き換えられます。
複数のフィールドを 1 つの文字列に連結することで、1 つの入力にまとめることも可能です。例:

```yaml
input "title: " . title . " text: " . text | generate names_extractor | summary | index
```

プロンプトテンプレートには `{jsonSchema}` プレースホルダーを含めることもでき、これは生成されるフィールドの型に基づく JSON スキーマに置き換えられます。詳細は[構造化出力のセクション](#structured-output)を参照してください。
プロンプトに JSON スキーマを含めることで、言語モデルが特定のフォーマットで出力を生成しやすくなります。
ただし、フィールドジェネレーターは既に JSON スキーマを個別の推論パラメーターとして、基盤となる言語モデルクライアントに提供していることを理解しておくことが重要です。
ローカル LLM と OpenAI クライアントはどちらも[構造化出力](#structured-output)機能を利用しており、LLM にスキーマに準拠した出力を強制します。
このため、ほとんどのユースケースでは、プロンプトテンプレートに `{jsonSchema}` を明示的に含める必要はありません。

構造化出力は `<responseFormatType>TEXT</responseFormatType>` を指定することで無効化できます。
この場合、生成されるフィールドは `string` 型でなければなりません。
これは、構造化出力の生成が難しい非常に小さなモデル(パラメーター数が 10 億未満)で有用です。
ほとんどのユースケースでは、`string` フィールドであっても構造化出力の使用を推奨します。

フィールドジェネレーター設定の最後のパラメーターは `<invalidResponseFormatPolicy>` で、
基盤となる言語モデルの出力が生成フィールドの型に変換できない場合の動作を指定します。
構造化出力を使用している場合には発生しないはずですが、`TEXT` レスポンスフォーマットでは発生する可能性があります。
デフォルト値は `DISCARD` で、フィールドを空のままにし、`null` を設定します。
その他の値である `WARN` と `FAIL` は、それぞれ警告をログに記録するか、例外をスローします。

すべてのフィールドジェネレーターのパラメーターの概要は、
[設定定義ファイル](https://github.com/vespa-engine/vespa/blob/master/model-integration/src/main/resources/configdefinitions/language-model-field-generator.def)で確認できます。


## 言語モデルの設定

フィールドジェネレーターは、生成に使用する言語モデルクライアントを参照するために `<providerId>` を指定します。
言語モデルクライアントは、ローカル LLM、OpenAI クライアント、またはカスタムコンポーネントのいずれかです。

ローカル LLM と OpenAI クライアントの設定の詳細は、[ローカル LLM](/ja/rag/local-llms) と
[OpenAI クライアント](/ja/rag/external-llms)のドキュメントで説明されています。
このセクションでは、ドキュメント・エンリッチメントにおいて重要な設定パラメーターに焦点を当てます。

ローカル LLM と OpenAI クライアントはどちらも、異なるモデルで設定できます。
ドキュメント・エンリッチメントを効率的にスケールさせるためには、対象タスクに対して許容できる性能を発揮する最小のモデルを選択することを推奨します。
一般に、より大きなモデルはより良い結果をもたらしますが、コストが高く、処理も遅くなります。

情報抽出、要約、拡張、分類といったドキュメント・エンリッチメントのタスクは、より大きなモデルが対象とする問題解決能力に比べて複雑でないことが多いです。
これらのタスクは、ローカルモデルであれば [Microsoft Phi-3.5-mini](https://huggingface.co/microsoft/Phi-3.5-mini-instruct)、
OpenAI API であれば [GPT-4o mini](https://platform.openai.com/docs/models/gpt-4o-mini) のような、より小さくコスト効率の高いモデルで実現できます。

以下は GPT-4o mini モデルで設定した OpenAI クライアントの例です:

```xml
<container version="1.0">
    ...
    <container id="container" version="1.0">
        ...
        {/* OpenAI client */}
        <component id="openai" class="ai.vespa.llm.clients.OpenAI">
            <config name = "ai.vespa.llm.clients.llm-client">
                <apiKeySecretRef>openai-key</apiKeySecretRef>
                <model>gpt-4o-mini</model>
            </config>
        </component>
        ...
    </container>
    ...
</services>
```

OpenAI クライアントでは、モデルの選択が API のコストとレイテンシーに影響します。

モデルに加えて、ローカル LLM クライアントには、ドキュメント・エンリッチメントの性能にとって重要なパラメーターがいくつかあります。
以下の設定は良い出発点となります:

```xml expandable
<services version="1.0">
    ...
    <container id="container" version="1.0">
        ...
       <component id="llm" class="ai.vespa.llm.clients.LocalLLM">
            <config name="ai.vespa.llm.clients.llm-local-client">
                {/* For Vespa Cloud, specify model by model-id to speed-up deployment */}
                <model model-id="phi-3.5-mini-q4"/>

                {/* For self-hosted Vespa and Vespa Cloud, specify model by URL */}
                {/* <model url="https://huggingface.co/bartowski/Phi-3.5-mini-instruct-GGUF/resolve/main/Phi-3.5-mini-instruct-Q4_K_M.gguf"/> */}
                
                {/* Number of tokens a LLM can do inference with.
                This includes prompt and completion tokens for all parallel request. */}
                <contextSize>5000</contextSize>
                
                {/* Requests are processed in parallel using continuous batching.
                Each request is allocated 5000 / 5 = 1000 context tokens. */}
                <parallelRequests>5</parallelRequests>
                
                {/* Request context size split between prompt and completion tokens: 500 + 500 = 1000 */}
                <maxPromptTokens>500</maxPromptTokens>
                <maxTokens>500</maxTokens>
                
                {/* A waiting line for requests to start processing. 
                It is reasonable to set it to <= parallelRequests */}
                <maxQueueSize>3</maxQueueSize>
                
                {/* How long a request can wait until added to the queue, otherwise timeout. 
                On average, Ca. = number of milliseconds it takes to process all parallel requests. */}
                <maxEnqueueWait>60000</maxEnqueueWait>
                
                {/* How long a request can wait in the queue until starting processing
                In the worst case, ca. = number of milliseconds it takes to process all requests in the queue. */}
                <maxQueueWait>60000</maxQueueWait>
                
                {/* Context overflow occurs when a request uses more context tokens than allocated in contextSize / parallelRequests. 
                This should not happen if contextSize, parallelRequests, maxPromptTokens, maxTokens are configured correctly.
                In this case, we want the request to fail so we know if some configuration is wrong. */}
                <contextOverflowPolicy>FAIL</contextOverflowPolicy>
            </config>
        </component>
        ...
    </container>
    ...
</services>
```

この設定には、使用するモデルに加えて 3 つの重要な側面があります。

1. `model`、`contextSize`、`parallelRequests` は、モデルの実行に必要な計算リソースを決定します。
2. `contextSize`、`parallelRequests`、`maxPromptTokens`、`maxTokens` は、コンテキストオーバーフロー(指定されたプロンプトおよびコンプリーショントークン数で複数の並列リクエストを処理するにはコンテキストサイズが小さすぎる状況)を避けるように設定する必要があります。
3. `maxQueueSize`、`maxEnqueueWait`、`maxQueueWait` は、並列リクエストを保持して LLM ランタイム(llama.cpp)に供給するためのキューの管理に関係します。

[ローカル LLM のドキュメント](/ja/rag/local-llms)では、使用するモデルと計算リソースに応じて
`model`、`contextSize`、`parallelRequests` を設定する方法を説明しています。
これらのパラメーターを設定する際には、メモリ使用量(RAM または GPU の VRAM)を特に考慮することが重要です。

コンテキストオーバーフローを避けるには、`contextSize / parallelRequests >= maxPromptTokens + maxTokens` となるように
`contextSize`、`parallelRequests`、`maxPromptTokens`、`maxTokens` パラメーターを設定してください。また、`contextSize` が大きいほど処理に時間がかかることも考慮してください。

キュー関連のパラメーターは、レイテンシーとスループットのバランスを取るために使用します。これらのパラメーターの値は、基盤となる計算リソースに大きく依存します。上記のローカル LLM 設定は、16 コアと 32GB RAM の CPU ノード、および NVIDIA T4 GPU 16GB VRAM を搭載した GPU ノード向けに最適化されています。

### 計算リソースの設定

プロビジョニングされた計算リソースはローカル LLM の性能にのみ影響します。OpenAI クライアントは、サービスプロバイダーのインフラストラクチャーを利用するリモート API を呼び出すだけだからです。
実際には、ローカル LLM の実行には GPU を強く推奨します。CPU と比較して桁違いの高速化が得られます。
Vespa Cloud では、次のような設定が妥当な出発点です:

```xml
<container version="1.0">
    ...
    <container id="container" version="1.0">
        ...
        <nodes count="1">
            <resources vcpu="8.0" memory="32Gb" architecture="x86_64" storage-type="local" disk="225Gb" >
                <gpu count="1" memory="16.0Gb" type="T4"/>
            </resources>
        </nodes>
        ...
    </container>
    ...
</services>
```

この設定は、NVIDIA T4 GPU 16GB VRAM を搭載した単一ノードのコンテナー・クラスターをプロビジョニングします。
ローカルモデルのスループットは、フィードに使用するコンテナー・クラスターのノード数に対して線形にスケールします。
たとえば、8 台の GPU ノード(`<nodes count="8">`)でノードあたりのスループットが 1.5 generations/second の場合、
合計スループットは 12 generations/second 近くになります。

### フィード設定

生成フィールドは、フィード時にかなりのレイテンシーをもたらします。高レイテンシーの並列リクエストが多数発生すると、ドキュメント処理パイプラインでタイムアウトが発生する可能性があります。
これを避けるため、フィード時の接続数を減らすことを推奨します。
妥当な出発点は、GPU ノードあたり 3 接続、CPU ノードあたり 1 接続です。
GPU ノード 1 台の場合の例:

```sh
vespa feed data.json --connections 3
```

## 構造化出力

ドキュメント・エンリッチメントは、ドキュメント・スキーマで定義されたデータ型に基づいてフィールド値を生成します。
ローカル LLM と OpenAI クライアントはどちらも構造化出力をサポートしており、LLM に指定されたスキーマに準拠した JSON の生成を強制します。この JSON スキーマは、作成されるフィールドのデータ型に応じてフィールドジェネレーターが自動的に構築します。たとえば、ドキュメント `passage` の `field questions type array<string>` に対する JSON スキーマは次のようになります:

```json
{
    "type": "object",
    "properties": {
        "passage.questions": {
            "type": "array",
            "items": {
                "type": "string"
            }
        }
    },
    "required": [
        "passage.questions"
    ],
    "additionalProperties": false
}
```

さまざまなデータ型に対して構築されるスキーマは、フィードに使用される
[ドキュメント JSON フォーマット](/ja/reference/schemas/document-json-format)に対応しています。
サポートされているフィールド型は以下のとおりです:
- string
- bool
- int
- long
- byte
- float
- float16
- double
- 上記の型の array

サポートされていない型:
- map
- struct
- weightset
- テンソル
- リファレンス
- predicate
- position

## カスタム・フィールドジェネレーター

Vespa の常として、[カスタム・アプリケーション・コンポーネント](/ja/applications/developer-guide)を開発することで既存の機能を拡張できます。
カスタムジェネレーター・コンポーネントを使用すると、プロンプトの構築、LLM の入出力の変換と検証、複数の LLM の出力の組み合わせ、あるいはナレッジグラフなどの他のソースの利用といった、アプリケーション固有のロジックを実装できます。

`generate` と互換性のあるカスタム・フィールドジェネレーターは、フィールド値を返す `generate` メソッドを持つ
`com.yahoo.language.process.FieldGenerator` インターフェースを実装する必要があります。
以下はカスタム・フィールドジェネレーターの簡単な例です:

```java expandable
package ai.vespa.test;

import ai.vespa.llm.completion.Prompt;
import com.yahoo.document.datatypes.FieldValue;
import com.yahoo.document.datatypes.StringFieldValue;
import com.yahoo.language.process.FieldGenerator;

public class MockFieldGenerator implements FieldGenerator {
   private final MockFieldGeneratorConfig config;

   public MockFieldGenerator(MockFieldGeneratorConfig config) {
      this.config = config;
   }

   @Override
   public FieldValue generate(Prompt prompt, Context context) {
      var stringBuilder = new StringBuilder();

      for (int i = 0; i < config.repetitions(); i++) {
         stringBuilder.append(prompt.asString());

         if (i < config.repetitions() - 1) {
            stringBuilder.append(" ");
         }
      }


      return new StringFieldValue(stringBuilder.toString());
   }
}
```

このコンポーネントの設定定義は次のとおりです:
```yaml
namespace=ai.vespa.test
package=ai.vespa.test

repetitions int default=1
```

`generate` インデックス式で使用するには、このコンポーネントを `services.xml` に追加する必要があります:
```xml expandable
<container>
   ...
   <component id="mock_generator" class="ai.vespa.test.MockFieldGenerator" bundle="mock_field_generator_app">
      <config name="ai.vespa.test.mock-field-generator">
         <repetitions>2</repetitions>
      </config>
   </component>
   ...
</container>
```

最後のステップは、ドキュメント・スキーマでこれを使用することです。例:
```yaml
schema passage {
    document passage {
        field text type string {
            indexing: summary | index
            index: enable-bm25
        }
    }
    
    field mock_text type string {
        indexing: input text | generate mock_generator | summary
    }
}
```
