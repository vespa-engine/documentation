Vespa での LLM の利用の入門については、[Vespa における大規模言語モデル](/ja/rag/llms-in-vespa)を参照してください。

Vespa は、CPU と GPU の両方で、アプリケーション内での LLM の評価をサポートしています。

<Info>
**注:** これは現在ベータ機能であるため、変更される可能性があります。
</Info>

大規模言語モデル(LLM)を Vespa アプリケーション内で直接実行することには、特にデータ・セキュリティとプライバシーの面で、さまざまな利点があります。LLM をローカルで実行すれば、機微な情報はアプリケーションまたはネットワークの範囲内にとどまり、外部サービスへのデータ送信に伴うリスクが排除されます。これは、医療、金融、法務サービスなど、プライバシー・コンプライアンスとデータ・セキュリティが重大な懸念事項となる、機微データや専有データを扱う [RAG ユースケース](/ja/rag/rag)で特に重要です。

さらに、LLM をローカルでホストすることで、アプリケーションは外部プロバイダーが提供するモデルに限定されることなく、それぞれのニーズに最も適したモデルをより幅広い選択肢から選べます。この柔軟性により、企業は運用要件に合わせてパフォーマンス、コスト、効率を最適化できます。加えて、LLM を自社で管理することで、モデルのバージョンを制御でき、いつどのようにモデルを更新するかを選択することで、安定して一貫した出力を維持できます。

最後に、超大規模な基盤モデルが汎用ユースケースを支配している一方で、より小さく、より専門化されたモデル(「小規模言語モデル」と呼ばれることもあります)は、はるかに高性能になっています。

すぐに始めたい場合は、ローカル LLM のセットアップ方法を示す [RAG サンプルアプリ](https://github.com/vespa-engine/sample-apps/tree/master/retrieval-augmented-generation)をご覧ください。


### services.xml での LLM クライアントのセットアップ

<Info>
**注:** この機能は Vespa バージョン >= 8.331 で利用可能です
</Info>

モデルを実行するために必要な推論エンジンをセットアップするには、アプリケーションの [services.xml](/ja/reference/applications/services/services) に `LocalLLM` コンポーネントを定義する必要があります:

```xml
<services version="1.0">
    <container id="default" version="1.0">

        ...

        <component id="local" class="ai.vespa.llm.clients.LocalLLM">
            <config name="ai.vespa.llm.clients.llm-local-client">
                <model url="..." />
            </config>
        </component>

        ...

    </container>
</services>
```

このコンポーネントにより、コンテナー・ノードの起動時に、基盤となる推論エンジンが開始され、モデルがロードされます。クラスター内の各コンテナー・ノードが LLM をロードします。なお、[複数のコンテナー・ノードのクラスター](/ja/applications/containers)をセットアップできます。これは、たとえば利用可能な GPU メモリに収まらない複数の LLM がある場合や、パフォーマンス上の理由から LLM の推論を専用ノードにオフロードしたい場合に役立ちます。

[`model`](/ja/reference/applications/config-files#parameter-types) 設定パラメーターには、Vespa Cloud で既知の `model-id`、`url`、またはアプリケーション・パッケージ内のモデルへの `path` のいずれかを設定できます。ただし通常、LLM ファイルはアプリケーション・パッケージに含めるには大きすぎるため、`url` 属性が使用されます。Vespa で使用できるモデルの種類については、[下記](/ja/rag/local-llms#valid-llm-models)を参照してください。

推論の実行方法をカスタマイズするための設定パラメーターは他にも多数あります。詳細は[設定](/ja/rag/local-llms#local-llm-configuration)のセクションを参照してください。

### 有効な LLM モデル

内部的には、Vespa は [llama.cpp](https://github.com/ggerganov/llama.cpp) を使用しています。`llama.cpp` で動作するモデルファイルはすべて Vespa で使用できます。これには、次のベースモデルとそのファインチューニング版が含まれます:

- LLama 2/3
- Mistral 7B
- Mixtral MoE
- Gemma
- Command R+
- Phi 2/3
- その他多数

最新のモデルの完全なリストについては、`llama.cpp` の [supported models](https://github.com/ggerganov/llama.cpp?tab=readme-ov-file#description) セクションを参照してください。

Vespa は `GGUF` ファイル形式をサポートしています。`GGUF` モデルは [HuggingFace](https://huggingface.co/models) で `GGUF` を検索すると見つかります。safetensors や pytorch.bin モデルなど、他の LLM 形式は、使用前に GGUF に変換する必要があります。変換ツールについては `llama.cpp` を参照してください。

量子化されたモデルもサポートされています。モデルは通常 [FP16](https://en.wikipedia.org/wiki/Half-precision_floating-point_format) 精度で学習されますが、`GGUF` ファイルは 8 ビット以下への精度の削減をサポートしています。これによりサイズを節約でき、より大きなモデルをより少ないメモリに収められます。ただし、精度を下げると推論時間が長くなる場合があるため、トークン生成のパフォーマンスと出力品質の両面で、アプリケーションを適切にベンチマークしてください。

### ローカル LLM の設定

LLM のモデル推論には、`services.xml` で設定され、モデルのロード時に適用される多数の設定パラメーターがあります。また、推論時に設定できる、クエリーパラメーターとして渡されるパラメーターのセットもあります。それらの詳細については、下記の[推論パラメーター](#inference-parameters)を参照してください。

最も重要なモデル設定パラメーターは次のとおりです:

- `model`: 使用するモデルファイル。属性は、Vespa Cloud の既知のモデルを指定する `model-id`、モデルへの URL(たとえば HuggingFace 上のもの)を指定する `url`、またはアプリケーション・パッケージ内のファイルを指定する `path` のいずれかです。
- `parallelRequests`: 処理する並列リクエストの最大数。これは、同時に生成するテキストのバッチサイズです。
- `contextSize`: コンテキスト・ウィンドウのサイズ。モデルは通常、所定のコンテキストサイズで学習されますが、必要に応じて大きくできるのが一般的です。この設定はメモリ使用量に直接影響します。
- `useGpu`: 利用可能な場合に GPU の使用を切り替えます。デフォルトは `true` で、GPU が見つかれば使用されます。詳細は[下記の GPU のセクション](#using-gpus)を参照してください。
- `gpuLayers`: GPU にオフロードするモデルのレイヤー数。この設定により、CPU と GPU での部分的な評価が可能になり、利用可能な GPU メモリより大きなモデルを使用できます。デフォルトでは、すべてのレイヤーが GPU にオフロードされます。
- `threads`: CPU のみで推論する場合に使用するスレッド数。デフォルトは、利用可能なコア数 - 2 です。コア数より大きく設定しないでください。パフォーマンスに深刻な影響を及ぼします。
- `maxTokens`: 生成されるトークンの最大数。デフォルトは 512 です。
- `maxPromptTokens`: プロンプト内のトークンの最大数。プロンプトがこの数を超える場合は切り詰められます。デフォルトは -1 で、プロンプトは切り詰められません。
- `contextOverflowPolicy`: すべての並列リクエストのプロンプトと補完のトークンが `contextSize` に収まらない場合の動作を決定します。デフォルトは `NONE` で、新しいトークンが古いトークンを上書きできます。これにより、補完の品質低下やパフォーマンスの問題が生じる可能性があります。`DISCARD` はリクエストを黙って無視し、トークンを生成せずに返ります。`FAIL` はエラーを発生させます。

設定パラメーターの最新のリストについては、[ローカル LLM クライアントの設定定義](https://github.com/vespa-engine/vespa/blob/master/model-integration/src/main/resources/configdefinitions/llm-local-client.def)を参照してください。

ここでいくつか重要な点を考慮しておく価値があります。まずは `contextSize` パラメーターで指定されるコンテキスト・ウィンドウで、これはモデルが次のトークンを生成するために使用するサイズ(トークン数)です。一般に、[RAG アプリケーション](/ja/rag/rag)では、検索ステージからのコンテキストを保持するために、より大きなコンテキスト・ウィンドウが必要になります。モデルは特定のコンテキスト長で学習されますが、このコンテキスト長は、テキスト生成の品質を大きく損なうことなく、通常 4 倍程度まで拡大できます。

コンテキスト・ウィンドウのサイズは、メモリ使用量に直接影響します。たとえば、Mistral 7B のような典型的な 7B モデル(70 億パラメーター)は、FP16 精度で約 14Gb、8 ビット量子化で 7Gb のメモリを使用します。8 ビット量子化を使用すると仮定した場合:

- コンテキスト・ウィンドウが `4096` の場合、モデルに 7.3Gb、コンテキスト・ウィンドウに 512Mb、計算バッファーに 296Mb を使用し、合計で約 8Gb のメモリが必要になります。
- コンテキスト・ウィンドウが `32768` の場合、モデルに 7.3Gb、コンテキスト・ウィンドウに 4Gb、計算バッファーに 2.2Gb を使用し、合計でほぼ 14Gb のメモリが必要になります。

したがって、16Gb のメモリを持つ 1 台の GPU で、コンテキストサイズ `32768` の 7B モデルをぎりぎり保持できます。参考までに、Mistral 7B モデルはこのコンテキストサイズで学習されています。

さて、Vespa のコンテキストで実行する場合、一般には複数のリクエストを並列に処理したいはずです。コンテナー・ノードあたりに処理できる並列リクエスト数は、`parallelRequests` パラメーターで設定します。これは実質的に、同時に評価できる**スロット**の数を設定するものです。生成すべき各シーケンスは、生成されるトークンごとのコンテキストを保持するために、かなりの量のメモリを必要とします。

このタスクに設定されるメモリの総量は、`contextSize` パラメーターで指定されます。各リクエストの実効的なコンテキストサイズは、このサイズを並列リクエスト数で割ったものです。したがって、合計コンテキストサイズが `32768` トークンで並列リクエストが `10` の場合、各リクエストの実効的なコンテキスト・ウィンドウは `3276` トークンになります。リクエストあたりのコンテキストサイズを増やすには、合計コンテキストサイズを増やす必要があり、当然メモリ使用量に大きな影響を与えます。これは、利用可能なメモリが限られている GPU で最も深刻です。

このように、メモリの制約がこれら 2 つのパラメーターの設定を左右します。参考として、16Gb の GPU は、コンテキストサイズを `40960` に設定することで、7B の 8 ビット・モデルを、リクエストあたりコンテキストサイズ `4096` で `10` 並列リクエスト分保持できます。より大きなコンテキスト・ウィンドウが必要な場合は、並列リクエスト数を減らす必要があります。同様に、コンテキストサイズを減らすことで並列リクエスト数を増やせます。これはアプリケーションの要件次第です。


### 推論パラメーター

推論パラメーターの設定については、[LLM パラメーター](/ja/rag/llms-in-vespa#llm-parameters)の一般的な説明を参照してください。

ローカル LLM の推論には、クエリーとともに送信できる次の推論パラメーターがあります:

- `npredict`: 生成するトークン数。モデル設定の `maxTokens` 設定を上書きします。
- `temperature`: モデルの temperature 設定。通常 `0.0` から `1.0` の間です。
- `repeatpenalty`: トークンの繰り返しに対するペナルティ。
- `topk` と `topp`: トークン・サンプリングの確率。低い値はより一貫性があり焦点の定まったテキストを生成する傾向があり、高い値はより多様性と創造性をもたらしますが、誤りや支離滅裂さが増える可能性があります。
- `jsonSchema`: 構造化出力に使用する JSON スキーマ。このパラメーターを指定すると、構造化出力も有効になります。詳細は[構造化出力](/ja/rag/llms-in-vespa#structured-output)を参照してください。

ここで最も重要なのは `npredict` で、一定数のトークンが生成された後にトークン生成プロセスを停止します。モデルによっては、特定のプロンプトに対して、無限にトークンを生成し続けるループに入ることがあります。これは明らかに好ましくない状況なので、この数値は、レスポンスに必要なすべてのトークンを生成できる程度に十分大きく、かつモデルが無限にトークンを生成し続けるのを止められる程度に小さく設定すべきです。


## GPU の使用

GPU を使用するとトークン生成を大幅に高速化でき、一般的に推奨されます。前述のメモリ要件に関する議論は、メモリの制限があるため、GPU で実行する場合に特に深刻です。Vespa では、GPU が利用可能な場合はモデル全体を GPU にオフロードするのがデフォルトですが、`gpuLayers` パラメーターを使用して、モデルの一部を GPU にオフロードする実験ができます。

```xml
<services version="1.0">
    <container id="default" version="1.0">

        {/* Sets up the inference on a mistral 7B model */}
        <component id="local" class="ai.vespa.llm.clients.LocalLLM">
            <config name="ai.vespa.llm.clients.llm-local-client">
                <model url="url/to/mistral-7B-8bit" />
                <parallelRequests>10</parallelRequests>
                <contextSize>40960</contextSize>
                <useGpu>true</useGpu> {/* default is true */}
                <gpuLayers>100</gpuLayers>
            </config>
        </component>

    </container>
</services>

```

ここでは、モデル自体は 33 レイヤーを持ち、すべてが GPU にオフロードされます。モデルが大きすぎて GPU に収まらない場合は、モデルの一部を GPU にオフロードすることで、モデル評価を高速化できます。

セルフホスト環境での GPU のセットアップについては、[コンテナー GPU セットアップ](/ja/operations/self-managed/vespa-gpu-container)を参照してください。

Vespa Cloud では GPU アクセラレーションを非常に簡単に利用できます。GPU 推論を有効にするには、コンテナー・ノードで [GPU をリクエスト](/ja/reference/applications/services/services#gpu)する必要があります。より実践的な入門としては、Vespa Cloud の GPU 上で LLM を評価する方法も示している [RAG サンプルアプリ](https://github.com/vespa-engine/sample-apps/tree/master/retrieval-augmented-generation)をご覧ください。
