この時点で、[テキスト検索チュートリアル](/ja/learn/tutorials/text-search)を読み、以下のステップを完了していることを前提とします。

- Vespa で基本的なテキスト検索アプリを作成してデプロイした。
- MS MARCO のフルドキュメント・データセットをアプリにフィードした。
- 2 つの異なるランキング関数を比較・評価した。

これから、MS MARCO データセットの関連性情報と Vespa のランキング・フィーチャーを結合したデータセットを作成し、アプリケーションを改善するための ML モデルを学習できるようにする方法を紹介します。より具体的には、このチュートリアルでは以下のステップを行います。

- 特定のクエリーに関連付けられたランク・フィーチャー・データを Vespa から収集する方法を学ぶ。
- アプリのランキング関数を改善するために使用できるデータセットを作成する。
- データ収集ロジックのバグを検出し、プロセスの最後に適切に構築されたデータセットが得られていることを確認するためのサニティチェックを提案する。
- Learning To Rank (LTR) タスクを扱う際に、pointwise 損失関数を超えることの重要性を示す。

[Vespa Product Ranking](https://github.com/vespa-engine/sample-apps/tree/master/commerce-product-ranking) は、XGBoost と LightGBM を使った Learning To Rank の良いリソースであり、関連するブログ記事へのリンクもあります。


## Vespa からランク・フィーチャー・データを収集する

Vespa の[ランク・フィーチャー・セット](/ja/reference/ranking/rank-features)には、低レベルおよび高レベルのフィーチャーが数多く含まれています。これらのフィーチャーは、アプリの挙動を理解し、ランキング関数を改善するのに役立ちます。


### デフォルトのランク・フィーチャー

デフォルトのランキング・フィーチャー・セットにアクセスするには、クエリー・パラメーター [`ranking.listFeatures`](/ja/reference/api/query#ranking.listfeatures) を `true` に設定します。たとえば、以下は [クエリー](/ja/querying/query-language)において、前のチュートリアルで開発した `bm25` rank-profile を選択し、返される各結果に関連付けられたランク・フィーチャーを返す POST リクエストのボディです。

```bash
$ vespa query \
  'yql=select id,rankfeatures from msmarco where userQuery()' \
  'query=what is dad bod' \
  'ranking=bm25' \
  'type=weakAnd' \
  'ranking.listFeatures=true'
```

デフォルトで返されるランク・フィーチャーのリストは将来変更される可能性があります。現在のリストは[システム・テスト](https://github.com/vespa-engine/system-test/blob/master/tests/search/rankfeatures/dump.txt)で確認できます。上記のボディで指定されたリクエストに対して、次のような(編集済みの)JSON が返されます。各結果には、デフォルトのランキング・フィーチャーのセットを含む `rankfeatures` というフィールドが含まれます:

### 特定のランク・フィーチャーの選択と処理

ランク・フィーチャーの完全なセットを返す代わりに[特定のフィーチャー](/ja/reference/ranking/rank-features)を選択したい場合は、*msmarco.sd* スキーマ定義に新しい rank-profile(ここでは `collect_rank_features` と呼びます)を追加し、新しい rank-profile に `ignore-default-rank-features` を追加してデフォルトのランキング・フィーチャーを無効化できます。さらに、`rank-features` 要素内で目的のフィーチャーを指定できます。以下の例では、`bm25(title)`、`bm25(body)`、`nativeRank(title)`、`nativeRank(body)` のみを返すように Vespa を明示的に構成しています。

利用可能な*すべての*ランク・フィーチャーを使用すると、Vespa がこれらすべてのフィーチャーを計算する必要があるため、計算コストがかかることに注意してください。多くのフィーチャーを使用することは、通常、second phase ランキングを使用する場合にのみ推奨されます。[Vespa のフェーズド・ランキング](/ja/ranking/phased-ranking)を参照してください。

```sd expandable
schema msmarco {
    document msmarco {
        field id type string {
            indexing: attribute | summary
        }
        field title type string {
            indexing: index | summary
            index: enable-bm25
        }
        field url type string {
            indexing: index | summary
        }
        field body type string {
            indexing: index
            index: enable-bm25
        }
    }

    document-summary minimal {
        summary id {  }
    }

    fieldset default {
        fields: title, body, url
    }

    rank-profile default {
        first-phase {
            expression: nativeRank(title, body, url)
        }
    }

    rank-profile bm25 inherits default {
        first-phase {
            expression: bm25(title) + bm25(body) + bm25(url)
        }
    }

    rank-profile collect_rank_features inherits default {
        first-phase {
            expression: bm25(title) + bm25(body) + bm25(url)
        }
        second-phase {
            expression: random
        }

        match-features {
            bm25(title)
            bm25(body)
            bm25(url)
            nativeRank(title)
            nativeRank(body)
            nativeRank(url)
        }
    }
}
```


```
Paste the above into file text-search/app/schemas/msmarco.sd
```

[random](/ja/reference/ranking/rank-features#random) グローバル・フィーチャーは、次のセクションでデータ収集プロセスを説明する際に役立ちます。

`collect_rank_features` rank-profile を *msmarco.sd* に追加したら、アプリを再デプロイします:

```bash
$ vespa deploy --wait 300 app
```


## 学習データセットの作成

[前のチュートリアル](/ja/learn/tutorials/text-search)で説明した [MS MARCO](https://microsoft.github.io/msmarco/) データセットには、30 万を超える学習クエリーが含まれており、それぞれのクエリーには、そのクエリーに関連する特定のドキュメント ID が関連付けられています。このセクションでは、ペア `(query, relevant_id)` に含まれる情報と Vespa のランキング・フィーチャーで利用可能な情報を組み合わせて、msmarco テキスト・アプリのランキング関数を改善するための ML モデルの学習に使用できるデータセットを作成します。

収集プロセスの詳細な説明に移る前に、プロセス全体は、[このチュートリアルのリポジトリ](https://github.com/vespa-engine/sample-apps/tree/master/text-search)にあるデータ収集スクリプト `collect_training_data.py` を以下のように呼び出すことで再現できることをお伝えしておきます:

以下の手順では、フル・データセットをダウンロード済みであることが必要です。

```bash
$ ./src/python/collect_training_data.py msmarco collect_rank_features 99
```

上記のコマンドは、MSMARCO データセットの一部であるクエリー・ファイル(msmarco-doctrain-queries.tsv.gz)と関連性ファイル(msmarco-doctrain-qrels.tsv.gz)に含まれるデータを使用し、前のセクションで定義した `collect_rank_features` rank-profile を使って Vespa にクエリーを送信し、各クエリーについて、そのクエリーに関連付けられた関連ドキュメントに加えて、ランダムに選択された `99` 件のドキュメントをリクエストします。リクエストからのすべてのデータはパースされ、出力フォルダー(この場合は `data`)に保存されます。


### データ収集ロジック

アプリケーションの first-phase ランキング関数を改善したいので、ここでの目標は、未知の可能性のあるクエリーやドキュメントに対して実際に稼働している Vespa インスタンスの first-phase ランキングで使用されたときに、うまく汎化するモデルを学習するために使用されるデータセットを作成することです。これは一見当たり前のことのように思えますが、データ収集に関するいくつかの決定を行う際に見落としがちであることが分かります。

`collect_training_data.py` の背後にあるロジックは、以下の擬似コードで要約できます:

```python
hits = get_relevant_hit(query, rank_profile, relevant_id)
if relevant_hit:
    hits.extend(get_random_hits(query, rank_profile, number_random_sample))
    data = annotate_data(hits, query_id, relevant_id)
    append_data(file, data)
```

各クエリーについて、まずクエリーに関連付けられた関連ドキュメントを取得するために Vespa にリクエストを送信します。関連ドキュメントがクエリーにマッチした場合、Vespa はそれを返し、2 番目のリクエストを Vespa に送信して、クエリーに関連付けられるドキュメントの数を拡張します。2 番目のリクエストは、クエリーにマッチしたドキュメントの集合からサンプリングされた、ランダムなドキュメントを一定数返すよう Vespa に要求します。次に、Vespa から返されたヒットをパースし、ランク・フィーチャーと、クエリーとドキュメントのペアが関連しているかどうかを示す二値変数を含む表形式にデータを整理します。

クエリーにマッチしたドキュメントだけを収集することに関心があるのは、それらが本番環境で first-phase モデルに提示されるドキュメントだからです。つまり、関連ドキュメントに関する情報を含むいくつかのクエリーが収集されたデータセットから除外される可能性がありますが、それによって、先に述べた目標により近いデータセットが作成されます。言い換えれば、収集するデータセットはマッチ条件を前提条件としています。


### 関連ヒットの取得

最初の Vespa リクエストは、関数呼び出し `get_relevant_hit(query, rank_profile, relevant_id)` に含まれています。ここで、`query` パラメーターには目的のクエリー文字列が入り、`rank_profile` は先に定義した `collect_rank_features` に設定され、`relevant_id` はその特定のクエリーに関連しているとされるドキュメント ID です。

リクエストのボディは以下のとおりです:

```python
body = {
    "yql": "select id, rankfeatures from sources * where userQuery()",
    "query": query,
    "hits": 1,
    "recall": "+id:" + str(relevant_id),
    "ranking": {"profile": rank_profile, "listFeatures": "true"},
}
```

ここで、`yql` と `userQuery` パラメーターは、`collect_rank_features` rank-profile で定義された選択済みのランク・フィーチャーとともに、ドキュメントの *id* を返すよう Vespa に指示します。各クエリーには関連 id が 1 つしかないことが分かっているため、`hits` パラメーターは 1 に設定し、Vespa が結果セットで 1 件のドキュメントのみを返すようにします。`recall` パラメーターにより、取得したいドキュメントの *id* を正確に指定できます。

`recall` パラメーターは、ドキュメントがクエリーにマッチした場合にのみ機能することに注意してください。これはまさにこの場合に望む挙動です。

id が 1 のドキュメントを 1 件取得する `recall` の構文は `"recall": "+id:1"` であり、複数のドキュメント、たとえば id が 1 と 2 のドキュメントを取得する構文は `"recall": "+(id:1 id:2)"` です。

クエリーの指定にマッチしなくてもドキュメントを取得したい場合は、次のクエリー指定を使用するようにクエリーを変更できます:

```python
body = {
    "yql": "select id, rankfeatures from sources * where true or userQuery()",
    "query": query,
    "hits": 1,
    "recall": "+id:" + str(relevant_id),
    "ranking": {"profile": rank_profile, "listFeatures": "true"},
}
```


### ランダム・ヒットの取得

2 番目の Vespa リクエストは、マッチした集合からランダムに選択されたドキュメントを追加してデータセットを拡張したいときに行われます。このリクエストは関数呼び出し `get_random_hits(query, rank_profile, number_random_sample)` に含まれており、唯一の新しいパラメーターは `number_random_sample` で、マッチした集合からサンプリングするドキュメント数を指定します。

リクエストのボディは以下のとおりです:

```python
body = {
    "yql": "select id, rankfeatures from sources * where default contains text(@userQuery)",
    "userQuery": query,
    "hits": number_random_sample,
    "ranking": {"profile": collect_features, "listFeatures": "true"},
}
```

`get_relevant_hit` との唯一の違いは、`recall` パラメーターが不要になったことと、Vespa が返すヒット数を `number_random_sample` と等しく設定したことです。

second phase でランダムなスコアリングを使用するように構成していたことを思い出してください:

```sd
second-phase {
    expression: random
}
```

second-phase のランキング関数として `random` を使用することで、Vespa が返す上位のドキュメントが、クエリーにマッチしたドキュメントの集合からランダムに選択されることが保証されます。

## データ収集のサニティチェック

このチュートリアルを執筆し、上記のデータ収集ロジックを作成する過程で、プロセスのバグを見つけるのに役立つデータ収集のサニティチェックを開発することが有用であると分かりました。ここに唯一の正解はありませんが、私たちの提案は、改善したいベースラインと同じフィーチャーと関数形式を使用してモデルを学習するためにデータセットを使用することです。データセットが適切に構築され、関心のあるタスクに関する有用な情報を含んでいるならば、別のテスト・セットにおいて、少なくともベースラインと同等の結果が得られるはずです。

私たちの場合、ベースラインは[前のチュートリアル](/ja/learn/tutorials/text-search)で使用したランキング関数です:

```sd
rank-profile bm25 inherits default {
    first-phase {
        expression: bm25(title) + bm25(body)
    }
}
```

したがって、サニティチェック用のモデルは、上記の 2 つのフィーチャーのみを含む線形モデル、すなわち `a + b * bm25(title) + c * bm25(body)` となります。ここで、`a`、`b`、`c` は収集したデータセットを使って学習されるべきものです。

データセットを学習セットと検証セットに分割し、線形モデルを学習して検証データセットで評価します。そして、収集した検証セットにおけるモデルとベースラインの差が、独立したテスト・セットに適用したときに稼働中の Vespa インスタンスで観察される差と類似していることを期待します。さらに、ベースライン・モデルは学習可能なモデルの集合に含まれており、`a=0`、`b=1`、`c=1` のときに再現されるため、学習したモデルはテスト・セットにおいて少なくともベースラインと同等の性能を発揮することが期待されます。

これは単純な手順ですが、このチュートリアルの執筆中にいくつかのバグを実際に発見しました。たとえば、ある時点で

```sd
first-phase {
    expression: random
}
```

を `collect_rank_features` rank-profile に含めることを忘れてしまい、負例が実際にはクエリーにかなり関連しているという偏ったデータセットになってしまいました。学習したモデルは検証セットでは良好な結果を示しましたが、Vespa にデプロイしてテスト・セットに適用すると惨憺たる結果になりました。これは、データセットが稼働中の Vespa インスタンスで観察されるものとは異なる分布を持っている可能性が高いことを示しており、調査によってバグを発見することにつながりました。


## pointwise 損失関数を超えて

前のセクションで述べた線形モデルを学習する最も直接的な方法は、ターゲット変数 `relevant` が二値であるため、通常のロジスティック回帰を使用することです。この場合に最もよく使用される損失関数(バイナリー・クロスエントロピー)は、ドキュメントの相対的な順序を考慮しないため、LTR の文献では pointwise 損失関数と呼ばれます。しかし、[前のチュートリアル](/ja/learn/tutorials/text-search)で説明したとおり、この場合に最適化したいメトリクスは Mean Reciprocal Rank (MRR) です。MRR は、クエリーによって生成されたドキュメントのリストに割り当てる関連度の相対的な順序に影響され、その絶対的な大きさには影響されません。損失関数の特性と関心のあるメトリクスとのこの乖離は、最適とはいえない結果につながる可能性があります。

検索結果のランキングでは、線形モデルを学習する際に、モデル・パラメーターを更新するときにランク付けされたリスト全体を考慮する listwise 損失関数を使用することが望ましいです。これを示すために、[TF-Ranking フレームワーク](https://github.com/tensorflow/ranking)を使用して線形モデルを学習しました。このフレームワークは TensorFlow の上に構築されており、pointwise、pairwise、listwise の損失関数などを指定できます。

以下の 2 つの *rank-profile* は、それぞれ pointwise(シグモイド・クロスエントロピー)と listwise(ソフトマックス・クロスエントロピー)の損失関数で線形モデルを学習して得られたものです:

```sd
rank-profile pointwise_linear_bm25 inherits default {
    first-phase {
        expression: 0.22499913 * bm25(title) + 0.07596389 * bm25(body)
    }
}

rank-profile listwise_linear_bm25 inherits default {
    first-phase {
        expression: 0.13446581 * bm25(title) + 0.5716889 * bm25(body)
    }
}
```

pointwise 損失関数が body に比べて title により大きな重みを設定し、listwise 損失関数を使用すると逆のことが起こるのは興味深い点です。

以下の図は、これら 2 つのランキング関数が、Vespa から返されるドキュメントのリストの 1 位から 10 位の間に関連ドキュメントをどのくらいの頻度で(5,000 を超えるテスト・クエリーにわたって)配置するかを示しています。これらのモデル間に平均的には大きな差はありませんが、以下の図から、listwise 損失関数に基づくモデルは、pointwise モデルと比較して、ランク付けされたリストの最初の 2 つの位置により多くのドキュメントを配置していることが明確に分かります:

<Frame>
![pointwise と listwise の BM25 のプロット](/assets/img/tutorials/text_search_baseline_pointwise_listwise_rr.png)
</Frame>

全体として、平均的には、これらのモデル間に(MRR に関して)大きな差はありません。これは、ここで説明したモデルの単純さを考えると予想どおりでした。ポイントは、LTR タスクを扱う際により良い損失関数を選択することの重要性を指摘し、自分のアプリケーションで試してみたい人のためのクイック・スタートを提供することにありました。より複雑なモデルに移行するにつれて、pointwise と listwise の損失関数間の MRR の差は大きくなると予想されます。
