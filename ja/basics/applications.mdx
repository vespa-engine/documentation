---
title: Vespa アプリケーション
---

Vespa は、*アプリケーション*をデプロイすることで利用します。なぜアプリケーションなのでしょうか？ それは、Vespa がデータと、そのデータに対して行う計算の両方を扱うからです。両者を合わせたものがアプリケーションです。

アプリケーションは、*アプリケーション・パッケージ*（いくつかのファイルを含むディレクトリ）によって定義されます。アプリケーション・パッケージには、アプリケーションの実行に必要な*すべて*が含まれます: 設定、スキーマ、コンポーネント、ML モデルなどです。

アプリケーションを変更する*唯一の*方法は、アプリケーション・パッケージに変更を加えて再度デプロイすることです。Vespa は、クエリー、書き込み、データに影響を与えることなく、稼働中のシステムを新しいアプリケーション・パッケージのリビジョンに合わせて安全に変更します。

## 最小のアプリケーション・パッケージ

たった 1 つのファイル `services.xml` だけで、完全なアプリケーション・パッケージを作成できます。このファイルは、アプリケーションが実行すべきクラスターを指定します。次のように、*コンテナー*と呼ばれる単一のステートレス・クラスターだけでも構いません:

```xml
<services version="1.0">
    <container version="1.0" id="default">
        <nodes count="2">
            <resources vcpu="4" memory="16Gb" disk="50Gb"/>
        </nodes>
    </container>
</services>
```

これを `services.xml` というファイルに保存すれば、世界最小のアプリケーション・パッケージの完成です。ただし、これだけでは大したことはできません。通常は、データを保存し、インデックスを維持し、クエリーの分散処理部分を実行できる `content` クラスターが必要になります。また、コンテナー・クラスターにはそのために必要なミドルウェアをロードさせる必要があります。それらを加えると、services ファイルは次のようになります:

```xml
<services version="1.0">
    <container version="1.0" id="queryfeedendpoint">
        <search/>
        <document-api/>
        <nodes count="2">
            <resources vcpu="4" memory="16Gb" disk="50Gb"/>
        </nodes>
    </container>
    <content id="mydocs" version="1.0">
        <min-redundancy>2</min-redundancy>
        <nodes count="2">
            <resources vcpu="8" memory="64Gb" disk="200Gb"/>
        </nodes>
        <documents>
            <document type="myschema" mode="index"/>
        </documents>
    </content>
</services>
```

これはごく標準的でシンプルな Vespa アプリケーションの定義ですが、もう 1 つ別のファイルが必要になります: 使用するドキュメントタイプのスキーマです。これは `schemas/` ディレクトリに置くので、アプリケーション・パッケージは次のようになります:

```txt
services.xml
schemas/myschema.sd
```

スキーマファイルは、データの種類と、そのデータに対して行いたい計算（ランキング／スコアリングなど）を記述します。最低限、そのデータタイプのフィールドと、各フィールドをインデックスするかどうかを列挙するだけです:

```txt
schema myschema {

    document myschema {

        field text type string {
            indexing: summary | index
        }

        field embedding type tensor<bfloat16>(x[384]) {
            indexing: attribute | index
        }

        field popularity type double {
            indexing: summary | attribute
        }

    }

}
```

この 2 つのファイルだけで、フィルタリング付きのテキスト検索、ベクトル検索、ハイブリッド検索が可能な、完全に機能するアプリケーションを定義できました。

このようにゼロからアプリケーションを作成する代わりに、[はじめに](/ja/basics/deploy-an-application)で行ったように、サンプルアプリケーションをクローンして出発点にすることもできます。

スキーマについて詳しくは、[スキーマ](/ja/basics/schemas)ガイドを参照してください。アプリケーション・パッケージに含められるすべての内容については、[アプリケーション・パッケージのリファレンス](/ja/reference/applications/application-packages)を参照してください。

## アプリケーションのデプロイ

アプリケーションの実行インスタンスを作成する、またはアプリケーションへの変更を反映させるには、アプリケーションを*デプロイ*します。dev zone やセルフマネージドのクラスターへのデプロイメントでは単一のインスタンスがセットアップされ、プロダクションへのデプロイメントでは 1 つ以上のリージョンに複数のインスタンスをセットアップできます。

アプリケーション・パッケージをデプロイするには、Vespa CLI の [deploy コマンド](/ja/clients/vespa-cli#deployment)を使用します:

```bash
vespa deploy .
```

これにより、カレントディレクトリのアプリケーション・パッケージが、現在のターゲットとデフォルトの dev zone にデプロイされます（その他のオプションは `vespa deploy -h` で確認できます）。

プロダクション zone へのデプロイメントには、別のコマンドを使用します:

```bash
vespa prod deploy .
```

プロダクションへのデプロイメントでは、デプロイ先を指定するための追加ファイル `deployment.xml` をアプリケーション・パッケージに含める必要があります。[プロダクション・デプロイメント](/ja/operations/production-deployment)を参照してください。プロダクションへの推奨のデプロイ方法は、継続的デプロイメントのジョブをセットアップすることです。[自動デプロイメント](/ja/operations/automated-deployments)を参照してください。

アプリケーション・パッケージへの変更のデプロイは、一般的にいつでも安全に行えます。クエリーや書き込みを中断させることはなく、無効な変更や破壊的な変更は反映される前に拒否されます。また、プロダクション zone へのデプロイの前にアプリケーションを検証するテストを追加することもできます。
