Vespa Cloud は、アプリケーションへのリクエストをルーティングする複数の方法をサポートしています。このガイドでは、これらのルーティング方法の仕組み、フェイルオーバー、および設定方法について説明します。

デフォルトでは、Vespa Cloud アプリケーションの各デプロイメントにはゾーン・エンドポイントがあります。デフォルトのゾーン・エンドポイントに加えて、グローバル・エンドポイントを設定できます。

アプリケーションのすべてのエンドポイントは、コンソールの各デプロイメントの *endpoints* タブで確認できます。

## エンドポイントの形式

Vespa Cloud のエンドポイントは次の形式です: `{random}.{random}.{scope}.vespa-app.cloud`。

## エンドポイントのスコープ

### ゾーン・エンドポイント

これはデプロイメントのデフォルトのエンドポイントです。ゾーン・エンドポイントを経由するリクエストは、そのゾーンに直接送信されます。

ゾーン・エンドポイントは、[services.xml](/ja/reference/applications/services/container) で宣言されたコンテナー・クラスターごとに 1 つ、暗黙的に作成されます。ゾーン・エンドポイントは設定変更できません。

ゾーン・エンドポイントの接尾辞は `z.vespa-app.cloud` です

### グローバル・エンドポイント

グローバル・エンドポイントは、複数のゾーンにリクエストをルーティングできるエンドポイントです。[deployment.xml](/ja/reference/applications/deployment#endpoints-global) で設定できます。[CDN](https://en.wikipedia.org/wiki/Content_delivery_network) の動作と同様に、このエンドポイントを経由するリクエストは、地理的な近さに基づいて最も近いゾーン、つまりクライアントに最も近いゾーンにルーティングされます。

グローバル・エンドポイントの接尾辞は `g.vespa-app.cloud` です

<Warning>
**重要:** 

グローバル・エンドポイントはフィードをサポートしていません。フィードはゾーン・エンドポイントを通じて行う必要があります。
</Warning>


## ルーティング制御

Vespa Cloud には、ゾーンへのリクエストのルーティングを手動で制御する 2 つの機構があります:

- [deployment.xml](/ja/reference/applications/deployment) の該当する `<endpoint>` 要素から `<region>` 要素を削除し、アプリケーションの新しいバージョンをデプロイする。
- コンソールからステータスを変更する。

このセクションでは後者の機構について説明します。コンソールでアプリケーションの該当するデプロイメントに移動します。*GLOBAL ROUTING* バッジにカーソルを合わせると、現在のステータスと最終変更日時が表示されます。

### ステータスの変更

本番環境で緊急事態が発生した場合、ゾーンを手動で切り離してリクエストを受信しないようにできます:

1. 問題のあるデプロイメントの *GLOBAL ROUTING* バッジにカーソルを合わせ、*Deactivate* をクリックします。
2. ステータスを確認すると、*OUT* に設定されていることが表示されます。ゾーンを元に戻してリクエストの受信を再開させるには、再度 *GLOBAL ROUTING* バッジにカーソルを合わせ、*Activate* をクリックします。

### 動作

ルーティング・ステータスの変更は、使用しているエンドポイントのスコープとは独立しています。技術的には、デプロイメントが Vespa Cloud のルーティング・インフラストラクチャーに報告するルーティング・ステータスをオーバーライドしていることになります。つまり、ルーティング・ステータスの変更は、*ゾーン・エンドポイント*と*グローバル・エンドポイント*の両方に影響します。

デプロイメントを Deactivate すると、再度 Activate されるまで、グローバル・エンドポイント経由でそのデプロイメントへリクエストがルーティングされなくなります。これらのエンドポイントを経由するルーティングは DNS ベースであるため、すべてのトラフィックが他のデプロイメントに移行するまで 5~15 分程度かかる場合があります。

エンドポイントのすべてのデプロイメントが Deactivate された場合、リクエストはすべてのデプロイメントがアクティブであるかのように分散されます。これは、すべてのリクエストを破棄するよりも、元の設定に従ってトラフィックをルーティングしようとする方が望ましいためです。

## AWS クライアント

Vespa Cloud は AWS 上でホストされていますが、AWS のノードから Vespa Cloud と通信するクライアントは、インターネット上の他のクライアントと同様に扱われます。つまり、AWS 内のクライアントは、同じゾーンの AWS 内のサービスと通信していても、通常のインターネット・エグレス・トラフィックを発生させます。
