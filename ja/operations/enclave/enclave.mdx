<Frame>
![enclave のアーキテクチャー](/assets/img/enclave-architecture.png)
</Frame>

Vespa Cloud Enclave を使用すると、Vespa Cloud のアプリケーションをテナント自身のクラウドアカウント内で実行しながら、すべてを Vespa Cloud の自動化によって完全に管理された状態に保つことができ、テナントは自身のクラウドアカウント内で Vespa Cloud の全機能を利用できます。これにより、テナントのデータは常にテナントが管理するサービスの範囲内に留まり、また、クラウドサービス内で Vespa アプリケーションとのより緊密な統合を構築することもできます。

Vespa Cloud Enclave は AWS、Azure、GCP で利用できます。

<Note>
**Note:** 

Vespa Cloud Enclave のリソースは*お客様の*アカウント内で実行されるため、Vespa Cloud の費用に*加えて*、クラウドプロバイダーからのリソース費用が発生します。
</Note>

<Accordion title="Vespa のホスト上でエージェント／デーモンを安全に設定するにはどうすればよいですか？">

terraform を使用して Vespa のホストに必要なシークレットへのアクセスを許可し、それらを取得してアプリケーションを設定する RPM を作成してください。完全な例については [enclave-examples](https://github.com/vespa-cloud/enclave-examples/tree/main/systemd-secrets) を参照してください。
</Accordion>
<Accordion title="デプロイ失敗: Could not provision …">

これは、Terraform/CloudFormation テンプレートを実行する*前*に新しい zone にデプロイした場合に発生します:

```bash
Deployment failed: Invalid application: In container cluster 'mycluster': Could not provision load balancer mytenant:myapp:myinstance:mycluster: Expected to find exactly 1 resource, but got 0 for subnet with service 'tenantelb'
```
</Accordion>
<Accordion title="AWS から Amazon EC2 Instance Retirement、Amazon EC2 Instance Availability Issue、または Amazon EC2 Maintenance の通知が届いた場合、何か対応が必要ですか？">

Vespa Cloud はメンテナンス作業に対して事前に対応し、メンテナンスタスクが予定されているインスタンスを前もって置き換えることで、メンテナンスによる影響を軽減します。

すべての EC2 インスタンスの障害は当社のコントロールプレーンによって検出され、問題のあるインスタンスは自動的に置き換えられます。システムは、置き換えプロセスの一環として、ドキュメントの分散がアプリケーションの設定と一致した状態に保たれることも保証します。
</Accordion>
<Accordion title="Vespa Cloud Enclave は VPC ピアリングをサポートしていますか？">
VPC ピアリングはサポートされていません。[AWS PrivateLink](/ja/operations/private-endpoints#aws-private-link) と [Google Private Service Connect](/ja/operations/private-endpoints#gcp-private-service-connect) が優れた代替手段であり、パブリックインターネットを経由せずにエンドポイントにアクセスできます。[詳細はこちら](/ja/reference/applications/deployment#accessing-a-public-cloud-application-from-another-vpc-on-another-account)。
</Accordion>
</AccordionGroup>
