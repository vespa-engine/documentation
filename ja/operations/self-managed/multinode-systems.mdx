title: "マルチノード・システム"
---

Vespaの*システム*は、アプリケーション・パッケージによって設定される1つ以上のステートレスおよびステートフルなクラスターで構成されます。Vespaシステムは、以下に示すように、adminクラスターを通じて設定・管理されます。

<Frame>
![Vespaの概要](/assets/img/vespa-overview.svg)
</Frame>

Vespaシステムのすべてのノードには、同じソフトウェアがインストールされます。各ノードでどのプロセスが起動され、どのように設定されるかは、アプリケーション・パッケージ内の[services.xml](/ja/reference/applications/services/services)で与えられた仕様に基づき、adminクラスターによって決定されます。

## サンプル・アプリケーションからマルチノード・システムを作成する

単一ノードのサンプル・アプリケーションから、完全に機能する本番対応のマルチノード・システムを作成するには、以下の手順に従います([次のステップ](#next-steps)も参照してください):

<Steps>
<Step>
services.xmlに[adminクラスター](/ja/reference/applications/services/admin)を追加します:
	```xml
	<services version="1.0">
	    <admin version="2.0">
	        <configservers>
	            <configserver hostalias="node0"/>
	            <configserver hostalias="node1"/>
	            <configserver hostalias="node2"/>
	        </configservers>
	        <cluster-controllers>
	            <cluster-controller hostalias="node0"/>
	            <cluster-controller hostalias="node1"/>
	            <cluster-controller hostalias="node2"/>
	        </cluster-controllers>
	        <slobroks>
	            <slobrok hostalias="node0" />
	            <slobrok hostalias="node1" />
	            <slobrok hostalias="node2" />
	        </slobroks>
	        <adminserver hostalias="node3"/>
	    </admin>
	```
</Step>
<Step>
すべてのノードに、Vespaパッケージまたは*vespaengine/vespa* Dockerイメージをインストールします。
</Step>
<Step>
以下を実行します

```bash
$ echo "override VESPA_CONFIGSERVERS [configserver-hostnames]" >> $VESPA_HOME/conf/vespa/default-env.txt
```
ここで[`configserver-hostnames`]は、コンフィグ・サーバーの完全なホスト名(複数ある場合はカンマ区切りのリスト)に置き換えます。
</Step>
<Step>
*services.xml*に`node`タグを追加して、これらのノードをコンテナー・クラスターとコンテント・クラスターに追加します。
</Step>
<Step>
同じノードを*hosts.xml*に追加します。
</Step>
<Step>
各ノードでVespaを起動します
</Step>
</Steps>

AWSの例については以下を参照してください。トラブルシューティングについては[コンフィグレーション・サーバーの運用](/ja/operations/self-managed/configuration-server)を参照してください。

## AWS EC2

以下は、*AWS EC2*インスタンス上にマルチノード・アプリケーションをセットアップする手順です。以下のAWSの手順を実行する前に、まず[multinode-HA](https://github.com/vespa-engine/sample-apps/tree/master/examples/operations/multinode-HA)の手順を実行して、Vespaのさまざまな概念に慣れておいてください。この手順では同じホスト数である10を使用し、同じアプリケーションをセットアップします。

<Warning>
**重要:** 

`sudo`の使用に注意してください。Vespaの起動スクリプトは環境(ディレクトリ、システム制限)を変更するため、root権限が必要です - [vespa-start-configserver](/ja/reference/operations/self-managed/tools#vespa-start-configserver)と[vespa-start-services](/ja/reference/operations/self-managed/tools#vespa-start-services)を参照してください。環境のセットアップ後、Vespaは`vespa`ユーザーとして実行されます。
</Warning>

<Note>
**注:** 

以下の手順は、教育目的のための必要最小限のものです。アプリケーションの負荷に適したAWSインスタンス・タイプを使用し、適切なセキュリティ・メカニズムを実装するようにしてください。
</Note>

[AWS Auto Scaling](https://aws.amazon.com/autoscaling/)は使用できるのでしょうか? [オートスケーリングのQ/A](#autoscaling)をお読みください。

### ノードのセットアップ

- ノードをプロビジョニングします:
	- [CentOS AWS AMI Cloud Images](https://centos.org/download/aws-images/)でAMIを探します - この手順は*CentOS Stream 8 us-east-1 x86\_64 ami-0ee70e88eed976a1b*とvespa-8.30.50でテストされています。
	- 最低でも*t2.medium*インスタンスを使用します。
	- ノード用のセキュリティ・グループをAWSに作成させるか、既存のものを使用します。
	- ホストへのログインのため、SSHトラフィックのチェックを忘れないでください。

- セキュリティ・グループのセットアップ:
	- プロビジョニングしたノードのセキュリティ・グループ(securityタブの下)をクリックし、*Edit inbound rules*を選択します。ポート範囲0-65535の*All TCP*を追加し、Sourceとして現在のセキュリティ・グループの名前を指定します。これにより、ホスト同士が通信できるようになります。
- ssh-agentを使わないホスト・ログインの例:
    ```bash
    $ SSH_AUTH_SOCK=/dev/null ssh -i mykeypair.pem centos@ec2-3-231-33-190.compute-1.amazonaws.com
    ```
- 10台のホストのそれぞれで、[インストール手順](/ja/operations/self-managed/build-install#rpms)を使ってVespaをインストールします:$ sudo dnf config-manager \\
    ```bash
    $ sudo dnf config-manager \
      --add-repo https://raw.githubusercontent.com/vespa-engine/vespa/master/dist/vespa-engine.repo
    $ sudo dnf config-manager --enable powertools
    $ sudo dnf install -y epel-release
    $ sudo dnf install -y vespa
    $ export VESPA_HOME=/opt/vespa
    ```
- 10台すべてのホストで、コンフィグ・サーバーのホスト・リストを使って環境をセットアップします:
    ```bash
    $ echo "override VESPA_CONFIGSERVERS" \
    "ip-10-0-1-234.ec2.internal,ip-10-0-1-154.ec2.internal,ip-10-0-0-88.ec2.internal" \
    | sudo tee -a $VESPA_HOME/conf/vespa/default-env.txt
    ```
	コンフィグ・サーバーとVespaノードの両方を含むすべてのノードで、`VESPA_CONFIGSERVERS`の設定が同一であることが必要です。

### コンフィグ・サーバー・クラスターのセットアップ

- 3ノードのコンフィグ・サーバー・クラスターを起動します:
    ```bash
    $ sudo systemctl start vespa-configserver
    ```
- コンフィグ・クラスターが動作していることを検証します - コンフィグ・サーバー・ノードのいずれかで実行します
```bash
$ for configserver in \
  ip-10-0-1-234.ec2.internal \
  ip-10-0-1-154.ec2.internal \
  ip-10-0-0-88.ec2.internal; \
  do curl -s http://$configserver:19071/state/v1/health | head -5; done

{
  "time" : 1660034756595,
  "status" : {
    "code" : "up"
  },
{
  "time" : 1660034756607,
  "status" : {
    "code" : "up"
  },
{
  "time" : 1660034756786,
  "status" : {
    "code" : "up"
  },
```
	コンフィグ・サーバーの起動に成功すると、次のようなログ・エントリーが記録されます:

    ```bash
    $ $VESPA_HOME/bin/vespa-logfmt | grep "Application config generation"

        [2022-08-09 08:29:38.684] INFO    : configserver
        Container.com.yahoo.container.jdisc.ConfiguredApplication
        Switching to the latest deployed set of configurations and components.
        Application config generation: 0
    ```
    コンフィグ・サーバー・クラスターが正常に起動するまで、セットアップを続行しないでください。動画[Troubleshooting startup - multinode](https://www.youtube.com/embed/BG7XZmXpIzo)を視聴し、[コンフィグ・サーバーの起動シーケンス](/ja/operations/self-managed/configuration-server#start-sequence)を読んでください。
- 3台のコンフィグ・サーバー・ノードでVespaサービスを起動します - これにより、ログ転送などの基本的なVespaサービスが起動します:

    ```bash
    $ sudo systemctl start vespa
    ```
	*`$VESPA_HOME/logs/vespa/vespa.log`*には`APPLICATION_NOT_LOADED`のメッセージが記録されるようになりますが、アプリケーションがデプロイされる(次のセクション)までは正常な動作です。

### アプリケーションの設定

- サンプル・アプリケーションを設定します - コンフィグ・サーバー・ノードのいずれかで実行します:
    ```bash
    $ sudo dnf install -y git zip
    $ git clone https://github.com/vespa-engine/sample-apps.git && \
        cd sample-apps/examples/operations/multinode-HA
    ```

### インスタンスの終了

使用後は、AWSコンソールでインスタンスを終了することを忘れないでください。

### AWS EC2 シングルノード

これはマルチノード・インストールの変形で、1台のホストのみを使用し、コンフィグ・サーバーとその他のVespaサービスの両方を同じノードで実行します。

- ノードをプロビジョニングします。最低でも*t2.large*にします。`VESPA_CONFIGSERVERS`で使用するため、そのホスト名を取得します:
    ```bash
    $ hostname
    ```
- Vespaをインストールします:
    ```bash
    $ sudo dnf config-manager \
      --add-repo https://raw.githubusercontent.com/vespa-engine/vespa/master/dist/vespa-engine.repo
    $ sudo dnf config-manager --enable powertools
    $ sudo dnf install -y epel-release
    $ sudo dnf install -y vespa
    $ export VESPA_HOME=/opt/vespa
    $ echo "override VESPA_CONFIGSERVERS ip-172-31-95-248.ec2.internal" | \
      sudo tee -a $VESPA_HOME/conf/vespa/default-env.txt
    ```
- サンプル・アプリケーションを取得します:
    ```bash
    $ sudo dnf install -y git zip
    $ git clone https://github.com/vespa-engine/sample-apps.git && cd sample-apps/album-recommendation
    ```
- コンフィグ・サーバーを起動し、数秒後にヘルス・ポートを確認します:
    ```bash
    $ sudo systemctl start vespa-configserver
    $ curl http://localhost:19071/state/v1/health | head -5
    ```
- サンプル・アプリケーションをデプロイします
    ```bash
    $ zip -r - . -x "img/*" "scripts/*" "pki/*" "tls/*" README.md .gitignore | \
      curl --header Content-Type:application/zip --data-binary @- \
      http://localhost:19071/application/v2/tenant/default/prepareandactivate
    ```
- Vespaを起動し、数秒後にコンテナー・ノードのヘルスを確認します:
    ```bash
    $ sudo systemctl start vespa
    $ curl http://localhost:8080/state/v1/health | head -5
    ```
- 使用後は、AWSコンソールでインスタンスを終了することを忘れないでください。

## AWS ECS

以下は、[AWS ECS](https://us-east-1.console.aws.amazon.com/ecs)インスタンス上にマルチノード・アプリケーションをセットアップする手順です。以下のAWSの手順を実行する前に、まず[multinode-HA](https://github.com/vespa-engine/sample-apps/tree/master/examples/operations/multinode-HA)の手順を実行して、Vespaのさまざまな概念に慣れておいてください。この手順では同じホスト数である10を使用し、同じアプリケーションをセットアップします。前述の[EC2の手順](#aws-ec2)を実行しておくことも役立ちます。この手順は同様の構成になっています。

### 10ノードのECSクラスターの作成

- AWSにログインし、EC2 Container Serviceを開きます。*Clusters > Create Cluster > EC2 Linux + Networking > Next step*をクリックし、デフォルト設定に加えて以下を指定します:

- *Create*をクリックし、タスクの成功を待ってから*View Cluster*をクリックします - ACTIVE状態で*Registered container instances: 10*と表示されるはずです。

### ECSインスタンスの設定

- *ECS Instances tab*をクリックします - 10個のコンテナー・インスタンスが一覧表示されるはずです。
- 最初の3つのContainer Instanceのチェックボックスを選択し、*Actions `>` View/Edit attributes*をクリックします。
- *Add attribute*をクリックします。`Name=type`と`Value=configserver`を設定し、右側の緑のチェックボックスをクリックして、*Close*をクリックします。
- 次の7つのContainer Instanceのチェックボックスを選択し、*Actions `>` View/Edit attributes*をクリックします。
- *Add attribute*をクリックします。`Name=type`と`Value=services`を設定し、右側の緑のチェックボックスをクリックして、*Close*をクリックします。
- プライベート/パブリックのホスト名を書き留め、[EC2の手順](#node-setup)と同様の表を作成します。プライベート名はVespaの設定に使用し、パブリック名はステータス確認のためのログインに使用します。ホスト名を調べるには、*ECS Instance > Instance ID*をクリックし、*Private IP DNS name (IPv4 only)*と*Public IPv4 DNS*からホスト名をコピーします。

### コンフィグ・サーバー・タスクの起動

- *Task Definitions `>` Create new Task Definition `>` EC2 `>` Next step*をクリックします。
- *Configure via JSON*をクリックし、内容を以下に置き換えます(コンフィグ・サーバーのアドレスのホスト名がカンマ区切りであることに注意してください):
```json expandable
{
    "networkMode": "host",
    "containerDefinitions": [
        {
            "name": "configserver",
            "environment": [
                {
                    "name": "VESPA_CONFIGSERVERS",
                    "value": "ip-10-0-1-234.ec2.internal,ip-10-0-1-154.ec2.internal,ip-10-0-0-88.ec2.internal"
                }
            ],
            "image": "vespaengine/vespa",
            "privileged": true,
            "memoryReservation": 1024
        }
    ],
    "placementConstraints": [
        {
            "expression": "attribute:type == configserver",
            "type": "memberOf"
        }
    ],
    "family": "configserver"
}
```
- *Save `>` Create*をクリックします。
- *Actions `->` Run task*を選択し、以下を設定します:

      <th>Launch type</th>

      <td>Number of tasks</td>
      <td>3</td>

      <td>Placement templates</td>

- *Run Task*をクリックします。
- コンフィグ・サーバーが正常に起動したことを検証します - [EC2インスタンス](#config-server-cluster-setup)の場合と同じ手順で、*/state/v1/health*を確認します。この検証に成功するまで続行しないでください:
    ```bash

        "time" : 1660635645783,
        "status" : {
    ```

### アプリケーションの設定 - ECS

- コンフィグ・サーバーにログインします:

- *Task Definitions `>` Create new Task Definition `>` EC2 `>` Next step*をクリックします。

```json expandable
    "networkMode": "host",
    "containerDefinitions": [
        {
            "name": "services",
            "environment": [
                {
                    "name": "VESPA_CONFIGSERVERS",
                    "value": "ip-10-0-1-234.ec2.internal,ip-10-0-1-154.ec2.internal,ip-10-0-0-88.ec2.internal"

                "services"
            ],

        {
```

## ログ収集

ログは、すべてのノードからリアルタイムで、`adminserver`として指定されたadminノードへ自動的に収集されます。システムのログ・メッセージを確認するには、このノードで[vespa-logfmt](/ja/reference/operations/self-managed/tools#vespa-logfmt)を実行します。

## 稼働中のシステムへの変更

システムを変更するには、変更したアプリケーションをadminクラスターにデプロイします。adminクラスターは、必要に応じて参加ノードを自動的に変更します。これは、クエリーや書き込みのライブ・トラフィックを処理しながら実行しても安全です。場合によっては、変更を有効にするためにいくつかのプロセスを再起動しなければならないと、adminクラスターが報告することがあります。クエリーや書き込みトラフィックの中断を避けるため、そのような再起動は一度に1ノードずつ行い、ノードが完全に立ち上がるのを待ってから次のノードを再起動しなければなりません。

## 複数のprotonプロセス

コンテント・クラスターは複数のスキーマを持つことができます。ホスト間で負荷を分散するもう1つの方法として、複数のコンテント・クラスターを同じホストにマッピングする方法があります:

```xml
<content id="musiccluster" version="1.0">
    <documents>
        <document type="albums" mode="index" />
    </documents>
    <nodes>
        <node hostalias="node1" distribution-key="0" />
    </nodes>
</content>

<content id="lyricscluster" version="1.0">
    <documents>
        <document type="lyrics" mode="index" />
    </documents>
    <nodes>
        <node hostalias="node1" distribution-key="0" />
    </nodes>
</content>
```

両方のクラスターが`node1`を使用していることに注目してください。これはノードごとに複数の[proton](/ja/content/proton)プロセスを実行することになるため、推奨されない構成です。このような場合にプロセス間の干渉を減らすには、ホストを仮想化してより多くのノードに分割します。これには[コンテナーまたはVM](/ja/operations/self-managed/docker-containers)を使用できます:

<Frame>
![ノードごとの複数のprotonプロセス](/assets/img/schemas-and-content-clusters-multiple-proton.svg)
</Frame>

<Warning>
**重要:** 

[feed-block](/ja/writing/feed-block)のようなVespaの過負荷処理機能は、ノード上でprotonプロセスが1つだけ実行されていることを必要とします。
</Warning>

## オートスケーリング

よくある質問は、*「[AWS Auto Scaling](https://aws.amazon.com/autoscaling/)は使用できますか?」*というものです。これは答えるのが難しい質問です。以下は[Vespa Slack](https://slack.vespa.ai)からの引用です:

> *デプロイメントについて質問があります。[multinode-systems.html#aws-ec2](#aws-ec2)に基づいて、2つのAWSオートスケーリング・グループ(config & services)でクラスターをセットアップしました。しかし、インスタンスの1つがオートスケーリング・グループによって置き換えられた場合、hosts.xmlファイルを手動で更新し、zipして、新しいバージョンのアプリをデプロイする必要があります。CloudwatchとLambdaでこのプロセスを自動化することを考えています... たとえばインスタンスのタグを確認し、それに基づいてホスト設定を更新できるような、ノード・ディスカバリーのメカニズムはあるのでしょうか?*

まず、[aws-ec2](#aws-ec2)で見たように、ホストには`configserver`と`services`の2種類があります。configserverのセットアップ/運用は[コンフィグレーション・サーバーの運用](/ja/operations/self-managed/configuration-server)にドキュメント化されています。これを最初にセットアップする必要があります。これは[Apache ZooKeeper](https://zookeeper.apache.org/)クラスターに支えられているため、1ノードまたは3ノードの規模であるべきです。Yahooの私たち自身のクラスターでは、configserverクラスターをオートスケールしていません。その必要がないからです - 私たちは3台を使用しています。それが多すぎる場合は1台にしてください。というわけで、この質問への答えは簡単です - configserverはオートスケールしないでください。

servicesノードについては、ステートレスなコンテナーとステートフルなコンテント・ノードという2種類のノードがあることに注目してください - [概要](/ja/learn/overview)を参照してください。いずれにせよ、これらは別々に管理することになります - ステートレスなノードは、*services.xml*と*hosts.xml*を変更することで、より簡単に置き換え/増設/縮小できます。ステートレス・ノード向けのオートスケーリング・サービスを構築することは可能ですが、オートスケーリングのコードに適切なメトリクスを使用すること、そしてデプロイ自動化を他のデプロイメント(たとえばスキーマ変更)と統合することに注意が必要です。

はるかに難しい問題は、ステートフル・ノードのオートスケーリングです - これらはインデックスとデータを持つノードです。[エラスティシティ](/ja/content/elasticity)を参照してください - ノードの追加とデータの再分散には数時間かかることがあり、再分散中はノードの負荷が増加します。ここでオートスケーリングを安全かつ効率的に構築するのは非常に困難です。

これらはどれも不可能ではなく、実際に[cloud.vespa.ai/autoscaling](/#autoscaling)で実装されています - しかし、正しく実現するのが難しい機能です。

したがって、私の推奨は、[multinode-HA](https://github.com/vespa-engine/sample-apps/tree/master/examples/operations/multinode-HA)のように静的なホスト・セットから始めることです - そして並行して、[cloud.vespa.ai/en/free-trial](https://vespa.ai/free-trial/)で、自分のデータとユースケースを使ってオートスケーリングの実験を試してみてください。

オートスケーリングはコストを節約できますが、その前に[パフォーマンス](/ja/performance/)について読み、静的なノード・セットを使ってリソースを最適化する(またはVespa Cloud Consoleのサイジング提案を使用する)のが賢明です。つまり、まずノードのリソースを適切に設定し、その後で、自分の負荷パターンに対してノード数のオートスケーリングが意味を持つかを検討してください。
