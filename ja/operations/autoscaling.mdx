---
title: "オートスケーリング"
---

オートスケーリングにより、実際の使用状況に応じて、アプリケーションのクラスターに割り当てられるハードウェアリソースを自動的に調整できます。割り当てられたすべてのリソースの使用率を理想に近く保とうとし、必要に応じて、範囲で許可された最も安価なオプションに自動的に再構成します。

*services.xml* 内の [nodes](/ja/reference/applications/services/services#nodes) や[ノードリソース](/ja/reference/applications/services/services#resources)の値に、角括弧で *範囲* を指定することで有効化できます。Vespa Cloud はクラスターのリソース使用率を監視し、最適に近い使用率が得られる範囲内で最も安価なリソース割り当てを自動的に選択します。

オートスケーラーのステータスと最近のアクションは、コンソールのデプロイメント配下の *Resources* ビューで確認できます。

オートスケーリングは、異なる構成によって達成されるレイテンシーの違いを考慮しません。アプリケーションに、良好なスループットを生み出すもののレイテンシーが高すぎる構成がある場合、それらの構成をオートスケーリングの範囲に含めるべきではありません。

クラスターの割り当ての調整は、ステートレスなコンテナー・クラスターでは迅速に行われますが、大量のデータを持つコンテント・クラスターでははるかに遅くなります。オートスケーリングは、各クラスターを、そのリスケールに通常かかる時間スケール(データの再分散を含む)で調整します。

理想的な使用率は、ノードがダウンしたり故障したりする可能性、別のリージョンがダウンしてトラフィックが倍増する可能性、そしてメンテナンス・オペレーションや低レイテンシーでのリクエスト処理のための余裕が必要であることを考慮に入れています。オートスケーリングは、最近の期間にシステムで観測された内容に基づいて動作します。近い将来、現在よりもはるかに多くのキャパシティが必要になる場合は、これを考慮して下限を設定するとよいでしょう。上限は、ビジネス上意味のある最大サイズに設定すべきです。

## オートスケーリングを使用すべき場面

オートスケーリングは多くのシナリオで役立ちます。典型的なものは次のとおりです:

- 現実的なデータと使用状況でベンチマークできない新しいアプリケーションがあり、どのリソースを割り当てるべきか確信が持てない場合: すべてのリソースパラメーターに広い範囲を設定し、システムに構成を選択させます。経験を積んだら、構成空間を狭めることを検討できます。
- 1 日の中で負荷が急速に変動する、または何らかのイベントによって突然急増する可能性があり、コンテナー・クラスターのリソースを負荷に迅速に適応させたい場合: コンテナーのノード数や vcpu に範囲を設定します。
- データ量が時間とともに増加すると予想されるものの、リソースを早まって割り当てたくもなく、増やすべき時期かどうかを常に心配したくもない場合: システムのサイズがデータとともに成長するように、コンテント・ノードやノードリソースに範囲を設定します。

## リソースのトレードオフ

リソースを決定する際のその他の考慮事項:

- リソース/ノードの変更は簡単かつ安全であり、Vespa Cloud の強みの 1 つです。制御された変更を行い、レイテンシー、データ移行、コストへの影響を観察することをお勧めします。すべてが自動化されており、新しいアプリケーション・パッケージをデプロイするだけです。これは、後に負荷のピークやキャパシティ要件の変更の際に必要となる有用な学習になります。
- ノードリソースはすべてのゾーンで自由に選択できるわけではなく、CPU/メモリは多くの場合 2 倍刻みです。リソース構成が適切に適合していることを確認するようにしてください。
- CPU は最も高価なコンポーネントです。ほとんどのアプリケーションではこれを最適化してください。
- ノード数が少ないと、Vespa は 1 つのノード(または複数のグループを持つコンテント・クラスターでは 1 つのグループ)のダウンにシステムが対応できることを要求するため、余剰キャパシティが多くなります。最低 4〜5 ノードが良い経験則です。4〜5 ノードか、半分のサイズの 9〜10 ノードのどちらが良いかは、より迅速なアップグレードサイクルと、より滑らかなリソースのオートスケール曲線のどちらを取るかによります。レイテンシーは、静的なクエリーコストと動的なクエリーコストの比率に応じて、良くなることも悪くなることもあります。
- ノードリソースの変更は新しいノードの割り当てを意味する場合があるため、コンテナー・ノードはノード数を変更する方が速くスケールできる場合があります。
- その結果として、リソース不足(例: ディスクがほぼ満杯)の際には、ノードを追加し、他は変更しないでください。
- 一度に 1 つのことを変更する方が、キャパシティについて推論しやすくなります。

コンソールに *suggested resources* のアドバイスが表示された場合は、それに従うのが安全なことが多いです。質問がある場合はお気軽にお問い合わせください。

## 混合負荷

Vespa アプリケーションは、複数のソースからの読み取りと書き込みの組み合わせを処理しなければなりません。ユーザーの負荷は多くの場合、サインカーブのような曲線を描きます。バッチジョブのような機械生成の負荷は、スパイク状で突発的になることがあります。

デフォルトの Vespa 構成では、あらゆる種類の負荷が *1 つ* のデフォルトのコンテナー・クラスターを使用します。例: 日次のバッチジョブが高いレートでコーパスを更新するアプリケーション:

<Frame>
![ノードとリソース](/assets/img/load.png)
</Frame>

オートスケーリングは、スケール *アップ* をスケール *ダウン* よりもはるかに速く行います。これは、スパイクが一度観測された後は、新たなスパイクの発生確率が高くなるためです。この例では、日次の負荷スパイクに対するクラスターの急速な成長と、それに続く緩やかな減少が見られます。

このケースの最善の解決策は、バッチジョブが短時間で終わるものなので、その速度を落とすことです。ジョブの速度を落とすことが常に可能とは限りません - そのような場合は、複数の[コンテナー・クラスター](/ja/applications/containers)をセットアップするのが賢明です - 各クラスターをその負荷特性に合わせて最適化します。これは、オートスケールを使用するクラスターと固定サイズのクラスターの組み合わせにできます。オートスケーリングは多くの場合、ユーザー生成の負荷に最適に機能します。一方、機械生成の負荷は、チューニングするか、同じ Vespa アプリケーション内の別のクラスターにルーティングできます。

## 例

以下の例は、クラスタータイプごとの推奨される出発点を示しています。経験則として、コンテナー・クラスターは任意の次元でオートスケールできますが、コンテント・クラスターは固定のノードリソースと、ノード数またはグループ数の範囲指定が最適です。

### コンテナー・クラスター

コンテナー・クラスターはステートレスなので、ノードの追加、削除、置換を迅速に行うことができ、データを移動する必要もありません。ノード数のスケーリングは最もシンプルなオプションであり、良い出発点です:

```xml
<nodes count="[2, 8]">
    <resources vcpu="4" memory="8Gb"/>
  </nodes>
```

オートスケーリングに範囲内でノードリソースを選択させることもできます。ノードリソースの変更は通常ノードの置換を意味しますが、コンテナー・クラスターではオーバーヘッドはほとんどありません:

```xml
<nodes count="[2, 8]">
    <resources vcpu="[2, 4]" memory="[8Gb, 16Gb]"/>
  </nodes>
```

### コンテント・クラスター

コンテント・クラスターはデータを保持するため、そのスケーリングはドキュメントの再分散を意味します。vcpu、メモリ、ディスクの変更は通常、新しいノードリソース仕様を満たすための新しいノードの割り当てにつながり、クラスター内のすべてのノードが置換され、すべてのドキュメントが再分散されます。ノードリソースを固定し、代わりにノード数をオートスケールしてください - そうすれば、追加または削除されたノード上のデータのみが移動します:

```xml
<nodes count="[2, 8]">
    <resources vcpu="4" memory="16Gb" disk="500Gb"/>
  </nodes>
```

[グループ](/ja/reference/applications/services/services#nodes)を使用するコンテント・クラスターでは、`count` の範囲ではなく `groups` と `group-size` でトポロジーを表現し、グループ数をオートスケールします:

```xml
<nodes groups="[2, 4]" group-size="8">
    <resources vcpu="4" memory="16Gb" disk="500Gb"/>
  </nodes>
```

これは、各 8 ノードのグループを 2 から 4 グループの間で、合計 16 から 32 ノードでスケールします。各クエリーは単一のグループで処理されるため、クエリーのキャパシティはグループ数に応じてスケールし、グループの追加は、既存のノード間でドキュメントを再分散することなく新しいグループにデータを投入します。

<Warning>
**重要:** 

コンテント・クラスターでのノードリソース(vcpu、メモリ、ディスク)のオートスケーリングはサポートされていますが、リソースの変更ごとにすべてのノードが置換され、すべてのドキュメントが再分散されるため、サービス品質にある程度の影響を与える可能性があります。[paged attribute](/ja/content/attributes#paged-attributes) や HNSW インデックスを使用している場合、再分散はより高コストで時間のかかるものになります。
</Warning>

<Note>
**注:** 

クラスターへの初回フィード中はオートスケーリングを避けてください。トポロジーの変更はドキュメントの再分散を必要とし、場合によっては何度も行われるためです - [初回バッチフィード](/ja/writing/initial-batch-feed)を参照してください。
</Note>

### すべての次元での範囲指定は避ける

念のため、これは避けるべき構成です。特にコンテント・クラスターでは:

```xml
<nodes count="[2, 8]">
    <resources vcpu="[2, 8]" memory="[8Gb, 32Gb]" disk="[50Gb, 200Gb]"/>
  </nodes>
```

ノードリソースは多くの場合 2 倍刻みなので、これらの範囲は 7 通りのノード数 x 3 通りの vcpu x 3 通りのメモリ x 3 通りのディスクのステップに広がります - オートスケーラーが選択できる約 190 の構成です。コンテント・クラスターでは、異なるノードリソースを持つ構成間の移動のたびに、すべてのノードが置換され、すべてのドキュメントが再分散されます。多くの次元にわたる広い範囲は、ほとんどの場合、同じ使用率に到達するためのより高コストな方法をオートスケーラーに与えるだけです - 単一の次元でのスケーリングを優先し、[リソースのトレードオフ](#リソースのトレードオフ)を参照してください。

### GPU リソース

現時点では、ノードごとの GPU リソースをオートスケールすることはできませんが、GPU を持つノードの数はスケールできます:

```xml
<nodes count="[2, 8]">
    <resources vcpu="2" memory="16Gb" disk="50Gb">
      <gpu count="1" memory="16.0Gb"/>
    </resources>
  </nodes>
```

### 注記

- オートスケーリングには少なくとも 2 ノードのクラスターが必要です - 単一ノードのクラスターはオートスケールされません。
- 範囲は本番ゾーンでのみ有効です。[dev 環境](/ja/operations/environments#dev)は、デフォルトで `nodes` と `resources` の設定を無視します。
- 範囲の下限は通常のベースライン負荷に近い値に設定してください - 非常に広い範囲では、静かな期間にオートスケーラーが多くのノードを削減し、次の負荷ピークへの揺り戻しがより大きく、より遅くなります。
