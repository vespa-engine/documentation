*deployment.xml* は、アプリケーションをどのようにデプロイするかを制御します。

*deployment.xml* は、[アプリケーション・パッケージ](/ja/basics/applications)のルートに配置され、[自動アプリケーションデプロイ](/ja/operations/automated-deployments)の際に、アプリケーションをどの環境およびリージョンに、どのアプリケーションインスタンスとしてデプロイするかを指定します。

デプロイは、`test` および `staging` 環境を経て、*deployment.xml* に列挙された `prod` 環境へと進行します。

シンプルな例:

```xml
<deployment version="1.0">
    <prod>
        <region>aws-us-east-1c</region>
        <region>aws-us-west-2a</region>
    </prod>
</deployment>
```

より複雑な例:

```xml expandable
<deployment version="1.0">
    <instance id="beta">
        <prod>
            <region>aws-us-east-1c</region>
        </prod>
    </instance>
    <instance id="default">
        <block-change revision="false"
                      days="mon,wed-fri"
                      hours="16-23"
                      time-zone="UTC" />
        <backup frequency="7d" granularity="cluster" />
        <prod>
            <region>aws-us-east-1c</region>
            <delay hours="3" minutes="7" seconds="13" />
            <parallel>
                <region>aws-us-west-1c</region>
                <steps>
                    <region>aws-eu-west-1a</region>
                    <delay hours="3" />
                    <test>aws-us-west-2a</test>
                </steps>
            </parallel>
        </prod>
        <endpoints>
            <endpoint container-id="my-container-service">
                <region>aws-us-east-1c</region>
            </endpoint>
        </endpoints>
    </instance>
    <endpoints>
        <endpoint id="my-weighted-endpoint"
                  container-id="my-container-service"
                  region="aws-us-east-1c">
          <instance weight="1">beta</instance>
        </endpoint>
    </endpoints>
</deployment>
```

一部の要素は、`<deployment>` ルートの直下、**または**、1 つ以上の `<instance>` タグが列挙されている場合はその配下の*いずれか*に宣言できます。こうした要素については、配置可能な場所の説明に太字の**または**を付けています。

## block-change

`<deployment>`、**または** `<instance>` の中に配置します。これは、一致する時間帯において、変更が本番環境にデプロイされるのをブロックします。ただし、ブロック中でも変更のテストは実行されます。

デフォルトでは、アプリケーションのリビジョン変更と Vespa プラットフォームの変更(アップグレード)の両方がブロックされます。`revision` および `version` 属性を使うと、いずれか一方の変更だけをブロックできます。

以下の属性は任意の組み合わせで指定できます。ある日付における変更は、すべての条件が満たされた場合にブロックされます。無効な `<block-change>` タグ(すなわち、実際の日付に決して一致しない条件を含むもの)はシステムによって拒否されます。

このタグは、`<test>` および `<staging>` タグの後、`<prod>` の前に配置しなければなりません。複数回宣言できます。

以下の例は、PST タイムゾーンにおいて、週末のすべての変更をブロックし、営業時間外のリビジョンをブロックします:

```xml
<block-change days="sat-sun"
              hours="0-23"
              time-zone="America/Los_Angeles"/>
<block-change revision="false"
              days="mon-fri,sat,sun"
              hours="0-8,16-23"
              time-zone="America/Los_Angeles"/>
```

メンテナンス操作*のみ*をブロックするには、`revision` と `version` はデフォルトが `true` であるため、明示的に `false` に設定する必要があります。以下の例は、営業時間中のメンテナンスをブロックしつつ、アプリケーションのデプロイとプラットフォームのアップグレードは常に許可します:

```xml
<block-change maintenance="true"
              revision="false"
              version="false"
              hours="8-15"
              time-zone="America/Los_Angeles"/>
```

以下の例は、次の変更をブロックします:

- 2022-03-01 以降の日曜日のすべての変更
- 2022-02-10 から 2022-02-15 の間の 16 時から 23 時のすべての変更
- 2022-01-05 までのすべての変更

```xml
<block-change days="sun"
              from-date="2022-03-01"
              time-zone="America/Los_Angeles"/>
<block-change hours="16-23"
              from-date="2022-02-10"
              to-date="2022-02-15"
              time-zone="America/Los_Angeles"/>
<block-change to-date="2022-01-05"
              time-zone="America/Los_Angeles"/>
```

## backup

`<deployment>`、**または** `<instance>` の中に配置します。本番のコンテント・クラスターのスケジュールされたバックアップを設定します。この要素が存在する場合、指定された頻度でバックアップが作成されます。`<test>` および `<staging>` タグの後、`<prod>` の前に配置しなければなりません。

なお、この要素を追加しても、最初のバックアップがすぐに作成されるわけではありません。クラスターが最初のバックアップの対象となるのは、コンテントノードが少なくとも 1 回分の `frequency` 間隔にわたって稼働し続けた後であり、以降のバックアップは設定された頻度で作成されます。詳細は[自動バックアップ](/ja/operations/data-management#backup)を参照してください。

<table className="vespa-table">
  <thead>
    <tr>
      <th>属性</th>
      <th>必須</th>
      <th>値</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>frequency</td>
      <td>はい</td>
      <td>接尾辞 <code>{`h`}</code>(時間)または <code>{`d`}</code>(日)を付けた正の整数。例: <code>{`24h`}</code>、<code>{`7d`}</code>。最小値は 24h です。</td>
    </tr>
    <tr>
      <td>granularity</td>
      <td>いいえ、デフォルトは <code>{`cluster`}</code></td>
      <td>• <code>{`cluster`}</code>: クラスター内のすべてのコンテントノード<br/><br/> • <code>{`group`}</code>: 単一グループ内のすべてのコンテントノード</td>
    </tr>
  </tbody>
</table>

バックアップの実行はサービスの可用性には影響しませんが、パフォーマンス面でのコストがかかります。`granularity` を使用して、バックアップ速度と復元速度のトレードオフを制御できます。

- `cluster` バックアップは、データの整合性を確保するために各コンテントノードを一時的にサスペンドする必要があるため、より時間がかかります。ただし、復元にはコンテントの再分配が実質的にゼロで済みます。
- `group` バックアップは、グループ全体を同時にサスペンドしてバックアップするため、より高速です。ただし、復元にはクラスターのトポロジーによっては大量のコンテントの再分配が必要になる場合があります。
  
ほとんどの状況では、`cluster` バックアップを推奨します。

[ブロックウィンドウ](#block-change)は、指定された期間中に新しいバックアップが開始されるのも防ぎます。ただし、利用可能な時間が短すぎてフルバックアップが完了しない場合、処理はブロックウィンドウを超えて継続します。[詳細を読む](/ja/operations/data-management#backup)。

## resource-tags

`<deployment>`、**または** `<instance>` の中に配置します。テナントのクラウドアカウント内でプロビジョニングされるクラウドリソース(仮想マシンおよびアタッチされたディスク)に適用するカスタムタグを指定します。`cloud-account` が設定されている [Vespa Cloud Enclave](/ja/operations/enclave/enclave) のデプロイでのみ利用可能です。一般的にコスト追跡やリソース管理に使用されます。

`<deployment>` レベルで宣言されたタグはすべてのインスタンスに適用されます。`<instance>` レベルのタグはデプロイメントレベルのタグとマージされ、キーが競合した場合はインスタンスレベルの値が優先されます。

```xml
<deployment version="1.0" cloud-account="aws:123456789012">
    <resource-tags>
        <tag key="cost-center" value="engineering"/>
        <tag key="env" value="${environment}"/>
    </resource-tags>

    <instance id="prod">
        <resource-tags>
            <tag key="cost-center" value="search-team"/>
        </resource-tags>
        <prod>
            <region>aws-us-east-1c</region>
        </prod>
    </instance>
</deployment>
```

`<resource-tags>` 要素は、1 つ以上の `<tag>` 子要素を含みます。各 `<tag>` には 2 つの必須属性があります:

**リコンシリエーション。** タグは仮想マシンとアタッチされたディスクに適用されます。*deployment.xml* でタグが変更、追加、または削除されると、既存のリソースはバックグラウンドのリコンシリエーション・プロセスによって更新されます。以前 Vespa Cloud によって適用されたものの、もはや列挙されていないタグはリソースから削除されます。テナントがクラウドコンソールで手動で追加したタグは保持されます。

## upgrade

`<deployment>` または `<instance>` の中に配置します。アプリケーション、またはそのインスタンスの 1 つをアップグレードする際の戦略を決定します。デフォルトでは、アプリケーションのリビジョン変更はプラットフォームのアップグレードとは独立してデプロイされ、アプリケーションのリビジョンは進行中のプラットフォームアップグレードに追いつき、追い越すことができます。この動作を変更するには、以下の `rollout` 属性を参照してください。

<table className="vespa-table">
  <thead>
    <tr>
      <th>属性</th>
      <th>必須</th>
      <th>値</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>rollout</td>
      <td>いいえ、デフォルトは <code>{`simultaneous`}</code></td>
      <td>• <code>{`separate`}</code>: リビジョンがプラットフォームアップグレードに追いついた場合、アップグレード単独が失敗しない限り、リビジョンは後ろに留まります。<br/><br/> • <code>{`leading`}</code>: リビジョンがプラットフォームアップグレードに追いついた場合、両者は融合して一緒にロールアウトされます。<br/><br/>• <code>{`simultaneous`}</code> はデフォルトであり、リビジョンのロールアウトを優先します。リビジョン変更はプラットフォームアップグレードとは独立してデプロイされます。リビジョンがプラットフォームアップグレードに追いつくと、合流し、その後アップグレードを追い越します。</td>
    </tr>
    <tr>
      <td>revision-target</td>
      <td>いいえ、デフォルトは <code>{`latest`}</code></td>

    </tr>
    <tr>
      <td>max-risk</td>

    </tr>
    <tr>
      <td>min-risk</td>
      <td>いいえ、デフォルトは <code>{`0`}</code></td>
      <td>設定された <code>{`max-risk`}</code> 以下でなければなりません。新しいリビジョンのロールアウトを開始するための&#42;リスク&#42;の最小量。デフォルトの <code>{`0`}</code> では、何かが準備でき次第すぐに新しいリビジョンがロールアウトされますが、より高い値にすると、システムは十分な累積リスクが利用可能になるまで待機します。これは、些細な変更で時間のかかるデプロイプロセスをブロックしないようにするために使用できます。</td>
    </tr>
    <tr>
      <td>max-idle-hours</td>

### availability-zone

```xml
</region>
```

## delay

`<deployment>`、`<instance>`、`<prod>`、`<parallel>`、または `<steps>` の中に配置します。先行するすべてのステップの完了後、後続のステップが進行する前に経過しなければならない遅延を導入します。これは、変更を追加のゾーンにデプロイする前にエラーを発見するための猶予時間を設けたり、本番デプロイメントについてしばらく高レベルのメトリクスを収集してから本番テストで評価したりするのに役立ちます。デプロイメント仕様全体での最大合計遅延は 48 時間です。遅延は、`hours`、`minutes`、`seconds` 属性の任意の組み合わせで指定します。

## parallel

`<deployment>`、`<prod>`、または `<steps>` の中に配置します。含まれるステップを並列に実行します。`<deployment>` 内の場合はインスタンスを、それ以外の場合はプリミティブなステップ(デプロイ、テスト、遅延)またはそれらの直列の連なり([steps](#steps) を参照)を並列に実行します。複数の `<parallel>` 要素を指定できます。以下の例では、まず `us-west-1` にデプロイし、次に `us-east-3` と `us-central-1` に同時にデプロイし、最後に、両方の並列デプロイが完了した後に `eu-west-1` にデプロイします:

```xml
<region>us-west-1</region>
<parallel>
    <region>us-east-3</region>
    <region>us-central-1</region>
</parallel>
<region>eu-west-1</region>
```

## steps

`<parallel>` の中に配置します。含まれる並列ステップまたはプリミティブなステップ(デプロイ、テスト、遅延)を直列に実行します。以下の例では、並列に:

<Steps>
<Step>
`us-east-3` にデプロイし、
</Step>
<Step>
`us-west-1` にデプロイした後、1 時間遅延し、`us-west-1` のテストを実行し、
</Step>
<Step>
2 時間遅延します。
</Step>
</Steps>

したがって、この並列ブロックは、両方のデプロイが完了し、2 番目のデプロイのテストが成功し、ブロックの実行開始から少なくとも 2 時間が経過した時点で完了となります。

```xml
<parallel>
    <region>us-east-3</region>
    <steps>
        <region>us-west-1</region>
        <delay hours="1" />
        <test>us-west-1</test>
    </steps>
    <delay hours="2" />
</parallel>
```

この中で許可される要素は [`<nodes>`](/ja/reference/applications/services/services#nodes) です。

## endpoints (グローバル)

`<instance>` が宣言されていない `<deployment>` の中、**または** `<instance>` の中に配置します。これにより、1 つ以上の [`<endpoint>`](#endpoint-global) 要素による*グローバル*エンドポイントと、クラウドネイティブなプライベートネットワーク設定のための[ゾーンエンドポイント](#endpoint-zone)および[プライベートエンドポイント](#endpoint-private)要素を指定できます。

## endpoints (dev)

`<dev>` の中に配置します。これにより、[dev](/ja/operations/environments#dev) デプロイメントに対するクラウドネイティブなプライベートネットワーク設定のための[ゾーンエンドポイント](#endpoint-zone)要素を指定できます。なお、[プライベートエンドポイント](#endpoint-private)は `prod` でのみサポートされています。

## endpoint (グローバル)

`<endpoints>` または `<group>` の中に配置します。このアプリケーションのグローバルエンドポイントを指定します。各エンドポイントは、そのエンドポイント内で宣言されたリージョンを指します。リージョンが指定されていない場合、エンドポイントはデフォルトで `<prod>` 要素内に宣言されたリージョンを指します。以下の例は、すべてのリージョンへのデフォルトエンドポイントと、US リージョンのみを指す *us* エンドポイントを作成します。

```xml
<endpoints>
    <endpoint container-id="my-container-service"/>
    <endpoint id="us" container-id="my-container-service">
        <region>aws-us-east-1c</region>
        <region>aws-us-west-2a</region>
    </endpoint>
</endpoints>
```

## allow

`<endpoint type='private'>` の中に配置します。URN で識別されるプリンシパルが、宣言されたプライベートエンドポイント・サービスへの接続を設定することを許可します。この要素は、追加の URN ごとに繰り返し記述しなければなりません。エンドポイント・サービスは、互換性のあるタイプの許可された URN のみを考慮し、互換性のあるアクセスタイプと URN の組み合わせが少なくとも 1 つ指定されている場合にのみ作成されます:

- AWS デプロイメントの場合、`aws-private-link` と *ARN* を指定します。
- GCP デプロイメントの場合、`gcp-service-connect` と*プロジェクト ID* を指定します

```xml
<endpoint type='private' container-id="my-container">
    <allow with='aws-private-link' arn='arn:aws:iam::123123123123:root' />
    <allow with='aws-private-link' arn='arn:aws:iam::321321321321:role/my-role' />
    <allow with='aws-private-link' arn='arn:aws:iam::321321321321:user/my-user' />
    <allow with='gcp-service-connect' project='my-project' />
</endpoint>
```

## bcp

`<instance>` または `<deployment>` の中に配置します。このインスタンスの BCP(Business Continuity Planning、事業継続計画)の構造を定義します。あるゾーンの障害時に、どのゾーンがどのゾーンを引き継ぐか、そしてどれだけ速くそのキャパシティを準備しなければならないかを定義します。オートスケーリングはこの情報を使用して、各ゾーンの理想的な CPU 負荷を決定します。この要素が定義されていない場合、すべてのリージョンが他のすべてのリージョンのトラフィックを均等な割合でカバーし、そのキャパシティを常に準備しておくものと想定されます。

bcp 要素がルートに指定され、かつ明示的なインスタンスが使用されている場合、その bcp 要素は、自身に bcp 要素を含まないすべてのインスタンスのデフォルトになります。BCP 要素が group 要素を含まない場合、その要素が使用されているインスタンスのすべてのリージョンからなる単一のグループを暗黙的に定義します。

BCP 設定が正しいことを検証する手順については、[BCP テスト](https://cloud.vespa.ai/en/reference/bcp-test.html?_gl=1*1lsxxnq*_gcl_au*ODE0ODM4MTI2LjE3Nzk3MjQ3OTY)を参照してください。

    </tr>

```xml
<bcp>

        <region fraction="0.5">us-central1</region>
    </group>
    <group>
        <region>us-west1</region>
        <region>us-west2</region>
        <region fraction="0.5">us-central1</region>
    </group>
</bcp>
```

## group

`<bcp>` の中に配置します。BCP グループを定義します: リージョン障害時にメンバー同士が互いをカバーし合うリージョンの集合です。

グループ内の各リージョンは、(オートスケーリングの範囲が設定されている場合、許容される範囲で)グループ内の他の任意の 1 つのリージョンがダウンした場合に対応できる十分なリソースをプロビジョニングします。そのリージョンのトラフィックは、グループ内の残りのリージョンに均等に再ルーティングされるものと想定されます。つまり、グループにメンバーが 1 つしかない場合、そのメンバーの障害に対応するためのリソースはプロビジョニングされません。グループに 2 つのメンバーがある場合、それぞれが他方の実際のトラフィックを処理できる十分なリソースのプロビジョニングを目指します。グループに 3 つのメンバーがある場合、それぞれは、他の 2 つのうちトラフィックが最も多いリージョンで観測されたトラフィックの半分を処理できるようにプロビジョニングします。

リージョンは複数のグループに分数のメンバーシップで所属できます。この場合、残りのメンバーのトラフィックのうちその割合分だけを処理し、逆もまた同様です。あるリージョンのグループ間でのメンバーシップの合計は、常にちょうど 1 でなければなりません。

グループは、グループ内のリージョンメンバーに対するグローバルエンドポイントを定義することもできます。これは、エンドポイントを別途定義し、そのエンドポイントの下にグループのリージョンを繰り返し記述するのとまったく同じです。グループ配下のエンドポイントには、明示的な region サブ要素を含めることはできません。
