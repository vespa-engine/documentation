---
title: "デフォルトの JSON 結果フォーマット"
sidebarTitle: "The default result format"
---
デフォルトの Vespa クエリーレスポンスフォーマットは、[presentation.format](/ja/reference/api/query#presentation.format) が未設定または `json` に設定されている場合に使用されます。`format=cbor` を設定するか `Accept: application/cbor` を使用することで、代替のバイナリ [CBOR](https://cbor.io/) フォーマットを利用できます。CBOR はドロップインの代替であり、デシリアライズすると結果は JSON と同一です。CBOR はよりコンパクトで、生成も高速です。特にテンソルや埋め込み(エンベディング)などの数値データで顕著です。結果は 1 つ以上のオブジェクトでレンダリングされます:

- `root`: 返されるデータのツリーを持つ必須オブジェクト
- `timing`: クエリーのタイミング情報を持つオプションのオブジェクト
- `trace`: クエリー実行に関するメタデータのためのオプションのオブジェクト

結果とトレーシングの例については、[クエリー API ガイド](/ja/querying/query-api#result-examples)を参照してください。

すべてのオブジェクト名はリテラル文字列です。ノード `root` は、返される JSON オブジェクト内のマップキー "root" です。つまり、マップキーとして使用されるのは文字列のみです。

## 付録: レガシーな Vespa 7 の JSON レンダリング

Vespa 7 では、検索結果とドキュメントのレンダリングの間にいくつかの不整合がありましたが、Vespa 8 で修正されています。この付録では、以前の動作、変更点、および特定のレンダリングを選択するための設定方法について説明します。

### weightedset レンダリングの不整合

さまざまな weightedset 型を持つフィールドは、(フィード用の)JSON 入力表現として JSON オブジェクトを持ちます。たとえば、`weightedset<string>` フィールドの値としては `{"one":1, "two":2,"three":3}` のようになります。ドキュメントをレンダリングする際(たとえばビジット時)にも同じフォーマットが使用されます。

しかし検索結果では、中間の処理ステップがあり、その間フィールド値は item/weight のペアの配列として表現されます。そのため、検索結果ではフィールド値は `[ {"item":"one", "weight":1},{"item":"two", "weight":2},{"item":"three", "weight":3} ]` のようにレンダリングされます。

Vespa 8 では、検索結果のデフォルトの JSON レンダラーは、ドキュメントレンダリングと同じフォーマットを出力します。古いフォーマットに依存するコードがある場合は、クエリーで `renderer.json.jsonWsets=false` を設定する(通常は[クエリープロファイル](/ja/querying/query-profiles)を介して)ことで、これを無効にできます。

### map レンダリングの不整合

さまざまな map 型を持つフィールドは、(フィード用の)JSON 入力表現として JSON オブジェクトを持ちます。たとえば、`map<int,float>` フィールドの値としては `{"1001":1.0, "1002":2.0, "1003":3.0}` のようになります。ドキュメントをレンダリングする際(たとえばビジット時)にも同じフォーマットが使用されます。

しかし検索結果では、中間の処理ステップがあり、フィールド値は key/value のペアの配列として表現されます。そのため、検索結果ではフィールド値は(場合によっては)`[ {"key":1001, "value":1.0},{"key":1002, "value":2.0},{"key":1003, "value":3.0} ]` のようにレンダリングされます。

Vespa 8 では、検索結果のデフォルトの JSON レンダラーは、ドキュメントレンダリングと同じフォーマットを出力します。古いフォーマットに依存するコードについては、クエリーで `renderer.json.jsonMaps=false` を設定する(通常は[クエリープロファイル](/ja/querying/query-profiles)を介して)ことで、これを無効にできます。

### 地理的位置(geo position)のレンダリング

`position` 型を持つフィールドは、Vespa 7 では内部フィールド "x" と "y" を使用してレンダリングされていました。これらはマイクロ度(地理的な度数の 100 万倍)を表す整数で、x は経度、y は緯度です。また、`position` 型の任意のフィールド _foo_ に対して、2 つの追加の合成サマリーフィールド _foo.position_ と _foo.distance_ が追加されていました(詳細は下記参照)。

Vespa 8 では、位置は 2 つの JSON フィールド "lat" と "lng" でレンダリングされ、どちらも浮動小数点値を持ちます。"lat" フィールドは緯度です(南極の -90.0 から北極の +90.0 まで)。"lng" フィールドは経度です(極西としての日付変更線の -180.0 から、グリニッジ子午線の 0.0 を経て、極東としての日付変更線の +180.0 まで)。フィールド名は、Google の "places" API で使用されているものと同じフォーマットになるように選ばれています。

密接に関連する変更として、検索結果で返されていた 2 つの合成サマリーフィールドの削除があります。たとえば、スキーマに次のような記述がある場合:

```js
field mainloc type position {
    indexing: attribute | summary
}
```

Vespa 7 は _mainloc_ サマリーフィールドだけでなく、_mainloc.position_ と _mainloc.distance_ も含めていました。後者は、クエリーが距離を計算するための位置を実際に持っている場合のみです。

これらのうち最初のもの(この場合は _mainloc.position_)は、主に古い Vespa バージョンで XML 出力を生成するのに有用でしたが、現在では _mainloc_ サマリーフィールドとまったく同じ情報しか含んでいません。2 番目のもの(この場合は _mainloc.distance_)は内部単位での距離を返していましたが、サマリーフィーチャーで置き換えることができます。ここでは `distance(mainloc)` が同じ数値を返し、適切なコード変更を行うのであれば `distance(mainloc).km` が推奨される代替となります。

### "rankingExpression" でラップされる summary-features

Vespa 7 では、rank profile が関数 `foobar` を summary-features(または match-features)で返すようにしていた場合、出力では `rankingExpression(foobar)` としてレンダリングされていました。

プログラムでの利用のために、`FeatureData` クラスには `getDouble("foobar")` や `getTensor("foobar")` でのルックアップを可能にする追加のチェックがありますが、現在では指定された元の名前だけで存在し、レンダリングされます。

アプリケーションが JSON レンダリングを Vespa 7 とまったく同じにする必要がある場合は、rank profile でそれを指定できます。たとえば、スキーマに次のような記述がある場合:

```js
rank-profile whatever {
    function lengthScore() { expression: matchCount(title)/fieldLength(title) }
    summary-features {
        matchCount(title)
        lengthScore
        ...
```

Vespa 7 では、次のような JSON 出力が得られることがありました:

```json
summaryfeatures: {
        matchCount(title): 1,
        rankingExpression(lengthScore): 0.25,
        ...
```

Vespa 8 では、代わりに期待どおりの結果が得られます:

```json
summaryfeatures: {
        matchCount(title): 1,
        lengthScore: 0.25,
        ...
```

しかし、以前の動作にするには、次のように指定できます:

```js
rank-profile whatever {
    function lengthScore() { expression: matchCount(title)/fieldLength(title) }
    summary-features {
        matchCount(title)
			  rankingExpression(lengthScore)
        ...
```

これにより、以前と同じ出力が得られます。
