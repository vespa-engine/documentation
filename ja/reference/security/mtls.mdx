#### ピア認可ルール

`authorized-peers` メンバーは、クレデンシャルルールセット・オブジェクトの配列です。ピアが認可されたとみなされるためには、その証明書が少なくとも 1 つのルールセットに完全にマッチしなければなりません(MUST)。

各ルールセットには、クレデンシャルマッチャーの `required-credentials` 配列が含まれていなければなりません。証明書がルールセットにマッチするためには、そのすべてのクレデンシャルマッチャーにマッチしなければなりません(MUST)。

クレデンシャルは、`must-match` で与えられたパターンを、指定された証明書の `field` に対してチェックすることでマッチングされます。現在、次のフィールドがサポートされています:
* *CN* - 証明書の Distinguished Name 情報の Common Name 部分。複数の CN エントリが存在する場合、最後のものが考慮されます。
* *SAN_DNS* - タイプ DNS の Subject Alternate Name。証明書には多くの SAN エントリが含まれる場合があります。その場合、すべてのエントリがチェックされ、少なくとも 1 つのエントリがマッチすればクレデンシャルはマッチしたとみなされます。
* *SAN_URI* - タイプ URI の Subject Alternate Name。*SAN_DNS* に似ていますが、パターンマッチングのセマンティクスが少し異なります。

*CN* および *SAN_DNS* フィールドの場合、`must-match` パターンは次のセマンティクスを持つ「glob」スタイルのパターンです:
* `*` は、ドットで区切られた 1 つのホスト名パート内の 0〜n 個の非ドット文字にマッチします。これは、HTTPS のホスト名検証で証明書が使用するワイルドカードに似ています。例
  * `*.baz` は `bar.baz` にマッチしますが、`foo.bar.baz` や `foo.baz.bar` にはマッチしません。
  * `*.*.baz` は `foo.bar.baz` にマッチしますが、`bar.baz` にはマッチしません。
  * `*-myservice` は `foo-myservice` にマッチしますが、`bar.foo-myservice` にはマッチしません。
* `?` は、ドットで区切られた 1 つのホスト名パート内のちょうど 1 個の非ドット文字にマッチします。例:
  * `?.bar` は `x.bar` にマッチしますが、`bar`、`.bar`、`yx.bar` にはマッチしません。
  * `?.?.baz` は `x.y.baz` にマッチしますが、`x.baz` や `xx.yy.baz` にはマッチしません。

*SAN_URI* フィールドの場合も、`must-match` は「glob」スタイルのパターンですが、*CN*/*SAN_DNS* と比べていくつかの違いがあります:
* `*` ワイルドカードは 0〜n 個の非スラッシュ文字にマッチします。`/` は、ホストとパスのコンポーネント間の区切り、およびパスセグメント間の区切りとして使用されます。例:
  * `vespa://myapp/content/*` は `vespa://myapp/content/node1` にマッチしますが、`vespa://myapp/container/node1` や `vespa://myapp/content/node1/myservice` にはマッチしません。
  * `vespa://*/*/*` は `vespa://myapp/content/node1` にマッチしますが、`vespa://myapp/content` や `vespa://myapp/content/node1/myservice` にはマッチしません。
* パターン内の `?` に特別な動作はありません - リテラルの `?` にのみマッチします。URI では `?` はパスとクエリーのコンポーネント間の区切りとして使用されます。

description フィールドはオプションで、たとえば特定のルールセットが存在する理由を文書化するのに便利です。認可エンジンにとって意味的な意味はありません。

`authorized-peers` フィールドを指定しない場合、認可には証明書の有効性のみが使用されます。`authorized-peers` フィールドを指定する場合は、少なくとも 1 つのエントリを含める必要があります。

#### 例

```json expandable
{
    "files": {
        "ca-certificates": "/absolute/path/to/ca-certs.pem",
        "certificates": "/absolute/path/to/host-certs.pem",
        "private-key": "/absolute/path/to/private-key.pem",
        "disable-hostname-validation": false
    },
    "authorized-peers": [
        {
            "required-credentials": [
                { "field": "CN", "must-match": "vespa-monitoring.example.com" },
                { "field": "SAN_DNS", "must-match": "*.us-east-*.monitor.example.com" }
            ],
            "description": "Backend monitoring service access",
            "name": "monitoring"
        }, 
        {
            "required-credentials": [
                { "field": "SAN_DNS", "must-match": "*.mycluster.vespa.example.com" }
            ],
            "description": "Cluster-internal node P2P access",
            "name": "cluster"
        }
    ]
}
```
## Vespa がサポートする TLS 機能

Vespa は、モダンで高性能な暗号ライブラリを用いてビルドされています。セキュリティ上の理由から、Vespa の TLS スタックには常に適用されるいくつかの追加の制約があります:
* ネゴシエート可能な最も古い TLS バージョンは `TLSv1.2` です。
* [前方秘匿性](https://en.wikipedia.org/wiki/Forward_secrecy)をサポートする暗号スイートのみがネゴシエート可能です(すなわち、鍵交換の一部として ECDHE を使用する暗号スイート)。
* [AEAD](https://en.wikipedia.org/wiki/Authenticated_encryption#Authenticated_encryption_with_associated_data) の性質を持つモダンな共通鍵暗号のみがサポートされています。実際には、これは [AES-GCM](https://en.wikipedia.org/wiki/AES-GCM) または [ChaCha20-Poly1305](https://en.wikipedia.org/wiki/ChaCha20-Poly1305) を意味します。サポートされている暗号スイートは[こちら](#cipher-suites)に一覧があります。
* [CRIME](https://en.wikipedia.org/wiki/CRIME)/BREACH 型の圧縮オラクル攻撃を緩和するため、TLS 圧縮は明示的に無効化されています。
* TLS 再ネゴシエーションは明示的に無効化されています。
* TLS セッション再開は、リプレイ攻撃に関連する潜在的な脆弱性につながる可能性があるため、明示的に無効化されています。ただし、Vespa アプリケーションコンテナーのエッジは、プロキシやクライアントからの多数の頻繁で短命な接続をサポートする必要があるため、セッション再開をサポートしています。


<Note>
**注:**

上記は、`vespa_openssl` パッケージでビルドされた Vespa バージョンを使用していることを前提としています(すべてのオープンソース RPM と Docker イメージが該当します)。カスタムビルドを行う場合は、OpenSSL 1.1.1 以降に対してビルドすることを強く推奨します。それより古いバージョンでは、パフォーマンスの低下や暗号機能の制限がある可能性があります。1.0.1 より前の OpenSSL バージョンはサポートされていません。
</Note>


### デフォルトの TLS プロトコル設定

Vespa はデフォルトで次の TLS 設定を使用します(`accepted-ciphers` / `accepted-protocols` で上書きされない限り)。

#### プロトコルバージョン

* `TLSv1.3` - _注:_ 現在の Java ランタイムの特定の制限により、TLSv1.3 は今のところ C++ バックエンドでのみサポートされています。Java でも TLSv1.3 がデフォルトになるよう、近い将来に再検討する予定です。
* `TLSv1.2`

#### 暗号スイート

* `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`
* `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`
* `TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256` (JDK 12+)
* `TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256`
* `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`
* `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`
* `TLS_AES_128_GCM_SHA256` (TLSv1.3)
* `TLS_AES_256_GCM_SHA384` (TLSv1.3)
* `TLS_CHACHA20_POLY1305_SHA256` (TLSv1.3, JDK 12+)
