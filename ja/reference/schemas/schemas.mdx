このリファレンスは、スキーマ、ドキュメント・タイプ、フィールドの構文と内容を説明します。これはリファレンスです。概要と例については[スキーマ](/ja/basics/schemas)を参照してください。

## Syntax

このドキュメント全体を通して、角括弧で囲まれた文字列は何らかの引数を表します。括弧を含む文字列全体が、スキーマ内では具体的な文字列に置き換えられます。

スキーマ内の構成要素は規則的な構文を持ちます。各要素は要素の_識別子_で始まり、場合によってはその要素の特定の出現に対する_名前_が続き、場合によってはスペース区切りの_属性名_と_属性値_が交互に並んだリストが続き、場合によっては_要素本体_が続きます。したがって、次のような種類の要素が見られます:

```bash
[element-identifier] : [element-body]  
[element-identifier] [element-name] : [element-body]  
[element-identifier] [element-name] [attribute-name] [attribute-value]  
[element-identifier] [element-name] [attribute-name] [attribute-value] {
    [element-body]
}
```

1 行の要素値はコロンで始まり、改行で終わります。

複数行の値(それをサポートするフィールドの場合)は、波括弧で囲まれた任意のテキスト・ブロックです。

コメントはどこにでも挿入でき、ハッシュ(#)で始まります。

名前は_識別子_であり、`["a"-"z","A"-"Z", "_"]["a"-"z","A"-"Z","0"-"9","_"]*` にマッチする必要があります。

スキーマ・ファイルはインデントの影響を受けません。

## schema

スキーマのルート要素です。スキーマは、データの種類と、それに対して何を計算すべきかを記述します。スキーマは `[schema-name].sd` という名前のファイルで定義する必要があります。

```bash
schema [name] inherits [name] {
    [body]
}
```

`inherits` 属性はオプションです。スキーマが継承される場合、このスキーマは、継承元のすべての構成要素を、あたかもこのスキーマで定義されているかのように含みます(親のドキュメント・タイプを除く)。このスキーマ内のドキュメント・タイプは、親スキーマのドキュメント・タイプを継承することを宣言しなければなりません。

## document

[schema](#schema) に含まれ、ドキュメント・タイプを記述します。ドキュメントを直接クエリーしない場合は、これをスキーマのルートにすることもできます。

```bash
document [name] inherits [name-list] {
    [body]
}
```

ドキュメント名はオプションで、デフォルトでは包含する `schema` 要素の名前になります。包含する `schema` 要素がない場合、ドキュメント名は必須です。名前付きのドキュメントがスキーマ内で定義される場合、ドキュメント名は `schema` 要素の名前と一致しなければなりません。ドキュメント内で_ドキュメント・タイプ_と言及される場合は、ここで定義されるドキュメント名を指します。

`inherits` 属性はオプションで、値として他のドキュメント・タイプ名のカンマ区切りリストを取ります。ドキュメント・タイプは、1 つ以上の他のドキュメント・タイプのフィールドを継承できます。例については[ドキュメントの継承](/ja/schemas/inheritance-in-schemas)を参照してください。ドキュメント・タイプが明示的に継承されない場合、そのドキュメントは汎用の `document` タイプを継承します。

ドキュメント・タイプの body はオプションで、次を含むことができます:

## struct

[document](#document) に含まれます。複合型を定義します。struct は 0 個以上のフィールドで構成され、ユーザーはそれらをまとめて 1 つとしてアクセスできます。struct は、フィールド指定で型として使用される前に定義されていなければなりません。

```bash

    [body]
}
```

## field

[schema](#schema)、[document](#document)、または [struct](#struct) に含まれます。型を持つ名前付きの値と、(オプションで)このフィールドをどのように保存、インデックス、検索、表示するか、およびランキングにどのように影響させるかを定義します。

```bash
field [name] type [type-name] {
    [body]
}
```
インデキシング言語やスキーマ・ファイル内の他の場所で別の目的に使われている名前は使用しないでください。予約されている名前は次のとおりです:
- attribute
- body
- case
- context
- documentid
- else
- header
- hit
- host
- if
- index
- position
- reference
- relevancy
- sddocname
- summary
- switch
- tokenize

その他に使用してはいけない名前として、数字で始まる単語や特殊文字を含む単語があります。

_type_ 属性は必須です - サポートされる型:

指定した [struct 型](#struct)の配列フィールドを作成するためにも使用します。struct 型は別途定義されている必要があります。例:

```js
struct person {
    field first_name type string {}
    field last_name type string {}
}

field people type array<person> {
    indexing: summary
    summary: matched-elements-only
    struct-field first_name {
        indexing: attribute
        attribute: fast-search
    }
}
```

_people_ フィールド全体がドキュメント・サマリーの一部となります。[struct フィールド](#struct-field) _first\_name_ は、[fast-search](/ja/content/attributes#fast-search) を伴う検索用の _attribute_ として定義されています。struct フィールドの一部、またはすべてを attribute として定義できます。

同じ struct フィールドのインスタンス内でのマッチを保証するには、[sameElement](/ja/reference/querying/yql#sameelement) 演算子を使用します。

ドキュメント・サマリーで返されるデータ量を減らすには、[matched-elements-only](#matched-elements-only) を使用します。

<Warning>
 **重要:**

`key` と `value` は array\<struct\> における予約語です。これらは [map](#map) の実装に使用されるためです。これらを struct フィールドの名前として使用しないでください。
</Warning>

- struct 型の配列は[ランキング・フィーチャー](/ja/basics/ranking)をサポートせず、マッチングとフィルタリングにのみ使用できます。
- すべての struct 配列はフィードでき、取得でき、ドキュメント・サマリーで使用できます。

一意の各キーが単一の値にマップされるマップを作成するために使用します。_key-type_ には任意のプリミティブ型を、_value-type_ には任意のプリミティブ型または Vespa の struct 型を使用できます。プリミティブ型のマップの例で、_key_ フィールドと _value_ フィールドを _attribute_ として指定しています:

```
field my_map type map<string, int> {
    indexing: summary
    struct-field key { indexing: attribute }
    struct-field value { indexing: attribute }
}
```

Vespa のマップのエントリーは、_key-type_ と _value-type_ を型とする _key_ フィールドと _value_ フィールドを持つ _struct_ として扱われることに注意してください。これが上記の _struct-field_ 構文の理由です。_my\_map_ フィールド全体がドキュメント・サマリーに設定されます。

より複雑な例として、struct のマップがあります:

```
struct person {
    field first_name type string {}
    field last_name type string {}
    field age type int {}
}

field identities type map<string, person> {
    indexing: summary
    summary: matched-elements-only
    struct-field key {
        indexing: attribute
        attribute: fast-search
    }
    struct-field value.first_name {
        indexing: attribute
        attribute: fast-search
    }
    struct-field value.last_name {
        indexing: attribute
        attribute: fast-search
    }
}
```

この例は、struct の要素が個別に設定されることを示しています - _age_ に対するフィールド設定はありません - struct フィールドの一部だけを attribute として定義できます。

ここでは、_key_、_value.first\_name_、_value.last\_name_ が attribute として定義されています。これにより、これらは検索と[グルーピング](/ja/querying/grouping#grouping-over-a-map-field)で利用できるようになります。よくあるユース・ケースは、同じマップ・エントリー内でのマッチを要求すること(例: 同一人物の姓と名の両方にマッチさせる)です。この実装方法については [sameElement](/ja/reference/querying/yql#sameelement) 演算子を参照してください。ドキュメント・サマリーのデータ量を減らすには [matched-elements-only](#matched-elements-only) を使用します。

[fast-search](/ja/performance/feature-tuning#when-to-use-fast-search-for-attribute-fields) は、ルックアップ用のインデックス構造を作成することでクエリー・アクセスを高速化するために使用されます。

マップの代替として、[array\<struct\>](#array) は同じ要素を複数回含むことができ、順序を維持します。

 を使用します。たとえば、次のフィールドがあるとします: 
```
field surl type uri {
    indexing: summary | index
    alias: url
    alias hostname: site
}
```

"surl" と "url" での検索は URL 全体を検索し、"surl.hostname" または "site" は hostname を検索します。

## fieldset

[schema](#schema) に含まれます。

<Info>
 **注:** これは [Document fieldset](/ja/schemas/documents#fieldsets) とは関係ありません。異なる型/match 設定を使用した場合に何が起こるかについては [FAQ](/ja/learn/faq#must-all-fields-in-a-fieldset-have-compatible-type-and-matching-settings) も参照してください。
</Info>

fieldset は、検索のためにフィールドをグループ化します:

```js
fieldset myfieldset {
    fields: a,b,c
}
```

デフォルト(すなわちクエリーで指定されなかった場合)として使用される `default` という名前の fieldset を作成します:

```js
fieldset default {
    fields: a,b,c
}
```

[クエリーの例](/ja/querying/query-api#fieldset)を参照してください。

fieldset 内のフィールドは、indexing 句と [match モード](#match)の点でできるだけ類似しているべきです。そうでない場合は、アプリケーションを十分にテストしてください。fieldset 内のフィールドの match モードが異なる場合、アプリケーションのデプロイ時に警告が生成されます。_exact_ のような fieldset 固有の match 設定が必要な場合は、_match_ を使用して指定します:

```js
fieldset myfieldset {
    fields: a,b,c
    match {
        exact
    }
}
```

検索設定を設定するには、fieldset 内で [query-command](#query-command) を使用します。例:

```js
fieldset myfieldset {
    fields: a,b,c
    query-command:"exact @@"
}
```

fieldset を追加しても、メモリー/ディスク上に追加のインデックス構造が作成されることはありません。単なるマッピングです。

fieldset をマッチングする際、ドキュメント頻度はすべてのメンバー・フィールドにわたって集約されることに注意してください。これは [BM25](/ja/ranking/bm25) と significance の値に影響し、_"the"_ のような一般的なタームがあるメンバー・フィールドでは頻出するが別のフィールドでは稀な場合に、[weakAnd](/ja/ranking/wand) がそれらのマッチを刈り込む原因となることがあります。詳細とフィールドごとの回避策については [FAQ](/ja/learn/faq#why-can-common-words-like-the-hurt-recall-and-collapse-significance-across-a-fieldset) を参照してください。

## match-phase

[rank-profile](#rank-profile) に含まれます。match-phase 機能を使用すると、第 1 フェーズのランキングに渡されるヒットを、ある attribute の最高値(または最低値)に限定することでパフォーマンスを向上させることができます。特に第 1 フェーズの関数が高コストな場合、パフォーマンスの向上は大きくなり得ます。品質の低下は、選択した attribute が第 1 フェーズのスコアとどれだけよく相関するかに依存します。

選択した attribute に値を持たないドキュメントは、値 0 を持つものとして扱われます。

[グレースフル・デグラデーション](/ja/performance/graceful-degradation#match-phase-degradation)と[結果の多様性](/ja/querying/result-diversity#match-phase-diversity)も参照してください。

```js
match-phase {
    attribute: [numeric single value attribute]
    order: [ascending | descending]
    total-max-hits: [integer]
}
```

## strict

[rank-profile](#rank-profile) に含まれます。true または false。デフォルトでは、Vespa は緩い型チェックを使用し、クエリー・プロファイル・タイプで定義されていないのに使用されているクエリー・フィーチャーは float とみなされます。true に設定すると、クエリー・プロパティの型定義が欠けている場合に、代わりにデプロイの失敗を引き起こします。

```bash
strict: true
```

## diversity

[rank-profile](#rank-profile) に含まれます。diversity は、異なるクエリー・フェーズにおける多様性を保証するために使用されます。[match-phase](#match-phase) がある場合、match-phase から first-phase へ多様な結果を提供します。[second-phase](#secondphase-rank) がある場合、first-phase から second-phase へ多様な結果を提供します。

詳細は[結果の多様性](/ja/querying/result-diversity)を参照してください。

多様性を提供するために使用される attribute の名前を指定します。結果セットは、このフェーズから [diversity attribute](#diversity-min-groups) の一意な値を少なくとも [min-groups](#diversity-min-groups) 個得ることが保証されますが、max-hits を超えることはありません。[match-phase](#match-phase) の場合、max-hits = ノードの [match-phase total-max-hits](#match-phase-max-hits) の割り当て分です。[second-phase](#secondphase-rank) の場合、max-hits = ノードの [total-rerank-count](#secondphase-total-rerank-count) の割り当て分です。ドキュメントは次の場合に候補とみなされます:

- クエリーがこのフェーズから生成される _max-hits_ 数にまだ達していない。
- クエリーが 1 グループ内の候補の最大数にまだ達していない。これはフェーズの _max-hits_ を [min-groups](#diversity-min-groups) で割って計算されます

```js
diversity {
    attribute: [attribute name]
    min-groups: [integer]
}
```

## expression

[first-phase](#firstphase-rank)、[second-phase](#secondphase-rank)、または [global-phase](#globalphase-rank) に含まれます。[ランキング式](/ja/reference/ranking/ranking-expressions)を指定します。式は直接記述することも、ファイルから読み込むこともできます。直接記述する場合の構文は次のとおりです:

```bash
expression: [ranking expression]
```
または
```js
expression {
    [ranking expression]
    [ranking expression]
    [ranking expression]
}
```

2 番目の形式は主に、長い式を使用する際の便宜のための機能で、式を複数行に分割できるようにします。

式は別ファイルから読み込むこともできます。これは、たとえば MLR によって生成される長い式を扱う場合に便利です。構文は次のとおりです:

```js
expression: file:[path-to-expressionfile]
```

パスはスキーマ定義ファイルの場所からの相対パスです。ファイル自体は `.expression` で終わらなければなりません。このサフィックスはスキーマ内では省略可能です。したがって、`expression: file:mlrranking.expression` と `expression: file:mlrranking` は同一です。どちらも _schemas_ ディレクトリにある `mlrranking.expression` というファイルを参照します。

<Info>
 **注:** パスにディレクトリを含めることはできません。
</Info>

## function (inline)? [name]

[rank-profile](#rank-profile) に含まれます。ランキング式の一部として、または(引数を持たない場合は)フィーチャーとして参照できる名前付き関数を定義します。関数は任意の数の引数を受け取ります。

```js
function [name]([arg1], [arg2], [arg3]) {
    expression: â€¦
}
```
または
```js
function [name] ([arg1], [arg2], [arg3]) {
    expression {
        [ranking expression]
        [ranking expression]
        â€¦
}
```
名前の後には括弧が必須である点に注意してください。rank-profile の例を以下に示します:
```js
rank-profile default inherits default {
    function myfeature() {
        expression: fieldMatch(title) + freshness(timestamp)
    }
    function otherfeature(foo) {
        expression{ nativeRank(foo, body) }
    }

    first-phase {
        expression: myfeature * 10
    }
    second-phase {
        expression: otherfeature(title) * myfeature
    }
    summary-features: myfeature
}
```

引数を受け取る関数を summary features に含めることはできません。

`inline` 修飾子を追加すると、その関数が引数も持たない場合、呼び出し元の式にインライン展開されます。これは、小さく低コストな関数では高速になります(それ以外では、よりコストが高くなります)。

## summary-features

[rank-profile](#rank-profile) に含まれます。各結果ヒットとともに [summaryfeatures](/ja/reference/querying/default-result-format#summaryfeatures) フィールドに含められる[ランク・フィーチャー](/ja/reference/ranking/rank-features)のリスト。[結果でのフィーチャー値](/ja/ranking/ranking-expressions-features#accessing-feature-function-values-in-results)も参照してください。

指定されていない場合、フィーチャーは親プロファイル(存在する場合)で指定されたとおりになります。親プロファイルからフィーチャーを継承し、_かつ_追加のフィーチャーを指定するには、以下に示すようにフィーチャーを親から継承することを明示的に指定します。例については[スキーマの継承](/ja/schemas/inheritance-in-schemas)を参照してください。

ここで指定されたランク・フィーチャーは、マルチフェーズ・クエリーの [fill フェーズ](/ja/applications/searchers#multiphase-searching)で計算されます。

<Info>
 **注:** _summary-features_ 内のランク・フィーチャー参照は、(全ノードからの)グローバルな上位ランキング・ヒットに入ったヒットに対して、_fill プロトコル・フェーズ_中に**再計算**されます。代替手段については [match-features](#match-features) を参照してください。
</Info>

```bash
summary-features: [feature] [feature]â€¦
```

または

```bash
summary-features [inherits parent-profile (, other-parent-profile)*]? {
    [feature]
    [feature]
}
```

各行には、スペースで区切って任意の数のランク・フィーチャーを列挙できます。

<Info>
 **注:** 複合式は、match/summary-features からアクセスできるようにするために、[関数](/ja/ranking/ranking-expressions-features#accessing-feature-function-values-in-results)でラップしなければならない点に注意してください。 
</Info>

## match-features

[rank-profile](#rank-profile) に含まれます。各結果ヒットとともに [matchfeatures](/ja/reference/querying/default-result-format#matchfeatures) フィールドに含められる[ランク・フィーチャー](/ja/reference/ranking/rank-features)のリスト。[結果でのフィーチャー値](/ja/ranking/ranking-expressions-features#accessing-feature-function-values-in-results)も参照してください。

指定されていない場合、フィーチャーは親プロファイル(存在する場合)で指定されたとおりになります。親プロファイルからフィーチャーを継承し、_かつ_追加のフィーチャーを指定するには、以下に示すようにフィーチャーを親から継承することを明示的に指定します。[スキーマの継承](/ja/schemas/inheritance-in-schemas)も参照してください。

親ランク・プロファイルからの match-features を無効にするには、`match-features {}` を使用します。

_match-features_ は [summary-features](#summary-features) に似ていますが、ここで指定されたランク・フィーチャーは、[マルチプロトコル・クエリー実行](/ja/applications/searchers#multiphase-searching)の_最初のプロトコル・フェーズ_(_match_ プロトコル・フェーズとも呼ばれます)で計算されます。これにより、パフォーマンスのトレードオフが異なります。詳細は[結果でのフィーチャー値](/ja/ranking/ranking-expressions-features#accessing-feature-function-values-in-results)を参照してください。

```bash
match-features: [feature] [feature]â€¦
```

または

```bash
match-features [inherits parent-profile (, other-parent-profile)*]? {
    [feature]
    [feature]
}
```

各行には、スペースで区切って任意の数のランキング・フィーチャーを列挙できます。

<Info>
 **注:** 複合式は、match/summary-features からアクセスできるようにするために、[関数](/ja/ranking/ranking-expressions-features#accessing-feature-function-values-in-results)でラップしなければならない点に注意してください。 
</Info>

## dictionary

[field](#field) に含まれ、フィールドの転置インデックスで使用される辞書の詳細を指定します。`fast-search` が付与された [attribute](#attribute) にのみ適用されます。`btree` または `hash`、あるいは両方を指定できます。両方指定した場合、範囲/前方一致には btree が、完全一致のルックアップには hash が使用されます。

### Dictionary Types

**btree**(デフォルト): 完全一致、前方一致、範囲のルックアップで良好なパフォーマンスを提供します。ほとんどのユース・ケースで推奨されます。詳細は [attribute のインデックス構造](/ja/content/attributes#index-structures)を参照してください。

**hash**: 一意な ID フィールドのような、カーディナリティの高い(一意な値が多い)フィールド用に最適化されています。この場合、各ポスティング・リストには 1 つの項目しか含まれません。

<Info>
 **注:** `hash` を使用する場合、文字列の前方一致検索と数値フィールドの範囲検索はフル・スキャンにフォールバックします。これは主に、出現回数がそれぞれ少ない一意なタームが多数存在し、辞書ルックアップのコストがそうでなければ大きくなる場合に有効です。 
</Info>

### Case Handling for String Fields

文字列の attribute では、文字の大文字・小文字の扱いを指定できます:

- **uncased**(デフォルト): 大文字・小文字を区別しません - 'bear'、'Bear'、'BEAR' は同一として扱われます
- **cased**: 大文字・小文字を区別します - 'bear'、'Bear'、'BEAR' は異なるタームとして扱われます

この設定は、フィールドの [match:casing](#match) 設定と自動的に照合されます。

### Important Rules for String Fields with Dictionaries

**`btree` 辞書の場合**: `cased` と `uncased` の両方のオプションがサポートされます。

**`hash` 辞書の場合**: 文字列フィールドでは `cased` のみがサポートされます。`hash` 辞書を使用する場合:

    - フィールドに `match: cased` を設定**しなければなりません**
    - dictionary ブロックに `cased` を含め**なければなりません**

```js
dictionary {
  hashcased}
```

### Example: Case-Sensitive Hash Dictionary

```js
field id_str type string {
      indexing: summary | attribute
      attribute: fast-searchmatch: casedrank: filter
      dictionary {
        hashcased}
}
```

## distance-metric

[nearestNeighbor](/ja/reference/querying/yql#nearestneighbor) クエリー演算子とともに使用して、ドキュメントの位置とクエリーの位置の間の距離を計算するための距離メトリックを指定します。各テンソルが 1 つまたは複数のベクトルを保持する、テンソル attribute フィールドにのみ関係します。

どの距離メトリックを使用するかは、ベクトルを生成するために使用されたモデルに依存します。表現学習(モデル学習)中に使用された距離メトリックと一致していなければなりません。「既製の」モデルを使用してデータをベクトル化する場合は、そのモデルでの使用が推奨される距離メトリックと一致することを確認してください。ベクトル化モデルの種類によって、使用される距離メトリックの種類も異なります。

<Danger>
 **重要:** `distance-metric` または `max-links-per-node` を変更する場合、HNSW インデックスを再構築するためにコンテント・ノードを再起動しなければなりません - [再起動が必要だが再フィードは不要な変更](#changes-that-require-restart-but-not-re-feed)を参照してください
</Danger>

### euclidean

デフォルトのメトリックは[ユークリッド距離](https://en.wikipedia.org/wiki/Euclidean_distance)で、これは単に 2 点間の線分の長さです。nearestNeighbor クエリー演算子で既に計算されたものを取得する代わりに、ランキング式で直接ユークリッド距離を計算するには、[Euclidean\_distance ヘルパー関数](/ja/reference/ranking/ranking-expressions#euclidean-distance-t)を使用します:

```js
function mydistance() {
        expression: euclidean_distance(attribute(myembedding), query(myqueryvector), mydim))
    }
```

### angular

_angular_ 距離メトリックは、ベクトル間の_角度_を計算します。範囲は `[0,pi]` で、これが角距離です。これは[コサイン類似度](https://en.wikipedia.org/wiki/Cosine_similarity)による順序付けとしても知られており、その場合のスコア関数は単に角度のコサインです。ランキング式で直接角距離を計算するには、[cosine\_similarity ヘルパー関数](/ja/reference/ranking/ranking-expressions#cosine-similarity-t)を使用します:

```js
function angle() {
        expression: acos(cosine_similarity(attribute(myembedding), query(myqueryvector), mydim))
    }
```
 逆に、nearestNeighbor クエリー演算子を使用する場合、コサイン類似度は [distance ランク・フィーチャー](/ja/reference/ranking/rank-features#distance(dimension,name))から復元できます:

```js
rank-profile cosine {
        first-phase {
            expression: cos(distance(field, myembedding))
        }
    }
```
可能であれば、クエリー・ベクトルとドキュメント・ベクトルの両方を同じ L2 ノルムに正規化し、代わりに `prenormalized-angular` メトリックを使用する方がパフォーマンスの点でわずかに優れています。ただし、返される distance と closeness は異なる点に注意してください。

### dotproduct

_dotproduct_ 距離メトリックは、「最大内積」検索を最近傍検索で解ける形に_数学的に変換_するために使用され、内積が直接スコアとして使用されます(大きな正の内積が「近い」とみなされます)。内部的には、追加の次元が加えられ(すべてのベクトルが同じ長さに正規化されることを保証)、_prenormalized-angular_ に似た距離が HNSW インデックスの構築に使用されます。詳細は、[この論文のセクション 3.1 Order Preserving Transformations](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/XboxInnerProduct.pdf) に基づいた[このハイレベルなガイド](https://towardsdatascience.com/maximum-inner-product-search-using-nearest-neighbor-search-algorithms-c125d24777ef)を参照してください。

_dotproduct_ 距離メトリックを使用する場合、_distance_ および _closeness_ ランク・フィーチャーは通常の意味を持たない点に注意してください。特に、_closeness_ は単に内積 âˆ‘n(xi\*yi) を返し、これは任意の負または正の値を取り得ます。また _distance_ は単に内積の符号を反転したものです。`[0,1]` の範囲に正規化された closeness が必要な場合は、適切な[シグモイド関数](https://en.wikipedia.org/wiki/Sigmoid_function)を適用しなければなりません。たとえば、attribute の名前が "foobar" で、観測される最大の内積が 4000 前後の場合、式 `sigmoid(0.001*closeness(field,foobar))` が 1 つの選択肢になり得ます。

_dotproduct_ 距離メトリックは、正規化されていないベクトルで「最大内積」(MIP)を使用する、行列分解を含む一部のベクトル化モデルに有用です。これらのモデルは方向と大きさの両方を使用します。

### prenormalized-angular

_prenormalized-angular_ 距離メトリックは、クエリーとドキュメントの**両方**のベクトルが正規化されている場合に**のみ使用しなければなりません**。このメトリックは以前 "innerproduct" という名前で、単位長のベクトルを必要としました。新しいバージョンはクエリー・ベクトルの長さを一度だけ計算し、他のすべてのベクトルが同じ長さであると仮定します。

正規化されていないベクトルで _prenormalized-angular_ を使用すると、最近傍検索が予測不能になり、パフォーマンスと品質の両面で悪い結果をもたらすことが観測されています。

ベクトル _x_ の長さ、大きさ、またはノルムは `length = sqrt(sum(pow(xi,2)))` として計算されます。単位長に正規化されたベクトルは `[xi/length]` で与えられます。ゼロ・ベクトルはまったく使用できません。

Vespa の _prenormalized-angular_ は[コサイン類似度](https://en.wikipedia.org/wiki/Cosine_similarity)を計算し、`1.0 - cos(angle)` を距離メトリックとして使用します。これは `angular` 距離とまったく同じ順序を与えますが、コサイン類似度の範囲が [1,-1] であるため、距離は [0,2] の範囲になります。最終的な結果は、同じ方向のベクトルで 0.0、直角で 1.0、正反対の方向のベクトルで 2.0 になります。したがって、コサイン・スコア(または角度)を得るのは簡単です:

```js
rank-profile cosine {
        first-phase {
          expression: 1.0 - distance(field, embedding)
        }
        function angle() {
          expression: acos(1.0 - distance(field, embedding))
        }
    }
```
 nearestNeighbor クエリー演算子で既に計算されたものを取得する代わりに、ランキング式で直接コサイン類似度を計算するには、[cosine\_similarity ヘルパー関数](/ja/reference/ranking/ranking-expressions#cosine-similarity-t)を使用します:

```js
function mysimilarity() {
        expression: cosine_similarity(attribute(myembedding), query(myqueryvector), mydim))
    }
```

### geodegrees

_geodegrees_ 距離メトリックは、地理座標(地球上の緯度と経度を度単位で含む 2 次元ベクトル)に対してのみ有効です。[Haversine の公式](https://en.wikipedia.org/wiki/Haversine_formula)を使用して、2 つの地理的地点間の大円距離(キロメートル単位)を計算します。例については [geodegrees システム・テスト](https://github.com/vespa-engine/system-test/blob/master/tests/search/nearest_neighbor/geo.sd)を参照してください。

### hamming

[ハミング距離](https://en.wikipedia.org/wiki/Hamming_distance)メトリックは、ベクトルの座標が異なる次元の数を数えます。これは浮動小数点データには有用ではありません。各浮動小数点数から 1 ビットの情報しか得られないことになるためです。代わりに、各ビットが個別の座標とみなされるバイナリ・データに使用すべきです。実際には、テンソルに `int8` の[セル値型](/ja/performance/feature-tuning#cell-value-types)を使用し、ビット・パターンから数値への通常のエンコーディングを用いることを意味します。例:

- `00000000` â†’ `0` (hex `00`)
- `00010001` â†’ `17` (hex `11`)
- `00101010` â†’ `42` (hex `2A`)
- `01111111` â†’ `127` (hex `7F`)
- `10000000` â†’ `-128` (hex `80`)
- `10000001` â†’ `-127` (hex `81`)
- `11111110` â†’ `-2` (hex `FE`)
- `11111111` â†’ `-1` (hex `FF`)

このユース・ケースでは、`[-128,127]` の範囲の数値の代わりに ["hex dump"](/ja/reference/schemas/document-json-format#tensor-hex-dump) 形式でデータをフィードできます。これにより、バイナリ・データをより自然な形式で表現でき、大きな数値の JSON 配列をパースするオーバーヘッドを回避できます。

## bolding

[field](#field) または [summary](#summary) に含まれます。[summary](#summary) 内でマッチしたクエリー・タームをハイライトします:

```bash
bolding: on
```

デフォルトは太字化なしで、有効にするには `bolding: on` を設定します。このコマンドは `summary: dynamic` によってオーバーライドされる点に注意してください。両方指定された場合、bolding は無視されます。`summary: dynamic` の代わりに bolding を使用する場合の違いは、後者はクエリー・タームのハイライトに加えて動的な要約を提供するのに対し、前者はハイライトのみを行うことです。bolding は、string 型または array\<string\> 型の [index](#indexing-index) フィールドでのみサポートされます。

検索タームのハイライトに使用されるデフォルトの XML 要素は \<hi\> です - オーバーライドするには、_container.qr-searchers_ の設定を行います。`<strong>` を使用する例:

```xml
<container>
    <search>
        <config name="container.qr-searchers">
            <tag>
                <bold>
                    <open>&lt;strong&gt;</open>
                    <close>&lt;/strong&gt;</close>
                </bold>
                <separator>...</separator>
            </tag>
        </config>
    </search>
</container>
```

bolding の最大フィールド・バイト長は 64Mb です - これより大きいフィールド値は、`summary: dynamic` と同様にスニペットとして表現されます。

## id

[field](#field) に含まれます。このフィールドの数値 ID を設定します。すべてのフィールドは、転送と保存のために内部的にドキュメント内 ID を持ちます。ID は通常、31 ビットの数値としてプログラム的に決定されます。代わりに ID を 7 ビットの数値に明示的に設定することで、保存と転送のスペースをいくらか節約できます。

```js
id: [positive integer]
```

ID は次の要件を満たさなければなりません:

- 正の整数であること
- 100 未満または 127 より大きいこと
- ドキュメント内、およびこのドキュメントが継承するすべてのドキュメント内で一意であること

      <td>このフィールドの値を<a href="/ja/reference/writing/indexing-language#summary" aria-label="summary">サマリー</a>・フィールドに含めます。サマリー出力を変更するには <a href="#summary" aria-label="summary:">summary:</a> を使用します(例: 動的ティーザーの生成)。</td>

フィールドのインデキシング文で `index` と `attribute` の両方を組み合わせる場合(例: `indexing: summary | attribute | index`)、そのフィールドの [match](#match) モードは `text` になります。したがって、このフィールドへの検索は [attribute](#attribute) の内容ではなくインデックスを検索します。

例と詳細は[テキスト・マッチング](/ja/querying/text-matching)ガイドを参照してください。

## linguistics

このフィールドに対するコンテンツと検索を言語的にどのように処理するかを決定するリンギスティクスの「プロファイル」を設定します。プロファイル値は[リンギスティクス・コンポーネント](/ja/linguistics/linguistics)に伝播され、プロファイル固有の処理を行うように設定できます。

```js
linguistics {
    profile: myIndexAndSearchProfile
}
```
または
```js
linguistics {
    profile {
        index: myIndexProfile
        search: mySearchProfile
    }
}
```

```js
rank {
```

```bash
rank [field-name] {

```

### element-gap

[rank-profile](#rank-profile) に含まれます。多値フィールドの隣接する要素間の位置のギャップを指定するために使用します。デフォルト値は `infinity` です。`infinity` または正の整数として指定します。

3 つの要素 `["a c", "x b x a x x x x x x b", "x x d"]` を持つ `array<string>` フィールドを考えてみます。通常、距離計算は要素内でのみ実行されるため、ターム _a_ と _b_ の出現間の最小前方距離は 7 です。フィールドの `element-gap` を 0 に設定すると、隣接する要素が考慮され、ターム _a_ と _b_ の出現間の最小前方距離は 3 になります。ターム _c_ と _d_ の出現間の最小距離は、それらが隣接する要素にないため計算されません。

`element-gap` 設定は、[nativeProximity](/ja/reference/ranking/rank-features#nativeProximity) ランク・フィーチャー、[near](/ja/reference/querying/yql#near) クエリー演算子、[onear](/ja/reference/querying/yql#onear) クエリー演算子に影響します。

```bash
rank [field-name] {
    element-gap: 0
}
```

この設定の変更には再起動も再インデキシングも不要で、即座に有効になります。

## query-command

[fieldset](#fieldset)、[field](#field)、または [struct-field](#struct-field) に含まれます。検索時に、このフィールドのインデックスへのクエリー・タームに対して実行される機能を指定します。Search Container サーバーは、これらのコマンドを処理する Vespa Searcher プラグインの作成をサポートしています。

```js
query-command: [an identifier or quoted string]
```

インデックス固有の設定パラメーターを必要とするプラグイン・サーチャーを作成する場合、そのパラメーターをここで設定できます。

組み込みの query-command が 1 つあります: `phrase-segmenting`。これが設定されると、ユーザー・クエリー内で非単語文字で連結されたターム("a.b" など)は、デフォルトの connectivity が 1 に設定された AND アイテムではなく、フレーズ・アイテムとしてパースされます。

## weakand

[rank-profile](#rank-profile) に含まれます。

ドキュメント・コーパスに存在するドキュメント頻度の統計に基づいて、クエリーにおける重要度(significance)が低いと予想されるタームとドキュメントを自動的に除外するように、[weakAnd](/ja/ranking/wand#weakand) アルゴリズムをチューニングします。これにより、リコールが低下する可能性と引き換えにマッチングが高速になります。

```js
weakand {
    [body]
}
```

すべてのドキュメント頻度の計算は、_コンテント・ノード・ローカル_のドキュメント統計を使用して行われる点に注意してください(すなわち、[グローバル significance](/ja/ranking/significance#global-significance-model) は効果がありません)。つまり、結果はコンテント・ノードやコンテント・ノードのグループによって異なる可能性があります。

## import field

## Document and search field types

document の外側で、他のフィールドを入力として使用するフィールドを宣言することで、ある型のドキュメント・フィールドを、別の型の 1 つ以上の検索フィールドのインスタンスにできる点に注意してください。たとえば、ドキュメント内のカンマ区切りの整数リストを含む文字列から整数の attribute を作成するには、次のようにします:

```js
    }
```

## Modifying schemas

このセクションでは、稼働中のアプリケーションのスキーマをどのように変更できるかを説明します。カテゴリー:

1. [再起動も再フィードも不要な有効な変更](#valid-changes-without-restart-or-re-feed)
2. [再起動が必要だが再フィードは不要な変更](#changes-that-require-restart-but-not-re-feed)
3. [再インデキシングが必要な変更](#changes-that-require-reindexing)

新しいアプリケーション・パッケージに対して `vespa prepare` を実行すると、スキーマ・ファイルの変更が現在アクティブなパッケージのファイルと比較されます。一部の変更に再起動または再フィードが必要な場合、`vespa prepare` の出力に必要なアクションが示されます。

<Danger>
 **重要:** 以下でカバーされていない変更で、`vespa prepare` から出力が返されない場合、その影響は未定義であり、再フィードまでシステムが稼働し続けられることは一切保証されません。スキーマに関連しない変更については、[管理手順](/ja/operations/self-managed/admin-procedures)で説明しています。
</Danger>

手順:

1. 変更したアプリケーションに対して `vespa prepare` を実行します
2. `vespa activate` を実行します。変更は即座に有効になります

### Changes that require restart but not re-feed

手順:

1. 変更したアプリケーションに対して `vespa prepare` を実行します。出力に必要な再起動アクションが示されます 
2. `vespa activate` を実行します
3. `prepare` の出力で指定されたサービスで `services` を再起動します

### Changes that require reindexing

以下に列挙するすべての変更には、全ドキュメントの[再インデキシング](/ja/operations/reindexing)が必要です。外部のデータ・ソースを必要とする再フィードとは異なり、再インデキシングは Vespa に保存されているドキュメントを使用して行われ、(一度トリガーされれば)自動的です。フィードやサービングと並行して実行することもできますが、再インデキシングが完了するまで、影響を受けるフィールドは空になるか、クエリー処理と一致しない誤ったアノテーションを持つ可能性があります。手順:

1. 変更したアプリケーションに対して `vespa prepare` を実行します。出力に必要な再インデキシング・アクションが示されます 
2. `vespa activate` を実行します
3. 指定されたドキュメント・タイプとクラスターに対して[再インデキシングを有効化](/ja/reference/api/deploy-v2#reindex)します
4. 再インデキシング・プロセスを開始するために、再度 `vespa prepare` と `vespa activate` を実行します

### Changes that require re-feed

以下に列挙するすべての変更には、全ドキュメントの再フィードが必要です。上記のセクションに列挙されていない変更は、ここに列挙されているものとして扱ってください。再フィードが完了するまで、影響を受けるフィールドは空になるか、クエリー処理と一致しない誤ったアノテーションを持つ可能性があります。手順:

1. 変更したアプリケーションに対して `vespa prepare` を実行します。出力に必要な再フィード・アクションが示されます
