---
title: "Vespa Cloud ホスト・イメージ"
---

Vespa Cloud は、AWS の EC2 のようなコンピュート・インスタンス上で稼働します。ホストはイメージによってブートされ、このイメージは定期的に更新されます。ホストは OCI コンテナー・イメージ内で Vespa を実行します - Vespa のアップグレードは、新しいイメージでコンテナーを再起動することを意味します。この記事は、ホスト上で稼働するイメージと、その管理について説明します。

## ホスト・イメージの自動化

Vespa.ai は、おおむね週次で新しいホスト・イメージをリリースします:

- イメージは通常、火曜日にリリースされます。
- コンソールの *Enclave* ビューで、*9.0.0.20260724* のような *Target* イメージ名を確認できます。
- 同じビューで、アプリケーションのホスト一覧と、それらの更新ステータスを確認できます:

<Frame>![OS イメージの一覧](/assets/img/image-list.png)</Frame>

### 注意事項

- 新しいイメージは自動化によってリリースされ、固定されたスケジュールではありません。たとえば、優先度の高いイメージはいつでもリリースされる可能性があり、週次リリースは回帰テスト中にいつでも停止される可能性があります。
- OS 更新プロセスは、リージョン内のアベイラビリティー・ゾーン(AZ)ごとに、90% 完了するまで実行されます。つまり、通常は 1 つの AZ が完了してから次に進みますが、重複もあります。そのため、複数の AZ にまたがる同時更新が行われるリージョンでは、サービング能力が低下する可能性があります。経験則として、AZ の切り離しに加え、残りの AZ でノード 1 台のダウンに耐えられるキャパシティーを構築すべきです。
  - 段階的なロールアウトのため、*Target* イメージは AZ ごとに異なる場合があります - これは上記のビューで確認できます。
- 自動化をオーバーライドする(たとえば更新プロセスを一時停止する)には、[Vespa サポート](https://support.vespa.ai/)に連絡するか、ブロック・ウィンドウ(下記)を変更してください。
- ホストは最新のイメージ、すなわち *Target* OS バージョンに収束します。大規模なアプリケーションでは、プロセスの途中で複数のイメージ上で稼働する場合があります。
- 新しいホスト(障害ホストの交換、またはキャパシティー増強)は、常に *Target* イメージを使用して割り当てられます。

## ホスト・イメージの更新

イメージ更新の自動化プロセスは次のとおりです:

1. Vespa コンテナー・イメージを停止します(オーケストレーションされます)。
2. ホストを停止し、更新されたイメージで再度起動します。ホストが停止される際には、バックアップも作成されます。

つまり、1 つ以上のノードが可用性を考慮してオーケストレーションされながら停止され、アップグレードされます - これがすべてのホストに対して繰り返されます。この処理には、インデックスのサイズに応じてホストあたり数分かかります。

## イメージ更新の制御

オーケストレーションされた再起動の実行中は、サービング能力が低下します。[ブロック・ウィンドウ](/ja/reference/applications/deployment#block-change)の *maintenance* 属性を使用して、運用プロセスに合わせた時間帯(たとえば利用の少ない時間帯)にプロセスを実行してください。

次の例では、業務時間中のメンテナンスをブロックしつつ、アプリケーションのデプロイとプラットフォームのアップグレードは常時許可します:

```xml
<block-change maintenance="true"
              revision="false"
              version="false"
              hours="8-15"
              time-zone="America/Los_Angeles"/>
```

## デプロイメント・パイプライン

OS のアップグレードは[デプロイメント・パイプライン](/ja/operations/automated-deployments)とは統合されていません。ただし、ノードの再起動はオーケストレーションされるため、これによってデプロイが遅くなる場合があります。これは、デプロイの成功にはノードが設定のジェネレーションを報告する必要があり、ノードの再起動がこのプロセスを遅らせるためです。

## QA インスタンスで新しい Target イメージを先に実行する方法

アプリケーションのオーナーは、本番サービング・クラスターより先に、QA インスタンスに新しい Target OS バージョンをデプロイしたい場合があるでしょう。このプロセスは(上記のとおり)パイプライン化されていないため、選択肢については [Vespa サポート](https://support.vespa.ai/)に連絡してください。
