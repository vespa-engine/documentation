## はじめに

このドキュメントでは、Vespa Cloud サービスのセキュリティ機能と運用手順について説明します。

Vespa.ai は SOC 2 認証を取得しています。詳細は [Trust Center](https://trust.vespa.ai/) をご覧ください。

## 概念とアーキテクチャ

<Frame>![Vespa Cloud 全体アーキテクチャ図](/assets/img/overall-architecture.png)</Frame>

Vespa Cloud は、*コントロール・プレーン(Control Plane)* と *データ・プレーン(Data Plane)* で構成されます。それぞれ独自のウェブサービス API を持ち、前者は Vespa アプリケーションの管理(Control)、後者はデプロイされた Vespa アプリケーションとのやり取り(Data)を担います。

コントロール・プレーンは、アプリケーションが指定するゾーンへのデプロイを管理し、テナント管理者が Vespa Cloud 上のテナント情報を管理できるようにします。コントロール・プレーンは Vespa Cloud のすべてのテナントで共有され、グローバルに同期されています。

データ・プレーンは、テナントがデプロイ済みの Vespa アプリケーションと通信できるようにします。クエリー、フィード、およびテナントがアプリケーションで設定・デプロイしたその他あらゆる種類のリクエストをサポートします。データ・プレーンは、テナント、アプリケーション、および(オプションで)サービスごとに分離されています。

Vespa Cloud は*ゾーン(Zone)*に分割されています。ゾーンは*環境(environment)*と*リージョン(region)*の組み合わせであり、*prod.aws-us-east-1c* のような名前を持ちます。ゾーンは自己完結しており、ゾーン外のサービスに対する重要な依存関係を持ちません。テナントは、アプリケーションを複数のゾーンにデプロイするよう指定することで、サービスの冗長性を実現できます。

ゾーンは*コンフィグレーション・サーバー(Configuration Server)*のクラスターによって管理されます。コンフィグレーション・サーバーはデプロイ時に*コントロール・プレーン*からアプリケーション・パッケージを受け取り、ゾーン内のローカルなデプロイ・プロセスを管理します。これには、デプロイされたアプリケーションをゾーン内で実行するために必要なノードリソースのプロビジョニングも含まれます。それとは別に、これらのリソースの保守(障害ノードの交換、OS のアップグレードなど)も担当します。

Vespa アプリケーションは*ノード(Node)*上で実行されます。ノードは*ホスト(Host)*上で実行される Linux コンテナーです。*ホスト*はコンテナーを実行する実際のマシンです。各ホストには管理プロセスがあり、どのコンテナーをホスト上で実行すべきかについてコンフィグレーション・サーバーから指示を受け取ります。起動後、コンテナーはどのアプリケーションのどの Vespa サービスを実行すべきかをコンフィグレーション・サーバーのクラスターに問い合わせます。

インデックスやドキュメントなどの顧客データを保持し、顧客の認証・認可済みクライアントからのクエリーやフィードのリクエストを受け取るのは、個々のノードです。各ノードは常に単一の Vespa アプリケーション・クラスター専用です。ホストはデフォルトでは共有されますが、アプリケーションは追加のセキュリティ分離レベルを得るために専用ホストを要求するよう指定できます。

## サービスのデプロイ

### コントロール・プレーンの認証と認可

#### コントロール・プレーン API へのアクセス

Vespa Cloud のコントロール・プレーンに対するすべての API 操作には認可が必要であり、認可されていないアクセスに対してテナントやアプリケーションの情報が提示されることはありません。ユーザーは有効な OAuth2 トークンを提示でき、API がこれを検証します。OAuth2 トークンが利用できない場合、ユーザーは代わりに API キーを使用することもできます。API キーの本来の用途はサービスの自動化(CI/CD ワークフローや GitHub Actions など)ですが、開発者が使用することもできます。

#### ロールと権限

Vespa Cloud のテナントのメンバーには、異なる権限を付与する 3 つのロールを割り当てることができます:

- **Reader:** テナントとアプリケーションのメタデータを読み取れます。これはテナントのすべてのメンバーに暗黙的に付与される最小限の権限です。
- **Developer:** アプリケーションの作成、dev および prod ゾーンへのデプロイができます。アプリケーションの開発に携わるメンバーに必要な権限です。
- **Administrator:** テナントのメンバーと、テナントの連絡先情報や課金操作などのテナント・メタデータを管理できます。

すべてのロール・メンバーシップは外部のアイデンティティ・プロバイダーに保存されます。

#### コントロール・プレーンの監査ログ

コントロール・プレーンに対するすべての操作は監査ログに永続化され、*タイムスタンプ*、*クライアント*、*プリンシパル*(ユーザー)、*HTTP メソッド*、アクセスされた*リソース*、および(特定のリクエストについては)*ペイロード*が記録されます。このデータは機微な情報を含む可能性があるため、Vespa Cloud サポートへのリクエストに応じて提供されます。

### サービスの分離

<Frame>![image](/assets/img/service-isolation.png "Service isolation")</Frame>

同じアプリケーションに属するノード同士は通信が許可されますが、異なるアプリケーションのノードはネットワーク層および認可によって分離されます。

Vespa サービス間の通信は、相互 TLS(mTLS)を使用して暗号化および認証されます。アイデンティティと証明書は、設定を検証できるインフラストラクチャ・コンポーネントによって提供されます。

#### アクセス制御とサービス・アイデンティティ

各ホストとノードは、一意の暗号学的なサービス・アイデンティティを持ちます。このアイデンティティは、HTTPS や内部のバイナリ RPC プロトコルを含む、すべてのサービス間通信で必要です。ホスト、ノード、コンフィグレーション・サーバーの各レベルには認可ルールがあり、関連するサービスだけが相互に通信し、コンフィグレーション・サーバーのような共有サービスからリソースを取得できるようになっています。

#### ノードの分離

ノードのアイデンティティは、そのノードが属するテナント、アプリケーション、インスタンスに基づきます。ホストとコンフィグレーション・サーバーが協調してノードのアイデンティティを確立します。コンフィグレーション・サーバーはどのノードを起動すべきかをホストに伝え、ホストはアイデンティティ・プロバイダーにノード用の暗号学的アイデンティティを要求します。

このノード・アイデンティティは、アプリケーション内部のすべての内部通信に使用されます。

ノードはホスト上の Linux コンテナーとして実装されます。各ノードは独自のコンテナー・ユーザー名前空間で実行され、各ノードには専用の IP アドレスが割り当てられます。

#### ホストの分離

サービス・アーキテクチャにおける最下位の物理リソースはホストです。コンフィグレーション・サーバーはホストのプロビジョニングを担当し、既知のホストを追跡し、未知のホストを拒否します。ホストはコンフィグレーション・サーバーとのみ直接通信し、ホスト同士は通信できません。

#### 設定の分離

ノードとホストはどちらも、コンフィグレーション・サーバーからアプリケーション設定を取得します。コンフィグレーション・サーバーは、ホストとノードのアイデンティティに基づいて認可ルールを適用します。認可ルールは最小権限の原則に基づきます。ホストはどのノードを実行するかだけを参照でき、ノードはアプリケーション設定にアクセスできます。

#### ネットワークの分離

サービス間のすべての通信は mTLS によって保護されます。mTLS の認可は、前述のアイデンティティに基づきます。さらに、サービス間の不正なネットワーク・アクセスを防ぐために、ネットワークレベルの分離が使用されます。ネットワーク・ルールはコンフィグレーション・サーバーで設定され、ホストによって適用されます。トポロジーの変更は数分以内に反映されます。

## 通信

### データ・プレーン

アプリケーション・エンドポイントへのすべてのアクセスは、mTLS と(オプションで)トークン認証によって保護されます。デプロイ時に、すべてのアプリケーションには、エンドポイント名に一致する SAN DNS 名を持つ証明書が提供されます。この証明書は 90 日ごとに自動的に更新されます。アプリケーションの所有者は、信頼する認証局(CA)のセットを提供する必要があり、これは mTLS でエンドポイントにアクセスするすべてのクライアントによって使用されます。

### フェデレーション

アプリケーションの所有者は、サードパーティのサービスへの呼び出しをフェデレーションできます。スケジュールされたジョブとして、またはリクエストごとに実行できます。このユースケースをサポートするために、顧客の AWS アカウント内の資格情報ストレージへのアクセスを提供しています。

## データ・ストレージ

### 保存データの暗号化

すべての顧客データは、クラウド・プロバイダーのネイティブな暗号化機能(AWS KMS または Google Cloud KMS)を使用して保存時に暗号化されます。暗号化は次の特性で実行されます:

- 暗号方式: AES-256(またはプロバイダーのデフォルトの強力な暗号)のような、強力で業界標準の暗号
- 鍵管理: 各クラウド・プロバイダーの鍵管理サービス(AWS KMS または Google Cloud KMS)内の顧客管理鍵

鍵へのアクセスは、最小権限を採用した IAM ロールとポリシーによって厳格に制御・監査されます。鍵のローテーションは、クラウド・プロバイダーによって定期的かつ自動的に管理されます。

### データの分類

Vespa Cloud が扱うすべてのデータは、それぞれ異なるポリシーが関連付けられた 2 つのクラスに分類されます。

- **内部データ(Internal data):** Vespa Cloud の運用における内部利用を目的とした情報です。顧客データを扱わないサービスからのシステムレベルのログが含まれます。内部データは、認証・認可された Vespa Cloud エンジニアリング・チームのメンバーが読み取れます。
- **機密データ(Confidential data):** 機密データとは、Vespa Cloud または Vespa Cloud の顧客にとって機微なデータです。機密データへのアクセスは、厳格な業務上の必要性(need-to-know)に基づきます。機密データへのアクセスは規制されており、ピア承認済み、期限付き、かつ監査された方法でのみ Vespa Cloud チームのメンバーに付与されます。*すべての顧客データは機密として扱われます。*

#### ログ

すべてのログは、生成されたノード上に保存されるとともに、リモートのオブジェクト・ストレージにもアーカイブされます。すべてのログの保持期間は最大 30 日です。ログへのアクセスは、前述の分類に基づきます。すべてのログは、それを生成した Vespa アプリケーションと同じ地理的リージョンに永続化されます。

アーカイブされたログは、定期的に自動ローテーションされる鍵で保存時に暗号化されます。

ノード上のログは、インデックスやドキュメント・データベースを暗号化するのと同じ仕組みで保存時に暗号化されます。

### アクセス管理

機密データへのアクセスは、個別の事案ごとにのみ付与されます。アクセスはレビューされ、期限付きで、監査されます。Vespa Cloud チームのメンバーは、レビューなしにいかなる機密データにもアクセスすることを許可されていません。

## セキュリティ対策

Vespa Cloud は、脆弱性管理、セキュアな開発プラクティス、能動的なテストを含む、多層的なセキュリティ・アプローチを採用しています。これには以下が含まれます:

## セキュリティ・テスト

Vespa Cloud は、以下を通じてセキュリティ態勢を能動的に評価しています:

- https://vespa.ai/responsible-disclosure/ に詳細が記載されている脆弱性開示プログラム。セキュリティ研究者が潜在的な脆弱性を責任を持って報告できるようにします。
- Intigriti と提携して実施する年次のハイブリッド・セキュリティ・ペネトレーションテスト・プログラム。脆弱性を能動的に特定し、対処します。

### セキュアな開発

Vespa Cloud は、すべてのコミットに対してコードレビューを必須とする CI/CD プロセスに従っています。ソースコードとサードパーティの依存関係の問題を検出するために、静的解析ツールを使用しています。さらに、セキュリティ・チームは、開発ライフサイクル全体を通じて潜在的な脆弱性を特定・対処するために、コードとインフラストラクチャの内部セキュリティ・レビューを定期的に実施しています。

### 脆弱性管理

Vespa は週に最大 4 回リリースされており、すべてのアプリケーションと依存関係を最新バージョンに保つよう努めています。OS レベルの脆弱性に対処するため、オペレーティング・システムのアップグレードは 90 日ごとにロールアウトされます。深刻なセキュリティ問題が発生した場合は、修正を可能な限り迅速に適用し、ロールアウトします。

### インシデント対応

セキュリティ・インシデントを含む、予期しない本番環境の問題はすべて、当社のインシデント管理プロセスを通じて対処されます。セキュリティ以外のインシデントはコンソールを通じて告知されます。セキュリティ・インシデントは、影響を受ける顧客に直接連絡されます。すべてのインシデントの後には、ポストモーテム(事後検証)レビューのプロセスが開始されます。セキュリティ侵害の可能性がある場合は、フォレンジック調査が実施されます。
