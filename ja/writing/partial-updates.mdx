---
title: "部分更新"
---

部分更新とは、ドキュメント内の 1 つ以上のフィールドに対する更新です。これにはすべてのインデックス構造の更新も含まれるため、部分更新の効果はクエリーで即座に観測できます。可能なさまざまな部分更新オペレーションの詳細については、[ドキュメント更新 JSON フォーマット](/ja/reference/schemas/document-json-format#update)を参照してください。

<Frame>
![attribute はインメモリのデータ構造](/assets/img/attributes-update.svg)
</Frame>

Vespa では、デフォルトですべてのフィールドを部分更新できます。フィールドは index、attribute、summary、またはこれらの組み合わせであり、index フィールドと attribute フィールドの両方をクエリーできます。

- [index](/ja/content/proton#index) フィールドと summary フィールドの場合、更新は[ドキュメントストア](/ja/content/proton#document-store)への read-modify-write を意味し、スループットが制限されます。
- ほとんどの [attribute](/ja/content/attributes) フィールドはドキュメントストアの read-modify-write を必要とせず、書き込みスループットが桁違いに向上します。以下の attribute の型は、ドキュメントストアへの read-modify-write を必要とします:
  - [array of struct](/ja/reference/schemas/schemas#array)
  - [プリミティブおよび struct の map](/ja/reference/schemas/schemas#map)
  - [predicate](/ja/reference/schemas/schemas#predicate)
  - [reference](/ja/reference/schemas/schemas#reference)

<Warning>
**重要:**

フィールド更新で可能な限り高い書き込みスループットを得るには、attribute を使用してメモリ速度で書き込みます。
</Warning>

## ユースケース

部分更新には多くのユースケースがあります。*機能面* では、ID 以外の何も必要とせずにドキュメントを更新できるため、サービングスタックの上位レイヤーのロジックが簡素化されます。*パフォーマンス面* では、部分更新により、毎秒数万件の更新というリアルタイム更新フローを持つアプリケーションが実現できます。例:

      <td>「この人は私を好き」を「私を好き」<a href="/ja/reference/querying/yql#weightedset" aria-label="セット">セット</a>に追加します — 好き/嫌い/その他の関係のセットに基づいて候補を表示します。</td>

## 書き込みパイプライン

書き込みパイプラインと Transaction Log Server (TLS) の概要については、[proton](/ja/content/proton) を参照してください。

      <td>index</td>
      <td>すべての<a href="/ja/reference/schemas/schemas#index" aria-label="インデックスされたフィールド">インデックスされたフィールド</a>では、最近の変更に対して B-tree で実装されたメモリ・インデックスが使用されます。これは定期的にディスクベースのポスティングリスト・インデックスに<a href="/ja/content/proton#memory-index-flush" aria-label="フラッシュ">フラッシュ</a>されます。ディスクベースのインデックスはその後<a href="/ja/content/proton#disk-index-fusion" aria-label="マージ">マージ</a>されます。 <br/><br/> インメモリ B-tree の更新はロックフリーで、コピーオンライト・セマンティクスを使用して実装されています。これにより、予測可能な定常状態の CPU/メモリ使用で高いパフォーマンスが得られます。この設計の動機は、安定した予測可能な読み取りレイテンシーと、CPU/メモリの小さな一時的増加を伴う、持続的で高い変更レートの要件です。これは、小さなリアルタイム・インデックスを大きなインデックスにマージすることで一時的なホットスポットを引き起こすインデックス階層とは対照的です。<br/><br/>   インデックスされたフィールドを更新する場合、ドキュメントは<a href="/ja/content/proton#document-store" aria-label="ドキュメントストア">ドキュメントストア</a>から読み取られ、フィールドが更新され、完全なドキュメントがストアに書き戻されます。この時点で、変更は検索可能になり、クライアントに ACK が返されます。このようなドキュメントのディスクアクセスを回避し、部分更新のパフォーマンスを向上させるには、<a href="/ja/content/attributes/" aria-label="attribute">attribute</a> を使用してください。詳細は<a href="/ja/performance/sizing-feeding/" aria-label="フィード・パフォーマンス">フィード・パフォーマンス</a>を参照してください。</td>
    </tr>
    <tr>
      <td>attribute</td>
      <td>attribute フィールドはインメモリのフィールドです。<a href="/ja/content/attributes/" aria-label="attribute">attribute</a> を参照してください。これにより、更新は低コストで高速になります。attribute のデータは定期的にフラッシュされます。<a href="/ja/content/proton#attribute-flush" aria-label="attribute-flush">attribute-flush</a> を参照してください。オペレーションは Transaction Log Service (TLS) に永続化されることに注意してください。まれに電源障害や異常なシャットダウンが発生した場合、オペレーションは TLS から同期されます。<br/><br/>   フィールドをまたぐ更新にはトランザクションのサポートがないことに注意してください。高いレートをサポートするため、スレッド間の調整はありません - 例: <br/><br/>  <code>{`{`}</code><br/> <code>{`"update" : "id:namespace:doctype::1",`}</code><br/> <code>{`"fields" : {`}</code> <br/><code>{`"firstName" : { "assign" : "John" },`}</code><br/> <code>{`"lastName"  : { "assign" : "Smith" }`}</code><br/> <code>{`}`}</code><br/> <code>{`}`}</code><br/><br/>  上記では、attribute の &#42;firstName&#42; と &#42;lastName&#42; はクライアントからの同じオペレーションで更新されますが、検索コア内での更新は非トランザクショナルです。これはスループットと一貫性のトレードオフであり、多くのアプリケーションにとって実用上の制限にならずに、極めて高い更新レートを可能にします。詳細は <a href="/ja/content/attributes/" aria-label="attribute">attribute</a> を参照してください。<br/><br/>  <a href="/ja/querying/searching-multivalue-fields" aria-label="multivalue">multivalue</a> の attribute(配列、マップ、セット、テンソル)の更新は、現在の値を読み取り、更新を行い、書き戻すことを意味します:<br/><br/>  • <a href="/ja/reference/schemas/schemas#array" aria-label="プリミティブ型の配列">プリミティブ型の配列</a>、<a href="/ja/reference/schemas/schemas#weightedset" aria-label="weightedset">weightedset</a>、<a href="/ja/reference/schemas/schemas#tensor" aria-label="テンソル">テンソル</a>はメモリ内にあるため高速です。パフォーマンスに関する考慮事項は <a href="/ja/content/attributes/#data-structures" aria-label="attribute のデータ構造">attribute のデータ構造</a>を参照してください。 <br/><br/> • attribute フィールドが <a href="/ja/reference/schemas/schemas#array" aria-label="array of struct">array of struct</a> または <a href="/ja/reference/schemas/schemas#map" aria-label="map">map</a> の場合、値はドキュメントストアに書き込まれるため、更新レートは低くなります - <a href="https://github.com/vespa-engine/vespa/issues/10892" aria-label="#10892 updates of array of map/struct">#10892 updates of array of map/struct</a> を参照してください。 <br/><br/> <a href="/ja/performance/feature-tuning#when-to-use-fast-search-for-attribute-fields" aria-label="fast-search">fast-search</a> を使用してインメモリ B-tree ポスティングリスト構造を追加することで、クエリーの実行時間を改善できます。これにより、値とポスティングリストの両方が更新されるため更新時の作業が増え、その結果、更新スループットが低下します。<br/><br/>  レプリカを持つすべてのノードで attribute がメモリ内にあることを保証する方法(searchable-copies または fast-access)については、<a href="/ja/performance/sizing-feeding/#attribute-store" aria-label="sizing-feeding">sizing-feeding</a> を参照してください。</td>
    </tr>
    <tr>

    </tr>
  </tbody>
</table>
