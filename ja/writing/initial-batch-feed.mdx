Vespa アプリケーションを作成する際に最初に行うことの一つは、Vespa Cloud にデプロイしてすべてのデータをバッチフィードすることです。ここでは、スキーマファイルの最初のバージョンを作成し、一連の Vespa フィードファイルを生成済みであることを前提とします。その際、次のような疑問に直面するでしょう:

- インデックスを保持するコンテントノードに適したリソース構成は何か?
- ノードのリソース構成を変更すると何が起こるのか?
- 完全なインデックスを保持するには何ノード必要か?
- バッチフィード時にオートスケーリングを使うのは良い考えか?
- フィードのボトルネックが何かをどうやって知るのか?
- コンテナー・クラスターとコンテント・クラスターの違いは何か?

続行する前に、[Vespa 概要](/ja/learn/overview)の導入セクションを確認し、*コンテナー*・クラスターと*コンテント*・クラスターの違いを理解してください。

まず注目すべき点は、ノードリソース(すなわちインスタンスタイプ)の変更が[自動化されている](/ja/performance/node-resources)ことです。これにより、まずフィードを開始し、観察し、変更し、繰り返すという進め方が容易になります。

次に、ノードリソースの変更が適用されるまでには時間がかかります。データとインデックスが新しい構成のノードに移行されるためです — 詳細は後述します。これはつまり、下記の 1% ステップのように、デプロイされているデータが少なくノード数も少ない段階の方が変更しやすいということです。したがって、ディスク/メモリーのバランスを適切にするために 1〜2 回の反復を行ってください。

ノードリソースの構成がほぼ適切になったら、より多くのデータをフィードします。これには時間がかかる可能性があります。ボトルネックがコンテント・クラスターのノードであることを確認してください(少なくとも 1 つのスレッドが 100% になっているはずです)。フィードエンドポイントを持つ*コンテナー*・クラスターが CPU 100% になっていないことを確認するのがよく、そうなっている場合はノードを追加してください。[詳細](/ja/performance/sizing-feeding#feed-testing)。

最後に、このフェーズでは[オートスケーリング](/ja/operations/autoscaling)を使わないことを推奨します。オートスケーリングは漸進的な変化には優れていますが、*この*ケースではゼロからフルまでフィードします。ベストプラクティスは、小さめのフィードバッチに基づいておおよその見積もりができたら、見積もりより 50〜100% 多いコンテントノード容量を割り当てて、フルまでフィードすることです。これにより、実時間が短縮され、[フィードブロック](/ja/writing/feed-block)による遅延もなくなり、プロセスが高速化されます。初期フィードが完了したら、過剰な容量を評価してノード数を削減するのは簡単です。

## まとめ

インデックスをブートストラップする際には、ノードのリソース構成とノード数を考慮する必要があります。戦略は反復することです:

<Frame>![Vespa クラスターを段階的に拡張する](/assets/img/index-bootstrap.svg)</Frame>

1. 小さめのデータセットをフィードする
2. 評価する
3. 新しいノード数/ノードリソース構成をデプロイする
4. データ移行の完了を待つ
5. 評価する

この作業中は、クラスターの使用率が **50% を超えない**ようにしてください — これにより、後でインデックスを拡大/縮小したり、自動再インデックスを使ってスキーマ構成を容易に変更したりするための余裕が生まれます。ブートストラップ後にリソースを縮小するのは簡単であり、クラスターを制限内に保つことで多くの時間を節約できます — そのため最大 50% です。

## 準備

インデックスのブートストラップでは、コンテントノードのリソース構成に範囲指定を使わないでください。オートスケーリングがこのステップでの評価を妨げるためです。以下は良い出発点です。**[2,3] のような範囲指定がないことを確認してください**:

```xml
<nodes count="2">
    <resources vcpu="2.0" memory="8Gb" disk="50Gb" />
</nodes>
```

コンテント・クラスターの使用率を評価するには、Vespa Cloud Console の「Metrics」ビュー、またはコンテントノードの[メトリクス](/ja/operations/monitoring)を使用します — 例:

```sh
$ curl \
  --cert data-plane-public-cert.pem \
  --key  data-plane-private-key.pem \
  https://ab1f1234.b68a8765.z.vespa-app.cloud/prometheus/v1/values | \
  egrep 'disk.util|mem.util' | egrep 'clusterId="content/'
```

上記のメトリクスが確認できるようになれば、インデックスをブートストラップする準備は完了です。

## トラブルシューティング

[準備](#preparations)の例のように、ドキュメントのフィードとアクセスができることを確認してください。証明書/キーの使い方については[セキュリティガイド](/ja/security/guide)を参照してください。

フィードしすぎると[フィードブロック](/ja/writing/feed-block)状態になります。services.xml で満杯になったコンテント・クラスターにノードを追加し、データ移行が完了するまで待ってください — つまり、`vds.idealstate.merge_bucket.pending.average` メトリクスがゼロになるまで待ちます。データ移行がより速いため、ノードリソースを増やすよりノードを追加する方がよいです。
