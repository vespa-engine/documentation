理想的には、指定したタイムアウト内に Vespa クラスターにインデックスされたすべてのデータをクエリーしたいところですが、それが常に可能とは限りません:

- キャパシティの制約によりシステムが過負荷になり、クエリーがリソース待ちのキューに滞留してタイムアウト内に完了しない場合があります。
- 複雑なクエリーの実行に指定したタイムアウトより長い時間がかかる場合や、クエリーの複雑さと利用可能なリソース・キャパシティに対してタイムアウトが低すぎる場合があります。

このドキュメントでは、指定したタイムアウト内にクエリーを完了できない場合に、Vespa がどのように結果セットをグレースフルにデグレードできるかを説明します。

定義:

- **カバレッジ (Coverage)**: インデックスされたドキュメントのうち、クエリーによって評価されたドキュメントの割合。理想的なカバレッジは 100% です。
- **タイムアウト (Timeout)**: クエリーの実行が許される合計時間。[timeout](/ja/reference/api/query#timeout) を参照してください(デフォルトは 500 ms)。Vespa は分散システムであり、クエリーの実行には複数のコンポーネントが関与します。
- **ソフト・タイムアウト (Soft Timeout)**: ソフト・タイムアウトは、クエリーがタイムアウトに近づいている場合に、カバレッジが 100% 未満かつ 0% より大きくなることを許容します。ソフト・タイムアウトは*早期終了 (early termination)* の手法とみなすこともでき、デフォルトで有効です。[ranking.softtimeout.enable](/ja/reference/api/query#ranking.softtimeout.enable) を参照してください。

## 検出

デフォルトの JSON レンダラー・テンプレートは、常にルート要素の下に *coverage* 要素をレンダリングします。クエリーの実行が何らかの形でデグレードした場合、この要素には *degraded* 要素が含まれ、*coverage* フィールドは 100 未満になります。クエリー・タイムアウト 200 ms、*ranking.softtimeout.enable=true* でのリクエスト例:

```bash
/search/?searchChain=vespa&yql=select * from sources * where foo contains bar&presentation.format=json&timeout=200ms&ranking.softtimeout.enable=true
```

```json
{
    "root": {
        "coverage": {
            "coverage": 99,
            "degraded": {
                "adaptive-timeout": false,
                "match-phase": false,
                "non-ideal-state": false,
                "timeout": true
            },
            "documents": 167006201,
            "full": false,
            "nodes": 11,
            "results": 1,
            "resultsFull": 0
        },
        "fields": {
            "totalCount": 16469732
        }
    }
}
```

結果は 200 ms で返されましたが、カバレッジが 100 未満であるため、クエリーはデグレードしています。このケースでは、x 件のドキュメントのうち 167,006,201 件がクエリーされ、16,469,732 件のドキュメントが、デフォルトのランク・プロファイルの first-phase ランキング式を使用してマッチおよびランキングされました。

*degraded* フィールドには、結果のカバレッジが 100 未満になった理由を説明する以下のフィールドが含まれます:

- *adaptive-timeout* は、[アダプティブ・ノード・タイムアウト](#adaptive-node-timeout)が有効になっていて、1 つ以上のノードがタイムアウト内に結果をまったく生成できなかった場合に true になります。これは、ハードウェアが劣化したノードがクラスター内の他のノードより遅くなることで発生する可能性があります。
- *match-phase* は、ランク・プロファイルに[マッチ・フェーズによるランキング・デグラデーション](/ja/reference/schemas/schemas#match-phase)が定義されている場合に true になります。match-phase は、タイムアウト内にどのドキュメントをランキングするかを制御するために使用できます。
- *non-ideal-state* は、システムが[理想状態 (ideal state)](/ja/content/idealstate) にない場合に true になります。このケースは極めてまれです。
- *timeout* は、ソフト・タイムアウトが有効で、クエリー・タイムアウト内にすべてのドキュメントをマッチおよびランキングできなかった場合に true になります。

デグレードの理由は相互排他ではないことに注意してください。この例では、ソフト・タイムアウトがトリガーされ、時間の割り当てを使い切る前にドキュメントの 99% しかクエリーされませんでした。クエリーの実行に関与する 11 ノードのうち 10 ノードが正常でソフト・タイムアウトをトリガーして結果を返した一方、最後の 1 ノードが不良状態(ハードウェアの問題など)で結果をまったく生成できなかった、というシナリオも考えられます。その場合は *timeout* と *adaptive-timeout* の両方が true になります。

[Searcher](/ja/applications/searchers) で Result を処理する際には、カバレッジ情報をプログラムから取得できます:

```java
@Override
    public Result search(Query query, Execution execution) {
        Result result = execution.search(query);
        Coverage  coverage = result.getCoverage(false);
        if (coverage != null && coverage.isDegraded()) {
            logger.warning("Got a degraded result for query " + query + " : " +
                            coverage.getResultPercentage() + "% was searched");
        }
        return result;
    }
```

## アダプティブ・ノード・タイムアウト

[フラット](/ja/performance/sizing-search#data-distribution)なデータ分散を持つコンテント・クラスターでは、クエリーのパフォーマンスは最も遅いノードより良くなることはありません。最悪のシナリオは、クラスター内のノードが根本的なハードウェアの問題を抱えている場合に発生します。そのような状態のノードは、ヘルス・チェックや ping には応答するものの、タイムアウト内にクエリーを処理できないことがあります。

[アダプティブ・カバレッジ](/ja/reference/applications/services/content#coverage)を使用すると、遅いノードを無視できます。以下の例は、アダプティブ・タイムアウトの使い方を示しています。この例では 10 ノードのフラットなコンテント・クラスターを使用しています:

```xml
<content id="content" version="1.0">
    <search>
        <coverage>
            <minimum>0.9</minimum>
            <min-wait-after-coverage-factor>0.2</min-wait-after-coverage-factor>
            <max-wait-after-coverage-factor>0.3</max-wait-after-coverage-factor>
        </coverage>
    </search>
</content>
```
- Vespa のデフォルトのタイムアウト 500ms を使用すると仮定すると、ステートレス・コンテナーはクエリーを 10 ノードすべてに並列にディスパッチし、10 ノードのうち 9 ノードが応答するまで待ちます(最小カバレッジ 0.9)。
- 9 ノードが 100ms で応答できたと仮定すると、残り 400ms あります。ディスパッチャーは最後のノードの応答を最小 80 ms(0.2\*400ms)待ち、最大 120 ms(0.3\*400ms)で最も遅いノードを待つのをあきらめて結果を返します。
- min wait 設定は、ノードごとの応答時間のばらつきをある程度許容するために使用します。min wait を 0 にすると、最小カバレッジに達した時点(10 ノード中 9 ノードが応答)でクエリーは即座に返ります。min を 0 より大きい値にすると、あるノードが他のノードよりわずかに遅くても、全体として 100% のカバレッジに到達できるようになります。

## マッチ・フェーズによるデグラデーション

[match-phase リファレンス](/ja/reference/schemas/schemas#match-phase)を参照してください。マッチ・フェーズの具体的な使用例は[実践的パフォーマンス・ガイド](/ja/performance/practical-search-performance-guide#match-phase-limit---early-termination)にあります。

match-phase は、何らかの形でドキュメントの品質を測定する `attribute`(人気度、クリックスルー率、ページランク、広告入札額、価格、テキスト品質)を指定することで機能します。加えて、コンテント・ノード全体での合計ヒット数として、アプリケーションにとって「十分すぎる」件数を指定する `total.max-hits` 値を指定します。そして、クエリーに対して妥当な量のヒットを収集した後に推定が行われ、推定値がそのノードに割り当てられた `total-max-hits` 値の取り分より大きい場合、クエリーに追加の制限が加えられ、最も品質の高いドキュメントだけがヒットになるようにします。

事実上、これは実際にクエリーされるドキュメントを、コーパス全体のサブセットである最高品質のドキュメントに制限します。このサブセットのサイズは、クエリーがそのノードの `total-max-hits` の取り分のヒットを生むと推定されるように計算されます。推定を行うためにいくつかの(低品質な)ヒットがすでに収集されているため、実際に返されるヒット数は通常 total-max-hits より多くなります。しかし、ドキュメントの分布は完全に滑らかではないため、設定した `total-max-hits` より少ないヒットしか返らないこともあります。

match-phase でヒットを制限することは、[集約/グルーピング](/ja/querying/grouping)と total-hit-count にも影響することに注意してください。実際に制限を行うため、クエリーのヒット数は少なくなります。また、同様にヒットを制限する [WAND オペレーター](/ja/ranking/wand)とこの機能を併用することはあまり意味がありません。両者は同じように動作するため、互いに干渉して予測不能な結果を引き起こす可能性があります。以下のグラフは、100 000 ドキュメントのコーパスで、`total-max-hits` をノードあたり 10 000 に設定した場合の、可能なヒット数と実際のヒット数を示しています。このコーパスは合成された(わずかにランダム化された)データセットであり、実際にはグラフはこれほど滑らかにはなりません:

<Frame>![可能なヒット数と実際のヒット数のプロット](/assets/img/relevance/match-phase-max-hits.png)</Frame>

ランク・プロファイルごとに *content.proton.documentdb.matching.rank\_profile.limited\_queries* というコンテント・ノードのメトリクスがあり、これらの設定によって実際に影響を受けたクエリーの数を確認できます。対応する *content.proton.documentdb.matching.rank\_profile.queries* メトリクスと比較して割合を測定してください。

### マッチ・フェーズのトレードオフ

*match-phase* を使用する前に考慮すべき重要な点がいくつかあります。通常のクエリーのシナリオでは、レイテンシーはクエリーがマッチするヒット数に正比例します。少数のドキュメントにマッチするクエリーはレイテンシーが低く、多数のドキュメントにマッチするクエリーはレイテンシーが高くなります。match-phase は**逆**の効果を持ちます。つまり、マッチするドキュメントが少ないクエリーがある場合、match-phase はそれらのクエリーを大幅に遅くする可能性があります。実際には、フィルターなしでクエリーを実行する方が速いこともあります。

例: *created\_time* というドキュメント attribute を持つコーパスがあるとします。すべてのクエリーで最新のコンテンツを表面化させたいので、*created\_time* に対して match-phase を有効にします。ここまでは順調で、優れたレイテンシーが得られ、常にトップ k のヒットが得られます。問題はフィルターを導入したときに起こり得ます。過去 1 日のドキュメントだけが欲しいというフィルターがある場合、match-phase は非最適になり、場合によっては match-phase なしで実行するよりはるかに悪くなることがあります。

設計上、Vespa はクエリーの潜在的なマッチを内部 documentid の順に評価します。つまり、ノード上でインデックスされた順にドキュメントの評価を開始し、ほとんどのユースケースでは最も古いドキュメントが最初になります。フィルターがなければ、すべてのドキュメントが潜在的なマッチであり、match-phase は最適化の方法をすぐに見つけ出せます。一方、フィルターがある場合、アルゴリズムは潜在的なマッチ(1 日前のコーパス)に到達する前にほぼコーパス全体を評価する必要があり、アルゴリズムの実装方法のために大量の不要な処理を行うことになり、フィルターなしでクエリーを実行するより桁違いに高いレイテンシーになることがあります。

もう 1 つ言及すべき重要な点は、match-phase を有効にしてクエリーを実行すると、報告される total-hits が異なることです。これは、match-phase が推定された「仮想的な」コーパス上で動作するためで、これは実際のコーパス全体よりもはるかに少ないヒットしか持たない場合があります。

正しく使用すれば match-phase は救世主になり得ますが、何でも解決してくれる単純な特効薬ではありません。match-phase の使用については必ずテストと測定を行い、結果が期待どおりでない場合は Vespa チームにお問い合わせください。
