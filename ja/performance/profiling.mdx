プロファイリング時のガイドライン:

- 何をプロファイリングするのかを明確に定義します。
- プロファイリング対象を代表する負荷を見つけます。他のコンポーネントに負荷がかかるとノイズが多くなるため、これは多くの場合最も難しい部分です。
- プロファイリング対象のコンポーネントに負荷をかけることを妨げる他のボトルネックがないことを確認します。ネットワークやディスクが制限要因である場合、CPUプロファイリングを行う意味はほとんどありません。
- 可能であれば、プロファイリング対象そのものに負荷をかけるベンチマーク・プログラムのような特別なユニット・テストを書きます。
- システムがマルチスレッドの場合:
	- 常にまずシングルスレッドでプロファイリングします - これがスケーリング・テストのベースラインになります。期待どおりの数のコアが利用されていることを確認します。
	- スケーリングを、少なくともコア数の2倍まで、またはスループットが低下するまで、徐々に増やします。

[VespaでのValgrindの使用](/ja/performance/valgrind)も参照してください。

## perfを使ったCPUプロファイリング

リモート・クラスターでCPU使用率をデバッグしたり、パフォーマンスをデバッグしたりする際に、パフォーマンス・プロファイルのスナップショットを取得すると役立つことがあります。`perf` を使用するには、[vespa-proton-bin](/ja/content/proton) プロセスのpidを見つけます。これは [vespa-sentinel-cmd](/ja/reference/operations/self-managed/tools#vespa-sentinel-cmd) または *top/ps* で取得できます。記録します:

```bash
$ sudo perf record -g --pid=<pid-of-proton-process> sleep 60
```

パフォーマンス・プロファイルのレポートを表示します:

```text
$ sudo perf report
```

Linuxカーネルのシンボル情報を取得するために、カーネルのデバッグ情報をインストールしておくと役立つことがあります:

```bash
$ sudo yum install --enablerepo=base-debuginfo kernel-debuginfo-$(uname -r)
```

*kernel-debuginfo* は *kernel* パッケージとある程度同じバージョンのものを入手することが重要です。

### コンテナーの権限

非特権のDockerコンテナーをデバッグする場合、pid空間を共有する特権コンテナーの内部から `perf` コマンドを実行できます:

```bash
$ CONTAINER=host002-09
$ sudo docker run -ti --rm --privileged --pid container:$CONTAINER \
  --entrypoint bash $(sudo docker ps --filter name=$CONTAINER --format "{{.Image}}")
```

これは、デバッグ対象のコンテナーと同じDockerイメージを使用して、pid名前空間を共有する特権コンテナーを起動します。この特権コンテナー内で `perf record ...` を実行します。

## クエリー・コンテナーのプロファイリング

このセクションでは、パフォーマンスのボトルネック(ロック競合であれ、CPU集約的なアルゴリズムであれ)を特定するために、カスタムSearcherのプロファイリングを可能にするコンテナーの設定方法を説明します。

### コンテナーにYourKitプロファイラーをインストールする

YourKitは、Javaコードのホットスポットを見つけるための優れたシンプルなツールです。サンプリングとトレーシングの両方をサポートしています。多くの場合、両方のモードを使用する必要があります。トレーシングは、メソッドが何回、どこから呼び出されたかについて正確です。これを使って、実際には同じものを複数の場所から計算していないか、全体として必要以上の処理をしていないかを分析できます。ただし、キャッシュ・ミスの影響、特にアトミック操作や同期のコストは見えなくなります。

データ・センターにあるインストール環境をプロファイリングしたいとします。できればローカル・デスクトップ上で快適なUIを動かしながら行いたいところです。これはほんの数ステップで実現できます:
- YourKitをインストールします
- *services.xml* を変更します:

    ```xml
    <nodes>
        <jvm options="-agentlib:yjpagent" />
	...
	</nodes>
    ```
    詳細は [JVMチューニング](/ja/performance/container-tuning)を参照してください。freezedetectorを無効にすると、プロファイリング中にコンテナーがシャットダウンするのを防げます。
- アプリケーションを再デプロイします:

    ```bash
    $ vespa deploy appdir
    ```
- コンテナーを実行しているノードでVespaを再起動します


*$VESPA\_HOME/logs/vespa.log* でエラーを確認します。これでプロファイリングを実行する準備ができました。あとはデスクトップにUIをインストールするだけです。

### デスクトップにYourKit UIをインストールする

サーバー側のプロファイリング準備は整ったので、次はデスクトップにYourKitプロファイラーをインストールします。[YourKit](https://www.yourkit.com/) から、使用しているOSに合ったディストリビューションをダウンロードします。*ライセンス・サーバー* の設定を含め、インストール手順に従ってください。

<Note>
**注:** 

デフォルトでは、YourKitエージェントはポート10001で動作します。Vespaがデスクトップから直接到達できないホストで動作している場合は、SSHトンネルをセットアップすることで回避できます:
</Note>

```bash
$ ssh -L 1080:$hostname:10001
```

ここで *$hostname* は、YourKitエージェント・プロファイラー付きのコンテナーを実行しているノードです。localhost(デスクトップ)のポート1080へのすべてのトラフィックは、ポート10001で動作しているリモート・アプリケーションに転送されます。

### YourKitの使用

これでアプリケーションをプロファイリングする準備が整いました。(コンテナー・インスタンスに対して現実的な負荷をかける必要があります。[Vespaベンチマーク・ガイド](/ja/performance/benchmarking)を参照してください)負荷シミュレーションを開始したら、プロファイリング・セッションを開始できます。ローカルにインストールしたYourKitアプリケーションを開き、*Monitor Remote Applications => Connect to remote application* を選択します。*localhost:1080* を入力してConnectを押します。プロファイリング画面に *Remote application "Server" (PID XXXXX) is being profiled at localhost:1080* と表示されるはずです。
