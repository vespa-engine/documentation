Vespa には、可用性とのトレードオフを取りながら、コスト、クエリー・レイテンシー、スループットを同時に最適化する機能があります。このガイドでは、例を用いてさまざまなトポロジーを紹介し、最も関連性の高いトレードオフに焦点を当てるとともに、ノードの停止やトポロジーの変更といった運用イベントについて説明します。

グループ化トポロジーを使用するユースケースは、[エラスティシティ](/ja/content/elasticity#grouped-distribution)ガイドに記載されています。例えば、クエリー・レイテンシーによってノードあたりの最大ドキュメント数、ひいてはグループに必要なノード数が決まる場合があります。ドキュメント 100 万件でクエリー・レイテンシーが許容上限に達するのであれば、600 万件のインデックスにはグループあたり 6 ノードが必要です。

<Note>
**注記:** 

Vespa Cloud は 1 レベルのグループ化トポロジーをサポートしています。したがって、グループのグループはサポートされていません。
</Note>

コンテント・ノードはステートフルであり、クエリー対象となるドキュメントのレプリカを保持します。コンテント・ノードはさまざまなトポロジーでデプロイできます。6 ノードを使用した例:

<Frame>![4 つの異なるトポロジー](/assets/img/grouped-topology.svg)</Frame>

Vespa Cloud では、少なくとも 2 の冗長性が必要です。このガイドでは、[min-redundancy](/ja/reference/applications/services/content#min-redundancy) として構成される冗長性が n=3 に設定されていると仮定します。冗長性はデータの可用性・重要度とコストの関数であり、アプリケーションごとに異なります。

冗長性は、ノードにドキュメントのレプリカを保存するためのものです。すべてのレプリカが検索可能なわけではありません。サブデータベースの詳細な理解については [Proton](/ja/content/proton) を参照してください。

## 標準構成: 1x6

ほとんどのアプリケーションは、特定のユースケースに最適化するまでは、グループ化トポロジーなしで構成すべきです。上記リンクのエラスティシティ・ガイドを参照してください。したがって、次のような*フラット*な構成から始めます:

<Columns cols={2}>
<Frame>![1x6](/assets/img/1x6.svg)</Frame>

```xml
<min-redundancy>3</min-redundancy>
<nodes count="6">
    <resources .../>
</nodes>
```
</Columns>

これは、コーパスが 6 ノードに分散され、各ノードでドキュメントの 17% がクエリーでアクティブになることを意味します。このガイドでは、このトポロジーを 1x6 と呼びます。

これは、通常 n=1 の単一ノードで行われるレイテンシーのベンチマークの際に覚えておくべき重要な点です。n=3 の 6 ノードシステムでは、冗長レプリカのためにより多くのメモリとディスク領域が使用されます。これについては後で詳しく説明します。

このトポロジーはデフォルトのトポロジーであり、非常にうまく機能します:

- ノードが停止した場合（予期しない停止、またはソフトウェア・アップグレードなどの計画的な停止）、クエリーを処理する他の 5 つのノードがあり、5 つのノードはそれぞれ 1/5 大きいコーパスを処理することになります
- 容量の追加、例えば 17% の追加は、ノード数を 7 に増やすことで行います

<Note>
**注記:** 

このトポロジーはデフォルトであり、ほとんどのアプリケーションはここから始めるべきです。
</Note>

## 3 行トポロジー: 3x2

一部のアプリケーション、特に極めて低レイテンシーのサービングを行うアプリケーションでは、クエリーがクエリー実行の静的な部分に支配されていることがわかります。これは、クエリー対象のドキュメント数を減らしてもレイテンシーが下がらないことを意味します。

その裏返しとして、ドキュメント数を増やしてもレイテンシーはあまり増加しません。3x2 を考えてみましょう:

<Columns cols={2}>
<Frame>![3x2](/assets/img/3x2.svg)</Frame>

```xml
<min-redundancy>3</min-redundancy>
<nodes count="6" groups="3">
    <resources .../>
</nodes>
```
</Columns>

ここでは、n=3 で 3 つのグループを構成しています。これは、同じ行内のもう一方のノードはレプリカを持たないことを意味します。冗長性は行間で確保されます。

各ノードは（1x6 と比較して）クエリーあたり 3 倍のドキュメント数を持つようになりますが、各行が全ドキュメント・コーパスを保持するため、クエリー容量も 3 倍になります。これはクエリー・スループットをスケールさせる優れた方法となり得ます。注記:

- 計画的・非計画的なノード停止時には、行全体がクエリー・サービングから除外されます。残りは 2 行、合計 4 ノードです。したがって、クエリー容量は 67% に低下します。
- フィードの要件は 1x6 と同じです。すべてのドキュメント書き込みは 3 つのレプリカに書き込まれます。
- ドキュメントの整合性回復（リコンシリエーション）はトポロジーに依存しません。ノード停止後のノード再構築時には、すべてのノードのレプリカが使用されます。

## 6 行トポロジー: 6x1

ノードあたりのドキュメント数を最大化するのは、クエリー・レイテンシーが要件の範囲内に収まっており、行内のノード数が少ないほどランキングで候補を計算するノードが少なくなるため、全体の作業量が少なくなるケースに適しています。極端なケースは、すべてのドキュメントを単一ノードに置き、6 グループでレプリケートする構成です。これは、高いスループットとシンプルさから、かなり一般的な構成です:

<Columns cols={2}>
<Frame>![6x1](/assets/img/6x1.svg)</Frame>

```xml
<min-redundancy>6</min-redundancy>
<nodes count="6" groups="6">
    <resources .../>
</nodes>
```
</Columns>

注記:

- フィードの*総作業量*は多くなります。n=6 では 6 つのレプリカが書き込まれます（上記の 3 つと比較して）。以下の[フィード・レイテンシー](#feeding)の注記を参照してください。

## 2 行トポロジー: 2x3

この場合、アプリケーションの冗長性は 2 です。これは行数と同じでなければなりません:

<Columns cols={2}>
<Frame>![2x3](/assets/img/2x3.svg)</Frame>

```xml
<min-redundancy>2</min-redundancy>
<nodes count="6" groups="2">
    <resources .../>
</nodes>
```
</Columns>

デフォルトでは、ノードが停止すると（Vespa のアップグレードのために毎日停止します）、行全体がサービングを停止します。これは容量の 50% が失われることを意味します。

このトポロジーを使用する場合は、[min-active-docs-coverage](/ja/reference/applications/services/content#min-active-docs-coverage) をデフォルトの 97% より低い値に設定することを推奨します。例えば、グループに 3 ノードある場合、各ノードは 33.3% であり、1 ノードの喪失でカバレッジは 66.7% になります。min-active-docs-coverage を 65 に設定すると、グループ（行）がサービングを停止するには*複数のノード*が停止しなければならなくなります。これは通常、このトポロジーで望まれる動作です。

## トポロジーの移行

Vespa Cloud がドキュメントを自動的に移行するため、あるトポロジーから別のトポロジーへの移行は簡単です:

- すべての行は同じノード数でなければなりません。つまり、`count / groups` は整数でなければなりません。
- トポロジーを変更する際、Vespa Cloud はカバレッジの喪失が生じないように、必要に応じて新しいノードをプロビジョニングします。したがって、移行フェーズ中にノード数が増加するのは正常であり、余分なノードはデータ移行後にプロビジョニング解除されます。
- したがって、トポロジー移行は安全な操作であり、最良の価格性能比に向けた最適化を容易にします。

## フィード

ドキュメントは [`<document-api>`](/ja/reference/api/document-v1#configuration) エンドポイントを使用して Vespa Cloud にフィードされます。これは、1 つの Vespa コンテナー・ノードがドキュメントの書き込みをすべてのレプリカに並行して転送することを意味します。すべてのグループがレプリカを持つため、この並行性により、理論的にはグループを追加してもフィードの*レイテンシー*は増加しません。しかし、実際には増加します。ノードが増えるほどレイテンシーのばらつきが大きくなり、最も遅いノードが最終的なレイテンシーを決定するためです。
