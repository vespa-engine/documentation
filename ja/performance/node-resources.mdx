title: "ノードリソース"

このガイドでは、ノードリソース設定の以下の側面を扱います:

1. リソースの各次元の独立した設定
2. 自動化されたリソース提案の利用
3. 迅速な最適化サイクルのためのデプロイメントの自動化
4. 長期にわたって最適なパフォーマンスを維持するための自動インスタンスタイプ移行


## 独立したリソース次元
Vespa Cloud では、ノードの `resources` は次のように設定します:

```xml
<nodes count="8">
    <resources vcpu="4" memory="16Gb" disk="300Gb"/>
</nodes>
```

これにより、各次元を独立して指定できます。例えば、他のすべての次元を一定に保ったまま、CPU だけを 2 倍にすることができます。

アプリケーションの各部分には異なる最適点があるため、これは価格とパフォーマンスの最適なポイントに向けてチューニングする際に重要です。例えば、アプリケーションの商品検索クラスターは商品レコメンデーションよりも CPU バウンドになりやすく、後者は相対的により多くのメモリを必要とするかもしれません。

<Note>
**Note:** 

上記は簡略化した例です。GPU の使用や CPU アーキテクチャーなど、さらに多くのリソース次元が利用可能です。
</Note>

したがって、コスト／パフォーマンスの最適化は簡単です。単純化すると、アプリケーションは CPU、ディスク、またはメモリのいずれかがボトルネックになり得ます。一般的な経験則は、最も高価なコンポーネント（多くの場合 CPU）がボトルネックになるようにすることです。すべての次元については、ノードリソースの[リファレンス](/ja/reference/applications/services/services#resources)を参照してください。

## リソース提案

アプリケーションは時間とともに変化します:

- データサイズの増加
- クエリーレートの増加
- 書き込みレートの増加
- 新しいフィールドやバイナリ化された埋め込みなどのスキーマ変更

最適なノード構成を見つけるのは反復的なプロセスです。Vespa Console の Resource Suggestions ビューを使用すると簡単になります:

<Frame>![リソース提案](/assets/img/resource-suggestions-1.png)</Frame>

Vespa Cloud は使用量を長期的に追跡し、先週の負荷に基づいてノード構成と[トポロジー](/ja/performance/topology-and-resizing)の変更を提案します。上の例では、CPU に対してメモリを 2 倍にする提案が確認できます。

これにより、*何を*設定すべきかが分かりやすくなり、レイテンシーや関連性の品質などの他のビジネスメトリクスを観察しながら、個別の変更を段階的に展開できます。

## リソース設定の自動デプロイメント

リソース設定は[アプリケーション・パッケージ](/ja/basics/applications)の一部です。クラスターのリソースを変更するには、アプリケーション・パッケージの新しいバージョンを Vespa Cloud にデプロイし、変更が適用されるのを待ちます:

<Steps>
<Step>
ステートレスな Vespa Container クラスターへの変更は、クラウドプロバイダーのプロビジョニングのレイテンシーに依存しますが、ほぼ即時に反映されます。
</Step>
<Step>
（ドキュメントのインデックスが保存される）ステートフルな Vespa Content クラスターへの変更は、負荷を均一にするためにデータが再分散されるため、より時間がかかります:
	1. ノードの `count` を変更すると、既存のクラスターが変更されます。
	2. `resources` の設定を変更すると、並行クラスターがセットアップされ、そこにデータが移行されます。移動するデータが多くなるため、これは一般的にノード数の変更よりも時間がかかります。
</Step>
</Steps>

<Warning>
**Important:** 

Vespa Cloud はオンラインでの変更を前提に設計されています。上記のすべての変更は、稼働中のシステムに対して、中断ゼロまたは最小限の中断でデプロイできます。詳細は[コンテント・クラスターのエラスティシティ](/ja/content/elasticity)を参照してください。
</Warning>

したがって、リソース仕様への変更は完全に自動化されています。最適点に到達する最も速い方法は、最初に十分なキャパシティでデプロイし、コストを削減するために日次で再チューニングを行うことです。

Vespa Cloud は、このフェーズで関連するメトリクスを備えたパフォーマンス・ダッシュボードを提供します:

<Frame>![パフォーマンス・ダッシュボード](/assets/img/dashboard.png)</Frame>

最終的に、長時間のベンチマーク作業を行うことなく、アプリケーションは最適な価格／パフォーマンス特性を獲得します。

## 自動インスタンスタイプ移行

リソース設定は、AWS EC2 コンピュートインスタンスなど、クラウドプロバイダーの実際のリソースにマッピングされます。インスタンスのラインナップは、次のように時間とともに発展していきます:

- *r7g\_4xlarge (Graviton3)*
- *r8g\_4xlarge (Graviton4)*

どちらも 16 vCPU と 128G RAM を備えていますが、*r8g\_4xlarge* はより新しい世代であり、おそらくより高いパフォーマンスを発揮します: *"R8g instances deliver around 30% higher performance over R7g instances, …"*

<Warning>
**Important:** 

`resources` の設定は汎用的でインスタンスタイプに依存しないため、Vespa Cloud は時間の経過とともに、よりコスト効率の高いコンピュートインスタンスに負荷を自動的に移行します。
</Warning>

つまり、Vespa Cloud のアプリケーションは、**手動での介入を一切必要とせずに**、同じ構成のより新しいインスタンスタイプに移行されます。これにより、総コストが抑えられ、パフォーマンスはハードウェアの進歩に追随します。

サポートされているインスタンスタイプの一覧は、[AWS](/ja/performance/instance-types/aws-instance-types)、[GCP](/ja/performance/instance-types/gcp-instance-types)、[Azure](/ja/performance/instance-types/azure-instance-types) の各インスタンスタイプのページを参照してください。
