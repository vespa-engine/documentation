Vespaは、サービス提供中でも、またインスタンスへの計画的・非計画的な変更の最中でも、高いフィード負荷を維持できるように最適化されています。このガイドでは、フィード・パフォーマンスを最適化する方法の概要と、ボトルネックの理解について説明します。

[読み取りと書き込み](/ja/writing/reads-and-writes)ガイドには、Vespaのアーキテクチャーと、フィードおよび検索に関連するAPIの概要があります。重要なポイントの1つは、Vespaが2つの主要なサービスタイプに分かれていることです:

- ステートレスなコンテナー・クラスター
- ステートフルなコンテント・クラスター

ステートレスなコンテナー・クラスターは、Vespaへのすべてのドキュメント操作の処理を担当します。ステートフルなコンテント・クラスターは、すべてのドキュメント操作の書き込みと同期(状態の永続化とデータ構造の管理)を担当します。

一般的に、Vespaは基盤となるストレージが処理できる(MB/sおよびIOPS)を超える書き込みレートを維持することはできません。リソース使用率を理解するには、CPU、メモリ、ディスク、ネットワークなどのリソース使用状況を監視することが不可欠です。そうすることでのみ、システムを正しくサイジングし、ボトルネックを特定できます。

## ステートレスなコンテナー・クラスター

Vespaへのすべてのドキュメント操作の処理は、ステートレスな *コンテナー* クラスターを経由してルーティングされます。処理には、[言語処理](/ja/linguistics/linguistics)のようなVespaの処理と、カスタムの[ドキュメント処理](/ja/applications/document-processors)の両方が含まれます。ステートレスなコンテナー・クラスターは、[エンベディング](/ja/rag/embedding)の推論も担当します。エンベディング推論は、*embed* 呼び出しの数とエンベディング・モデルのサイズによっては、計算リソースを大量に消費する可能性があります。[エンベディングのパフォーマンス](/ja/rag/embedding#embedder-performance)を参照してください。

ステートレスなクラスターは計算(CPU/GPU使用率)バウンドであり、クライアントがネットワーク経由で十分な操作を届けられる限り、処理レートはクラスター内のノード数とV-CPU数に対して線形にスケールするはずです。

検索と書き込みを別々のコンテナー・クラスターに分離する方法については、[複数のコンテナー・クラスター](/ja/writing/document-routing#multiple-container-clusters)を参照してください。分離されたコンテナー・クラスターは、コンテナー・クラスターが計算バウンドで、検索と書き込みの負荷が同時に発生し、計算関連のリソース競合によって書き込み操作が検索クエリーに影響を与えるのを避けたい、高負荷のシナリオで有用です。

ステートレスなコンテナー・クラスターはJava(JVM)で実装されているため、過剰なJVMガベージコレクションを避けるために、ヒープに十分なメモリを割り当ててください。チューニングのオプションについては、[ステートレス・コンテナーのチューニング](/ja/performance/container-tuning)を参照してください。セルフホスト・デプロイメントでのデフォルトの最大ヒープサイズは、上書きされない限り1.5GBです。

## ステートフルなコンテント・クラスター

Vespaへの**すべてのフィード操作**は、コンテント・ノード上の[トランザクションログ](/ja/content/proton#transaction-log)に**書き込まれ、同期されます**。これには、新しいドキュメントの書き込みと既存ドキュメントの更新の両方が含まれます。Vespaのトランザクションログは、データの耐久性を保証するライトアヘッドログ(WAL)です。操作がトランザクションログに正常に書き込まれ、適用された(検索/getで参照可能になった)ときにのみ、クライアントに応答が返されます。

書き込みパターンは追記型のシーケンシャル(ランダムではない)IOです。Vespaは基盤となるストレージが処理できるレートを超える書き込みレートを維持できないことに注意してください。コンテント・ノードがネットワーク接続ストレージを使用している場合、(耐久性のための)sync操作のコストがローカル接続ストレージ(SSDなど)よりもはるかに高いため、フィードが深刻な影響を受ける可能性があります。[sync-transactionlog](/ja/reference/applications/services/content#sync-transactionlog)を参照してください。

### ドキュメント・ストア

ドキュメントは、すべての[インデックス・モード](/ja/reference/applications/services/content#document)において[ドキュメント・ストア](/ja/content/proton#document-store)に書き込まれます - ここにドキュメントのコピーが永続化されます。

ドキュメント・ストアへの新しいドキュメントの追加は、シーケンシャルIOパターンの追記専用です。ドキュメントの新しいバージョンを書き込むこと(既に存在するドキュメントのPUT)は、存在しないドキュメントIDの場合と同じです。どちらの場合も、ドキュメントIDからサマリー・データファイルの位置へのインメモリ・マッピングが最新バージョンを指すように更新されます。サマリー・ファイルは、古いバージョンのドキュメントを削除するために[デフラグ](/ja/content/proton#defragmentation)されます。

### Attributeストア

[attribute](/ja/content/attributes)プロパティで定義されたフィールドはインメモリのフィールドであり、\`index\` プロパティでインデックスされたフィールドよりも高い[部分更新](/ja/writing/partial-updates)スループットでインプレース更新をサポートします(read-apply-writeパターンを回避)。attributeストアはメモリのみのデータ構造で、[attributeストア](/ja/content/proton#attributes)で定期的にディスクへ永続化されます。

```js
schema ticker {
    document ticker {
        field volume type int {
            indexing: summary | attribute
        }
    }
}
```

詳細は[部分更新](/ja/writing/partial-updates)を参照してください。

#### 冗長性の設定

メモリのみの更新(およびトランザクションログへの書き込み)を実現するには、更新対象のすべてのattributeが[ready](/ja/content/proton#sub-databases)であること、つまりコンテント・ノードがattributeフィールドをメモリにロードしていることを確認してください:

- これを保証する方法の1つは、[searchable copies](/ja/reference/applications/services/content#searchable-copies)を[redundancy](/ja/reference/applications/services/content#redundancy)と同じ値に設定することです - つまり、ドキュメントのレプリカを持つすべてのノードが、それをsearchableとしてロードしている状態にします
- もう1つの方法は、更新対象の各attributeに[fast-access](/ja/reference/schemas/schemas#attribute)を設定することです

### インデックス

インデックス・フィールドへの変更は、[ドキュメント・ストア](#document-store)と[インデックス](/ja/content/proton#index)に書き込まれます。UPDATE操作はドキュメント・ストアへのread-modify-writeを必要とし、スループットを制限することに注意してください。詳細は[部分更新](/ja/writing/partial-updates)を参照してください。

```js
schema music {
    document music {
        field artist type string {
            indexing: summary | index
        }
    }
}
```

## 親子関係

[親ドキュメント](/ja/schemas/parent-child)はグローバルであり、すべてのノードにレプリカを持ちます。親ドキュメントのフィールドへの書き込みは、すべての(子)ドキュメントを更新する非正規化のケースと比較して、多くの場合ロジックを簡素化します。書き込みパフォーマンスは、子ドキュメントの平均数とクラスター内のノード数との比較によって決まります - 例:

- 10ノードのクラスター、子の平均数=100、redundancy=2: 親への書き込みは10回の書き込みを意味し、200回の書き込みと比較して20倍良い
- 50ノードのクラスター、子の平均数=10、redundancy=2: 親への書き込みは50回の書き込みを意味し、20回の書き込みと比較して2.5倍悪い

つまり、子が多いほど、親への書き込みのパフォーマンス効果が高くなります。

## 条件付き更新

条件付き更新は次のようになります:

```json
{
    "update" : "id:namespace:myDoc::1",
    "condition" : "myDoc.myField == \"abc\"",
    "fields" : { "myTimestamp" : { "assign" : 1570187817 } }
}
```

条件の評価時に[ドキュメント・ストア](/ja/content/proton#document-store)へのアクセスが発生すると、永続化されたデータ構造への単純な追記ではなくランダムアクセスになるため、パフォーマンスが大幅に低下します。高いパフォーマンスを得るには、条件はattribute値を使用して評価されるべきです - 上記の例では、*myField* はattributeであるべきです。

<Note>
**注:** 

条件がstructまたはmapを使用する場合、値はドキュメント・ストアから読み取られます:
</Note>

```bash
    "condition" : "myDoc.myMap{1} == 3"
```

これは、すべてのstructフィールドがattributeとして定義されている場合でも当てはまります。これに対する改善は[#10892](https://github.com/vespa-engine/vespa/issues/10892)で追跡されています。

## クライアントのラウンドトリップ

同じドキュメントに2つのフィールドのassignを送信する場合の違いを考えてみましょう:

```json
{
    "update" : "id:namespace:doctype::1",
    "fields" : {
        "myMap{1}" : { "assign" : { "timestamp" : 1570187817 } }
        "myMap{2}" : { "assign" : { "timestamp" : 1570187818 } }
    }
}
```

と

```json
{
    "update" : "id:namespace:doctype::1",
    "fields" : {
        "myMap{1}" : { "assign" : { "timestamp" : 1570187817 } }
    }
}
{
    "update" : "id:namespace:doctype::1",
    "fields" : {
        "myMap{2}" : { "assign" : { "timestamp" : 1570187818 } }
    }
}
```

前者の場合、[vespa feed](/ja/clients/vespa-cli)から *1つ* の更新操作が送信されます - 後者の場合、クライアントは最初の操作のackを受信した *後に* 2つ目の更新操作を送信します。複数のフィールドを更新する場合は、できるだけ少ない操作に更新をまとめてください。[順序付けの詳細](/ja/content/content-nodes#ordering)を参照してください。

## フィード vs. 検索

コンテント・ノードは通常、固定されたリソース(CPU、メモリ、ディスク)を持ちます。フィードと検索のCPU割り当ては[concurrency](/ja/reference/applications/services/content#feeding)で設定します - 値は0から1.0で、値が大きいほどフィードにより多くのCPUリソースが割り当てられます。

さらに、フィードと検索の優先度、より正確にはフィードをどれだけ「nice」にするかも制御できます。プロセスがフィードの優先度を上げるにはroot権限が必要なため、フィードの優先度を下げる(niceにする)方式を採用しています。これは0から1.0の[niceness](/ja/reference/applications/services/content#feeding-niceness)値で制御されます - 値が大きいほど、フィードよりも検索が優先されます。デフォルトは0です。

## フィードのテスト

フィード容量をテストする場合:

<Steps>
<Step>
[vespa feed](/ja/clients/vespa-cli)を使用します。
</Step>
<Step>
1つのコンテント・ノードを使用してテストし、その容量と、ボトルネックがどこにあるか(リソース使用率メトリクス)およびVespaメトリクスを確認します
</Step>
<Step>
フィーダー・インスタンスを追加して、フィード・パフォーマンスをテストします。飽和するまで、ネットワークとCPU(コンテント・ノードとコンテナー・ノード)の使用率が増加することを確認します。
</Step>
<Step>
エラーがないことを確認するために、末尾のトラブルシューティングを参照します。
</Step>
</Steps>

その他のシナリオ: 定常状態のシステム、状態変更中、クエリー負荷中における持続的な負荷に対する容量のフィード・テスト。
