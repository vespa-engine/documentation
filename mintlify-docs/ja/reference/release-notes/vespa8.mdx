このドキュメントは、Vespa のメジャー・バージョン 7 と 8 の間の変更点を一覧にしたものです。[Vespa のバージョン](/ja/learn/releases#versions)に記載されているとおり、Vespa の新機能はマイナー・バージョンで導入され、メジャー・バージョンは互換性を破壊するリリースを示すために使用されます。Vespa 8 は新しい機能を導入していないため、それに先行する Vespa 7 のバージョンと同等に安全で成熟しています。重大なセキュリティ修正の可能性を除き、Vespa 7 のリリースは今後行われません。

## 概要

Vespa 8 における互換性を破壊する変更は、次のカテゴリーに分類されます:

- [デフォルト動作の変更](#changed-defaults)
- [アプリケーション・パッケージの構造と設定](#application-package-changes) - *スキーマ* や *services.xml* などで非推奨となっていた設定や構成要素が削除されます。
- [Java API](#java-api-changes) - 非推奨の API が削除されるか、Vespa の[パブリック API](https://javadoc.io/doc/com.yahoo.vespa/annotations/latest/com/yahoo/api/annotations/PublicApi.html) の対象から除外されます。
- [コンテナー・ランタイム環境](#container-runtime) - Java のビルド環境およびランタイム環境に対する互換性のない変更。
- [HTTP API の変更](#removed-http-api-parameters)
- [削除されたコマンドライン・ツール](#removed-command-line-tools)
- [削除または名前変更されたメトリクス](#removed-or-renamed-metrics)
- [ドキュメント・セレクション言語の変更](#document-selection-exact-type-matching)
- [セキュリティ関連の変更](#security)
- [オペレーティング・システムのサポート](#operating-system)
- 上記のいずれのカテゴリーにも含まれない[その他の変更](#other-changes)。

アプリケーションが Vespa 8 と互換性があることを確認するために、アプリケーションの所有者は次のことを行う必要があります:

- [デフォルトの変更](#changed-defaults)の一覧を確認し、Vespa 7 の動作を維持したい場合は必要なオプションを追加します。
- Vespa 7 に対してコンパイルした際に非推奨警告が出ないことを確認します。
- [アプリケーション・パッケージの変更](#application-package-changes)を確認し、Vespa 7 でデプロイした際にデプロイ警告が出ないことを確認します。
- [HTTP API の変更](#removed-http-api-parameters)の一覧を確認し、アプリケーションのクライアントを更新します。
- このドキュメントの残りのセクションを確認し、それに応じてアプリケーションとその環境を更新します。

非推奨の Java API を使用するとコンパイル時に警告が出力され、アプリケーション・パッケージの非推奨項目およびコンテナー・ランタイム環境のほとんどの変更については *デプロイ警告* が出力されます。ホステッド Vespa または Vespa Cloud では、デプロイ警告はアプリケーションのコンソール・ビューに表示されます。ただし、その他の種類の変更については非推奨警告を出力する手段がないため、このドキュメントおよびその他の Vespa ドキュメントでのみ説明されています。

以下のセクションでは、Vespa 7 から Vespa 8 へのすべての変更を詳しく説明します。

## デフォルトの変更

これらの変更はクライアントを壊す可能性があり、パフォーマンスとユーザー・エクスペリエンスの両方に影響を与えます。本番環境で稼働中でこれらのデフォルトに依存しているアプリケーションは、Vespa 8 にアップグレードする際に既存の動作を維持するための設定変更を行うべきです。これはアップグレード *前* に Vespa 7 上で行うことができます。[バケット・テスト](/ja/applications/testing#feature-switches-and-bucket-tests)の利用が役に立つ場合があります。

### TensorFlow のインポート

Vespa 8 では、[TensorFlow モデル](/ja/ranking/tensorflow)の直接インポートのサポートが削除されました。現在は [ONNX](https://onnx.ai/) が推奨される ML モデル形式であり、[ランキング](/ja/ranking/onnx)と[ステートレス・モデル評価](/ja/ranking/stateless-model-evaluation)の両方で動作します。ONNX には TensorFlow から ONNX へモデルを変換するツールが含まれていますが、Vespa はこれを提供しなくなります。

### *application/* フォルダーのサポート廃止

アプリケーション・パッケージのコンテンツ(*services.xml*、*schemas/* フォルダーなど)は、アプリケーション zip のルート・レベルに配置されることが想定されています。つまり、解凍したアプリケーション・パッケージには *./services.xml* などが存在するようにします。

しかし、以前はアプリケーション・パッケージのコンテンツを *application* ディレクトリ内に配置することができました。このサポートは Vespa 8 で削除されました。

### *searchdefinitions/* フォルダーは非推奨

検索定義スキーマは、現在は *schemas/* フォルダーに配置する必要があります。古いフォルダーは Vespa 8 でも引き続き動作しますが、デプロイ時に非推奨警告が発生します。

いつものように、プロジェクトで必要とされていない依存関係は削除してください。推移的に含まれる依存関係を削除する方法については、Maven ドキュメントの [Dependency Exclusions](https://maven.apache.org/guides/introduction/introduction-to-optional-and-excludes-dependencies.html#dependency-exclusions) を参照してください。

*org.json:json* を compile スコープの依存関係として追加する例:

```xml
<dependencies>
  ...
  <dependency>
    <groupId>org.json</groupId>
    <artifactId>json</artifactId>
    <version>20211205</version>
    <scope>compile</scope>
  </dependency>
  ...
</dependencies>
```

## 削除されたコマンドライン・ツール

### vespa-http-client

`vespa-http-client` コマンドライン・ツールは Vespa 8 で削除され、新しい [vespa-feed-client](/ja/clients/vespa-feed-client) に置き換えられました。新しいクライアントは [HTTP/2](/ja/performance/http2) と [Document v1 API](/ja/writing/document-v1-api-guide) を使用します。

vespa-http-client が使用していた基盤の rest API は、Vespa 8 でも引き続き利用可能でサポートされます。したがって、Vespa 7 で配布された古いクライアントを使用して Vespa 8 インストールにフィードし続けることは可能です。Vespa 8 の最初のリリース以降、vespa-http-client の更新はリリースされませんが、rest API 実装への修正とセキュリティ更新は Vespa 8 の一部として継続されることに注意してください。早めに vespa-http-client から移行することを強くお勧めします。

## セレクション言語におけるドキュメント・タイプの厳密なマッチング

[ドキュメント・セレクション言語](/ja/reference/writing/document-selector-language)は、ドキュメント・タイプに対して *継承*("is-a")マッチングではなく *厳密な* マッチングを使用するようになりました。

2 つの最小限のドキュメント・スキーマを使用した例:

- `document my_doc_type {}`
- `document my_extended_doc_type inherits my_doc_type {}`

以前は、セレクション式 `my_doc_type` は、`my_doc_type` 型のドキュメント・インスタンス *と* `my_extended_doc_type` 型のドキュメント・インスタンスの両方にマッチしていました。現在は `my_doc_type` 型のドキュメントに *のみ* マッチします。

## セキュリティ

### デフォルトで有効になった Strict モード

jdisc コンテナーにおけるリクエスト・フィルタリングの *Strict モード* は、Vespa 8 でデフォルトで有効になっています。詳細については、services.xml の [strict-mode](/ja/reference/applications/services/http#filtering) 属性に関するドキュメントを参照してください。

### アクセス・ログのリモート・ホスト/ポートを制御するリクエスト・ヘッダー


jdisc コンテナーは、アクセス・ログのリモート・ホストとポートをそれぞれ設定するために、*X-Forwarded-For* および *X-Forwarded-Port* リクエスト・ヘッダーを使用します。次のリクエスト・ヘッダーはデフォルトでは処理されなくなります:

- y-ra
- yahooremoteip
- client-ip
- y-rp

## Vespa アーティファクトのオペレーティング・システム・サポート

### RPM

Vespa RPM のサポート対象 OS は、Vespa 8 では [CentOS Linux 7](https://www.centos.org/centos-linux/) から [CentOS Stream 8](https://www.centos.org/centos-stream/) に変更されます。RPM は引き続き [Fedora Copr](https://copr.fedorainfracloud.org/coprs/g/vespa/vespa/) でビルド・配布されます。Vespa RPM をインストールする場合は、OS を [CentOS Stream 8](https://www.centos.org/centos-stream/) にアップグレードする必要があります。

### OCI コンテナー(Docker コンテナー)

OCI コンテナーで使用されるベース・イメージは、Vespa 8 では [docker.io/centos:7](https://hub.docker.com/_/centos) から [quay.io/centos/centos:stream8](https://quay.io/repository/centos/centos?tab=tags) に変更されます。これは、コンテナー・イメージがカーネル・バージョン *4.18.0*(CentOS Stream 8 の現行カーネル)を実行するシステムでビルドおよびテストされることを意味します。Vespa のコンテナー・イメージを使用する場合は、コンテナーを実行するホストを同じかそれ以降のカーネル・バージョンにアップグレードすべきです。

## その他の変更

### 未知のランク・プロファイル

クエリー対象のすべてのスキーマに存在しないランク・プロファイルを指定したクエリーは、`default` プロファイルへのフォールバックではなく失敗するようになりました。複数のスキーマに対するクエリーでは、それらすべてに存在するランク・プロファイルを使用する必要があります。これは共通のスキーマを[継承](/ja/schemas/inheritance-in-schemas)することで保証できます。

### 未知のサマリー・クラス

存在しない[サマリー・クラス](/ja/querying/document-summaries)を指定したクエリーは、空のままレンダリングされるのではなく、失敗するようになりました。複数のスキーマに対するクエリーでは、それらすべてに存在するサマリー・クラスを使用する必要があります。これは共通のスキーマを[継承](/ja/schemas/inheritance-in-schemas)することで保証できます。

### "qrserver" サービス名

Vespa コンテナーは一般に "container" をサービス名として使用しています。しかし、[document-processing](/ja/reference/applications/services/docproc) と [document-api](/ja/reference/applications/services/container#document-api) のいずれも宣言していないコンテナー・クラスターは、以前は "qrserver" という名前でした。Vespa 8 では、すべてのコンテナー・クラスターがサービス名 "container" を使用します。これは、すべてのメトリクス API の出力と Vespa ログの出力に影響します。

### コンテナーのアクセス・ログ

コンテナーのアクセス・ログのフォルダーは、`$VESPA_HOME/logs/vespa/qrs/` から `$VESPA_HOME/logs/vespa/access/` に移動しました。

デフォルトの圧縮形式は gzip から zstd に変更されました。[デフォルトの変更](#changed-defaults)を参照してください。

### サマリー・フィーチャーにおける ONNX 出力

サマリー・フィーチャーで ONNX モデルの出力を定義する場合、Vespa 8 では、サマリー・フィーチャー名が以前のバージョンの `onnxModel` ではなく `onnx` になります。

### rankfeatures の変更

Vespa は、すべての [rank-features](/ja/reference/api/query#ranking.listfeatures) を計算し、`rankfeatures` サマリー・フィールドで返すことができます。Vespa 8 ではこの一覧にいくつかの変更があります:

- `now` が削除されました
- `bm25(field)` が追加されました
- `matches(field)` が追加されました

### "storage" メッセージ・バス・ルーティング・ポリシーの削除

"storage" ルーティング・ポリシーは Vespa 7 の初期に削除され、これを指定したクライアントは後方互換性のために content ルーティング・ポリシーに転送されてきました。この転送は Vespa 8 で削除され、クライアントは更新が必要です。

"storage" ポリシーのすべての使用箇所を、同一の動作をする "content" に置き換えてください。

### vespa-dispatch-bin プロセスの削除

ディスパッチ機能は Vespa コンテナーに移動され、*vespa-dispatch-bin* プロセスは削除されました。これはパブリックなインターフェースではないため、Vespa-7.109.10 でデフォルトが vespa-dispatch-bin を使用 **しない** 設定に切り替えられました。このプロセスはその後の Vespa リリースで削除されました:

### YQL 形式

- Vespa が YQL ステートメントを出力する際、文字列の末尾にセミコロンを付けなくなりました。ステートメントをセミコロンで終端することは、引き続き任意で有効な入力です。
- [アノテーション](/ja/reference/querying/yql#annotations)は `[]` 括弧で囲まれません(引き続き有効な入力です)。
- アノテーション名は引用符で囲まれません(引き続き有効な入力です)。

Vespa 7 / Vespa 8 の例:

```js
where text contains ([{"distance": 5}]near("a", "b"));
where text contains ({distance: 5}near("a", "b"))
```

### アップグレード手順

Vespa 8 では、[アップグレード手順](/ja/operations/self-managed/live-upgrade)が簡素化されました(Vespa 7 から Vespa 8 へのアップグレード、または Vespa 8 のバージョン間のアップグレードの場合)。Vespa 7.x から Vespa 7.y にアップグレードする場合は、[アップグレード手順](/ja/operations/self-managed/live-upgrade)の項目 3 [設定サーバーのアップグレード](/ja/operations/self-managed/live-upgrade#upgrade-config-server)を次の手順に置き換えてください:
- 設定サーバーのアップグレード中、アプリケーションのノードは自身がアップグレードされるまで設定を受け取ることができません。続行する前に、各ノードで次のコマンドを実行して、すべてのノードをスタンドアロン・モードに設定する必要があります:   

    ```bash
    $ vespa-configproxy-cmd -m setmode memorycache
    ```
    各ノードは、アップグレードされると自動的に再接続します。
- 設定サーバーに新しい Vespa バージョンをインストールし、1 台ずつ[再起動](/ja/operations/self-managed/admin-procedures#vespa-start-stop-restart)します。再び起動するまで待ちます。vespa ログで "Changing health status code from 'initializing' to 'up'" を確認するか、[ヘルスチェック](/ja/operations/self-managed/configuration-server#troubleshooting)を使用してください。
- アプリケーションを再デプロイしてアクティブ化します:
    
    `$` [`vespa deploy`](/ja/clients/vespa-cli#deployment)
