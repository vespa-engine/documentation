
## vespa-configproxy-cmd

*vespa-configproxy-cmd* は、[config proxy](/ja/operations/self-managed/config-proxy) のステータス確認および制御用ツールです。config proxy はすべてのノード上で、1 つ以上の [config server](/ja/operations/self-managed/configuration-server) のプロキシーとして動作します。デフォルトでは localhost 上の config proxy に接続します。

引数なしで実行すると、アクティブな configId の一覧を出力します - フォーマット仕様:

`<config definition name>,<config id>,<config generation>,<MD5 checksum>,<xxHash checksum>`

構文: `vespa-configproxy-cmd [args]`

例:

```bash
$ vespa-configproxy-cmd -m sources
```

より包括的な例は [inspecting config](/ja/operations/self-managed/config-proxy#inspecting-config) を参照してください。

## vespa-feeder

*vespa-feeder* は、[JSON](/ja/reference/schemas/document-json-format) 入力を Vespa のドキュメント操作としてパースし、Vespa アプリケーションに送信するフィード・クライアントです。入力の内容を順にパースし、各操作を順番にフィードします。ただし、常に多くの操作が同時に処理待ちになっており、操作の処理時間もさまざまであるため、操作がどの順序でコンテント・ノードに到達するかは保証されません。同じドキュメント ID に適用される操作についてはこれが重要になり得るため、処理待ちの操作が既に存在するドキュメント ID への操作は送信しないというロジックが組み込まれています。

*vespa-feeder* は、フィードの最後にレポートを出力します。このレポートを 1 分ごとに出力するには、*\--verbose* を使用します:

```bash
Messages sent to vespa (route default) :
----------------------------------------
PutDocument: ok: 999997 msgs/sec: 411.38 failed: 0 ignored: 0 latency(min, max, avg): 2, 4360, 99
```

*ignored* は、[設定されたドキュメント・タイプ](/ja/reference/applications/services/content#documents)や selection のいずれにも一致しなかったため、どの[コンテント・クラスター](/ja/reference/applications/services/content)にもルーティングできなかったドキュメント数を報告します - 例:

- ドキュメント・タイプがアプリケーションから削除されており、フィード・ファイルにそのタイプのドキュメントが含まれている
- 1 つ以上の selection 式によってクラスターが受け入れるドキュメントが制限されており、フィード・ファイルに除外対象のドキュメントが含まれている。例としては、[失効したドキュメント](/ja/schemas/documents#document-expiry)のフィードが挙げられます - 30 日以内のドキュメントを対象とする selection があるのに、フィード・ファイルに 30 日以上経過したドキュメントが含まれている場合です

構文: `vespa-feeder [--abortondataerror true|false] [--abortonsenderror true|false] [--file arg] [--maxpending arg] [--maxpendingsize arg] [--maxfeedrate arg] [mode standard|benchmark] [--noretry] [--retrydelay arg] [--route arg] [--timeout arg] [--trace arg] [--validate] [--dumpDocuments filename] [--numthreads arg] [create-if-non-existent] [-v,--verbose] filename`

例:

```bash
$ vespa-feeder file.json
```

## vespa-logctl

VESPA サービスのログ・レベル(*$VESPA\_HOME/var/db/vespa/logcontrol/service.logcontrol* に保存)を表示または変更します。詳細は[ログ・レベルの制御](/ja/reference/operations/log-files#controlling-log-levels)を参照してください。*component-specification* は、サービスのどのサブコンポーネントを制御するかを指定します。空の場合、すべてのコンポーネントが制御されます:

- `x.` : コンポーネント x のみに一致
- `x` : コンポーネント x とそのすべてのサブコンポーネントに一致

構文(ログ・レベルの表示): `vespa-logctl [OPTION] <service>[:component-specification]`

構文(ログ・レベルの設定): `vespa-logctl [OPTION] <service>[:component-specification] <level-mods>`

*level-mods* は次のように定義されます : `<level>=<on|off>[,<level>=<on|off>]...`

*level* は次のいずれかです: `all`、`fatal`、`error`、`warning`、`info`、`event`、`config`、`debug`、`spam`

例: サービス `container` について、`com.yahoo.search.searchchain` と `com.yahoo.search.searchchain` のすべてのサブコンポーネントに対し、spam と debug 以外のすべてを有効にします:

```bash
$ vespa-logctl container:com.yahoo.search.searchchain all=on,spam=off,debug=off
```

## vespa-logfmt

`vespa-logfmt` は Vespa のログ・ファイルを読み込んでメッセージを選択し、それらのメッセージを整形して標準出力に書き出します。ファイル引数が与えられない場合、vespa-logfmt は最新の Vespa ログ・ファイル `$VESPA_HOME/logs/vespa/vespa.log` を読み込みます(これは `-f` オプションでも機能します)。それ以外の場合は、引数として与えられたファイルのみを読み込みます。標準入力を読み込むには、ファイル引数として単一のダッシュ ’-’ を指定します。[ログのリファレンス](/ja/reference/operations/log-files)を参照してください。

構文: ` vespa-logfmt [-l levellist ] [-s fieldlist ] [-p pid ] [-S service ] [-H host ] [-c regex ] [-m regex ] [-f ] [-N ] [-t ] [-ts ] [file …]`

例:

ログ・レベルが "event" のメッセージのみを表示し、人間が読める形式の時刻(小数秒なし)、イベントを生成したサービス、およびイベント・メッセージを出力します:

```bash
$ vespa-logfmt -l event -s fmttime,service,message
...
[2017-09-05 06:16:16] config-sentinel  stopped/1 name="sbin/vespa-config-sentinel -c hosts/vespa-container (pid 1558)" pid=1558 exitcode=1
[2017-09-05 06:16:16] config-sentinel  starting/1 name="sbin/vespa-config-sentinel -c hosts/vespa-container (pid 1564)"
[2017-09-05 06:16:16] config-sentinel  started/1 name="config-sentinel"
[2017-09-05 06:17:00] configserver     count/1 name=configserver.failedRequests value=0
[2017-09-05 06:17:00] configserver     count/1 name=procTime value=0
[2017-09-05 06:17:00] configserver     count/1 name=configserver.requests value=0
```

ログ・レベルが *info、debug、event* の*いずれでもない*メッセージを表示し、秒とマイクロ秒での時刻、ログ・レベル、コンポーネント名、およびメッセージ・テキストを出力します:

## vespa-significance

グローバルなシグニフィカンスのための[シグニフィカンス・モデル・ファイル](/ja/ranking/significance#significance-model-file)を生成します。

構文: `vespa-significance <command> [options]`

コマンド:

- `generate` – Vespa ドキュメント(JSONL)または Vespa Significance TSV(VSTSV)ファイルからシグニフィカンス・モデルを構築します。
- `export` – インデックスから VSTSV ファイルにターム統計をダンプします。
- `merge` – 複数の VSTSV ファイルをマージします。低頻度のタームをフィルタリングすることもできます。

### vespa-significance generate

このコマンドはデフォルトのクエリー・プロセッサーと同じトークナイザーを使用します。詳細は [linguistics in Vespa](/ja/linguistics/linguistics) を参照してください。カスタム・トークナイザーには対応するエクストラクターが必要です。クエリー処理と整合させるため、トークンはステミングなしで小文字化されます。

構文: `vespa-significance generate [options] --in <FILE>`

例:

```bash
$ vespa-significance generate --in vespa-dump.jsonl --out en_model.json --field text --language en
```

この例は、Vespa ドキュメントのコレクション(jsonl ファイル)から `en_mode.json` というシグニフィカンス・モデルを生成します。これは Vespa バージョン 8.426.8 以降で利用可能です。

Docker で実行する場合は、入出力ファイルを永続化するためにデータ・ディレクトリをマウントします。例:

```bash
$ podman run -it --entrypoint bash -v $PWD/data:/data -w /data vespaengine/vespa:latest /opt/vespa/bin/vespa-significance generate --in docs.jsonl --out model.zst --field text --language en
```

JSONL 入力用にドキュメントをダンプするには、[vespa-visit](#vespa-visit) を `--field-set` オプション付きで使用します:

```bash
$ vespa visit --field-set mydocument:text_field > ./data/docs.jsonl
```

生成されたモデル・ファイルは `zstdcat` と `jq` で確認できます:

```bash
$ zstdcat ./data/model.zst | jq
```

VSTSV からモデルを生成する例:

```bash
$ vespa-significance generate --format vstsv --in dumped_term_df.vstsv --out un_model.json
```

この例では、入力は `vespa-significance export` で生成されたものです。これは Vespa バージョン 8.597.8 以降で利用可能です。VSTSV フォーマット使用時に言語が指定されていない場合、デフォルトは unknown に設定されます。

## vespa-visit

[visit](/ja/clients/vespa-cli) 操作を、[vespa visit](/ja/clients/vespa-cli) より多くのオプション付きで実行するために使用します。[Vespa Message Bus](/ja/writing/document-routing) を使用しており、Vespa アプリケーション内で実行する必要があります - Vespa HTTP API は使用しません。

<Note>
**注:** 

このツールは [vespa CLI](/ja/clients/vespa-cli) の `vespa visit` と混同されやすいです。後者はビジット用の一般的なツールであり、`vespa-visit` はデバッグや複雑なユースケース向けに作られています。
</Note>

デフォルトでは、vespa-visit はビジットされたドキュメントを取得して stdout に出力します。ただし、このツールでは [vespa-visit-target](#vespa-visit-target) を指定し、再処理や移行を実行するツールとして使用することもできます。ディスク上に進捗ファイルを保持することをサポートしているため、何らかの理由で途中で失敗した場合に再開できます。

あるクラスターから別のクラスターへドキュメントのセットを移行するには、*visiting* を使用します - データはコンパクトなシリアライゼーション・フォーマットを使用して、ソース・ノードからターゲットに直接転送されるため、パフォーマンス上最適です(データはビジット・クライアントを経由しません)。バックアップやファイルへのダンプもこの方法で実装できます。

検索ノードのリカバリー: ドキュメントを検索クラスターに直接フィードします。例として、タイプ *music* のドキュメントを選択します:

```bash
$ vespa-visit --selection music --datahandler indexing
```

これは、同じアプリケーション内で、ソースから検索クラスターへフィードします。同時にフィードが行われていると、更新が失われる可能性があることに注意してください。

*\--visitremove* を使用してビジット操作に [remove-entries](/ja/operations/self-managed/admin-procedures#data-retention-vs-size) を含めると、最近削除されたドキュメントのトゥームストーンをダンプできます。

[content ポリシー](/ja/writing/document-routing#content)は、別のクラスターの設定サーバー群を使用して自身を設定するように構成できます。これは *config* パラメーターで指定します。例として、次のルートは、*myconfigserver.mydomain.com:12345* に設定サーバーを持つコンテント・クラスター *mycluster* にルーティングします:

```bash
[Content:config=tcp/myconfigserver.mydomain.com:12345;cluster=mycluster]
```

以下の例は、vespa-visit を使用してソース・クラスターから別のクラスターへすべてのデータをコピーする方法を示しています:

```bash
# Copies all data in the local cluster, routing it to the remote mycluster
$ vespa-visit --datahandler '[Content:config=tcp/myconfigserver.mydomain.com:12345;cluster=mycluster]'

# Limit to 'music' documents only
$ vespa-visit --datahandler '[Content:config=tcp/myconfigserver.mydomain.com:19070;cluster=mycluster]' \
  --selection music

# Limit to all documents for user '1234'
$ vespa-visit --datahandler '[Content:config=tcp/myconfigserver.mydomain.com:12345;cluster=mycluster]' \
  --selection id.user=1234
```

    </tr>

    </tr>

    </tr>
