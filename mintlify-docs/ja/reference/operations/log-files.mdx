すべての Vespa コンポーネントは、ロギングに共通のログモジュールを使用します。これらのログメッセージは、*`$VESPA_HOME/logs/vespa/`* にあるローカルのログファイルに追加され、フィルタリングされた後、管理ノード上のログサーバーに転送されます。ログのアーカイブとローテーションについては、[ログサーバー](#log-server)で説明します。

<Note>
**注:** 

Vespa がローカルのコンテナー(名前が「vespa」)で実行されている場合は、`docker exec vespa vespa-logfmt` を実行するとログをすばやくダンプできます。
</Note>

## ログファイルのフィールド

ログファイルは機械可読なログ形式で書かれており、[vespa-logfmt](/ja/reference/operations/self-managed/tools#vespa-logfmt) を使うと人間にとって読みやすくなります。特定のプログラムからのログメッセージのフィルタリング、特定のログレベルのみの表示、より直接理解しやすい形式での時刻表示などができます。ログの各行は、次のフィールドがこの順序で、TAB(ASCII 9)文字で区切られて構成されます:

```bash
time host pid service component level message
```

## ログレベルの制御

サービスとして実行中の Vespa プログラムのアクティブなログレベルを実行時に変更するには、[vespa-logctl](/ja/reference/operations/self-managed/tools#vespa-logctl) を使用します。クラウドで実行している場合は、services.xml でチューニングできます。[admin 要素(logging)](/ja/reference/applications/services/admin#logging)を参照してください。スタンドアロンのプログラムは、代わりに起動時に環境変数 *VESPA\_LOG\_LEVEL* を読み取り、どのログレベルをアクティブにすべきかを決定します。*VESPA\_LOG\_LEVEL* のデフォルト設定は *"all -debug -spam"* で、debug と spam を除くすべてのログレベルが有効になります。

*vespa-logctl* は、実行中のプログラム、またはプログラムの一部について、アクティブなログレベルを表示または変更します。これは、問題を診断するために稼働中のシステムの一部でデバッグ出力を有効にするのに便利です。ログが冗長すぎるプログラムを黙らせるのにも使えます。

*vespa-logctl* で制御できるプログラムは、ログ制御ファイルを *`$VESPA_HOME/var/db/vespa/logcontrol/service.logcontrol`* に置きます。プログラム起動時にこのファイルが存在する場合、そのファイルを使用してロギング・レベルが設定されます。つまり、*vespa-logctl* によるログレベルの変更は永続的(sticky)であり、プログラムが実行されていなくても実行できます。

## ログイベント

イベントメッセージは、*event* タイプのログメッセージです。イベントには明確に定義されたペイロードが含まれており、アラートなど、さまざまな種類の自動処理に適しています。イベントは、コンポーネントに何か注目すべきことが起きたとき、または外部と共有したいメトリクス・データがあるときに、そのコンポーネントによって発行されます。他のすべてのログメッセージと同様に、イベントは logserver コンポーネントによって管理ノードに集約され、そこで Vespa ログから確認したり、logserver プラグインによってプログラム的に捕捉したりできます。

メトリクスは、特定のコンポーネントが実行する処理の詳細を示す内部変数を報告するために使用されます。*VALUES* は、キューの長さやレイテンシーのような、その瞬間に意味を持つ数値です。*COUNTER* は、処理されたドキュメント数やクエリー数のように、処理ステップごとに単調に増加する数値です。[メトリクス API](/ja/operations/metrics) を参照してください。

各イベントは、イベント *type*、*version*、およびオプションの *payload* を持ちます。ログ形式では、イベントタイプは 1 つの単語、バージョンは単純な整数、ペイロードは *key=value* ペアの集合として表現されます。イベントのペイロードは、一般のログメッセージと同様にバックスラッシュでクォートされます。つまり、イベントは転送中に二重にクォートされることがあります。ダブルクォートによる区切りはサポートされていません。

## Logd

*logd* という小さなプログラムが、`vespa.log` ファイルのローテーションと、ほとんどのログメッセージのログサーバーへの転送(詳細は次のセクションを参照)を担当します。ログファイルは 24 時間後、または大きくなりすぎた場合にローテーションされます。ローテーションされたログは、30 日後、または合計サイズが 1000 MB を超えた場合に logd によって削除されます。

## ログサーバー

管理ノード上のログサーバーでは、*Archiver* プラグインが各ノードからのログメッセージをログアーカイブに書き込みます。これらのメッセージは、メッセージのタイムスタンプに基づいてログファイルに書き込まれます。ログファイルは `$VESPA_HOME/logs/vespa/logarchive` ディレクトリにあります。カタログ構造は次のとおりです:

```bash
logarchive/<year>/<month>/<day>/<hour>-<serial>
```

たとえば、2016-07-22 08:05:00 にログ出力されたメッセージは、次の場所にあります:

```bash
logarchive/2016/07/22/08-0
```

日付と時刻はすべて UTC です。ログファイルが 20 Mb を超えると、ファイルはローテーションされ、シリアル番号が増加します。ローテーションされてから *2 時間*以上経過したログファイルは、ディスク領域を節約するために圧縮されます。ログアーカイブ内のアーカイブ済みログファイルは、次の 2 つの理由で削除されます:

- ログファイルが 30 日より古い
- ログアーカイブの合計サイズが 30GB を超えた

<Note>
**注:** 

ストレージ領域の枯渇を防ぐなどの目的で、これよりも積極的にログファイルを削除する必要がある場合は、不要になったログファイルをパージする仕組みを自分で追加する必要があります。
</Note>

レベルが *debug* および *spam* のイベントとログメッセージは、通常、ログアーカイブへの送信前にフィルタリングされて除外されます。例として、イベントと *debug* ログメッセージを転送するには、次を *services.xml* に追加します:

```xml
<services>
    <config name="cloud.config.log.logd">
        <loglevel>
            <event>
                <forward>true</forward>
            </event>
            <debug>
                <forward>true</forward>
            </debug>
        </loglevel>
    </config>
```

## アクセスログファイルの内容

コンテナーは各リクエストをアクセスログに記録します。ログファイルは *`$VESPA_HOME/logs/vespa/access/`* にあります。詳細は[アクセス・ロギング](/ja/operations/access-logging)を参照してください。

### アクセスログの時間値と、メトリクスおよびログイベントの比較

アクセスログのタイミングは、一般に vespa.log のタイミング値と比べてわずかにずれています。その理由は、システムへの「プローブ」がわずかに異なる抽象レベルに配置されているためです。ここでの説明は、経験豊富なユーザーとトラブルシューティングを対象としています。

#### アクセスログにおける処理時間の定義

アクセスログの処理時間は、検索ハンドラーから実行が最初に呼び出された時点から始まります。終了は、レスポンスが非同期かどうかに依存します。同期レスポンスの場合、終了はレンダラーが呼び出された後、レンダリング・バッファーがフラッシュされる前です。非同期レスポンス(通常の検索レスポンスなど)の場合、終了は完了ハンドラーが作成された時点と定義されます。つまり、制御フローがサーチ・チェーンから戻った後、ネットワーク通信やレンダリングが行われる前です。

#### vespa.log における処理時間の定義

StatisticsSearcher は、メトリクス *query\_latency* とログイベント *mean\_query\_latency* を定義します。両者に入力されるデータは同じです。この区間の開始は、制御フローが StatisticsSearcher に入った時点、終了は StatisticsSearcher の次のサーチャーが search() から戻った時点と定義されます。これには、結果が StatisticsSearcher から渡された時点でまだ fill されていなかった場合、fill 時間が*含まれない*という副作用があります。これは、SearchHandler が自分で fill() を呼び出さなければならない場合、たとえばヒットのフィールドにアクセスするサーチャーが 1 つもない場合に起こり得ます。

#### タイミングのまとめ

アクセスログにはレンダリング前に起きるすべてが含まれますが、高コストなレンダリング・ロジックや低速なネットワークは除外されます。クエリー・レイテンシーのイベントとメトリクスは、StatisticsSearcher が配置されたサーチ・チェーン内で起きることだけをカバーし、サマリーの取得は除外される場合があります。

### ZooKeeper ログ

ZooKeeper のログファイルは、通常は定期的に監視する必要はありませんが、Vespa の設定システムをデバッグする必要が生じた場合の情報源となり得るため、ここで触れておきます。場所は `$VESPA_HOME/logs/vespa/zookeeper.<servicename>.log` です。
