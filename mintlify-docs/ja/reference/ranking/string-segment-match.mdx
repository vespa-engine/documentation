title: "文字列セグメントマッチ"
---

**文字列セグメントマッチ**アルゴリズムは、一連のメトリクス — **文字列セグメントマッチ・メトリクス** — を計算します。これは、検索エンジンでのマッチング時に通常得られる限られた情報から、_クエリー_ 文字列が _フィールド_ 文字列にどの程度よくマッチするかについてのあらゆる情報を捉えることを目的としたもので、検索におけるドキュメントのランキングに役立ちます。

このアルゴリズムは、_セグメント_ を見つけることによって動作します。セグメントとは、クエリーの 1 つ以上の隣接する用語を含む、フィールド内の局所的な領域です。フィールド内のすべてのセグメント開始点が探索され、全体として最良のセグメンテーションを生み出すものが選択されます。非形式的にいえば、セグメンテーションは、クエリーのマッチが互いに近接した少数のセグメントで構成されているほど良いものです。例:

ここでは、クエリーをカバーする 2 つのセグメントが見つかっています。代替となる 2 番目のセグメントも見つかっていますが、クエリー用語の近接性が劣るため破棄されます。もう 1 つの単独の "Bush" のインスタンスは、"Bush" をセグメントの開始トークンとするセグメンテーションが存在しない(すなわち、単独の "George" が存在しない)ため、まったく考慮されません。

メトリクスの一部は、見つかったセグメントの _内部_ のトークンから計算され、別の一部のメトリクスは、セグメント自体の数と配置を特徴づけます。これにより、メトリクスは、近接するトークンは(典型的には同じ文の一部として)同じ意味の一部であることが多く、やや離れたトークンは弱い関連しか持たないという自然言語の性質を反映できます。

クエリーは通常、複数の意図されたセグメントで構成されます。各セグメントは連続していて順序どおりですが、セグメント間の順序はあまり重要ではありません(ただし、より重要なセグメントが先に来る傾向はあります)。

クエリーを用語の順序どおりに、フィールドの最良かつ最少のセグメントにマッチさせることで、このアルゴリズムは利用可能なフィールドデータを活用し、その証拠から尤もらしいクエリーのセグメンテーションを発見します。明示的なセグメンテーション情報も、セグメントスコアに影響を与え、その結果選択されるセグメントに影響を与える接続性スコアの形で使用できます。

## ソース情報

このアルゴリズムがこれらのメトリクスを計算するために使用する情報は次のとおりです(最後の 3 つはオプションです):

- クエリーおよびフィールド内で _マッチした_ 用語の各出現位置
- クエリーおよびフィールド内の用語数
- 各クエリー用語のウェイト(重要度)を示す、クエリー用語ごとの数値
- 用語の相対頻度を示す、クエリー用語ごとの数値
- 用語間の言語的な接続性を示す、隣接するクエリー用語ペアごとの数値

## アルゴリズム

このアルゴリズムは、与えられた開始クエリー用語からセグメントを次のように見つけます:

```python expandable
i = the position of the first query term
j = the position of the first match of the query term at i
while (i < query.length) {
    nextJ = the first location of query term i+1 at mostproximityLimitsteps to the right of j
    if (nextJ not found)
        nextJ = the first location query term i+1 at mostproximityLimitsteps to the left backwards of j

    if (nextJ is found) { // Find next token in this segment
        i = i+1
        j = nextJ
    }
    else {
        nextJ = the first location of query term i+1 at any location to the right forwards from j
        if (nextJ not found)
            nextJ = the first location of query term i+1 at any location to the left backwards from j
        if (nextJ not found) { // Skip a non-existing query term
        	i = i+1
        }
        else { // End of segment
            return i,j as the segment end
        }
    }
}
```

つまり、セグメントとは、クエリー用語の隣接する部分列に対応するフィールド内の用語の集合であり、フィールド内で隣接するクエリー用語間のギャップが前方または後方に最大 `proximityLimit` であり、フィールドに存在しないクエリー用語は無視されます。

上記で使用したフィールド用語の探索順序を、2 つのフィールド位置間の _意味的距離_ と呼ぶことにします。たとえば

- nextJ が j の n 個後ろに位置し、n\<`proximityLimit` の場合、j と nextJ の間の意味的距離は n です
- nextJ が j の _左側_ n 個の位置にあり、n\<`proximityLimit` の場合、j と nextJ の間の意味的距離は `proximityLimit`+n です

このアルゴリズムは、意味的距離の空間でトークンとセグメントを探索します。このアルゴリズムは、意味的距離のどのような定義でも動作します。アルゴリズムは、各セグメント開始点について次を記録します:

- metrics - この時点までに結合されたセグメントの、現在知られている最良のメトリクス
- previousJ - フィールド内の前のセグメントの終了位置 j(存在する場合)
- i - このセグメントの開始となるクエリー用語 i
- semanticDistanceExplored - previousJ からこれまでに探索された距離
- open - semanticDistanceExplored を超えてさらに j が見つかる可能性があるかどうか

これを踏まえて、アルゴリズムの高レベルの擬似コードを示します:

```js expandable
currentSegment=a segment start point at starting at i=0 (the start of the query)
while (there are open segment start points) {
    newSegment=find the next segment, at currentSegment.i with semanticDistance > currentsegment.semanticDistance
    if (no newSegment) {
        currentSegment.open = false
        continue;
    }
    SegmentStartPoint existingStartPoint=find stored segment at start point newSegment.i+1
    if (no existingStartPoint) {
        create and store a new (empty open) segment start point at newSegment.i+1
    }
    else {
        if (newSegment.score > existingStartPoint.score) {
            existingStartPoint.metrics.score = newSegment.metrics.score
            existingStartPoint.previousJ = newSegment.endJ
            existingStartPoint.semanticDistanceExplored = newSegment.semanticDistance+1
        }
    }
    currentSegment=the next open start point (in the order they are found)
}
finalMetrics=metrics of segmentStartPoint at query.length
```

2 つのセグメンテーションパスのどちらが良いかを決定する `metric.score` は `absoluteProximity/segments^2` です。部分的なセグメンテーションに対して計算できるメトリクスの任意の組み合わせを使用できます。

詳細は[コード](https://github.com/vespa-engine/vespa/tree/master/searchlib/src/main/java/com/yahoo/searchlib/ranking/features)を参照してください。

## 計算量

このアルゴリズムは、以前のセグメントの再計算を避けるために線形計画法のテクニックを使用します。可能なセグメント開始点ごとに一定量のデータが保存されます。開始点は最大でもクエリー用語の数と同じであるため、メモリの計算量は `O(query.length)` です。アルゴリズムはすべての可能なセグメント開始点を(上限まで)試行し、開始点はクエリー用語ごとに最大 1 つであるため、時間計算量は `O(query.length*total number of term occurrences)` です。平均の時間計算量は `O(average segment length/average number of term occurrences)` です。

## メトリクスセット

このアルゴリズムによって計算される、文字列セグメントマッチ・メトリクスの完全なセットは次のとおりです:

- match
- proximity
- completeness
- queryCompleteness
- fieldCompleteness
- orderness
- relatedness
- earliness
- longestSequenceRatio
- segmentProximity
- unweightedProximity
- absoluteProximity
- occurrence
- absoluteOccurrence
- weightedOccurrence
- weightedAbsoluteOccurrence
- significantOccurrence
- weight
- significance
- importance
- segments
- matches
- outOfOrder
- gaps
- gapLength
- longestSequence
- head
- tail
- segmentDistance

これらは `fieldMatch(name)` を前置したフィーチャーとしてドキュメント化されています。[ランクフィーチャーのリファレンス](/ja/reference/ranking/rank-feature-configuration)を参照してください。

このメトリクスセットには、文字列セグメントマッチ・アルゴリズムの概念に直接対応する低レベルで非正規化のメトリクス(例: `segments`、`gaps`)、正規化された基本フィーチャー(例: `proximity`、`queryCompleteness`)、低レベルのメトリクスを組み合わせて有用な部分的真実を表す正規化されたメトリクス(例: `completeness`、`orderness`)、そして他のほとんどのメトリクスを 1 つの正規化された値に組み合わせたメトリクス(`match`)の両方が含まれています。アプリケーションは、重要であると判断した特性を、扱いやすい粒度で捉えるメトリクスのサブセットを選択することになります。
