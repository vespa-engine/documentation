コンポーネントとは、そのライフタイムがコンテナーによって管理される任意の Java クラスです。導入については[開発者ガイド](/ja/applications/developer-guide)を参照してください。コンポーネントは services.xml で指定・設定され、構築時に他のコンポーネントやコンフィグ(生成された "Config" クラスで表現される)を[インジェクション](/ja/applications/dependency-injection)でき、また自身も他のコンポーネントにインジェクションされることができます。

コンポーネント、またはコンポーネントが依存するリソースが再デプロイによって変更されるたびに、コンポーネントは再構築されます。変更されたすべてのコンポーネントの再構築が完了すると、新しいリクエストはアトミックに新しいセットを使用するように切り替えられ、古いものは破棄されます。

コンポーネントに複数のコンストラクタがある場合は、インジェクションに使用するものに `@com.yahoo.component.annotation.Inject` アノテーションを付けてください。

識別可能なコンポーネントは `com.yahoo.component.Component` を実装する必要があり、削除時にリソースを破棄する必要があるコンポーネントは `com.yahoo.component.AbstractComponent` をサブクラス化して `deconstruct()` を実装する必要があります。

コンポーネントの一意性やライフタイムに関するよくある質問については、[例](/ja/operations/metrics#example-qa)を参照してください。

## コンポーネントの構成

以下は、Vespa コンテナーによってセットアップされる典型的なコンポーネント構成を示しています:

![Vespa コンテナーのコンポーネント構成](/assets/img/container-components.svg)
</Frame>

ネットワーク層は Request を *response handler* に関連付け、(通常は URI バインディング・パターンに基づいて)正しい種類の[リクエスト・ハンドラー](#request-handlers)にルーティングします。

アプリケーションが、チェーン化された一連の論理ユニットによる分解を用いた軽量なリクエスト・レスポンス処理を必要とする場合、[プロセッシング・フレームワーク](/ja/applications/processing)が使用すべき正しいコンポーネント・ファミリーです。リクエストは ProcessingHandler から 1 つ以上の [Processor](#processors) インスタンスのチェーンを経由してルーティングされます。出力の正確なフォーマットは、[Renderer](#renderers) を使用してカスタマイズできます。

クエリーを実行する場合、SearchHandler は Query オブジェクトを作成し、それを該当する [Searcher](#searchers) インスタンスのチェーンにルーティングし、返された Result を正しい [Renderer](#renderers) インスタンスに関連付けて、出力フォーマットを必要に応じてカスタマイズします。

DocumentProcessingHandler は通常 messagebus から呼び出され、ドキュメントをインデックスまたはストレージにフィードするために使用されます。受信データから Document オブジェクトが構築され、これが [DocumentProcessor](#document-processors) インスタンスのチェーンを通じてフィードされます。

カスタム HTTP API(たとえば任意の REST API)を持つアプリケーションを構築する場合、最も簡単な方法はカスタムの [RequestHandler](#request-handlers) を構築することです。これは、基本的にキーと値のペアのセットである Request を受け取り、任意のデータのストリームをネットワークに返します。

## コンポーネントのバージョニング

コンポーネントは、コンテナー内の他の多くのアーティファクトと同様に、バージョン管理できます。このドキュメントでは、これらのバージョンの形式とセマンティクス、およびその参照方法について説明します。

### 形式

バージョンは次の形式です:

```js
version ::=    major [ "." minor [ "." micro [ "." qualifier ]]]
```

ここで `major`、`minor`、`micro` は整数で、`qualifier` は任意の文字列です。

バージョンは、コロンで区切って id に追加されます。コンポーネントのバージョンごとにファイルが作成される場合、ファイル名ではコロンはダッシュに置き換えられます。

### 順序

バージョンは、まず major、次に minor、次に micro、最後に qualifier の辞書順で順序付けられます。つまり `a:1 < a:1.0 < a:1.0.0 < a:1.1 < a:1.1.0 < a:2` となります

### バージョン付きコンポーネントの参照

コンポーネントが(コードまたは設定で)id によって参照される場合、`id:versionSpecification` という形式を使用して、完全にまたは部分的に指定されたバージョンを参照に含めることができます。このような参照は、次のルールを使用して解決されます:

- バージョン指定のない id は、qualifier を持たない最も高いバージョンに解決されます。
- 部分的または完全なバージョン指定は、指定にマッチする、qualifier を持たない最も高いバージョンに解決されます。
- qualifier を持つバージョンは、完全一致によってのみマッチします。

例: id `a` を持つコンポーネントに次のバージョンがあるとします: `[1.1, 1.2, 1.2, 1.3.test, 2.0]`

- 参照 `a` は `a:2.0` に解決されます
- 参照 `a:1` は `a:1.2` に解決されます
- "test" qualifier 付きのバージョンに解決する唯一の方法は、正確な参照 `a:1.3.test` を使用することです
- 次の参照は解決されません: `a:1.3`、`a:3`、`1.2.3`

### チェーン化されたコンポーネントの指定のマージ

場合によっては、複数の参照を 1 つにマージする必要があります。例として、バージョン参照のチェーンの継承があり、複数の継承されたチェーンが同じコンポーネントを参照する場合があります。

2 つのバージョン参照は、一方が他方のプレフィックスである場合、*互換*であると言います。この場合、最も具体的なバージョンが使用されます。互換でない場合、それらは*競合*しています。例:

```xml
<search>
    <searcher id="Searcher:2.3" class="com.yahoo.search.example.Searcher" bundle="the name in <artifactId> in your pom.xml" />
    <searcher id="Searcher:2.4" class="com.yahoo.search.example.Searcher" bundle="the name in <artifactId> in your pom.xml" />
    <chain id="parenta">
        <searcher id="Searcher:2"> bundle="the name in <artifactId> in your pom.xml" </searcher>
    </chain>
    <chain id="parentb">
        <searcher id="Searcher:2.3"> bundle="the name in <artifactId> in your pom.xml" </searcher>
    </chain>
    <chain id="parentc">
        <searcher id="Searcher:2.4"> bundle="the name in <artifactId> in your pom.xml" </searcher>
    </chain>

    <!-- This chain will get Searcher:2.3 -->
    <chain id="childa" inherits="parenta parentb" />

    <!-- Error, as Searcher:2.3 and Searcher:2.4 are conflicting -->
    <chain id="childb" inherits="parentb parentc" />
</search>
```
