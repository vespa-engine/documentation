### バケット管理

ノードが起動すると、まずどのドキュメントとバケットを保持しているかの全体像を把握する必要があります。すべてのバケットのメタデータが判明すると、コンテントノードは down 状態から up 状態に遷移します。ディストリビューターはバケットメタデータへの迅速なアクセスを必要とするため、これらのリクエストを効率的に処理できるようにインメモリのバケットデータベースを維持しています。バケットデータベースの状態は、永続化された検索ノードの状態から常に再構築できますが、これはコストが高いため、プロセスの起動時にのみ行われます。

このデータベースは、プロセスの存続期間中、ノードのバケットメタデータの状態に関する信頼できる情報源(source of truth)と見なされます。受信した操作がノード上のドキュメントの状態を変更するため、データベースが常にこれらの変更と同期していることが極めて重要です。

### 永続化スレッドと操作のディスパッチ

コンテントノードには、起動時に作成され、プロセスの存続期間中サイズが固定される *永続化スレッド* のプールがあります。永続化スレッドの責務は、コンテントノードが受信した書き込みおよび読み取り操作をスケジュールし、それらを検索コアにディスパッチし、書き込み操作によって生じた変更とバケットデータベースの同期を維持することです。

明示的に設定されていない限り、スレッドプールのサイズは利用可能な CPU コア数に基づいて自動的に設定されます。

永続化スレッドは *永続化キュー* によって支えられています。RPC サブシステムが受信した読み取り/書き込み操作は、このキューにプッシュされます。このキューは操作のデッドラインを認識しており、キューに入っている間に操作がデッドラインを超過した場合、実行されることなく直ちに送信元に失敗として返されます。これにより、高負荷のノードがキューを十分な速さで消化できないために、すでに失敗が確定している操作の処理にますます多くの時間を費やすという特有の障害シナリオを回避できます。

特定のデータバケット宛てのすべての操作(Put や Get など)は、*バケットロック* のコンテキストで実行されます。ロックは読み取りに対しては *共有*、書き込みに対しては *排他* です。つまり、同じバケットに対して複数の読み取り操作を並列に実行できますが、1 つのバケットに対して同時に実行できる書き込み操作は 1 つだけです(また、あるバケットに対する既存の書き込みと並行して読み取りを開始することはできず、その逆も同様です)。なお、安全な場合にはこれらのロック制約の一部を緩和できます。詳細は[パフォーマンス最適化](#performance-optimizations)を参照してください。

永続化スレッドがキューから操作を取り出そうとしたときに、その操作の対象バケットがすでにロックされていることを検知した場合、その操作はキューに残したまま、次の操作を試みます。つまり、キューは *単一の* バケットに対するクライアント操作については FIFO として機能しますが、*複数の* バケットにまたがる場合はそうではありません。

#### 書き込み操作

書き込み操作は *非同期*(つまりノンブロッキング)タスクとして検索コアにディスパッチされます。これにより、永続化スレッドが解放されて他の操作を処理できるようになるため並列性が向上し、より深いパイプラインによって検索コアはトランザクションログの同期とデータ構造更新のバッチ処理を最適化できます。

より深いパイプラインは、多数の操作が同時に処理中(in flight)である場合にレイテンシーが増加する可能性というコストを伴うため、同時実行可能な非同期操作の最大数は、適応型の永続化スロットリング機構によって制限されます。スロットラーは並行性のウィンドウを動的にスケールし、ウィンドウサイズをさらに増やすと操作レイテンシーも増加する飽和点に達するまで調整します。処理中の操作数が現在の最大値に達すると、永続化スレッドはその数が減るまで新たな書き込みをディスパッチしません。その間も読み取りは処理できます。

非同期の書き込みタスクは、その存続期間中、排他バケットロックを保持し続けます。検索コアが書き込み操作を完了すると、ロックを解放する前に、バケットデータベースがそのバケットの新しいメタデータ状態(書き込みの副作用を反映したもの)で更新されます。その後、操作への応答が生成され、RPC サブシステム経由で送り返されます。

#### 読み取り操作

読み取り操作は常に永続化スレッドによって *同期的*(つまりブロッキング)に評価されます。潜在的にコストの高いメンテナンス読み取り操作([レプリカの整合](/ja/content/consistency#replica-reconciliation)に使用されるものなど)がクライアント操作を長時間ブロックするのを避けるため、永続化スレッドの一部はそのようなメンテナンス操作の処理を許可されて *いません*。

なお、test-and-set 書き込みの条件評価ステップは *読み取り* サブ操作と見なされるため、同期的に実行されます。これは書き込み操作の一部であるため、上位の操作の排他ロックのコンテキスト内でアトミックに行われます。

#### パフォーマンス最適化

スレッドのコンテキストスイッチを減らすため、一部の書き込み操作は永続化スレッドのキューをバイパスし、操作を受信した RPC スレッドから直接、非同期に検索コアへディスパッチされることがあります。そのような操作でも、適切な排他バケットロックの取得に成功する必要があります。ロックを即座に取得できない場合、操作は代わりに永続化キューにプッシュされます。

ロックの競合とスレッドのウェイクアップを減らすため、少数の永続化スレッドが *ストライプ* としてグループ化され、ストライプごとの専用永続化キューを共有します。操作はバケット ID に基づいて特定のストライプに決定論的にルーティングされるため、各ストライプはバケット空間の重複しない部分を処理します。多数のストライプとキューが一体となって、バケット空間全体をカバーする 1 つの上位レベルの *論理的な* キューを形成します。

キューに同じバケットへの *競合しない* 複数の書き込み操作が含まれている場合、これらは *同一の* 書き込みロックのコンテキストで並列にディスパッチされることがあります。これにより、同じバケットへの次の書き込みをディスパッチする前に、ロック取得・実行・ロック解放という一連のラウンドトリップ全体を待つ必要がなくなります。競合する書き込みの例としては、同じドキュメント ID への複数の Put があります。並列にディスパッチされる操作の最大数は実装依存です。

### ドキュメントデータベース

各ドキュメントデータベースは、単一のドキュメントタイプを担当します。ドキュメントデータベースには FeedHandler と呼ばれるコンポーネントがあり、受信したドキュメント、更新、削除リクエストを処理します。すべてのリクエストはまず[トランザクションログ](#transaction-log)に書き込まれ、その後、リクエストタイプに基づいて適切なサブデータベースに渡されます。

### サブデータベース

サブデータベースには 3 つのタイプがあり、それぞれが独自の[ドキュメントメタストア](/ja/content/attributes#document-meta-store)と[ドキュメントストア](#document-store)を持ちます。ドキュメントメタストアは、ドキュメント ID からローカル ID へのマップを保持します。このローカル ID は、ドキュメントストア内のドキュメントをアドレス指定するために使用されます。ドキュメントメタストアはまた、サブデータベースに存在するバケットの状態に関する情報も管理します。

サブデータベースは *Maintenance Controller* によって管理されます。システムのサイズが変更されると、ドキュメントの分散が変化します。システム内のノード数が変わると、Maintenance Controller は新しい分散を反映するために、Ready サブデータベースと Not Ready サブデータベースの間でドキュメントを移動します。Removed サブデータベース内のエントリーが古くなると、パージされます。サブデータベースは以下のとおりです:

## トランザクションログ

コンテントノードは、変更を伴う操作を永続化するためのトランザクションログを持っています。トランザクションログはファイルへの追記によって操作を永続化します。トランザクションログがあることで proton のインメモリ・インデックス構造が簡素化され、定常状態での高いパフォーマンスが実現されます。詳細は以下をお読みください。

すべての操作は[トランザクションログ](/ja/content/proton#transaction-log)に書き込まれ、同期されます。これはシーケンシャルな(ランダムではない)IO ですが、sync 操作のコストがローカル接続ストレージ(SSD など)よりもはるかに高い NAS 接続ストレージ上で実行している場合、フィード全体のパフォーマンスに影響を与える可能性があります。[sync-transactionlog](/ja/reference/applications/services/content#sync-transactionlog) を参照してください。

デフォルトでは、proton はシャットダウン時にアトリビュートベクターやメモリインデックスなどの[コンポーネントをフラッシュ](/ja/reference/applications/services/content#flush-on-shutdown)し、計画的な再起動後の起動を高速化します。

## ドキュメントストア

ドキュメントは、圧縮されたシリアライズ済みのブロブとして *ドキュメントストア* に格納されます。Put、update、remove 操作は、ドキュメントストア内のドキュメントを更新する前に[トランザクションログ](#transaction-log)に永続化されます。操作はクライアントに ack され、操作の結果は即座に検索結果に反映されます。

ドキュメントストアのファイルはシーケンシャルに書き込まれ、ペアで存在します。例:

```bash
-rw-r--r-- 1 owner users 4133380096 Aug 10 13:36 1467957947689211000.dat
-rw-r--r-- 1 owner users   71192112 Aug 10 13:36 1467957947689211000.idx
```

ディスク上の .dat ファイルあたりの[最大サイズ](/ja/reference/applications/services/content#summary-store-logstore-maxfilesize)(バイト単位)は、以下のように設定できます:

```xml highlight= {9}
<content id="mycluster" version="1.0">
  <engine>
    <proton>
      <tuning>
        <searchnode>
          <summary>
            <store>
              <logstore>
                <maxfilesize>8000000000</maxfilesize>
```

注意事項:

- ファイルは順番に書き込まれます。*proton* は 1 つのペアから始めて、*maxfilesize* に達するまでそれを拡大します。満杯になると、新しいペアが開始されます。
- つまり、書き込み対象である最後のペアを除き、ペアはイミュータブルです。 

- ドキュメントは複数のファイルに複数のバージョンで存在します。あるペアが新しいアクティブペアとしてスケジュールされる際に、古いバージョンはコンパクションによって取り除かれます。廃止されたバージョンが削除され、アクティブなドキュメントバージョンのみが新しいファイルペアに残り、それが新しいアクティブペアになります。 
- *maxfilesize* を設定することの影響について、詳しくは [proton メンテナンスジョブ](/ja/content/proton#document-store-compaction)を参照してください。 
- ファイルは圧縮設定を使用して、[チャンク](/ja/reference/applications/services/content#summary-store-logstore-chunk)単位で書き込まれます。

## デフラグメンテーション

[ドキュメントストアのコンパクション](#document-store-compaction)は、ドキュメントストアのファイルをデフラグおよびソートします。これはドキュメントの古いバージョン(つまり更新されたドキュメントの旧バージョン)を削除します。これは、ドキュメントストアのディスクブロートが、ドキュメントストアの総ディスク使用量に [diskbloatfactor](/ja/reference/applications/services/content#flushstrategy-native-total-diskbloatfactor) を掛けた値より大きくなったときにトリガーされます。詳細は[サマリーのチューニング](/ja/reference/applications/services/content#summary)を参照してください。

デフラグメンテーションの状況は、[max_bucket_spread](/ja/reference/operations/metrics/searchnode#content_proton_documentdb_ready_document_store_max_bucket_spread) メトリクスを時系列で追跡することで最もよく観察できます。時間とともに変化するコーパスでは、のこぎり波状のパターンが正常です。[document_store_compact](/ja/reference/operations/metrics/searchnode#content_proton_documentdb_job_document_store_compact) メトリクスは、proton がドキュメントストアのコンパクションジョブを実行しているタイミングを追跡します。コンパクション設定が厳しすぎる場合、このメトリクスは常に(またはほぼ常に)1 になります。

ベンチマークを行う際は、正しいコンパクション設定を行うことが重要であり、また proton がその後ファイルのコンパクションを完了しており(数時間かかることがあります)、アクティブにコンパクションを実行していないこと(*document_store_compact* はほとんどの時間 0 であるべき)を確認することも重要です。
  

<Note>
**注:**

ファイル間をまたぐバケットコンパクションはありません。ドキュメントがファイル間で移動することはありません。
</Note>

チャンクを使用した最適化された読み取り

ドキュメントは .dat ファイル内でクラスター化されているため、proton はドキュメントにアクセスする際により大きなチャンクを読み取ることで読み取りを最適化します。visit の際、ドキュメントは *バケット* 順で読み取られます。これはデフラグメンテーションジョブが使用する順序と同じです。

あるバケットに対する visit 操作で最初に読み取られるドキュメントは、.dat ファイルからチャンクをメモリに読み込みます。それ以降のドキュメントアクセスは、メモリのルックアップのみで処理されます。チャンクサイズは [maxsize](/ja/reference/applications/services/content#summary-store-logstore-chunk-maxsize) で設定します:

```xml highlight= {9}
<engine>
  <proton>
    <tuning>
      <searchnode>
        <summary>
          <store>
            <logstore>
              <chunk>
                <maxsize>16384</maxsize>
              </chunk>
            </logstore>
```

チャンクは 2^22=4M 個まで存在できます。これにより、*maxfilesize* に基づく最小チャンクサイズが定まります。例えば 8G のファイルでは最小チャンクサイズは 2k になります。最後に、バケットサイズは [bucket-splitting](/ja/reference/applications/services/content#bucket-splitting) を設定することで構成します:

```xml highlight= {3}
<content id="imagepersonal" version="1.0">
  <tuning>
    <bucket-splitting max-documents="1024"/>
```

関連するサイジングの単位は以下のとおりです:

.dat ファイルサイズ - *maxfilesize*。ファイルが大きいほどファイル数が減り、ローカリティが向上しますが、コンパクションにはより多くのメモリと完了までの時間が必要になります。チャンクサイズ - *maxsize*。チャンクが小さいほど無駄な IO バイトは減りますが、IO 操作は増えます。バケットサイズ - *bucket-splitting*。バケットが大きいほどバケット数が減り、ノードおよびファイルへのローカリティが向上しますが、コンテントレイヤーのバケットメンテナンス操作時のオーバーヘッドが増加します。オーバーヘッドは、CPU、メモリ、ネットワーク使用量のいずれについても、バケットサイズに対して線形と見なせます。

### メモリ使用量

ドキュメントストアは、ローカル ID(LID)からドキュメントストアファイル(.dat)内の位置へのマッピングをメモリ内に保持しています。このマッピングの一部は、.dat ファイルとペアになっている .idx ファイルに永続化されます。ドキュメントストアが使用するメモリは、ドキュメント数とそれらへの更新数に対して線形です。

メトリクス [content.proton.documentdb.ready.document_store.memory_usage.allocated_bytes](/ja/reference/operations/metrics/searchnode#content_proton_documentdb_ready_document_store_memory_usage_allocated_bytes) がメモリ上のサイズを示します。[メトリクス API](/ja/reference/api/state-v1#state-v1-metrics) を使用して確認してください。目安はドキュメントあたり 12 バイトです。

## アトリビュート

[アトリビュート](/ja/content/attributes)フィールドは、マッチング、ランキング、ソート、グルーピングに使用されるインメモリのフィールドです。各アトリビュートは独立したコンポーネントであり、サブデータベース内のすべてのドキュメントにわたってそのフィールドの値を格納するための一連の[データ構造](/ja/content/attributes#data-structures)で構成されます。アトリビュートは Ready サブデータベースによって管理されます。一部のアトリビュートは Not Ready サブデータベースでも管理できます。詳細は[高スループット更新](/ja/content/attributes#fast-access)を参照してください。

## インデックス

インデックスフィールドは、テキスト検索に使用される文字列フィールドです。その他のフィールドタイプには[アトリビュート](/ja/content/attributes)と[サマリーフィールド](/ja/querying/document-summaries)があります。

Ready サブデータベース内のインデックスは、メモリインデックスと 1 つ以上のディスクインデックスで構成されます。ドキュメントを変更する操作はメモリインデックスに適用され、メモリインデックスは定期的に[フラッシュ](#memory-index-flush)されます。フラッシュされたメモリインデックスは、プライマリーのディスクインデックスと[マージ](#disk-index-fusion)されます。

Proton は、近接性による関連度評価のために、デフォルトでテキストインデックスに位置情報を格納します - `posocc`(後述)。ある語のすべての出現が、その位置とともにポスティングリストに格納されます。これは優れたランキングフィーチャーを提供しますが、ドキュメントごとに単一の出現のみを格納するよりもややコストが高くなります。ほとんどのアプリケーションにとって、これは正しいトレードオフです。コストの大半は通常他の場所にあり、関連度には価値があるためです。

フィルタリングのための出現情報のみが必要なアプリケーションは、[rank: filter](/ja/reference/schemas/schemas#rank) を使用してクエリーパフォーマンスを最適化し、`boolocc`\-ファイル(後述)のみを使用できます。

メモリインデックスは、インデックスフィールドごとにディクショナリーを持ちます。これにはそのフィールド内のすべてのユニークな単語が含まれ、位置情報付きのポスティングリストへのマッピングを持ちます。位置情報はランキングの際に使用されます。テキストマッチスコアの計算方法の詳細は [nativeRank](/ja/ranking/nativerank) を参照してください。

ディスクインデックスは、各インデックスフィールドの内容を個別のフォルダーに格納します。各フォルダーには以下が含まれます:

- ディクショナリー。ファイル: `dictionary.pdat`、`dictionary.spdat`、`dictionary.ssdat`。
- 位置情報付きの圧縮されたポスティングリスト。ファイル: `posocc.dat.compressed`。
- 出現情報のみを持つポスティングリスト(ビットベクター)。これらは一般的な単語に対して生成されます。ファイル: `boolocc.bdat`、`boolocc.idx`。

例:

```bash
$ pwd
/opt/vespa/var/db/vespa/search/cluster.mycluster/n1/documents/myschema/0.ready/index/index.flush.1/myfield
$ ls -la
total 7632
drwxr-xr-x  2 org users     145 Oct 29 06:09 .
drwxr-xr-x 74 org users    4096 Oct 29 06:11 ..
-rw-r--r--  1 org users    4096 Oct 29 06:11 boolocc.bdat
-rw-r--r--  1 org users    4096 Oct 29 06:11 boolocc.idx
-rw-r--r--  1 org users    8192 Oct 29 06:11 dictionary.pdat
-rw-r--r--  1 org users    8192 Oct 29 06:11 dictionary.spdat
-rw-r--r--  1 org users    4120 Oct 29 06:11 dictionary.ssdat
-rw-r--r--  1 org users 7778304 Oct 29 06:11 posocc.dat.compressed
```

上記の例のように、出現回数が少ない場合、`boolocc`\-ファイルは空になることに注意してください。

各ジョブは同時に 1 つのインスタンスのみ実行されます。例えば、アトリビュートは順番にフラッシュされます。ジョブが実行中のとき、そのメトリクスは 1 に設定され、それ以外は 0 です。これを使用して、観測されたパフォーマンスやリソース使用量とジョブの実行を関連付けることができます。後述の *Run metric* を参照してください。

## /state/v1 API

[/state/v1 API リファレンス](/ja/reference/api/state-v1)に記載されている共通エンドポイントに加えて、Proton には /state/v1 API の一部として、検索ノードの内部状態に関する情報を公開する追加のエンドポイントがあります。この API は `http://host:stateport/state/v1/` で利用できます。

JSON HTTP の stateport を見つけるには、[vespa-model-inspect](/ja/reference/operations/self-managed/tools#vespa-model-inspect) を実行します:

```
vespa-model-inspect service searchnode
```
