コンテント・クラスターのプロセスは、*distributor*、*proton*、*cluster controller* です。

distributor は、分散アルゴリズムと[クラスター状態](#cluster-state)を使用して正しいコンテントノードを算出します。既知のクラスター状態がない場合、クライアントライブラリーはランダムなノードにリクエストを送信し、そのノードが正しくなかった場合は、更新されたクラスター状態を含む応答が返されます。クラスター状態はバージョン管理されており、古い distributor にアクセスしたクライアントが、更新された状態を古い状態で上書きすることはありません。

[distributor](#distributor) は、[redundancy](/ja/reference/applications/services/content#redundancy) と *cluster controller* からの情報に基づいて、各バケットのレプリカをどのコンテントノードが保存しているか(それぞれ最大 1 レプリカ)を追跡します。1 つのバケットは 1 つの distributor のみにマッピングされます。distributor は、バケットのメタデータを持つバケットデータベースを保持します。メタデータには、バケットのレプリカを保存しているコンテントノード、バケット内容のチェックサム、およびバケット内のドキュメント数とメタエントリー数が含まれます。各ドキュメントはアルゴリズムによってバケットにマッピングされ、正しいコンテントノードに転送されます。distributor は、コンテントノード上に十分なバケットレプリカがあるかどうかを検出し、必要に応じて追加/削除します。書き込み操作はすべてのレプリカからの応答を待ち、タイムアウト内に redundancy 未満の数しか永続化されなかった場合は失敗します。

[cluster controller](#cluster-controller) は、distributor とコンテントノードの状態を管理します。この*クラスター状態*は、ドキュメント処理チェーンがどの distributor にドキュメントを送るべきかを知るために使用されるほか、distributor がどのコンテントノードがどのバケットを持つべきかを知るためにも使用されます。

## クラスター状態

状態には 3 つの種類があります: [unit state](/ja/reference/api/cluster-v2#state-unit)、[user state](/ja/reference/api/cluster-v2#state-user)、[generated state](/ja/reference/api/cluster-v2#state-generated)(いわゆる*クラスター状態*)です。

新しいクラスター状態が生成されるたびに、クラスター状態のバージョンがインクリメントされ、新しいクラスター状態がすべてのノードにブロードキャストされます。クラスター状態の変更と変更の間には最小時間が設けられています。

クラスター状態が `up` であるための最小キャパシティを設定することができます。
  
利用不可のノードが多すぎてクラスターがダウンと見なされる場合、各ノードの状態は無関係となるため、クラスターが復旧するのに十分な数のノードが戻るまで、新しいクラスター状態は作成もブロードキャストもされません。したがって、クラスター全体がダウンしていることを示すクラスター状態は、ノードレベルでは古いデータを持っている可能性があります。

## Cluster controller

cluster controller の主なタスクは、[クラスター状態](#cluster-state)を維持することです。これは、ノードの状態を*ポーリング*し、クラスター状態を*生成*し、それをクラスター内のすべてのコンテントノードに*ブロードキャスト*することで行われます。クライアントは cluster controller とやり取りしないことに注意してください - クライアントはクラスター状態を distributor から取得します - [詳細](#distributor)。

### マスター選出

Vespa は 1 つの cluster controller で構成することもできます。cluster controller がダウンした場合でも読み取りと書き込みは問題なく動作しますが、クラスターに対するその他の変更(コンテントノードのダウンなど)は処理されません。そのため、複数の cluster controller を構成することが推奨されます。

cluster controller ノードはマスターを選出し、マスターがノードのポーリングとクラスター状態のブロードキャストを行います。他の cluster controller ノードは、マスター選出を行うため、およびマスターが停止した場合に引き継ぐ可能性があるためだけに存在します。

すべての cluster controller は、準備ができていると申告している中で最も低いインデックスを持つ cluster controller に投票します。ある cluster controller が過半数の票を得た場合、その cluster controller がマスターに選出されます。過半数の票が必要となるため、cluster controller の数は 3 以上の奇数にすべきです。新しいマスターは、遷移時間が経過するまで状態をブロードキャストしません。これにより、古いマスターが自分はもはやマスターではないと気付くための時間が確保されます。

## Distributor

バケットは、[理想状態アルゴリズム](/ja/content/idealstate)を使用して distributor にマッピングされます。クラスター状態が変化すると、バケットはただちに再マッピングされます。このマッピングは重複しません - 1 つのバケットは 1 つの distributor によって所有されます。

distributor はバケットデータベースを永続化しません。バケットからコンテントノードへのマッピングは、distributor のメモリー内に保持されます。バケットごとのドキュメント数、永続化サイズ、メタデータのチェックサムも保存されます。distributor の(再)起動時には、コンテントノードにバケット情報をポーリングし、コンテントノードは(理想状態アルゴリズムを使用して)この distributor が所有するバケットを返します。中央集権的なバケットディレクトリーノードは存在しません。同様に、distributor のクラスター状態が変化するたびに、バケットの引き継ぎのためにコンテントノードがポーリングされます - その後、distributor は新しいバケットのセットを扱うことになります。

ドキュメント操作は、バケットの位置に基づいてコンテントノードにマッピングされます - 各 put/update/get/remove は[バケット](/ja/content/buckets)にマッピングされ、正しいコンテントノードに送信されます。ドキュメントセットの増大やノードの変化に対応するため、バケットはコンテントノード間を移動します。

Document API クライアント(つまり [document-api](/ja/reference/applications/services/container#document-api) を持つコンテナーノード)は、cluster controller と直接通信せず、起動時にはクラスター状態を知りません。そのため、クライアントはまずランダムな distributor にリクエストを送信することから始めます。ドキュメント操作が間違った distributor に到達した場合、`WRONG_DISTRIBUTION` が返され、応答には現在のクラスター状態が含まれます。したがって、`WRONG_DISTRIBUTION` はコールドスタートや状態変化のイベント時には想定される正常な動作です。

### タイムスタンプ

[書き込み操作](/ja/writing/reads-and-writes)には、distributor を通過する際に*最終更新時刻*のタイムスタンプが割り当てられます。このタイムスタンプは、それが保存されている[バケット](/ja/content/buckets)内で一意であることが保証されています。タイムスタンプは、どの操作が最新かを判断するためにコンテントレイヤーで使用されます。これらのタイムスタンプは、[visiting](/ja/writing/visiting) の際に、指定した時間範囲内のドキュメントを処理/取得するために使用できます。タイムスタンプの一意性を保証するため、タイムスタンプはマイクロ秒単位です - マイクロ秒の部分は、他のドキュメントとの競合を避けるために生成されます。

ドキュメントがクラスター*間*で移行される場合、移行先クラスターのエントリーには新しいタイムスタンプが付与されます。また、クラスター*内*で[ドキュメントを再処理する](/ja/applications/document-processors)場合も、変更されていなくてもドキュメントには新しいタイムスタンプが付与されます。

### 順序性

Document API は、[ドキュメント ID](/ja/schemas/documents#document-ids) を使用して操作の順序を決めます。Document API クライアントは、同時に保留される操作が 1 つだけであることを保証します。これにより、クライアントが同じドキュメントに対して複数の操作を送信した場合、それらは定められた順序で処理されることが保証されます。これは、保留中の操作をクライアント側で*ローカルに*キューイングすることによって実現されます。

<Note>
**注:**

同じドキュメントに対して 2 つの書き込み操作を送信し、最初の操作が失敗した場合でも、キューに入れられた操作は送信されます。言い換えれば、クライアントは、同じドキュメントに対する別々の操作の間に何らかの依存関係が存在するとは想定しません。これを強制する必要がある場合は、書き込みに [test-and-set 条件](/ja/writing/document-v1-api-guide#conditional-writes)を使用してください。
</Note>

*異なる*クライアントが同じドキュメントに対して保留中の操作を持っている場合、順序は不定です。

### メンテナンス操作

distributor は、どのコンテントノードがどのバケットを持っているかをバケットデータベースで追跡します。distributor は次に、[理想状態アルゴリズム](/ja/content/idealstate)を使用して、バケットの*メンテナンス操作*を生成します。安定したシステムでは、すべてのバケットが理想状態のとおりに配置されています:

- バケットのレプリカが少なすぎる場合、他のコンテントノード上に新しいレプリカが生成されます。
- レプリカに差異がある場合、レプリカを一致させるためにバケットのマージが実行されます。
- バケットのレプリカが多すぎる場合、余分なものは削除されます。不整合がある場合は、削除の前にバケットがマージされます。
- 両方に同じドキュメントが含まれている可能性のある 2 つのバケットが存在する場合、そのような重複バケットを取り除くためにバケットが分割または結合されます。詳細は[不整合のあるバケット](/ja/content/buckets)を参照してください。
- バケットが小さすぎる/大きすぎる場合、結合または分割されます。

メンテナンス操作には異なる優先度があります。メンテナンス操作が不要な場合、クラスターは*理想状態*にあると言われます。distributor はメンテナンスの負荷をユーザーの負荷と同期させます。たとえば、バケットの分割や結合の後、リクエストを他のバケットに再マッピングします。

### 再起動

distributor が停止するとき、まず保留中のクラスター状態リクエストに応答しようとします。シャットダウン開始後の新しい受信リクエストは、ソケットがリクエストを受け付けなくなるため、ただちに失敗します。そのため、cluster controller はプロセスの停止をほぼ即座に検出します。

クラスター状態は、cluster controller 内部で新しい状態に更新されます。その後、cluster controller は、短期的な状態の変動を減らすため、新しいクラスター状態を公開する前に最大 [min_time_between_new_systemstates](https://github.com/vespa-engine/vespa/blob/master/configdefinitions/src/vespa/fleetcontroller.def) の時間待機します。

cluster controller は、他の distributor にバケットの所有権を引き継がせるように状態を設定することも、変化をマスクして、再起動中の distributor が所有するバケットを当面利用不可にしておくこともできます。

distributor が `up` から `down` に遷移した場合、他の distributor は、再起動中の distributor が以前所有していたバケットの所有権を引き継ぐために、コンテントノードからメタデータをリクエストします。distributor がすべてのコンテントノードからこの新しいメタデータを収集し終えるまで、これらのバケットへのリクエストは処理できず、クライアントに失敗として返されます。再起動中のノードが復帰してクラスター状態で再び `up` とマークされると、追加のノードは以前に取得した余分なバケットに関する知識を破棄します。

タイムアウトが数秒あるリクエストの場合、クライアントの自動再送により、この遷移は見えないはずです。タイムアウトがそれより短いリクエストは失敗する可能性があり、再送するか失敗したリクエストを処理するかはアプリケーション次第です。

再起動中の distributor が所有していないバケットへのリクエストは影響を受けません。

## コンテントノード

コンテントノードは、クエリーバックエンドである *proton* を実行します。

### 再起動

コンテントノードが制御された再起動を行うとき、自身を `stopping` 状態にマークし、新しいリクエストを拒否します。シャットダウンの前に、保留中のリクエストキューを処理します。したがって、クライアントリクエストは通常、コンテントノードの再起動の影響を受けません。現在保留中のリクエストは通常完了します。新しいリクエストを適切な冗長性で保存するため、バケットの新しいコピーが他のノード上に作成されます。これは、ノードが `down` 状態を経由するか `maintenance` 状態を経由するかにかかわらず発生します。違いは、`maintenance` を経由する場合、distributor は新しいコピーを既存のコピーと同期させる作業を開始しないことです。メンテナンス中のノードが復帰するまで、新しいリクエストを保存するだけです。

起動時、コンテントノードはまず、どのバケットのデータを保存しているかの情報収集から始めます。この処理が行われている間、サービスレイヤーは `down` であることを公開します。
