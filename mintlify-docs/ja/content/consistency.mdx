## Vespa と CAP

Vespa は、[CAP 定理](https://en.wikipedia.org/wiki/CAP_theorem)における AP の限定的なサブセットとみなすことができます。

CAP の下では、ノード同士がパーティション(P)によって分断されるシナリオにおいて、分散システムが一貫性(C)または可用性(A)の保証を提供できるかどうかについて、根本的な制限があります。パーティションが発生しうるし実際に発生するということから逃れられない以上、システムは CP か AP の _いずれか_ であると語られます。

CAP における一貫性(C)は、読み取りと書き込みが強一貫性を持つこと、すなわちシステムが _線形化可能性(linearizability)_ を提供することを意味します。因果一貫性や「read your writes」一貫性のような、より弱い形式では十分では _ありません_。冒頭で述べたように、Vespa は結果整合性のデータストアであるため、この性質を提供しません。実際、一貫性には多数決合意アルゴリズムの使用が必要ですが、Vespa は現在これを使用していません。

CAP における可用性(A)は、ネットワークがどのようにパーティション分断されても、_すべてのリクエスト_ がエラーでないレスポンスを受け取ることを意味します。Vespa は、中央集権的な(ただしフォールトトレラントな)ノードのヘルスチェッカー兼コーディネーターに依存しています。コーディネーターとノードのサブセットの間でネットワークパーティションが発生する可能性があります。このサブセット内のノードへの操作は、パーティションが解消されるまで成功が保証されません。その結果、Vespa は強可用性が _保証_ されているわけではないため、これを AP の「限定的なサブセット」として扱います(ただし、これは厳密には CAP の定義の一部ではありません)。

_実際には_、Vespa のベストエフォートのセマンティクスは、一般的なデータセンターのネットワークにおいて、堅牢かつ高可用であることが実証されています。

## 書き込みの永続性と一貫性

クライアントが成功した[書き込み](/ja/writing/reads-and-writes)レスポンスを受け取った時点で、その操作は書き込まれ、ディスクに同期されています。レプリケーションレベルは設定可能です。操作はデフォルトで、レスポンスを送信する前に、利用可能な _すべての_ レプリカノードに書き込まれます。ここでの「利用可能」とは、[クラスター状態](/ja/content/content-nodes#cluster-state)において Up であることを意味し、これはフォールトトレラントで中央集権的な Cluster Controller サービスによって決定されます。クラスターに合計 3 つのノードがあり、そのうち 2 つが利用可能で、レプリケーション係数が 3 の場合、利用可能な両方のノードが操作を ACK すれば、書き込みはクライアントに ACK されます。

各レプリカノードでは、操作は適用される前に先行書き込みログ(write-ahead log)に永続化されます。システムは、ログに記録された操作を再生することで、クラッシュ後に自動的に復旧します。書き込みは、クライアントに成功レスポンスを送信する前に永続ストレージへ同期されることが保証されているため、確認済みの書き込みは、突然の電源喪失があっても保持されます。

クライアントが書き込み操作の失敗レスポンスを受け取った場合、その操作はレプリカのサブセットで実行されたかもしれないし、されていないかもしれません。すべてのレプリカに書き込めなかった場合、それらは乖離している(非同期状態)とみなされます。システムは乖離したレプリカを検出し、調整します。これはユーザーの介入なしに行われます。

各ドキュメントの書き込みは、結果として生じるドキュメントバージョンに新しい実時間(wall-clock)タイムスタンプを割り当てます。そのため、クロックのずれをできるだけ小さく保つよう、サーバーには NTP を設定してください。クロックのずれが大きいと、タイムスタンプの衝突や予期しない操作の順序が発生する可能性があります。

Vespa は、test-and-set 操作を通じて、個々のドキュメントに対する条件付き書き込みをサポートしています。複数ドキュメントのトランザクションはサポートされていません。

成功レスポンスの後、検索インデックスへの変更は、デフォルトで即座に参照可能になります。

## 読み取りの一貫性

読み取りはベストエフォートベースで一貫性があり、線形化可能であることは保証されません。

[Get](/ja/reference/api/document-v1#get) または [Visit](/ja/writing/visiting) 操作を使用する場合、クライアントが部分的に更新されたドキュメントを観測することは決してありません。これらの読み取り操作では、書き込みはアトミックであるかのように振る舞います。

検索では、部分的な更新を観測する可能性があります。更新はインデックス構造をまたいでアトミックではないためです。これは、書き込みが開始された _後_、完了する _前_ にのみ起こりえます。書き込みが完了すれば、すべてのインデックス更新が参照可能になります。

ノードがダウンすると、検索で一時的なカバレッジの喪失を観測する可能性があります。これが発生した場合、Vespa は自動的にカバレッジを復元します。その速さは、設定された [searchable-copies](/ja/reference/applications/services/content#searchable-copies) の値に依存します。

Get の実行中にレプリカが乖離している場合、Vespa は read-repair を実行します。これは、乖離しているすべてのレプリカから要求されたドキュメントを取得します。クライアントは、最も新しいタイムスタンプを持つバージョンを受け取ります。

Visit の実行中にレプリカが乖離している場合、その挙動は Document V1 API と [vespa-visit](/ja/reference/operations/self-managed/tools#vespa-visit) とで少し異なります:

- Document V1 は、最も多くのドキュメントを含むレプリカを直ちに visit することを優先します。つまり、バケット内のドキュメントの一部が返されない可能性があります。
- `vespa-visit` は、デフォルトでは、バケットが同期されるまで visit を再試行します。システムの大部分が非同期状態の場合、これには長い時間がかかることがあります。

この挙動の違いの理由は、Document V1 は通常リアルタイムのリクエストのコンテキストで呼び出されるのに対し、`vespa-visit` は通常バックグラウンド / バッチ処理のコンテキストで呼び出されるためです。

Visitor 操作は、実装固有の順序でドキュメントコーパスを反復処理します。任意のドキュメントは、そのドキュメントを含むデータバケットを visitor が反復処理した時点の状態で返されます。これは、<em>スナップショット分離がない</em>ことを意味します — visitor と並行して発生するドキュメントの変更は、そのドキュメントを含むバケットの反復処理の前に発生したか後に発生したかに応じて、返されるドキュメントセットに反映される場合も、されない場合もあります。

## レプリカの調整

調整(reconciliation)とは、乖離したレプリカを再び同期させる行為です。これは通常、ノードの再起動や障害の後に発生します。ネットワークパーティションの後にも発生します。

他のいくつかの結果整合性データベースとは異なり、Vespa は分散レプリカ操作ログを使用しません。代わりに、レプリカの調整では、タイムスタンプ付きドキュメントのセットを交換します。ドキュメントの和集合がすべてのレプリカに存在した時点で、調整は完了です。レプリカが互いに同期しているかどうかは、メタデータのチェックサムによって判定されます。

レプリカを調整する際、利用可能な最も新しいバージョンのドキュメントが「勝ち」、参照可能になります。このバージョンは remove(トゥームストーン)である場合もあります。トゥームストーンは通常のドキュメントと同じ方法でレプリケートされます。

調整はドキュメントレベルで行われ、フィールドレベルでは行われません。すなわち、異なるバージョン間で個々のフィールドがマージされることはありません。

test-and-set 操作が少なくとも 1 つのレプリカを更新すると、それは最終的に他のレプリカでも参照可能になります。

この調整操作は、Vespa ドキュメントの他の箇所では「マージ」と呼ばれています。

トゥームストーンのエントリには、コンパクションで削除されるまでの設定可能な生存期間(TTL)があります。この TTL よりも長い期間ネットワークから分断されていたノードは、クラスターへの復帰を許可する前に、インデックスを削除するのが理想的です。そうしないと、以前に削除されたドキュメントが復活するリスクがあります。Vespa は現在、このシナリオを自動的に検出または処理しません。

[data-retention-vs-size](/ja/operations/self-managed/admin-procedures#data-retention-vs-size) のドキュメントを参照してください。

## Q/A

<AccordionGroup>
<Accordion title="Vespa は Get 操作に対してどのように read-repair を実行し、いくつのレプリカが参照されますか?">
特定のデータバケットを担当するディストリビューター・プロセスが Get 操作を受け取ると、ローカルにキャッシュされたレプリカのメタデータ状態に不整合がないかをチェックします。

すべてのレプリカのメタデータに整合性がある場合、操作は単一のレプリカにルーティングされます — 可能であれば、ディストリビューターと同じホスト上にあるレプリカが優先されます。これは、バケットのレプリカが同期している通常のケースです。

少なくとも 1 つのレプリカのメタデータに不一致がある場合、ディストリビューターは自動的に read-repair プロセスを開始します:

1. ディストリビューターは、メタデータに基づいてバケットのレプリカをサブセットに分割します。各サブセット内のすべてのレプリカは同じメタデータを持ちます。次に、各サブセット内の 1 つのレプリカに、軽量なメタデータのみの Get を送信します。中心となる前提は、これらのレプリカがすべて同じドキュメントバージョンのセットを持っており、セット内の 1 つのレプリカを参照すれば十分であるということです。メタデータの読み取りが失敗した場合、ディストリビューターは自動的にサブセット内の別のレプリカにフェイルオーバーします。
2. 次に、_最も高い_ タイムスタンプを返したレプリカセット内のノードに、完全な Get を 1 回送信します。

つまり、100 個のレプリカがあり、そのうち 1 個が残りの 99 個と異なるメタデータを持つ場合、最初に問い合わせられるのは合計 2 ノードのみで、実際の(完全な)Get 読み取りを受け取るのは 1 ノードのみです。

read/write-repair をトリガーする可能性のある他の操作でも、同様のアルゴリズムが使用されます。
</Accordion>

<Accordion title="Vespa は不整合が検出されると read-repair を実行するので、応答は強一貫性を持つということですか?">
残念ながら、そうではありません。Vespa はドキュメントをまたぐトランザクションを提供していないため、この場合の強一貫性は、単一オブジェクトの _線形化可能性_(複数オブジェクトにまたがる _厳密な直列化可能性_ とは対照的)を意味します。線形化可能性には、既知で安定した特定のレプリカ構成の中で多数決合意に到達できる能力が必要です(補足: Raft や Paxos のような強一貫性アルゴリズムではレプリカセットの再構成が可能ですが、そのような再構成も合意の仕組みを通して行われなければなりません)。

特定のデータバケット(したがってそれが論理的に含むドキュメント)のアクティブなレプリカセットは、(クラスターコントローラーから見て)クラスター内で現在利用可能なノードに基づく、一時的かつ動的なものです。これにより、多数決の決定に使用できる安定したレプリカセットを持つことができません。

[Vespa と CAP](#vespa-and-cap) も参照してください。
</Accordion>

<Accordion title="どのようなシナリオで Vespa は古いバージョンのドキュメントを返す可能性がありますか?">
最新のドキュメントバージョンを含むすべてのレプリカが利用不能になった場合に、古いドキュメントバージョンが返される可能性があります。

2 つのノード `{A, B}` を持つクラスターでのシナリオ例(簡単のため — ただし一般性を失わずに — 冗長性 1 を想定):

1. ドキュメント X が、タイムスタンプ 100 でノード A 上のレプリカに保存されている。
2. ノード A がダウンし、ノード B が所有権を引き継ぐ。
3. ドキュメント X への書き込みリクエストを受信。タイムスタンプ 200 でノード B に保存され、クライアントに ACK される。
4. ノード B がダウンする。
5. ノード A が復帰する。
6. ドキュメント X への読み取りリクエストが到着。参照可能な唯一のレプリカはノード A 上にあり、そのノードがリクエストを処理することになる。
7. タイムスタンプ 100 時点のドキュメントバージョンがクライアントに返される。

`t=200` の書き込みは `t=100` の書き込みの _後に発生(happens-after)_ しているため、`t=100` のバージョンを返すことは線形化可能性に違反します。
</Accordion>
</AccordionGroup>
