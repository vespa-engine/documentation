スキーマは、データの型と、そのデータに対して計算したい内容を定義します。アプリケーション・パッケージには、異なる種類のデータに対応する複数のスキーマを含めることができます。`services.xml` で指定された各コンテント・クラスターは、そのクラスターで保存・インデックスされるべきスキーマを参照します。スキーマは、共通の内容の繰り返しを避けるために他のスキーマを継承できます。

スキーマは、アプリケーション・パッケージの `schemas/` ディレクトリに、スキーマと同じ名前で拡張子 `.sd`（schema definition の意）を持つファイルとして配置します。

## ドキュメント・フィールド

スキーマにはドキュメント・タイプが含まれます。これは名前付きのフィールドの集まりです:

```js
schema mySchema {

    document mySchema {

        field myField type string {
            indexing: summary | index
        }

        ... more fields

    }

}
```

各フィールドは、型、処理およびインデックスの方法、そしてオプションでその他の設定を持ちます。最も重要な決定は、フィールドをクエリーでどのように使用するかであり、これは `indexing` ステートメントで決まります:

- `indexing: summary`: フィールドをクエリー応答（[ドキュメント・サマリー](/ja/querying/document-summaries)）で利用可能にします。
- `indexing: index`: 文字列の場合: ディスク上の全文インデックスを作成します。テンソルの場合: HNSW ベクトルインデックスを作成します（`attribute` の追加指定が必要です）。
- `indexing: attribute`: あらゆるフィールド型に対して: フィールド値を[インメモリ・カラムストア](/ja/content/attributes)での構造化検索（完全一致、範囲、正規表現など）、ランキング、ソート、グルーピング、集約に利用できるようにします。構造化データに適しています。
- `indexing: attribute` と `attribute: fast-search`: 上記に加えて、このデータに対するインデックスを作成して効率的なフィルターにします。クエリーで強力なフィルターとして使用される構造化フィールドに適しています。

indexing ステートメントにはパイプ文字で区切られた複数の式を含めることができ、これらは値の前処理も行えるため、パイプは Unix と同様に次の式へ渡すものとして読むべきです。フィールドのすべての型と内容については[リファレンス](/ja/reference/schemas/schemas#field)を参照してください。

スキーマを定義してコンテント・クラスターに追加すると、それに従って[データを書き込み](/ja/basics/writing)、その中の attribute やインデックスされたフィールドを使用して[クエリー](/ja/basics/querying)できるようになります。インデックス作成は常にリアルタイムで自動的に行われます。

## シンセティック・フィールド

スキーマ内のドキュメント・タイプは、そのドキュメント・タイプに対して put および get（読み書き）できるフィールドを定義します。しかし、入力フィールドを保存・インデックスする前に何らかの方法で処理したい場合があります。そのためには、スキーマ内のドキュメントの外側に追加のシンセティック・フィールドを作成できます（例えば [embed](/ja/rag/embedding) 関数を使用して）:

```js
schema mySchema {

    document mySchema {

        field myField type string {
            indexing: summary | index
        }

        ...

    }

    field mySyntheticField type tensor(x[386]) {
        indexing: input myField | embed | attribute | index
    }

}
```

## ランクプロファイル

*ランクプロファイル*は、スキーマで記述されたデータに対して何を計算すべきか、そしてクエリー応答で返すドキュメントを選択するためにドキュメントをどのようにランク付けすべきかを指定します:

```js
schema mySchema {

    ...

    rank-profile hybrid {

        first-phase {
            expression {
                0.3 * bm25(myText) +
                0.5 * closeness(myEmbedding) +
                0.2 * attribute(popularity)
            }
        }

    }

}
```

スキーマは、さまざまなユースケースや実験などに対応する任意の数のランクプロファイルを持つことができ、それぞれが、返される値やランキングで使用される値を計算する複数の関数を持つことができます。上記のような単純な数学的関数に加えて、機械学習モデルを使用することもできます。詳細は[ランキング](/ja/basics/ranking)を参照してください。

## スキーマの操作

スキーマは、継承や、相互に呼び出し合う複数のランク関数などにより、数千行に及ぶことがあります。最も効率的な作業方法は、IDE を使用して Vespa プラグインをインストールし、シンタックスハイライト、補完、ナビゲーションを利用することです。[IDE サポート](/ja/applications/ide-support)を参照してください。

稼働中のアプリケーションのスキーマを変更するとどうなるでしょうか？

- **新しいフィールドの追加**: 問題ありません。新しいフィールドが追加され、データが書き込まれるまで値を持ちません。
- **フィールドのインデックス方法の変更**: これにより Vespa Cloud では自動的にバックグラウンドで再インデックスが行われますが、その間、クエリーと書き込みでのフィールドの使われ方に不整合が生じる可能性があるため、本番環境では代わりに新しいフィールドを作成する方が望ましい場合があります。
- **フィールドの削除**: そのフィールドのデータとインデックスが削除されます。
- **フィールドの型の変更**: そのフィールドの既存のデータとインデックスが削除されます。このため、多くの場合、代わりに新しいフィールドを追加してデータを投入し、使用箇所を新しいフィールドに切り替えてから古いフィールドを削除する方が望ましいです。

詳細は[スキーマの変更](/ja/reference/schemas/schemas#modifying-schemas)を参照してください。

### 複数のスキーマ

アプリケーション・パッケージは 1 つ以上のスキーマを持ちます。スキーマ数に厳密な上限はなく、最大級のアプリケーションは数百のスキーマを持っています。

スキーマは、データが[コンテント・クラスター](/ja/learn/overview#content-clusters)にどのように保存されるかを定義します。最も一般的なアプローチは、すべてのスキーマを単一のコンテント・クラスターに保存することです。負荷を分離したり、クラスターごとに異なるスケーリングを行ったりするには、より多くのコンテント・クラスターを使用します。

スキーマは[ドキュメント・タイプ](/ja/schemas/documents)を定義します。同じドキュメント・タイプのドキュメントを異なるコンテント・クラスターに保存することができます。ユースケースとしては、A/B テストやデータのホット/コールドのバリエーションがあります。Vespa は、同じドキュメント・タイプを持つすべてのコンテント・クラスターのドキュメントを更新します。このマッピングは、[services.xml](/ja/reference/applications/services/content#document) で *type* を使用して設定します。
