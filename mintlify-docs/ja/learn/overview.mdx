## はじめに

Vespa を使用すると、アプリケーション開発者は、レイテンシーや信頼性を犠牲にすることなく、大量のデータと高い負荷にスケールするアプリケーションを作成できます。Vespa アプリケーションは、いくつかの*ステートレスな Java コンテナー・クラスター*と、データを保存するゼロ個以上の*コンテント*・クラスターで構成されます。

### コンテナー・クラスター

[ステートレスな**コンテナー**・クラスター](/ja/applications/containers)は、受信データやクエリー、およびそれらのレスポンスを処理するコンポーネントをホストします。これらのコンポーネントは、インデックス変換やクエリー実行のグローバルステージなど、プラットフォームに属する機能を提供しますが、アプリケーションのミドルウェアロジックを含めることもできます。アプリケーション開発者は、こうした機能すべてを実行する単一のステートレス・クラスターで Vespa システムを構成することも、タスクの種類ごとに異なるクラスターを作成することもできます。コンテナー・クラスターは、クエリーとデータ操作をコンテント・クラスター内の適切なノードに渡します。アプリケーションが自身で所有していないデータを使用する場合は、外部サービスからデータにアクセスするコンポーネントを追加することもできます。

### コンテント・クラスター

Vespa の[**コンテント**・クラスター](/ja/content/elasticity)は、データの保存と、データに対するクエリーおよび推論の実行を担当します。クエリーは、コンテンツ配信のためのシンプルなデータ検索から、関連データを選択するための複雑な条件、機械学習モデルを使用したランキング、クエリーに参加するすべてのノードにわたるデータのグルーピングと集約まで、多岐にわたります。Vespa が提供するすべての操作は、コンテント・クラスターにノードを追加するだけで、より多くのコンテンツ、より高コストな推論、より高いクエリーボリュームにスケールします。

スケーリングやノード障害のためにコンテント・クラスターのノードを変更すると、コンテント・クラスターは、設定された冗長性レベルでバランスの取れた分散を維持するために、バックグラウンドで自動的にデータを再バランスします。また、障害のあるノードは、クエリーと書き込みへの影響を避けるために、サービングパスから自動的に除外されます(フェイルオーバー)。

コンテナー・クラスターでの中間処理の後、データはコンテント・クラスターに書き込まれます。書き込みは永続的であり、書き込みメッセージの ack を受信した後、数ミリ秒ですべてのクエリーから参照可能になります。各書き込みは、所定の時間制限内に成功するか失敗情報のレスポンスを返すかのいずれかが保証されており、書き込みは利用可能なリソースに応じて際限なく線形にスケールします。ドキュメント全体の書き換えや削除に加えて、書き込みでは個々のドキュメントフィールドのみを選択的に変更することもできます。書き込みは HTTP/2 で直接送信することも、Java クライアントを使用して送信することもできます — [API ドキュメント](/ja/reference/api/api)を参照してください。

コンテナー・クラスターとコンテント・クラスターは Vespa アプリケーションのすべてのエンドユーザートラフィックを処理しますが、3 つ目のタイプのクラスターである*管理・設定クラスター*もあります。これらは、設定に従ってアプリケーション内の他のクラスターをセットアップおよび管理し、設定が変更された際にトラフィックを中断することなく安全にクラスターを変更するプロセスを管理します。

### スキーマ

Vespa に保存される各ドキュメントインスタンスは、設定された[スキーマ](/ja/basics/schemas)で定義された型を持ちます。スキーマは、ドキュメントのフィールドと、その保存方法およびインデックス作成方法、さらにそのドキュメント型に属するランキングおよび推論のプロファイルを定義します。アプリケーションは、異なるデータ型のために任意の数のスキーマを持つことができ、それらを同じコンテント・クラスターに保存するか、複数のコンテント・クラスターに保存するかを設定できます。

### アプリケーション・パッケージ

Vespa アプリケーションは、[*アプリケーション・パッケージ*](/ja/basics/applications)によって完全に指定されます。これは、アプリケーションの一部として実行するクラスターの宣言、コンテントのスキーマ、機械学習モデルや Java コンポーネント、およびさまざまな機能に必要なその他の設定ファイルやデータファイルを含むディレクトリ構造です。アプリケーション開発者は、アプリケーション・パッケージを設定クラスター内の任意のノードに*デプロイ*することで、実行中のアプリケーションを作成します。実行中のアプリケーションへの変更も同じ方法で行います。すなわち、アプリケーション・パッケージを変更して再度デプロイします。Vespa がノードにインストールされて起動されると、そのノードは設定システムによって管理されるため、システム全体を単一のユニットとして扱うことができ、アプリケーションの所有者はアプリケーションを実行しているノード上でローカルに管理タスクを実行する必要がありません。また、Vespa ではノードを*ログサーバー*として設定することもできます。ログサーバーは、アプリケーションのすべてのノードからリアルタイムでログを収集します。デフォルトでは、設定サーバークラスターの最初のノードがこの役割を担います。

このドキュメントの残りの部分では、Vespa が実行する機能についてさらに詳しく説明します。

## Vespa の操作

Vespa は以下の操作を受け付けます:

- 書き込み: ドキュメントの Put(追加および置換)と Remove、およびそれらのフィールドの更新。
- ID によるドキュメント(またはその一部)の検索。
- [クエリー](/ja/querying/query-api): フィールドが条件にマッチするドキュメントを [*Select*](/ja/querying/query-language) します。条件には、フリーテキストフィールド、構造化データ、または[ベクトル空間(ANN)](/ja/querying/nearest-neighbor-search)の検索が使えます。このような条件は任意の数だけブーリアンツリーで自由に組み合わせて、実行するクエリー全体を定義できます。Vespa は条件に対するクエリープランを計算し、たとえばフィルターと ANN 条件の組み合わせなど、任意の数の条件を効率的に実行します。クエリーへのマッチは推論ステップに渡すことができ、そこでは[ランキング式](/ja/reference/ranking/ranking-expressions)や [ONNX モデル](/ja/ranking/onnx)として表現された任意のビジネスロジックや機械学習モデルを計算できます。オプションで、スコアの高いマッチに対して第 2 ステージの推論を実行し、有望な候補により多くの計算リソースを費やすこともできます。最終的なドキュメントは、これらの推論によるスコア([*ランキング*](/ja/basics/ranking))、または明示的な[*ソート*](/ja/reference/querying/sorting-language)に従って順序付けられます。クエリーへのマッチは、フィールド値によって階層的に[*グルーピング*](/ja/querying/grouping)でき、各グループにはグループ内のデータに対する集約値を含めることができます。これは、たとえばナビゲーション補助、タグクラウド、グラフの値の計算や、分散データを単一のコンテナーノードに転送することなく分散的にクラスタリングを行うために使用できます。
- データダンプ: 何らかの条件にマッチするコンテンツは、[*visit*](/ja/writing/visiting) 操作を使用して、バックグラウンドでの再処理やバックアップなどのためにストリーミングで出力できます。
- コンテナー・クラスターにデプロイされたアプリケーションコンポーネントで処理できる、[その他の任意のカスタムネットワークリクエスト](/ja/reference/applications/components)。

## ステートレス・コンテナー

[コンテナー・クラスター](/ja/applications/containers)は、上記の操作を利用してその返却データを処理するアプリケーションコンポーネントをホストします。Vespa は、コンポーネントのインフラストラクチャとともに、一連のコンポーネントを標準で提供します。すなわち、管理サーバーやアプリケーション・パッケージからの設定の注入をサポートする依存性注入、OSGi ベースのコンポーネントモデル、モジュール性のためにコンポーネントをハンドラーチェーンに連結する共有メカニズム、さらにメトリクスとロギングです。コンテナーは、リモートリクエストの処理と発行のためのネットワークレイヤーも提供します - HTTP は標準で提供され、他のプロトコル / トランスポートはコンポーネントとして透過的にプラグインできます。

開発者は、アプリケーション・パッケージを再デプロイするだけでコンポーネント(および当然その設定)に変更を加えることができます - システムが、クラスターのノードへのコンポーネントのコピーと、リクエストのサービングに影響するコンポーネントのロード / アンロード、またはノードの再起動を処理します。

## コンテント・クラスター

[コンテント・クラスター](/ja/content/elasticity)は、データを保存し、検索とセレクトのためにデータの分散インデックスを維持します。データはアプリケーションが指定した数のコピーで複数のノードに複製されるため、ノードやディスクの喪失時にクラスターは自動的に自己修復できます。同じメカニズムを使用して、アプリケーション・パッケージで宣言された利用可能なノードのセットを変更するだけで、クラスターをオンラインのまま拡大または縮小することもできます。

個々のドキュメントの検索は、そのドキュメントを保存しているノードに直接ルーティングされますが、クエリーは、クエリー対象のドキュメントを含むノードのサブセットに分散されます。複雑なクエリーは、コンテナーとコンテントノード間で複数のステップを行き来する分散アルゴリズムとして実行されます。これは、Vespa の主要な設計目標の 1 つである低レイテンシーを実現するためです。

## 管理クラスターと開発者サポート

[単一の設定クラスター](/ja/basics/applications)が、システム内の他のすべてのクラスターを制御します。

設定サーバーは、個々のクラスター、ノード、プロセスの低レベルな設定を導出するため、アプリケーション開発者は、その詳細な実現方法を気にすることなく、より高いレベルで望ましいシステムを指定できます。アプリケーション・パッケージが再デプロイされるたびに、システムは設定に必要な変更を計算し、クエリーや書き込みを中断することなく、現在の設定から新しい設定へ安全に移行するプロセスを管理します。

Vespa のその他の管理クラスターには、クラスターコントローラー・クラスター(1 つ以上のコンテント・クラスターを制御)、ログサーバー・クラスター(ログサーバーはアプリケーション内のすべてのノードからのログのアーカイブを保持)、サービスロケーションブローカー(slobrok、Vespa の一部のサービスで使用されるネームサービス)があります。

### アプリケーション・パッケージ

アプリケーション・パッケージは、HTTP REST API または[コマンドラインインターフェース](/ja/clients/vespa-cli#deployment)を通じて、[変更、再デプロイ](/ja/reference/api/deploy-v2)および[検査](/ja/reference/api/config-v2)ができます。管理クラスターは [ZooKeeper](https://zookeeper.apache.org) 上で動作し、設定への変更を単一かつ一貫したものにし、単一障害点を回避します。

アプリケーション・パッケージは、数百ノードの大規模なシステムを指定する場合でも、すべてのサービスを実行する単一ノードを指定する場合でも、同じ見た目で、同じ方法でデプロイされます。必要な変更は、クラスターを構成するノードのリストだけです。コンテナー・クラスターは、メソッド呼び出しからアプリケーション・パッケージを「デプロイ」することで、単一の Java VM 内で起動することもできます。これは、IDE でのアプリケーションのテストや単体テストに便利です。コンポーネントを含むアプリケーション・パッケージは、サンプルアプリケーションを起点に、Maven を使用して IDE で[開発](/ja/applications/developer-guide)できます。

## まとめ

Vespa を使用すると、機能が豊富で高可用性のアプリケーションを、それに必要となる相当な低レベルの複雑さを開発者に負わせることなく、高い水準でスケールし動作するように開発できます。開発者はシステムをオフラインにすることなくアプリケーションを進化させ成長させることができ、パーソナライズできない古いデータにつながる複雑なデータやページの事前計算スキームを避けることができます。こうしたスキームが必要になるのは、多くの場合、絶えず変化し続けるデータに対して複雑なクエリーを実際のユーザーの時間内に完了させる必要があるためです。

詳細については、[Vespa の機能](/ja/learn/features)を読むか、[アプリケーションのデプロイ](/ja/basics/deploy-an-application)を試してください。
