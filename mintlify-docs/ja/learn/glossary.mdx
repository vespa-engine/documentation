description: "これは、Vespa 固有の用語と、この文脈で役立つ一般的な用語の両方の用語集です。"
---

- **Application(アプリケーション)**

    デプロイと管理の単位です。任意の数のクラスターやスキーマなどを含むことができますが、すべて一緒にデプロイされます。アプリケーションを定義するファイル群は[アプリケーション・パッケージ](/ja/basics/applications)と呼ばれます。

- **Attribute(アトリビュート)**

    アトリビュートは、インデックス付きフィールドとは異なるプロパティを持つフィールドです。アトリビュート・フィールドには、完全一致、前方一致、大文字小文字を区別するマッチングなど、柔軟なマッチモードがあります。アトリビュートは、ディスクアクセスなしでメモリに直接書き込むことで、高い持続的な更新レートを可能にします。グルーピング、ソート、[親/子](/ja/learn/glossary#parent-child)などの機能はアトリビュートを使用します。

- **Boolean Search(ブーリアン検索)**

    [Predicate フィールド](/ja/schemas/predicate-fields)を使用して、クエリーをドキュメント内のブーリアン制約のセットにマッチさせます。典型的なユースケースは、広告を表すブーリアン制約のセットを持ち、そのターゲットグループを指定することです。例: `hobby in [Music, Hiking] and age in [20..30]`。

- **Cluster(クラスター)**

    すべてが同じタスクを実行する同種のノードのセットです。Vespa には 2 つのタイプがあります: コンテナー・クラスターはステートレスであり、コンテント・クラスターはデータを保存・処理します。

- **Component(コンポーネント)**

    コンポーネントは、Container コードモジュールの基底クラスを拡張します。一部は実行のために[チェーン化](/ja/applications/chaining)されます。コンポーネントの種類は次のとおりです:

    - [プロセッサー](/ja/applications/processing#processors)
    - [サーチャー](/ja/learn/glossary#searcher)
    - [ドキュメント・プロセッサー](/ja/learn/glossary#document-processor)
    - [検索結果レンダラー](/ja/applications/result-renderers)
    - [プロバイダー・コンポーネント](/ja/applications/dependency-injection#special-components)

- **Configuration Server(設定サーバー)**

    設定サーバーは Vespa のコントロール・プレーンの大部分をホストし、アプリケーション・パッケージのデプロイ先となります。しばしば "config server" と略されます。config server は単体またはクラスターとしてデプロイされます。[概要](/ja/learn/overview)を参照してください。config server はすべての Vespa プロセスに設定を提供し、通常は最初に起動されるクラスターです。

- **Container(コンテナー)**

    Vespa の Java コンテナーで、すべてのアプリケーション・コンポーネントと Vespa 自体のステートレスなロジックをホストします。詳細は[コンテナー](/ja/applications/containers)をお読みください。[Docker コンテナー](/ja/learn/glossary#docker)と混同しないでください。

- **Content Node(コンテント・ノード)**

    コンテント・ノードはステートフルであり、ドキュメントとインデックスのデータを保持します。[コンテント・ノード](/ja/content/content-nodes)を参照してください。これらのノードは、シームレスなデータ移行とスケーリングのための Vespa の[エラスティシティ](/ja/content/elasticity)を実装しています。

- **Control Plane(コントロール・プレーン)**

    deploy コマンド群が Vespa のコントロール・プレーンです。コントロール・プレーンは多くの場合、[データ・プレーン](/ja/learn/glossary#data-plane)とは別の認証情報で保護されます。多くの場合スループットは低く、GitHub Actions のような自動化によってアプリケーション・パッケージの新しいバージョンをデプロイするために使用されます。

- **Data Plane(データ・プレーン)**

    Document API と Query API が Vespa のデータ・プレーンを構成します。[コントロール・プレーン](/ja/learn/glossary#control-plane)も参照してください。ユーザー向けのサービスであるため、多くの場合、高スループット/低レイテンシです。

- **Deploy(デプロイ)**

    `deploy` は、[アプリケーション・パッケージ](/ja/learn/glossary#application)の新しいバージョンをアップロードして有効化するためのコントロール・プレーンのコマンドです。

- **Deployment(デプロイメント)**

    デプロイメントとは、[deploy](/ja/learn/glossary#deploy) を使用して作成された、稼働中の Vespa アプリケーションです。

- **Diversity(ダイバーシティ)**

    結果のダイバーシティとは、結果セットに多様な結果が含まれることを意味します。たとえば、ランキング上位 n 件の結果をそのまま返すのではなく、同じドメインからのヒットなど、類似したヒットを除外します。類似したヒットを除外したりグループ化したりする機能については、[diversity](/ja/reference/schemas/schemas#diversity) と[グルーピング](/ja/querying/grouping)を参照してください。

- **Docker**

    Vespa は [hub.docker.com](https://hub.docker.com/r/vespaengine/vespa) からコンテナー・イメージとして入手できます。このイメージを実行するプロダクトには Docker、Podman、runC があり、複数のプラットフォーム上の明確に定義された環境で Vespa を実行できます。詳細は [Docker コンテナー](/ja/operations/self-managed/docker-containers)をお読みください。

- **Document(ドキュメント)**

    Vespa はデータをドキュメントとしてモデル化します。ドキュメントは、アプリケーションによって設定される、すべてのドキュメントにわたって一意な文字列識別子を持ちます。ドキュメントはキーと値のペアのセットです。ドキュメントは[スキーマ](/ja/learn/glossary#schema)を持ちます。詳細は[ドキュメント](/ja/schemas/documents)をお読みください。

- **Document frequency (normalized)(ドキュメント頻度(正規化))**

    ある語の*ドキュメント頻度*は、その語がドキュメント・コーパス内で全ドキュメント数に対してどのくらいの頻度で出現するかを捉えます。ランキングの目的では、この値は常に [0, 1] の範囲になるように正規化されます。たとえば、ある語が 1000 件中 600 件のドキュメントに出現する場合、その正規化されたドキュメント頻度は \(600/1000 = 0.6\) になります。

    情報検索の観点からは、正規化されたドキュメント頻度は、ある語がどの程度一般的(または稀)であるかの尺度を与えます。稀にしか出現しない(つまりドキュメント頻度が低い)クエリーの語は、より具体的であるため、通常はクエリーに対してより*関連性が高い*と期待されます。他方、非常に一般的な語(ドキュメント頻度が高い)は、しばしば("the" や "an" などの)「ストップワード」と見なされ、クエリーの関連度への寄与は低いと期待されます。これは、[tf-idf](https://en.wikipedia.org/wiki/Tf%E2%80%93idf) や [BM25](/ja/ranking/bm25) といった古典的なテキスト・ランキング・アルゴリズムで使用される[逆ドキュメント頻度](https://en.wikipedia.org/wiki/Tf%E2%80%93idf#Inverse_document_frequency)に直接関係しています。

- **Document summary(ドキュメント・サマリー)**

    [ドキュメント・サマリー](/ja/querying/document-summaries)は、クエリー結果で各ドキュメントに対して表示される情報です。どの情報を含めるかは、ドキュメント・サマリー・クラスによって決まります。これは、どの情報を含むべきかの設定を持つ、名前付きのフィールドのセットです。Vespa がドキュメントを保存すると、それは[ドキュメント・ストア](/ja/content/proton#document-store)に書き込まれ、サマリーの生成に使用されます。[ストリーミング検索](/ja/performance/streaming-search)を使用する際には、ドキュメント・ストアがスキャンされます。

- **Document Processor(ドキュメント・プロセッサー)**

    ドキュメント処理は、ドキュメント操作を読み取り・変更する、設定可能な[コンポーネント](/ja/learn/glossary#component)のチェーンを作成するためのフレームワークです。ドキュメント・プロセッサーは `getFieldValue()` と `setFieldValue()` を使用してフィールドを処理します。代わりに [Concrete Documents](/ja/schemas/concrete-documents) から生成されたコードを使用することもできます。

- **Document Type(ドキュメント・タイプ)**

    [スキーマ](/ja/learn/glossary#schema)のデータ型の部分で、フィールドのコレクションです。

- **Elasticity(エラスティシティ)**

    Vespa のクラスターはエラスティックです。ユーザーは、サービスを中断することなく、稼働中のアプリケーションでノードを追加・削除できます。ステートフルなコンテント・ノードでは、これにより均一な分散のためにノード間でデータの同期が行われますが、データの再分散は最小限に抑えられます。詳細は[エラスティシティ](/ja/content/elasticity)をお読みください。

- **Enclave**

    Vespa Cloud Enclave は、ご自身の AWS または GCP アカウント内で Vespa Cloud の Vespa アプリケーションを実行するための機能です。[Enclave のドキュメント](/ja/operations/enclave/enclave)を参照してください。

- **Embedding(エンベディング)**

    現代のビッグデータ・サービング・アプリケーションで一般的な手法として、対象データ(たとえばテキストや画像)を抽象的なベクトル空間内の点にマッピングし、そのベクトル空間で計算を行うというものがあります。たとえば、ベクトル空間内の近くの点を見つけることで類似データを取得したり、ベクトルをニューラルネットへの入力として使用したりします。このマッピングは通常*エンベディング*と呼ばれ、Vespa はこれを[組み込みでサポート](/ja/rag/embedding)しています。

- **Estimated hit ratio(推定ヒット率)**

    Vespa がクエリーを可能な限り効率的に評価する方法を計画する際、最も重要な情報の一つは、クエリーのさまざまな部分がどれだけの*ヒット*を生み出すかです。推定ヒット率は [0, 1] の範囲に正規化された数値で、クエリーの特定の部分にマッチすると予想されるドキュメントの割合を表します。

    たとえば、複数の語に対する `AND` 演算子を持つクエリーでは、クエリー・プランナーが、推定ヒット率が*最も低い*語を AND の評価順序の*最初*に配置することで恩恵を受けます。これは、その語が最も評価コストが低く(反復処理する候補ドキュメント数が最も少ない)、それがマッチしなければ、他のすべての語をマッチ候補から除外できるためです。

- **Federation(フェデレーション)**

    [コンテナー](/ja/learn/glossary#container)を使用すると、複数のデータソースを共通の検索サービスに[フェデレーション](/ja/querying/federation)できます。データソースは、検索クラスターでも外部サービスでもよく、Vespa またはその他のあらゆる種類のサービスによって支えられていてもかまいません。外部サービスにフェデレーションするコンテナー・ノードのみで構成されるシステムをセットアップすることで、コンテナーを純粋なフェデレーション・プラットフォームとして使用できます。

- **Field(フィールド)**

    ドキュメントは[フィールド](/ja/basics/schemas#document-fields)を持ちます。フィールドには型があり、ドキュメントに含まれるフィールドは書き込み、読み取り、クエリーが可能です。フィールドは生成されたもの(すなわち合成フィールド)にすることもできます。この場合、フィールド定義はドキュメントの外側にあります - [例](/ja/writing/indexing#date-indexing)。フィールドは、文字列のような単一値でも、文字列の配列のような複数値でもかまいません。

- **Fieldset(フィールドセット)**

    Vespa において、*fieldset* という用語には 2 つの意味があります:

- **一緒にクエリーされるフィールドのコレクション - [スキーマ](/ja/reference/schemas/schemas#fieldset)で設定します:**

    ```sql
    fieldset myset {
        fields: artist, title, album
    }
    ```

- **GET または VISIT 操作で返すフィールドのコレクション。[ガイド](/ja/schemas/documents#fieldsets)を参照してください:**

    ```text
    $ vespa visit --field-set restaurant:name,rating
    ```

- **Garbage Collection(ガベージ・コレクション)**

    [ドキュメント・セレクション](/ja/reference/applications/services/content#document)を使用して、時間やその他の任意の基準でドキュメントを[自動的に期限切れ](/ja/schemas/documents#document-expiry)にします。

- **Grouping(グルーピング)**

    Vespa のグルーピングは、クエリーのヒットをどのようにグループ化、集約し、結果セットとして提示するかを記述するリスト処理言語です。グルーピング文は、クエリーへのすべてのマッチのリストを入力として受け取り、それをグループ化/集約します。場合によっては、複数のネストした並列な方法で出力を生成します。[詳細はこちら](/ja/querying/grouping)。

- **Handler(ハンドラー)**

    *Request Handler* とも呼ばれます。ハンドラーは、[コンテナー](/ja/learn/glossary#container)上に API エンドポイントを構築するために使用される[コンポーネント](/ja/learn/glossary#component)です。ドキュメントは[リクエスト・ハンドラーの開発](/ja/applications/request-handlers)、使用例は[こちら](https://github.com/vespa-engine/sample-apps/tree/master/model-inference/src/main/java/ai/vespa/example)にあります。

- **Indexing(インデクシング)**

    インデックス構造を作成するプロセスです。これには、ドキュメントの書き込みをインデクシング・プロセッサーにルーティングすること、ドキュメントを処理(/ja/writing/indexing )すること、ドキュメントをコンテント・クラスターに書き込むことが含まれます。[ストリーミング検索](/ja/learn/glossary#streaming-search)のような設定では、リソース使用を最適化するためにインデックスを作成しません。

- **Instance(インスタンス)**

    Vespa.ai では *Instance* は常に "default" です(つまり 1 つしかありません)。[Vespa Cloud](/) のようなマネージド・サービスは複数をサポートします - [詳細はこちら](/ja/learn/tenant-apps-instances)。インスタンスとは、本番サービングのような特定の目的のためのアプリケーションのデプロイメントです。統合テストのようなより多くのユースケースをサポートするために、1 つのアプリケーションの複数のインスタンスを使用できます。

- **Namespace(ネームスペース)**

    [ドキュメント ID](/ja/learn/glossary#document) のセグメントで、一意な値のソースが複数ある場合でも一意な id を生成するのに役立ちます。ネームスペースは、コーパスのサブスペースを [Visit](/ja/learn/glossary#visit) するために使用できます。

- **Nearest neighbor search(最近傍検索)**

    [最近傍検索](/ja/querying/nearest-neighbor-search)、または[ベクトル検索](/ja/querying/vector-search-intro)は、高次元ベクトル空間において、与えられたクエリー点に最も近いデータ点を見つけるために使用される手法です - [距離メトリック](/ja/querying/nearest-neighbor-search#distance-metrics-for-nearest-neighbor-search)を参照してください。厳密にも近似的にも行えます。

    これは Vespa では [nearestNeighbor](/ja/reference/querying/yql) クエリー演算子を使用してサポートされています。

- **Node(ノード)**

    ノードとは、1 つ以上の[サービス](/ja/learn/glossary#service)を実行するホスト/コンテナー・インスタンスです。論理名から実際の名前へのマッピングは [hosts.xml](/ja/reference/applications/hosts) で設定します。

- **Parent / Child(親/子)**

    ドキュメント参照を使用することで、ドキュメントは[親/子](/ja/schemas/parent-child)関係を持つことができます。親ドキュメントからフィールドをインポートしてデータを結合するために使用します。親ドキュメントは、クラスター内のすべてのノードにレプリケートされます。

- **Partial Update(部分更新)**

    部分更新とは、ドキュメント内の 1 つ以上のフィールドへの更新です。すべてのインデックス構造の更新も含まれるため、部分更新の効果はクエリーで即座に観測できます。部分更新はドキュメント全体を必要とせず、メモリのみの操作で高い書き込みスループットを可能にします。[詳細はこちら](/ja/writing/partial-updates)。

- **Posting List(ポスティング・リスト)**

    ポスティング・リストは、情報検索と検索エンジンにおける基本的なデータ構造です。転置インデックスにおいて、ドキュメントのコレクション内での語の出現を保存するために使用されます。[詳細はこちら](/ja/performance/feature-tuning#posting-lists)。

- **Quantization(量子化)**

    量子化とは、連続的な、あるいは大きな値の集合(実数など)からの入力を、離散的な集合(整数など)に制約するプロセスです。[最近傍検索](/ja/learn/glossary#nearest-neighbor-search)における[テンソル演算](/ja/learn/glossary#tensor)のメモリと CPU の使用量を削減し、スループットやレイテンシを改善する方法です。

- **Query(クエリー)**

    [Query API](/ja/querying/query-api) を使用してコーパスにクエリーを実行します。クエリーは [YQL](/ja/reference/querying/yql) で書くか、[サーチャー](/ja/learn/glossary#searcher)内でプログラム的に作成できます。クエリーの実行は[クエリー・プロファイル](/ja/querying/query-profiles)で設定します。

- **Ranking(ランキング)**

    ランキングは、Vespa がドキュメントに対して計算(推論)を行う場所です。実行すべき計算は、[ランキング式](/ja/ranking/ranking-expressions-features#ranking-expressions)と呼ばれる関数で表現され、[スキーマ](/ja/learn/glossary#schema)で定義された [rank profile](/ja/basics/ranking#rank-profiles) にまとめられます。これらは、いくつかのランク・フィーチャーを組み合わせた単純な数式から、テンソル式や大規模な機械学習モデルまでさまざまです。ランキングは単一フェーズでも[マルチフェーズ](/ja/ranking/phased-ranking)でも実行できます。

- **Schema(スキーマ)**

    特定の種類のデータと、その処理/ランキング方法の記述です。[スキーマ・ガイド](/ja/basics/schemas)を参照してください。

- **Searcher(サーチャー)**

    サーチャーは、通常 OSGi バンドルの一部としてデプロイされる[コンポーネント](/ja/learn/glossary#component)です。すべてのサーチャーは単一のメソッド `search(query)` を実装する必要があります。開発者はアプリケーションのクエリー・ロジックをサーチャーに実装します - [詳細はこちら](/ja/applications/searchers)。

- **Semantic search(セマンティック検索)**

    セマンティック検索は、検索エンジンがクエリーの単語の文字通りの一致を探す字句検索(lexical search)とは区別される、意味を伴う検索を指します。セマンティック検索の詳細、参考資料へのポインター、実装方法については、[Revolutionizing Semantic Search with Multi-Vector HNSW Indexing](https://blog.vespa.ai/semantic-search-with-multi-vector-indexing/) をお読みください。

- **Service(サービス)**

    サービスは、コンテナー・ノードまたはコンテント・ノードの[クラスター](/ja/learn/glossary#cluster)内で実行され、[services.xml](/ja/reference/applications/services/services) で設定されます。

- **Streaming search(ストリーミング検索)**

    [ストリーミング検索](/ja/performance/streaming-search)は、インデックス構造を持たないフィールドへのクエリーです。インデックスが生成されないため、インデクシングのコストは最小限です。したがって、クエリーはすべてのデータのスキャンとなり、通常はインデックス構造を使用するよりも遅くなります。ストリーミング検索は、検索対象のデータ量が少ないパーソナル検索のようなアプリケーションで使用されます。候補となる近傍のセットが全体よりも桁違いに小さい最近傍アプリケーションでは、メモリ使用量を劇的に制限する強力な選択肢になり得ます。

- **Tenant(テナント)**

    [アプリケーション](/ja/learn/glossary#application)を所有する組織単位です。Vespa.ai の API では、*tenant* と *application* は常に "default" であり、Vespa システムはちょうど 1 つのテナントと 1 つのアプリケーションを持ちます。[Vespa Cloud](/) では、複数のテナントとアプリケーションがサポートされます - [詳細はこちら](/ja/learn/tenant-apps-instances)。

- **Tensor(テンソル)**

    [テンソル](/ja/ranking/tensor-user-guide)は、スカラー、ベクトル、行列を任意の次元数に一般化したデータ構造です: スカラーはランク 0 のテンソル、ベクトルはランク 1 のテンソル、行列はランク 2 のテンソルです。テンソルはスカラー値のセルのセットで構成され、各セルは一意なアドレスを持ちます。セルのアドレスは、そのテンソルのすべてのディメンションにおけるインデックスまたはラベルによって指定されます。テンソルのディメンション数がテンソルのランクであり、各ディメンションは mapped または indexed のいずれかです。

- **Visit**

    [Visit](/ja/writing/visiting) は、[ドキュメント・セレクション式](/ja/reference/writing/document-selector-language)によって識別される、一連の/すべてのドキュメントを効率的に取得または処理するための機能です。Visit は、すべての、または一部のバケットを反復処理し、ドキュメントを(1 つまたは複数の)ターゲットに送信します。
