title: "Config sentinel"
---

Config sentinelはサービスの起動と停止を行い、手動で停止されていない限り、障害が発生したサービスを再起動します。Vespaシステム内のすべてのノードでは、少なくとも次のプロセスが実行されています:

<table className="vespa-table">
  <thead>
    <tr>
      <th>プロセス</th>
      <th>説明</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><a href="/ja/operations/self-managed/config-proxy" aria-label="config-proxy">config-proxy</a></td>
      <td>VespaアプリケーションとConfigサーバー・ノードの間でconfigリクエストをプロキシします。すべての設定はローカルにキャッシュされるため、Configサーバーが停止しても、このノードは現在の設定を維持できます。</td>
    </tr>
    <tr>
      <td>&#42;&#42;config-sentinel&#42;&#42;</td>
      <td>&#42;config-proxy&#42; に自身を登録し、ノード設定を購読して適用します。すなわち、どのサービスをどのパラメーターでローカルに実行すべきかという設定です。</td>
    </tr>
    <tr>
      <td><a href="/ja/reference/operations/log-files#logd" aria-label="vespa-logd">vespa-logd</a></td>
      <td>他のすべてのサービスが使用する &#42;$VESPA_HOME/logs/vespa/vespa.log&#42; を監視し、すべてを <a href="/ja/reference/operations/log-files#log-server" aria-label="log-server">log-server</a> に中継します。</td>
    </tr>
    <tr>
      <td><a href="/ja/operations/self-managed/monitoring#metrics-proxy" aria-label="metrics-proxy">metrics-proxy</a></td>
      <td>すべてのノードとサービスに対するメトリクス・アクセス用のAPIを提供します。</td>
    </tr>
  </tbody>
</table>

起動シーケンス:

<Steps>
<Step>
*config server(s)* が起動され、アプリケーションのconfigがそこにデプロイされます - [Configサーバーの運用](/ja/operations/self-managed/configuration-server)を参照してください。
</Step>
<Step>
*config-proxy* が起動されます。環境変数 [VESPA\_CONFIGSERVERS](/ja/operations/self-managed/files-processes-and-ports#environment-variables) と [VESPA\_CONFIGSERVER\_RPC\_PORT](/ja/operations/self-managed/files-processes-and-ports#environment-variables) を使用して [config-server(s)](/ja/operations/self-managed/configuration-server) に接続します。一部のConfigサーバーがダウンしている場合は、すべてのConfigサーバーに対してリトライします。
</Step>
<Step>
*config-sentinel* が起動され、自身のホスト名を [config id](/ja/applications/configapi-dev#config-id) として使用して、*config-proxy* からノード設定(すなわちサービス・リスト)を購読します。ホスト名がどのように検出されるか、およびそのオーバーライド方法の詳細については、[Node and network setup](/ja/operations/self-managed/node-setup) を参照してください。config-sentinelのconfig(サービス・リスト)には、起動すべきプロセスと、それぞれに割り当てる *config id*(通常はそのサービス・インスタンスの論理名)が列挙されています。
</Step>
<Step>
*config-proxy* が *config-server* からノード設定を購読してキャッシュし、その結果を *config-sentinel* に返します
</Step>
<Step>
*config-sentinel* が、config idを引数として、ノード設定に指定されたサービスを起動します。以下の出力例の *id="search/qrservers/qrserver.0"* のような形です。*logd* と *metrics-proxy* は設定に関わらず常に起動されます。各サービスは:
	
    a. *config-proxy* から設定を購読します。
	
    b. *config-proxy* は *config-server* から設定を購読してキャッシュし、その結果をサービスに返します。
	
    c. サービスは自身の設定に従って実行され、ログを *`$VESPA_HOME/logs/vespa/vespa.log`* に書き込みます。プロセスは内部コンポーネントをインスタンス化し、それぞれに同じまたは別のconfig idが割り当てられ、さらにコンポーネントがインスタンス化されていきます。

ノードの最小起動数の設定については、[クラスターの起動](#cluster-startup)も参照してください。
</Step>
</Steps>

新しいconfigが *config-servers* にデプロイされると、変更された設定がそれを購読しているノードへ伝播されます。それを受けて、これらのノードは自身を再設定します。

## ユーザー・インターフェース

Config sentinelはRPCサービスを実行しており、これを使ってそのノード上で実行されるべきサービスの一覧表示、起動、停止を行えます。これはテストやデバッグに役立ちます。これらのアクションを実行するには [vespa-sentinel-cmd](/ja/reference/operations/self-managed/tools#vespa-sentinel-cmd) を使用します。`vespa-sentinel-cmd list` の出力例:

```bash

```

プロセスとサービスの詳細については、[ファイルとプロセス](/ja/operations/self-managed/files-processes-and-ports)を参照してください。ノード上で実行されているサービスを一覧表示するには [vespa-model-inspect host *hostname*](/ja/reference/operations/self-managed/tools#vespa-model-inspect) を使用します。

## クラスターの起動

Config sentinelは、他のノードのうち最小限の数(デフォルトは50%)への接続性がない限り、ノード上のサービスを起動しません。この機能の例は、[multinode-HA](https://github.com/vespa-engine/sample-apps/tree/master/examples/operations/multinode-HA#start-the-admin-server) サンプル・アプリケーションにあります。設定例:

```xml
<services>
    <config name="cloud.config.sentinel">
        <connectivity>
            <minOkPercent>20</minOkPercent>
            <maxBadCount>1</maxBadCount>
        </connectivity>
    </config>
```

例: `minOkPercent 10` は、10%以上のノードが稼働している場合にのみサービスを起動することを意味します。アプリケーションに11ノードある場合、最初に起動されたノードはそのサービスを起動しません - 2番目のノードが起動されると、両方のノードでサービスが起動されます。

`maxBadCount` は、相手ノードは稼働しているものの、適切な双方向の接続性がまだ確立できていない場合の接続性チェックのためのものです。通常、一方向のみの接続性はネットワーク設定が壊れていて調査が必要なことを意味するため、この値は低く設定してかまいません(1、あるいは0が推奨値です)。一時的な問題がある場合(以下の例では、起動時にさまざまな問題を引き起こすDNSの無応答)、config sentinelはループしてリトライするため、サービスの起動がわずかに遅れるだけで済みます。
