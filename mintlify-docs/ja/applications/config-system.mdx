## ノードの設定

ノードを設定するという課題は3つの部分に分けられ、それぞれ異なるソリューションによって対処されます:

- **ノードのシステムレベル設定:** タイムゾーンなどのOSレベルの設定と、ノード上のユーザー権限を設定します。
- **パッケージ管理**: 正しいソフトウェア・パッケージのセットがノードにインストールされていることを保証します。この機能は、連携して動作する3つのツールによって提供されます。
- **Vespaの設定:** 設定されたプロセス群を、設定された起動パラメーターとともに各ノードで起動し、これらのサービスが実行するモジュールに動的な設定を提供します。ここでいう *設定(Configuration)* とは、次の条件を満たす任意のデータです:
            
  - コンパイル時に固定できない
  - ほとんどの場合は静的である

これらの定義によれば、すべてのノードが同じソフトウェア・パッケージを持つことが可能になる点に注意してください(バージョンの違いは後述するとおり除きます)。各ノードでどのサービスを実行するか、およびその振る舞いの違いは、すべてVespaの設定(Vespa Configuration)を使って実現されるためです。これにより、ノードごとの違いの複雑さを、複数のシステムにまたがるのではなく、設定システムの中だけで管理できます。

システムの設定は次の2つに分けられます:

- **設定の組み立て(Configuration assembly):** システムの設定に関与する各当事者から提供される入力をもとに、配信用の完全な設定一式を組み立てること
- **設定の配信(Configuration delivery):** 個々の設定の定義、設定を要求・アクセスするためのAPI、および設定をその発生源から受信側コンポーネントへ配信する仕組み

この分割により、大規模分散システムにおける信頼性の高い設定配信という課題は設定の配信側で対処し、完全な設定を組み立てる複雑さはVMローカルの設計課題として扱うことができます。

Vespaの設定の重要な特徴は、配信サブシステムと組み立てサブシステムの間のインターフェースの性質にあります。組み立てサブシステムは、分散システムの(Javaの)オブジェクト・モデルを出力として生成します。配信サブシステムはこのモデルに問い合わせて、システムのすべてのコンポーネントの具体的な設定を取得します。これにより、組み立てサブシステムはより高レベルで使いやすい抽象を入力として受け取り、正しい相互依存関係を持つ詳細な設定を自動的に導出できます。この分割によって、外部インターフェースと設定対象のコンポーネントは、互いの変更から隔離されます。さらに、システム・モデルは、ノード/コンポーネントのインスタンスごとの設定の違いを実装するロジックの置き場所にもなります。

## 設定の組み立て

設定の組み立て(config assembly)とは、設定の入力ソースを、名前とconfig idを与えられたconfigの問い合わせに応答できる、目的のシステムのオブジェクト・モデルへと変換するプロセスです。Vespaシステムの設定の組み立ては、複数の当事者が所有する情報をマージする必要があるため、複雑になることがあります:

- **Vespaの運用者** はノードを所有し、サービス/アプリケーションへのノードの割り当てを制御します
- **Vespaのサービス・プロバイダー** は、Vespa上で動作する複数のアプリケーションをホストするサービスを所有します
- **Vespaのアプリケーション** は、ノードと共有サービス上で動作する最終的なアプリケーションを定義します

現在のconfigモデルの組み立て手順は、単一のソース、すなわち *アプリケーション・パッケージ* を使用します。アプリケーション・パッケージは、定義されたファイルとサブディレクトリを含むディレクトリ構造であり、これらが一体となってシステムを完全に定義します - どのノードがシステムに属するか、それらがどのサービスを実行すべきか、そしてこれらのサービスとそのコンポーネントの設定を含みます。アプリケーションのデプロイ担当者がアプリケーションを変更したい場合、アプリケーション・パッケージを引数として、Configサーバーに対して [vespa prepare](/ja/reference/clients/vespa-cli/vespa_prepare) を発行します。

この時点でシステム・モデルが組み立てられて検証され、フィードバックがデプロイ担当者に返されます。デプロイ担当者が新しい設定を有効にすることを決めた場合、続いて [vespa activate](/ja/reference/clients/vespa-cli/vespa_activate) を発行します。これにより、Configサーバー・クラスターは新しいシステム・モデルに切り替わり、新しいシステム・モデルによってconfigが変化したすべてのアクティブな購読に対して、新しいconfigを応答します。これにより、変更時に購読者がタイムリーに新しいconfigを受け取れること、そして伝播される変更が最小限のセットであること、つまりアプリケーション・パッケージへの小さな変更がシステムへの相応に小さな変更をもたらすことが保証されます。

configモデル自体はプラグイン化が可能であり、サービス・プロバイダーは特定のサービスを組み立てるためのプラグインを書くことができます。プラグインはJavaで書かれ、Vespaの設定とともにインストールされます。サービス・プラグインは、Vespaアプリケーションが設定できるサービスを指定するための独自の構文を定義します。これにより、コンポーネントに配信される設定から切り離された、抽象的な形でアプリケーションを指定できます。

## 設定の配信

設定の配信は、次の側面を含みます:

- 設定の定義
- 設定のコンポーネント視点(API)
- 設定の配信メカニズム

これらの側面は連携して、次の目標を実現します:

- コードと設定の間の不整合を排除する。
- 望ましい設定と各ノード上の状態の間の不整合を排除する。
- 再設定後の一時的な不整合を抑える。

続く3つのサブセクションで上記の3つの側面を説明し、その後、2つの特別な関心事 - ブートストラップとシステムのアップグレード - についてのサブセクションが続きます。

### 設定の定義

*設定(configuration)* とは、名前と型を持つ、単純な、または配列のキーと値の集合であり、ネストすることもできます - 例:

```txt
myProperty "myvalue"
myArray[1]
myArray[0].key1 "someValue"
myArray[0].key2 1337
```

設定オブジェクトの *型定義*(またはクラス)は、設定が含みうるフィールドの集合を、その型とデフォルト値とともに定義し、ドキュメント化します。型定義は名前と名前空間を持ちます。たとえば、上記のconfigインスタンスは次のような定義を持つかもしれません:

```txt
namespace=foo.bar

# Documentation of this key
myProperty string default="foo"

# etc.
myArray[].key1 string
myArray[].key2 int default=0
```

個々のconfigは通常、*logging* や *indexing* のような、あるトピックに関する一貫した設定の集合を含みます。完全なシステムは、多くのconfig型の多くのインスタンスから構成されます。

### コンポーネント視点

システムの個々のコンポーネントは、このようなconfigを1つ以上消費し、その値を使って自身の振る舞いを変えます。configを *要求* するためのAPIと、提供されたconfigの値に *アクセス* するためのAPIが必要です。

configへの *アクセス* は、config定義ファイルから生成される(JavaまたはC++の)クラスを通じて行われます。これにより、config型で宣言されたフィールドと、それにアクセスするコードの期待との間の不整合は、コンパイル時に検出されることが保証されます。config定義は、それを消費するコンポーネントに属する、別の形のソース構文を持つもう1つのクラスと見なすのが最適です。config定義の型からそのようなクラスを生成するためのMavenターゲットが提供されています。

コンポーネントは、設定を *要求* するために、購読(subscription)と依存性注入(dependency injection)という2つの異なる方法を使用できます:

**購読:** コンポーネントが *ConfigSubscriber* をセットアップし、1つ以上のconfigを購読します。これは単純なアプローチであり、configを取得する[その他の方法](/ja/applications/configapi-dev)もあります:

```java
ConfigSubscriber subscriber = new ConfigSubscriber();
ConfigHandle<MydConfig> handle = subscriber.subscribe(MyConfig.class, "myId");
if (!subscriber.nextConfig()) throw new RuntimeException("Config timed out.");
if (handle.isChanged()) {
    String message = handle.getConfig().myKey();
    // ... consume the rest of this config
}
```

**依存性注入:** コンポーネントはコンストラクターでconfigへの依存を宣言し、購読はコンポーネントの代わりにセットアップされます。変更されたconfigが利用可能になると、コンポーネントの新しいインスタンスが生成されます。この方法の利点は、コンポーネントのライフタイム全体を通じてconfigが不変(immutable)であるため、スレッド間の調整が不要なことです。この方法は現在、[Container](/ja/applications/containers) を使用するJavaでのみ利用できます。

```java
public MyComponent(MyConfig config) {
    String myKey = config.myKey();
    // ... consume the rest of this config
}
```

ユニットテストでは、[Builderでconfigを作成](/ja/applications/configapi-dev#unit-testing)して、コンポーネントに直接渡すことができます。

### 配信メカニズム

configの配信メカニズムは、システム・モデルへの変更によってあるconfigインスタンスが変化するたびに、新しいconfigインスタンスが購読中のコンポーネントに配信されることを保証する役割を担います。configの購読は2つのパラメーターで識別されます。*config定義の名前と名前空間*、および購読を行う特定のコンポーネント・インスタンスを識別するために使用される [config id](/ja/applications/configapi-dev#config-id) です。

プロセス内のconfigライブラリは、これらの購読リクエストをノード・ローカルの [configプロキシ](/ja/operations/self-managed/config-proxy)へ転送します。configプロキシは、キャッシュと、プロセスからノードへのファンインを提供します。プロキシは次に、これらの購読をConfigurationサーバー・クラスター内のノードへ発行します。各Configサーバーはシステム・モデルのコピーを保持しており、システム・モデルに問い合わせることでconfigリクエストを解決します。

Configサーバーのフェイルオーバーを提供するため、configの購読は長いタイムアウトを持つget(タイムアウトすると即座に再送される)として実装されていますが、概念的にはプッシュ型の購読として理解するのが最適です:

<Frame>
![](/assets/img/config-delivery.svg)
</Frame>

configはノード上にローカルファイルとして保存されないため、ローカルでの編集による不整合や、メンテナンスから復帰したノードが古い設定を持つといった問題は発生し得ません。設定の変更はConfigサーバー・クラスターが許す限り速やかにプッシュされるため、再設定中の時間的な不整合は最小化されますが、グローバルなトランザクションが存在しないため、完全に回避されるわけではありません。

アプリケーションのコードとconfigは一般にConfigサーバーからプルされます - ただし、[url](/ja/reference/applications/config-files#url) config型を使って、ノードにダウンロードする任意のリソースを参照することもできます。

### ブートストラップ

各Vespaノードは [config-sentinel](/ja/operations/self-managed/config-sentinel) プロセスを実行しており、これがノード上で実行されるサービスを起動し維持します。

### システムのアップグレード

Configurationサーバーは、マイナー・アップグレードにおいて、要求されるconfig定義と設定モデルが生成するconfig定義との間に差異が生じる場合、configのバージョン間の変換(アップ/ダウングレード)を動的に行います。設定プロトコルやシステム・モデルへの互換性のない変更を伴うメジャー・アップグレードには、[手順](/ja/operations/self-managed/config-proxy)が必要です。

## 補足

Vespa config APIの使用に関する詳細は、[リファレンス・ドキュメント](/ja/applications/configapi-dev)を参照してください。

Vespaの設定は、それを使用するノードについて次のことを前提としています:

- すべてのノードには、設定システムと、そのノード上で実行するように設定されるあらゆるサービスを実行するために必要なソフトウェア・パッケージがある。これは通常、すべてのノードが同じソフトウェアを持つことを意味しますが、必須ではありません
- すべてのノードで [VESPA_CONFIGSERVERS](/ja/operations/self-managed/files-processes-and-ports#environment-variables) が設定されている
- すべてのノードが自身の完全修飾ドメイン名を知っている

Vespaを使用したり、VespaコンテナーのJavaコンポーネントを開発したりするために、このドキュメントを読む必要はありません - その目的であれば、[コンポーネントの設定](/ja/applications/configuring-components)を参照してください。
