- [基本的な HTTP テスト](/ja/reference/applications/testing): リクエストと期待されるレスポンスを JSON で表現し、[Vespa CLI](/ja/clients/vespa-cli) で実行します。
- [Java JUnit テスト](/ja/reference/applications/testing-java): より高度なテスト向けで、いくつかの追加設定を行い、通常の Java テストとして実行します。

これら 2 つのフレームワークには、アプリケーションがアップグレードされ、バックエンドの状態が古いアプリケーション設定に依存するシナリオのためのアップグレード(またはステージング)テストの仕組みや、本番検証テスト(基本的には本番デプロイメントのヘルスチェック)も含まれています。システムテストとステージングテストのために、フレームワークは指定されたテストデプロイメントに対して HTTP リクエストを実行する簡単な方法を提供し、テストをテストクラスターのデプロイメントや設定から分離します。

このドキュメントでは、Vespa アプリケーションへの変更を継続的かつ安全にデプロイするための、想定上の CI/CD システムの一部として、これらの各テストカテゴリーをどのように実行できるかを説明します。

最後に、フィーチャースイッチを使用した [A/B テスト / バケットテスト](/ja/applications/testing#フィーチャースイッチとバケットテスト)のセクションがあります。

## システムテスト

システムテストは、デプロイされた Vespa アプリケーションがフィードとクエリーの際に期待どおりに動作することを検証する機能テストにすぎません。システムテストの実行は、テストするアプリケーション・パッケージで別のデプロイメントを行い、その後、システムテスト・スイート、またはそのうちの 1 つないし数個のテストを実行するだけの簡単なものです。

<Note>
**注:**

各システムテストは自己完結型であるべきです。つまり、各テストを単独で実行することも、すべてのテストを任意の順序で実行することもできる必要があります。これを実現するために、**システムテストは一般に、テスト対象のクラスターからすべてのドキュメントをクリアすることから始めるべきです。** 私たちのサンプルのシステムテストもそうなっているため、本番クラスターに対して実行しないよう注意してください。
</Note>

ほとんどの場合、システムテストはアプリケーション・パッケージの変更に伴って更新する必要があります。まれに、Vespa バージョンのアップグレードが機能の変更につながることもありますが、メジャーバージョン内では、これは新機能とバグ修正のみであるはずです。いずれの場合も、Vespa プラットフォームのアップグレードの前にも、アプリケーション・パッケージの変更を本番にデプロイする前にも、常に専用のテストデプロイメントに対してシステムテストを実行するのが良い方法です。

### システムテストの実行

[Vespa CLI](/ja/clients/vespa-cli) を使うと、テストデプロイメントのセットアップと、システムテストおよびステージングテストの実行が簡単になります。システムテストを実行するには、まずテストデプロイメントをセットアップします:

  

```sh
$ vespa deploy --wait 600
```

基本的な HTTP テストを実行します(通常のテストにはこのテストスイートの使用を推奨します) - [例](https://github.com/vespa-engine/sample-apps/tree/master/examples/operations/CI-CD/production-deployment-with-tests)のアプリケーションも参照してください:

  

```sh
$ vespa test tests/system-test/feed-and-search-test.json
```

Java API テストの例(複雑なテストケースに使用します) - [例](https://github.com/vespa-engine/sample-apps/tree/master/examples/operations/CI-CD/production-deployment-with-tests-java)のアプリケーションも参照してください:

  

```sh
$ mvn test -D test.categories=system -D vespa.test.config=/path-to/test-config.json
```

maven-plugin のテストランナーが使用するテスト設定ファイルは、[services.xml](/ja/reference/applications/services/services) 内の各クラスターのエンドポイントを、`localEndpoints` JSON オブジェクトの下のフィールドとして定義します:

  

```json
{
  "localEndpoints": {
  "query-service": "http://localhost:8080/",
  "feed-service" : "http://localhost:8081/"
  }
}
```

`feed-service` は、[services.xml](/ja/reference/applications/services/services) で `<document-api>` を持つコンテナー・クラスターのエンドポイントです。`query-service` は、[services.xml](/ja/reference/applications/services/services) で `<search>` を持つコンテナー・クラスターのエンドポイントです。

## ステージングテスト

ステージング(アップグレード)テストの目的は、新しいデプロイメントが機能仕様を満たすことを保証することでは *ありません*。それはシステムテストでカバーされるべきです。むしろ、アプリケーション・パッケージや Vespa プラットフォームのアップグレードがアプリケーションを壊さず、既存のクライアントが期待する動作と互換性があることを保証することです。

例として、ドキュメントのインデックス方法の変更、例えば新しいドキュメント・プロセッサーの追加を考えてみましょう。システムテストは、ドキュメントをフィードし、ドキュメント・プロセッサーがドキュメントを変更したこと(あるいは何か他のことをしたこと)を検証することで、この新しい動作をテストします。一方、ステージングテストは、ドキュメント・プロセッサーが追加される *前* にドキュメントをフィードするため、アップグレード後にそのドキュメントをクエリーすると、システムテストが期待する結果とは異なる結果になる可能性があります。

デプロイ後に追加の対応を必要とするこのような変更の多くは、[バリデーション・オーバーライド](/ja/reference/applications/validation-overrides)でも保護されていますが、ステージングテストは、その変更の正確な影響が何であるか、そしてそれにどう対処するかを把握するための優れた方法です。

システムテストとは対照的に、ステージングテストは自己完結型ではありません。アップグレード中の状態の変化こそがテスト対象だからです。代わりに、状態を変更するステージングテスト、特にアップグレード後のものの実行順序を制御する必要があります。実際、一部の変更ではデータの再フィードが必要になり、その場合、これは *ステージングテスト* コードの一部にするべきです。最後に、アップグレード前に期待される状態を検証することも良い方法です。

Vespa アプリケーションのクライアントは、システムテストとステージングテストの両方の期待と互換性があるべきです。これが、破壊的変更をデプロイする際のワークフローを規定します - 手順:

<Steps>
  <Step>
  アプリケーションコードとシステムテストおよびステージングテストを更新してテストが通るようにし、更新されたテストコードを反映するようにクライアントを更新します。
  </Step>

  <Step>
  アプリケーションをアップグレードします。
  </Step>

  <Step>
  *ステージングセットアップ* のコードを、新しいアプリケーションコードに合わせて更新します。

  繰り返しになりますが、アプリケーション・パッケージの変更であれ、Vespa プラットフォームのアップグレードであれ、すべての変更のデプロイの前に常にステージングテストを実行するのが良い方法です。
  </Step>

</Steps>

### ステージングテストの実行

例のアプリケーションへのリンクは上記の[システムテスト](#システムテスト)を参照してください。手順:

<Steps>
  <Step>
  *現在の* セットアップ(パッケージと Vespa バージョン)で専用のデプロイメントを作成します。
  </Step>

  <Step>
  *ステージングセットアップ* のコードを実行して、テストクラスターを特定の状態(通常は本番クラスターの状態を模倣したもの)にします。
  </Step>

  <Step>
  次に、デプロイメントを *新しい* セットアップ(パッケージや Vespa バージョン)にアップグレードします。
  </Step>

  <Step>
  *ステージングテスト* のコードを実行して、アップグレード後にクラスターが期待どおりに動作することを検証します。

  JSON テストを使用した例:

  ```sh
  # load old application code, deploy it, run setup
  $ vespa deploy --wait 600
  $ vespa test tests/staging-setup

  # make changes to the application, deploy it, run tests
  $ vespa deploy --wait 120
  $ vespa test tests/staging-test
  ```

  Java テストを使用した例(*test-config.json* については[システムテスト](#システムテストの実行)を参照):

  ```sh
  # load old application code, deploy it, run setup
  $ vespa deploy --wait 600
  $ mvn test -D test.categories=staging-setup -D vespa.test.config=/path-to/test-config.json

  # make changes to the application, deploy it, run tests
  $ vespa deploy --wait 120
  $ mvn test -D test.categories=staging -D vespa.test.config=/path-to/test-config.json
  ```
  </Step>

</Steps>

## フィーチャースイッチとバケットテスト

継続的デプロイメントでは、機能が完成するまでリリースを保留し、動作すると確信できるまで手動でテストしてから本番にリリースする、というやり方は現実的ではありません。では代わりにどうするか? 答えは *フィーチャースイッチ* です: 新機能は開発され次第本番にリリースしますが、準備が整うまで、または一部のユーザーで本番検証が済むまで、それらを無効のままにしておくロジックを含めます。

*バケットテスト* とは、制御されたユーザーのサブセットに対して、新しい機能や動作を体系的にテストする手法です。これは新しいサイエンスモデルをリリースする際の一般的な手法です。テスト環境での検証が難しいためですが、他の機能にも使用できます。

Vespa で新しい動作をテストするには、[クエリー・プロファイル](/ja/querying/query-profiles)によって制御される[検索チェーン](/ja/applications/chaining)と [rank profile](/ja/reference/schemas/schemas#rank-profile) の組み合わせを使用します。ここでは 1 つのクエリー・プロファイルが 1 つのバケットに対応します。これらの機能は継承をサポートしており、繰り返しなしにバリエーションを表現しやすくなっています。

新しい機能が[データフィールドへの互換性のない変更](/ja/reference/schemas/schemas#modifying-schemas)を必要とする場合があります。そのような変更を CD できるようにするには、新しいバージョンのデータを含む新しいフィールドを作成する必要があります。これには追加のリソースコストがかかりますが、代替手段(新しいデータで新しいシステムのコピーを立ち上げること)よりは低コストです。新しいフィールドは、システムの稼働中に追加してデータを投入できます。

互換性のない変更の必要性を減らす 1 つの方法は、フィールドのセマンティクスをより正確にすることです。例えば、フィールドがドキュメントの「品質」として定義されていて、数値が高いほど品質が高いことを意味する場合、異なる範囲と分布を生成する新しいアルゴリズムは、通常、互換性のない変更になります。しかし、フィールドが「クリックされた後にそのドキュメントで費やされた平均時間」としてより正確に定義されていれば、この値のより良い推定値を生成する新しいアルゴリズムは、互換性のない変更にはなりません。正確なセマンティクスを使用することには、データの使用方法とその統計的特性が妥当かどうかを理解しやすくなるという利点もあります。
