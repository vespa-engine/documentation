すべてのコンポーネントは、Containerコードモジュールの基底クラスを継承（extend）する必要があります。たとえば、searcherは`com.yahoo.search.Searcher`クラスを継承しなければなりません。主に利用できるコンポーネントのタイプは以下のとおりです:

- [processor](/ja/applications/processing)
- [searcher](/ja/applications/searchers)
- [document processor](/ja/applications/document-processors)
- [検索結果レンダラー](/ja/applications/result-renderers)
- [providerコンポーネント](/ja/applications/dependency-injection#special-components)

searcherとdocument processorは、[チェーン化コンポーネント（chained components）](/ja/applications/chaining)と呼ばれるコンポーネントのサブクラスに属します。異なるコンポーネント・タイプがどのように連携するかの入門については、[コンポーネント・タイプの概要](/ja/reference/applications/components#component-types)を参照してください。

検索コンテナーのコンポーネントは、通常[OSGiバンドル](/ja/applications/bundles)の一部としてデプロイされます。バンドルはmavenと[bundleプラグイン](/ja/applications/bundles#maven-bundle-plugin)を使用してビルドします。マルチバンドルの例については、[multiple-bundlesサンプルアプリ](https://github.com/vespa-engine/sample-apps/tree/master/examples/multiple-bundles)を参照してください。

## 並行性

コンポーネントは複数のスレッドによって並行に実行されます。これは、すべてのコンポーネント・クラスに重要な制約を課します: *finalでないインスタンス変数は安全ではありません。* それらは排除するか、何らかの方法でスレッドセーフにする必要があります。

## リソース管理

スレッド、ファイルハンドル、またはコンポーネントがスコープ外になったときに解放する必要があるその他のネイティブ・リソースを使用するコンポーネントは、`deconstruct`というメソッドをオーバーライドする必要があります。以下は、'executor'という名前のスレッドプールを使用するコンポーネントの実装例です:

```java
@Override
public void deconstruct() {
    super.deconstruct();
    try {
            executor.shutdown();
            executor.awaitTermination(10, TimeUnit.SECONDS);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}
```

常にスーパークラスのメソッドを最初に呼び出すことが推奨されることに注意してください。YourKitのようなツールで使用する[デバッグ・オプション](/ja/reference/applications/services/container#jvm)の設定方法については、[SharedResource.java](https://github.com/vespa-engine/vespa/blob/master/jdisc_core/src/main/java/com/yahoo/jdisc/SharedResource.java)も参照してください。これはコンポーネントのライフタイムや（脱）構築の問題を追跡するために使用できます。例:

```xml
<nodes>
    <jvm options="-Djdisc.debug.resources=true"/>
</nodes>
```

詳細は[コンテナー・プロファイリング](/ja/performance/profiling#profiling-the-query-container)を参照してください。

## 依存性注入（Dependency injection）

コンポーネントは、他のコンポーネントやconfigなどのリソースにアクセスする必要がある場合があります。これらはコンストラクターに直接注入されます。以下のタイプのコンストラクター依存が許可されています:

    - [Configオブジェクト](/ja/applications/configuring-components)
    - [他のコンポーネント](/ja/applications/dependency-injection)
    - [Linguisticsライブラリ](/ja/linguistics/linguistics)
    - [システム情報](#the-systeminfo-injectable-component)

[コンポーネント・リファレンス](/ja/reference/applications/components#injectable-components)には、組み込みの注入可能コンポーネントの完全なリストがあります。

コンポーネント・クラスに複数のpublicコンストラクターが必要な場合、コンテナーが使用するコンストラクターには、[annotations](https://search.maven.org/artifact/com.yahoo.vespa/annotations)の`@com.yahoo.component.annotation.Inject`アノテーションを付ける必要があります。

### SystemInfo注入可能コンポーネント

このコンポーネントは、コンポーネントが実行されている環境に関する情報を提供します。たとえば:

- 該当する場合、Vespa Cloudにおけるゾーン。
- コンテナー・クラスター内のノード数とそのインデックス。
- 実行中のノードのインデックス。

後者の2つは、たとえばノードのサブセットで新機能の[バケットテスト](/ja/applications/testing#feature-switches-and-bucket-tests)を行うために使用できます。ノードのインデックスは、必ずしも連続していたりゼロから始まったりするとは限らないことに注意してください。

## コンポーネントのデプロイ

コンテナーは、[アプリケーション・パッケージ](#adding-component-to-application-package)で指定されたとおりに、コンポーネントのインスタンスを1つ以上作成します。コンテナーは再設定されたときにのみこのコンポーネントの新しいインスタンスを作成するため、コンポーネントが必要とするデータは、コンポーネントのコンストラクターで読み込んで準備できます。

コンポーネントで利用できる完全なAPIについては、[Container Javadoc](https://javadoc.io/doc/com.yahoo.vespa/container-disc/latest/com/yahoo/container/package-summary)を参照してください。

コンポーネントがユニットテストに合格したら、デプロイできます。その手順は、コンポーネントのjarファイルのビルド、Vespaアプリケーション・パッケージへの追加、アプリケーション・パッケージのデプロイです。これらの手順を、searcherを例として以降のセクションで説明します。

### プラグイン.jarのビルド

プラグインjarをビルドするには、プロジェクト・ディレクトリで`mvn install`を実行します。ビルドされたjarはtargetディレクトリにあり、*-deploy.jar*というサフィックスが付きます。

このドキュメントの残りの部分では、artifactIdが`com.yahoo.search.example.SimpleSearcher`、バージョンが`1.0`であると仮定します。ビルドされるプラグインの名前は*com.yahoo.search.example.SimpleSearcher-1.0-deploy.jar*になります。

### Vespaアプリケーション・パッケージへのプラグインの追加

前の手順でプラグインjarファイルが生成されるはずです。これを[アプリケーション・パッケージ](/ja/basics/applications)（少なくとも*hosts.xml*と*services.xml*を含むディレクトリ）に追加することで、Vespaにデプロイできます:

- `com.yahoo.search.example.SimpleSearcher-1.0-deploy.jar`をアプリケーション・パッケージのルート配下の`components/`ディレクトリに配置します
- [services.xml](/ja/reference/applications/services/services)を変更してSearcherを含めます

searcherを含めるには、検索チェーン（search chain）を定義し、そこにsearcherを追加します。例:

```xml
<?xml version="1.0" encoding="utf-8" ?>
<services version="1.0">

    <admin version="2.0">
        <adminserver hostalias="node1" />
        <configservers>
            <configserver hostalias="node1" />
        </configservers>
        <logserver hostalias="node1" />
    </admin>

    <container version="1.0">
        <search>
            <chain id="default" inherits="vespa">
                <searcher id="com.yahoo.search.example.SimpleSearcher"
                          bundle="the name in <artifactId> in your pom.xml" />
            </chain>
        </search>
        <nodes>
            <node hostalias="node1" />
        </nodes>
    </container>

</services>
```

上記のsearcher idは、`artifactId`によって決まる`Bundle-SymbolicName`（[jarファイルのマニフェスト内のフィールド](/ja/applications/bundles)）によって、追加したプラグインjarへと解決され、クラス名によってバンドル内の適切なクラスへと解決されます。`searcher id`、`class name`、`artifactId`を同じにしておくことで物事をシンプルに保っていますが、これらが異なるようなより高度な使い方もサポートされています。これについては後のセクションで説明します。

これらのタグのリファレンスについては、[検索チェーンのリファレンス](/ja/reference/applications/services/search#chain)を参照してください。

`hosts.xml`の例:

```xml
<?xml version="1.0" encoding="utf-8" ?>
<hosts>
    <host name="localhost">
        <alias>node1</alias>
    </host>
</hosts>
```

この`services.xml`、`hosts.xml`、および`components/com.yahoo.search.example.SimpleSearcher-1.0-deploy.jar`を含むディレクトリを作成することで、そのディレクトリはバンドルを含む完全なアプリケーション・パッケージとなり、デプロイできるようになります。

### アプリケーション・パッケージのデプロイ

[クイックスタート](/ja/basics/deploy-an-application-local)を使用してVespaインスタンスをセットアップします。コンポーネントとconfigがアプリケーション・パッケージに追加されたら、`vespa deploy`を実行して[デプロイ](/ja/basics/applications#deploying-applications)できます。この手順により、変更されたバンドルがそれを必要とするクラスター内のノードにコピーされ、クエリーが新しいバージョンのコンポーネントの実行に切り替わります。

これは、アプリケーション・パッケージに、すでにクエリーを実行中のクラスへの変更が含まれている場合でも、プロセスの再起動を必要とせずに安全に動作します。この切り替えはクエリーの観点からアトミックです - すべてのクエリーは、アプリケーション・パッケージの以前のバージョンのコンポーネントのみを使用するか、新しいバージョンのコンポーネントのみを使用して完了まで実行されるため、複数のsearcherコンポーネントにまたがる相互依存の変更も問題なくデプロイできます。

#### JNIには再起動が必要

上記の例外は、JNIパッケージを含むバンドルです。ネイティブ・ライブラリのインスタンスは1つしか存在できないため、そのようなバンドルはリロードできません。ベストプラクティスは、JNIライブラリをコンストラクターでロードすることです。これにより、新しいバンドルはロード*されず*、現在のバージョンで継続します。その後の再起動で新しいバンドルがロードされます。したがって、これによって障害が発生することはありません。あるいは、JNIライブラリが遅延初期化される場合（たとえば最初の呼び出し時）、バンドルのリロードは成功しますが、JNIライブラリを使用するコードのその後の呼び出しは失敗します。つまり、新しいバージョンは動作しますが、失敗します。

デプロイ時に、通常の*Switching to the latest deployed set of handlers*ではなく、警告がログに出力されます - 例:

```txt
[2016-09-21 14:22:05.387] WARNING : container        stderr     Cannot load mylib native library
```

再起動を最小限に抑えるため、JNIコンポーネントは最小限の独立したバンドルに入れることを推奨します。これにより、JNIバンドル自体が変更されない限り、JNIバンドルのリロードが防止されます。

#### アクティブなアプリケーションのモニタリング

すべてのコンテナーは、コンポーネントやチェーンを含む、アクティブなアプリケーションに関するJSON形式の情報を出力する組み込みハンドラーも提供します（[ユーザー定義バージョン](/ja/reference/applications/application-packages#versioning-application-packages)を表示するように設定することもできます）。このハンドラーは、パス`/ApplicationStatus`へのリクエストに応答します。たとえば、'localhost'がポート8080でHTTPを設定したコンテナーを実行している場合:

```txt
http://localhost:8080/ApplicationStatus
```

外部依存は[バンドルに含めることができます](/ja/applications/bundles#maven-bundle-plugin)。

### バンドルにおけるパッケージのエクスポート、インポート、インクルード

[OSGiは情報隠蔽を備えています - デフォルトでは、バンドル内で使用されるすべてのクラスは外部から見えません。](/ja/applications/bundles)

### グローバル・パッケージとエクスポートされたパッケージ

JDisc Containerには、*グローバル*パッケージのセットが1つあります。これらはインポートなしで利用できるパッケージであり、JDisc ContainerのサポートされたAPIを構成します。これらのパッケージには後方互換性のない変更は行われません。

また、*エクスポートされた*パッケージのセットもあります。これらはインポートすることで利用でき、すべてのレガシー・パッケージに加え、コアAPIの一部ではない拡張パッケージが含まれます。これらは、グローバル・パッケージのような「公開」APIとは見なされず、後方互換性のない変更が行われる*可能性があり*、削除される可能性もあることに注意してください。

エクスポートされたパッケージとグローバル・パッケージのリストは、[container-discのpom.xml](https://github.com/vespa-engine/vespa/blob/master/container-disc/pom.xml)の`project/properties/exportedPackages`と`project/properties/globalPackages`にあります。

### バージョン

検索コンテナーのうちidで参照できるすべての要素は*バージョン管理*できます。これにはチェーン、コンポーネント、クエリー・プロファイルが含まれます。これにより、これらの要素の複数のバージョンを同時に使用でき、同じクラスの複数のバージョンも使用できます。これは新しいバージョンの[バケットテスト](/ja/applications/testing#feature-switches-and-bucket-tests)に便利です。

idまたはid参照には、次の構文でバージョンを含めることができます: `name:version`。これは検索リクエスト、services.xml、コード、クエリー・プロファイルのidで機能します。

バージョンの形式は次のとおりです:

```txt
major.minor.micro.qualifier
```

ここで、major、minor、microは整数で、qualifierは文字列です。バージョン文字列の右側部分は省略できます。*バージョン*では、省略された値は「0」を意味します（qualifierの場合は*空*）。*バージョン参照*では、省略された値は「未指定」を意味します。未指定の数値は利用可能な最大の数値にマッチしますが、qualifierが指定されている場合は*必ず*正確にマッチしなければなりません（qualifierはめったに使用されません）。

バンドルのバージョンを指定するには、pom.xmlでversionを指定します（*qualifier*の使用は推奨しません）:

```xml
<groupId>com.yahoo.example</groupId>
<artifactId>MyPlugin</artifactId>
<version>major.minor.micro</version>
```

これは自動的にバンドル・マニフェストの`Bundle-Version`の設定に使用されます。

詳細については、[コンポーネントのバージョン管理](/ja/reference/applications/components#component-versioning)を参照してください。

## トラブルシューティング

### コンテナーの起動

アプリケーション・パッケージに何らかのエラーがある場合、通常は`vespa prepare`ステップで検出され、エラーメッセージが表示されます。しかし、一部のクラスのエラーは、アプリケーションがデプロイされて初めて検出されます。そのため、アプリケーションを再デプロイする際には、以下を実行してvespaログを監視することを推奨します:

```txt
vespa-logfmt -N
```

新しいアプリケーションは、次のINFOメッセージの後にアクティブになります:

```txt
Switched to the latest deployed set of handlers...;
```

`vespa activate`の完了後、妥当な時間が経過してもこのメッセージが表示されない場合は、代わりに何らかのエラーや警告が表示され、それがアプリケーションのデバッグに役立ちます。

### コンポーネントのロード

デプロイ時またはコンテナーの起動時に、コンポーネントが構築されます。構築は失敗することがあります - デバッグするには、より多くのログを有効にします（必要に応じて「container」をコンテナーidに置き換えてください）:

```txt
$ vespa-logctl container:com.yahoo.container.di.componentgraph.core.ComponentNode debug=on
.com.yahoo.container.di.componentgraph.core.ComponentNode   ON  ON  ON  ON  ON  ON  ON OFF
```

*vespa.log*で「Constructing」と「Finished constructing」を探してください - これにより、構築されなかったコンポーネントを特定できます。

モデルのダウンロード失敗は以下のように表示され、コンテナーへのモデルのダウンロードに失敗したことが原因です:

```json
ERROR   container        Container.com.yahoo.jdisc.core.StandaloneMain    JDisc exiting: Throwable caught:
exception=
java.lang.RuntimeException: Not able to create config builder for payload '{
"tokenizerPath": "\\"\\" https://huggingface.co/Snowflake/snowflake-arctic-embed-l/raw/main/tokenizer.json \\"\\"",
"transformerModel": "\\"\\" https://huggingface.co/Snowflake/snowflake-arctic-embed-l/resolve/main/onnx/model_int8.onnx \\"\\"",
"transformerMaxTokens": 512,
"transformerInputIds": "input_ids",
"transformerAttentionMask": "attention_mask",
"transformerTokenTypeIds": "token_type_ids",
"transformerOutput": "last_hidden_state",
"normalize": true,
"poolingStrategy": "cls",
"transformerExecutionMode": "sequential",
"transformerInterOpThreads": 1,
"transformerIntraOpThreads": -4,
"transformerGpuDevice": 0
}
```

URLや名前を確認し、Vespaコンテナーが実行されているネットワークでモデルがダウンロードできることを確認してください。
