title: "Permissions"
---

Vespa on Kubernetes uses two ServiceAccounts, each with its own set of namespace-scoped [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/) permissions:

- The **Vespa Operator** ServiceAccount, used by the operator Deployment. Its permissions are installed by the [Helm chart](/en/operations/kubernetes/reference/helm-chart).
- The **ConfigServer** ServiceAccount, used by the ConfigServer pods. It is either generated by the operator (`spec.configServer.generateRbac: true`) or provided externally through `spec.configServer.serviceAccount` — see the [VespaSet CRD reference](/en/operations/kubernetes/reference/vespaset-crd#configserver).

The tables below list the permissions per resource, by Kubernetes API verbs.

<a id="generate-rbac" />
### Generate RBAC Resources

When `spec.configServer.generateRbac` is set to `true` in the [VespaSet](/en/operations/kubernetes/reference/vespaset-crd#configserver), the operator generates the RBAC resources for the ConfigServer pods itself: it creates the ConfigServer ServiceAccount, a Role holding the [ConfigServer permissions](#configserver), and a RoleBinding tying the two together. This removes the need to manage the ConfigServer ServiceAccount externally through `spec.configServer.serviceAccount`.

Generating these resources requires the following additional permissions. They can be omitted when the ConfigServer ServiceAccount is managed externally.

## ConfigServer

The ConfigServer pods provision and manage the pods, volumes, and endpoints of the Vespa application clusters. All ConfigServer pods share one ServiceAccount: either the operator-generated one (`generateRbac: true`), or the one referenced by `spec.configServer.serviceAccount`. When providing the ServiceAccount externally, it must be granted the following permissions.
